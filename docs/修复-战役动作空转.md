## 1. 任务与范围

**现象**：战役 JSON 里出现 13 种 `action`，执行注册表 `help/sim/EventTrigger.kt` 的 `when (ev.action)` 只有 5 个分支（moraleChange / surrender / setIntent / supplyCut / strengthDelta），其余静默空转、用户零反馈。

**本单目标**：把"数据里出现、代码不认"的动作全部补齐为真实生效，不许降级成"忽略也不报错"；未知 action 必须走 else 记告警。

**改动文件域**（硬约束内）：
- `app/src/main/java/io/legado/app/help/sim/EventTrigger.kt`（并行纯 JVM 引擎注册表 + 执行分支）
- `app/src/main/java/io/legado/app/ui/map/crossing/model/Enums.kt`（EventAction 枚举登记）
- `app/src/main/java/io/legado/app/ui/map/crossing/engine/CampaignController.kt`（在线壳层动作执行）
- 新增测试：`app/src/test/java/io/legado/app/help/sim/EventTriggerTest.kt`、`app/src/test/java/io/legado/app/ui/map/crossing/engine/CampaignEventActionTest.kt`

**未动**：JSON 资产（史实素材，不改数据）；既有测试期望值；replay 种子栈；任何 git 写操作。

## 2. 语义判定表（13 种动作逐个一行）

判定原则（任务书核心）：**事件型**改士气 / 兵力 / 补给 / 阵亡，落执行分支；**意图型**让某军转追击 / 侧击 / 溃退，落 intent 字段由 IntentResolver 后续回合消费；**混合型**两者都做。两类不混进同一个语义层。

| # | action | 类型 | 落地字段（help/sim SimArmy / crossing Corps） | 生效判据（可观察结果） |
|---|---|---|---|---|
| 1 | `fireAttack` | 事件型 | 兵力按默认 0.35 折损（value 合法 0..1 可覆盖）；士气降一级；打空出局 | strength 下降；morale downgrade；strength=0 → alive=false |
| 2 | `siegeEngine` | 事件型 | 兵力按 0.55 折损；士气直接 BROKEN | strength 显著下降；morale=BROKEN |
| 3 | `breakthrough` | 事件型 | 兵力按 0.25 折损；士气降一级 | strength 下降；morale downgrade |
| 4 | `navalRout` | 混合型 | 兵力按 0.20 折损；morale=BROKEN；intent=rout | strength 下降；BROKEN；intent=ROUT |
| 5 | `defendFall` | 事件型 | strength=0；alive=false；morale=BROKEN；**surrendered 保持 false**（殉国非被俘） | !alive；strength=0；!surrendered |
| 6 | `feignedRetreat` | 意图型 | intent=advance（诱敌追击）；exposed=true；士气降一级 | intent=ADVANCE；exposed=true |
| 7 | `ambush` | 意图型 | intent=ambush；清旧路径 / 追击绑定 | intent=AMBUSH |
| 8 | `flank` | 意图型 | intent=flank；清旧路径 / 追击绑定 | intent=FLANK（寻路走 flankPath 侧路） |
| 9 | `rout` | 混合型 | morale=BROKEN；intent=rout | BROKEN；intent=ROUT |
| 10 | `capture` | 事件型 | surrendered=true；alive=false；strength=0 | surrendered=true；!alive |
| 11 | `annihilate` | 事件型 | strength=0；alive=false；morale=BROKEN；**非投降** | !alive；strength=0；!surrendered |
| 12 | `retreat` | 意图型 | intent=retreat；清旧路径 / 追击绑定 | intent=RETREAT |
| 13 | `escape` | 意图型 | help/sim：intent=escape（规则 14 急行军脱走点）；crossing：intent=BREAKOUT（向最弱方向突围） | intent 落突围 / 脱走分支 |

既有 5 分支口径不变：`moraleChange`（含溃兵归队复振）、`surrender`、`setIntent`（含 targetPos）、`supplyCut`、`strengthDelta`。

**双栈对齐说明**：仓内有两套并行推演栈——`help/sim`（SimEngine/EventTrigger，纯 JVM 并行引擎）与 `ui/map/crossing`（CampaignController，在线 Compose 壳实际接线）。同一动作在两栈落地相同语义，折损比例常量两边一致（0.35 / 0.55 / 0.25 / 0.20）。

## 5. 二阶三阶影响（铁律 59）

### 5.1 直接效果

13 种事件从"静默空转"变为有可观察结果：兵力 / 士气 / 存活 / 投降 / 暴露 / 意图之一发生变化，`FiredEvent` 照常登记。

### 5.2 连带影响（受影响文件 / 接口 / 调用方）

- **回合快照 `TurnSnapshot.events`**（`CampaignController.snapshot()`）：新分支写入的事件日志进入事件条尾队列（`LOG_TAIL=8`），壳层事件面板、回放时间轴直接消费这些文案。
- **分支存档 `BranchSnapshot`**：`saveBranch()` 深拷贝的 `Corps` 现在可能携带折损后兵力 / BROKEN 士气 / 新意图 / exposed 标志；`restoreBranch()` 原样回滚，备份 / 回档口径不变量仍成立。
- **胜利判定 `VictoryChecker`**：`annihilate` / `capture` / `defendFall` 现在会真正把目标军移出棋盘，`ANNIHILATE` / `CAPTURE` / `DEFEND` 三类终局条件第一次能被事件触发推到（此前目标军不会因这些事件死，终局只能靠遭遇战 / 兜底）。
- **情报面板 / 视野**：`exposed` 标志（feignedRetreat 写入）参与伏击可见性判定；`CorpsView` 的 alive / surrendered / morale / intent 字段随之变化，棋子 token 与状态色刷新。
- **意图裁决 `IntentResolver`**：意图型动作写入的 intent 在下一回合被规则裁决读取（ambush 规则 4、flank 走侧路寻路、rout/retreat/escape 对应溃退 / 突围分支）。
- **解析层 `CampaignJsonParser.parseEvents`**：13 种标签不再被 `fromLabel=null` 丢弃记 warning，事件进入 `definition.events` 参与触发器求值。

### 5.3 二阶三阶后果

- **新战役素材接入成本下降**：后续写新 campaign JSON 直接用这 13 个标签即可生效，不必再改执行层；代价是"动作表"成为跨三处分发的契约（注册表枚举 / help/sim when / crossing when），新增动作必须三处同改——已由两个 selfcheck 脚本做门禁兜底。
- **回放一致性**：事件现在真实改状态，回放切片与当时快照的兵力 / 士气必须一致；若回放管道另存了旧版"空转"录像，需要重跑生成（本单不改回放种子数据）。
- **系统复杂度**：两栈语义靠注释 + 同名常量对齐，存在再次漂移的长期风险；彻底解法是合并双栈（见交接节，本单不做）。
- **维护成本**：动作分类（事件 / 意图 / 混合）写进 KDoc 与代码分区注释，新人新增动作时可照表归类，不再把意图标签误填进 action 位。

## 6. 跨领域对照（铁律 60）

- **编译器 opcode 表 vs 本单动作表**：指令集不认识的 opcode 必须走非法指令异常（本例 = else 告警），不许静默跳过；本单采纳——未知 action 登记 FiredEvent + 写 warnings，与"非法指令不静默"同构。
- **UI 事件总线的命令模式**：命令对象（事件声明）与执行器（when 分支）分离，新增命令只需注册新条目；本单 `EventAction.jsonLabel` 主标签表 + 别名表的结构，参照命令注册表做法，别名类比历史命令兼容层。
- **不采纳**：规则引擎 DSL / 数据驱动反射分发（按 action 名反射查 handler 表）。理由：本仓战役事件只有二十种上下，反射会牺牲纯 JVM 可测性与可读性，静态 when 穷尽覆盖对编译期检查更友好。

## 7. 反例与边界（铁律 61，先自我否证）

最强反对者论点："这些动作本来就是意图标签，填进 action 位是数据错误，应该改 JSON 而不是补代码。"
**否证与结论**：任务书硬约束"禁改 JSON 资产（改数据等于造假）"，且 13 种标签承载的史实语义（火攻、破城、被俘、覆没、佯退……）在事件位是合理的；故采纳"代码侧补齐落地语义"，数据原样保留。否证后方案成立。

穷举边界与兜底：

| 边界 | 实现兜底 |
|---|---|
| value 为空 | 折损动作回落各自默认比例；strengthDelta / moraleChange 走既有默认 |
| value 非法数字（`"not-a-number"` / `""`） | `toDoubleOrNull() ?: default`，不抛异常 |
| value 越界（如 `5.0`） | `coerceIn(0.0, 1.0)` 钳制，不超扣 |
| target 不存在（id 拼错 / 同名消歧失败） | 记 warnings / 日志，军队状态不变，不崩 |
| target 已阵亡 / 已投降 | 守卫跳过结算并告警；`moraleChange` 复振路径例外放行 |
| 重复触发 | `EventSpec.done` / `firedEvents` 一次性标记，第二次不叠加折损 |
| 同回合多事件冲突（先 fireAttack 再 surrender） | 按 JSON 数组顺序顺序结算；后者覆盖前者；surrender 后 alive=false，后续事件被守卫跳过并告警 |
| JSON 缺字段 | EventSpec / ArmySpec 全字段默认值；解析层整条事件兜底跳过 + warning |
| 极小兵力被比例折损 | `roundToInt` 可能扣 0，不死不崩；打空才出局 |
| 全局事件（target=null） | FiredEvent 照常登记，无目标不执行状态变更 |
| 未知 action | else 告警 + 事件登记，不静默 continue |

## 8. 历史包袱审计（铁律 62）

- **既有 5 分支**：U12 初始提交有意为之，口径保留不动。
- **help/sim 与 crossing 双栈并行**：历史遗留（两套纯 JVM 引擎并存，在线壳只接 crossing）。本单只对齐两栈语义，不做合并；是否废弃 help/sim 交总控决策（见交接 1）。
- **replay 种子栈 `EventAction`（3 值）**：种子数据专用构造，不解析 campaign JSON，非本单消费路径，保留。
- **可安全移除项**：无。本单未发现"为解决已不存在问题而引入"的死代码；第一版枚举 when 里的 camelCase 死双写已在本单重构中消除。

## 9. 认知成本（铁律 63）

- **收敛位置**：13 种动作的认知入口只有三处——`EventTrigger.kt` 一个 when（并行栈执行）、`Enums.kt` 一张标签表（登记）、`CampaignController.kt` 一个 when（在线栈执行）。新人改一个动作，按判定表在这三处同改即可。
- **分类写在注释里**：事件型 / 意图型 / 混合型三段分区注释 + KDoc 判定表，不需要翻 JSON 反推语义。
- **文件规模**：改动后主文件 193 / 603 / 253 行，均未越千行；无新增抽象层，无第二份同职责实现。
- **命名**：枚举条目沿用既有 `UPPER_SNAKE` 风格；`jsonLabel` 显式标明它是 JSON 原始标签，避免与 Kotlin 枚举名混淆。

## 10. 最慢环节（铁律 64）

1. **本单无运行时**：本机无 Android SDK、禁 gradle/kotlinc，最慢的编译 / 单测环节发生在云端 CI，本单无法测量；静态层唯一耗时点是两个 selfcheck 脚本全量扫 70 个 JSON，秒级完成。
2. **历史慢点对照**：`runBlocking` / `Thread.sleep` 集中在阅读链路，不在本单事件路径；事件派发在回合主线程内同步执行，无新增阻塞 IO。
3. **可自动化**：`selfcheck-data.py`（JSON action ↔ EventTrigger 字面量对账）与 `selfcheck-flow.py`（枚举登记 ↔ 执行分支对账）已是门禁脚本，新增 action 漏登记会直接 FAIL。

## 11. 返工复盘沉淀（铁律 65）

- **根因类别**：契约漂移 + 边界缺失——JSON schema 实际出现 17 种 action，执行注册表只登记 5 种；解析层对未知标签"跳过 + warning"，执行层对未登记分支"静默落空"，两层都没把缺口顶到用户可见处。
- **预防手段**（已落地）：两个 selfcheck 脚本把"JSON 出现的每个 action 必须在注册表有字面量、在执行层有分支"做成可执行门禁；本单后 action 相关失败项归零。
- **沉淀规则**：后续任何新增 action，必须同改三处（枚举标签表 / help/sim when / crossing when），任一缺失由脚本拦截；事件型与意图型归类先查 §2 判定表，不许把意图标签填进事件语义。
