### 判据 2 · 复位时机是否安全、会不会把本场第一批告警清掉 —— PASS（附一帧级观察）

- 时序推演（`ReplayScreen.kt:57-80`、`ReplayDirector.kt:215-245`）：
  1. composition 解析 `activeDirector`（`:57-59`）；
  2. `LaunchedEffect(activeDirector)` 协程启动，首句 `clearWarnings()`（`:68`）；
  3. `withFrameNanos` 取首帧时间戳初始化 `lastFrameNanos`（`:69-71`）；
  4. 进入 `while(true)` 帧循环，首帧回调内才调 `activeDirector.update(dtMs)`（`:73-77`），事件派发 `dispatchEvents` 发生在 `update` 内（`ReplayDirector.kt:230`）。
- main 内 `director.update(...)` 的唯一调用点是 `ReplayScreen.kt:76`（命令：`grep -rn "\.update(" app/src/main --include=*.kt`，逐条排除 Book/Globe/Canvas 等同名方法后，本导演仅这一处）。effect 挂接前不存在任何派发入口，因此复位发生在本场首次派发之前。
- 结论：内部 remember 新建导演台账本为空，复位为 no-op；外部注入导演在挂接前若已带旧告警，属上一场残留，清空符合预期。本场第一批告警由首帧及之后的 `dispatchEvents` 产生，排在 `clearWarnings()` 之后；同实例后续重组不重启 effect，不会二次清空。**复位不会把本场第一批告警清掉。**
- 一帧级瞬时窗观察：`LaunchedEffect` 块在 composition 之后的协程中启动；在「composition 完成 → effect 首句执行」之间，壳层读取点 `ReplayScreen.kt:156` 理论上可能读到注入实例残留旧告警一帧，随后即被复位。当前无 Compose UI 测试可观测该窗口（见判据 6），记观察项，不判 FAIL。
