## 三、观察项 A：跨收集器缓存 var 无同步 —— 已落地

### 3.1 问题（验收报告判据 5 / 观察项 3）

旧 `InkSearchViewModel.kt:250-251` 的 `historyKeys` / `usageKeys` 是普通可变 `var`，两路 IO 收集器分别写、`publishHot` 互读对方缓存，无锁、非 `@Volatile`；并发「新搜一词 + 清空历史」时存在可见性与交错风险。

### 3.2 处置

- 缓存下沉 `SearchHotBinder`：`AtomicReference<HotSnapshot>`（`SearchHotBinder.kt:50`）持有不可变双路快照；时间序路 `updateAndGet` 合并 history（:59），频次序路合并 usage（:68）；`publishHot` 一次性取快照再交 resolver 解析（:79-80）。
- KDoc 写明原因（`SearchHotBinder.kt:22-31`）：普通 var 跨协程写无同步、读无可见性保证，并发时另一路可能读到未发布的陈旧缓存，且普通 var 写入不保证对另一线程立即可见；`AtomicReference` 提供 volatile 可见性与原子合并，快照字段不可变、合并时整体替换，不会暴露可写引用。
- 收敛语义不变：最坏情况仍是一帧级陈旧（下一次流重发收敛），状态写入本身走 `MutableStateFlow.update` 原子更新；消除的是跨协程可见性窗口与交错写坏列表的风险，不改变三档回落行为。

## 四、观察项 B：备份导出含全部搜索词无脱敏 —— 裁决：本单不脱敏，不改 Backup.kt

### 4.1 调用点穷举（全仓 grep `SearchKeyword` / `searchKeywordDao` / `searchHistory.json`）

- `Backup.kt:83-85`：`searchHistory.json` 仅在 `BackupConfig.historyContentKey`（`backupHistory`）勾选时进入压缩包清单；清单组装见 `Backup.kt:400` `selectedBackupFileNames(...)`。
- `Backup.kt:300`：`writeListToJson(appDb.searchKeywordDao.all, "searchHistory.json", backupPath)` 暂存写出。
- `Restore.kt:353-354`：`fileToListT<SearchKeyword>(...)` 后整批 `insert`。
- 测试锁定：`BackupMediaTest.kt:44`、`:76` 文件清单断言；`ReadRecordSnapshotContractTest.kt:65` 文本断言。
- 其余消费方：`AppDatabase.kt:167` DAO 声明；`InkSearchViewModel.kt` 七处 DAO 引用（:95 单条删、:103 清空、:257/:258 双路流、:268/:271/:272 频次累加写库）；无第二个业务模块读取 `search_keywords` 表。

### 4.2 裁决与理由

判为「不脱敏」，本单不改导出字段：

1. 本机备份属用户自有数据；`searchHistory.json` 已受 `backupHistory` 内容开关门控，用户显式勾选才入包，取消勾选即不导出，已有排除入口。
2. 恢复语义依赖原文：`Restore.kt:353-354` 整批 `insert SearchKeyword(word, usage, lastUseTime)`；对 `word` 做不可逆脱敏 / 截断 / 哈希后，恢复出的历史是占位词，频次榜与历史行无法还原，破坏「备份 → 换机恢复」闭环。
3. 同类数据 `readRecord.json` / `bookmark.json` / `highlight.json` 均明文入包；只对搜索词脱敏是不一致的隐私姿态。
4. `BackupMediaTest` 等静态契约锁定文件清单与字段；改导出字段必须同步改恢复侧与契约测试，超出本单允许的改动范围（硬约束仅允许 `Backup.kt` 必要时改动）。

### 4.3 反例与边界（什么情况下应回炉做加密 / 排除）

- 反例 1：备份上传 WebDAV（`Backup.kt:456` `AppWebDav.backUpWebDav(zipFileName)`）且未设备份口令；zip 整体不加密码（`ZipUtils.zipFiles` 无口令参数），仅 cookies / runtime / servers / 口令字段经 `BackupAES` 加密，`searchHistory.json` 在包内明文，搜索词会离开本机落到第三方云盘。
- 反例 2：局域网互传备份（`backupForLanTransferLocked`，`Backup.kt:163-190`），接收方非本人；LAN 路径只剔除 cookies / runtime 两类，搜索历史仍随包。
- 反例 3：设备转借 / 二手出售前未删除外部存储里用户主动导出的旧 zip；暂存目录在 `Backup.kt:467-468` finally 中清理，但用户导出的外部副本不自动擦除。
- 边界与后续建议（不在本单改码）：后续批次可评估独立「搜索历史」排除子开关，或导出时按备份口令做可逆 AES 加密（与 cookies 同路径）；不可逆脱敏不可取，会破坏恢复语义。当前缓解手段即取消勾选 `backupHistory`。

## 五、二阶 / 三阶推演

### 5.1 首屏冷启耗时

- 单次收集多一次 CAS（`updateAndGet`）与不可变 list 引用替换；`search_keywords` 表体量为 `HISTORY_LIMIT=12` / `HOT_LIMIT=10` 量级，纳秒级开销，冷启首屏无可测影响。
- binder 构造只取 DAO Flow 引用，Room 订阅在 `collect` 时建立，不在 `attach` 主线程开查询；与旧 `execute` 路径一致。
- `AtomicReference` 无锁，不会在 IO 收集线程上引入锁竞争。

### 5.2 Room 流双订 / 页面来回切换

- 两路流仍各订一次；`start()` 只在 `attach()` 首次初始化（`searchScope` 未初始化分支）调用，再次进入不重复订阅，守卫与旧逻辑一致。
- 收集器挂 `viewModelScope`，`onCleared` 随 scope 取消；`pause` / `resume` 不重建 binder，状态保留。
- 快照整体替换，resolver 不会读到半更新列表；页面来回切换期间最坏一帧陈旧，下流重发收敛。

### 5.3 备份策略变更对恢复流程的影响

- 本单备份 / 恢复零改动，恢复链路无影响。
- 若后续做导出脱敏：`Restore.kt:353-354` 必须同步改造，否则占位词入库；`BackupMediaTest` / `ReadRecordSnapshotContractTest` 需同步更新；属后续批次范围，不在本单。
