### 3.2 独立判断：等长归名物是否等于 O1 没解决

O1 担心的是「名物槽截胡本该由 word 槽命中的普通多字词」。B35 把碰撞拆成两类：

- 名物短词 vs 更长普通词组：已解决。artifact 2 字、word 4 字时 word 胜（`SlotArbitrator.kt:37`；测试 #3 `:87-91`、#8 `:133-145`）。
- 等长同形碰撞：未解决。两侧 token 长度相等时仍判 artifact 胜，同样 2 字的普通词继续被压在名物泡里。

具体反例（古籍语境）：

- 「白马」：《公孙龙子·白马论》「白马非马」中「白马」是泛指类名（白色的马），词义气泡更贴切；若名马库收「白马」为专名（祭祀 / 封号之马），等长 2 字仲裁归 artifact，词义泡被压制。写码报告 §2.5-1 已举此例，验收侧复核成立。
- 「龙泉」：剑名 vs 泉水普通词；「铜雀」：台名 vs 普通词。同形等长时同样归名物。

### 3.3 口径一致性

等长归名物与规格次级键「同位置多命中取更高优先级；同优先级取更长词」（`BubbleResolver.kt:14` 类注释）不冲突：长度是次级键，长度持平后回退既有领域优先。仲裁器把这条隐式链序口径显式化、单源化，方向可辩护；但 O1 中「等长普通词被截胡」这一碰撞类在当前信号集（只有长度）下无解，写码报告 §2.5-1、§七 已如实挂账给 tier / 置信字段接入单。

### 3.4 小结

更长普通词被救回，等长普通词仍让位名物；残留风险真实存在但已登记、未被掩盖。**判据 3 有条件通过**，必做后续：证据强度（tier / 消歧置信）接入后在仲裁器内补等长裁决。

## 六、判据 6：性能二阶影响 —— PASS（增量有界，实测待真实数据落地）

### 6.1 当前空数据状态

- 默认装配 `BubbleResolver.kt:157` `artifact = ArtifactBubbleProvider(EmptyEntityProvider())`；空实现下 artifact 恒返回 null（`ArtifactBubbleProvider.kt:48`），word 槽原本就会被查询。B35 未改变当前状态的调用次数：artifact 旧链本来就会先问一次，word 在 artifact 为 null 后也必问。

### 6.2 真实数据落地后的增量

- 旧链：artifact 命中即 return，word 不再查询。
- 新链：artifact 命中分支仍会多跑一次 `word.matchWord`（dispatch，`:112`）/ `word.query`（queryToken，`:91`）。
- 增量查询复杂度：`ChineseDict.wordAt`（`ChineseDict.kt:75-106`）走内存 `HashMap` 索引（`:135` / `:171`），窗口 5→2 字（`:89`），每窗做 substring + hash 查找；最坏 ≤ 4 个长度档 × ≤ 5 个起点，约十几次 hash 查找，不整表线性扫。`wordAt` 开头的连续汉字串边界扫描（`:84-85`）随既有 word 路径本来就存在，不是 B35 新增。
- artifact 侧成本未变：`ArtifactBubbleProvider.hitAt`（`:54-57`）仍是 2~5 字窗口 × 14 类实体槽遍历。

### 6.3 量级与放大判断

- 段落长度量级：一次点击触发一次解析；词窗上限 5 字，候选查找不随段落总长放大。唯一线性于汉字串长度的操作是 `wordAt` 的串边界定位，该操作在 B35 之前的 word 路径上已存在。
- 候选数量量级：word 侧 HashMap 单查；artifact 侧 14 槽 × 4 窗。B35 增量为「artifact 命中时多一次 word 索引查找」，属常数级槽内查表，不引入新的全表扫描或跨槽对齐复杂度。
- 预算口径：`BubbleBenchmarkTest.kt:22-23` 冷启 ≤300ms、热路径 ≤80ms；bench 装配（`:37-39`）走七参构造，artifact 用默认空实现。真实 Provider 接入后，artifact 命中分支的额外 word 查找耗时须按同一 bench 口径复测。

### 6.4 小结

增量为一次内存索引查找，有界、不随段落长度放大；当前空数据状态零增量。本机未实测耗时，以 CI bench 与真机复测为准。**判据 6 PASS（附复测条件）。**

## 七、判据 7：空态与兜底 —— 兜底壳不会被当真实命中压制 word —— PASS（防护点在适配层，不在仲裁器）

### 7.1 兜底壳识别链路

- `EmptyEntityProvider.query`（`EmptyEntityProvider.kt:16-22`）无论 type / anchor 都经 `ArtifactFallback.notFound(...).content` 取结构完整壳，不返回 null。
- 壳的 `source` 固定为 `MISSING_SOURCE`（「未命中」）：`ArtifactFallback.kt:57`（notFound）、`:91`（ambiguous）、`:103-104`（timeout 委托 notFound）。
- 适配层过滤：`ArtifactBubbleProvider.kt:45` `if (result.source == MISSING_SOURCE) continue`；14 类全部未命中后 `:48` `return null`。段落窗 `hitAt`（`:51-59`）逐窗走同一 `query`，过滤口径一致。

### 7.2 仲裁器入口实测推演

- 默认装配下 artifact 侧每窗每类都拿到 `source=未命中` 壳，适配层全部 `continue`，最终 `artifactHit = null`；`SlotArbitrator.kt:30` `if (artifactHit == null) return wordHit`，word 候选正常胜出，兜底壳不会进入长度比较。
- 既有测试 `ArtifactBubbleProviderTest.kt:154-158`（空数据兜底壳不作为命中返回 null 下钻）守住该口径；B35 测试 #4（`:94-97`）、#10（`:163-171`）、#12（`:191-199`）覆盖单侧 null 与双侧皆空。

### 7.3 防护位置与残留风险

- 仲裁器自身（`SlotArbitrator.kt:29-43`）只比较 `token.length`，不读 `source` / `kind`，不识别兜底壳。「壳不冒充命中」的防护完全依赖 `ArtifactBubbleProvider.kt:45` 的契约过滤。
- 若后续真实 EntityProvider 漏过滤、返回一只 `source != MISSING_SOURCE` 的壳或残缺件，仲裁器会把它当真实命中并压制 word。该纵深缺口记入新发现 N2。

### 7.4 小结

当前 `EmptyEntityProvider` 兜底壳不会被当真实命中，不会压制 word；两侧皆空返回 null 交 char / Missing 兜底，不留空白态。**判据 7 PASS。**
