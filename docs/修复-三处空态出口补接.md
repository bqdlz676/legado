## 一、缺陷复述与 HEAD 现状判定

### 1.1 FilePickerDialog 目录读取失败态（假接线按钮）

1. 触发条件：`state.error != null`。由 `FilePickerViewModel.upFiles` 两条路径置真：一是 `parentFile == null` 落「根目录不可用」（`FilePickerViewModel.kt:49-52`）；二是目录扫描协程 `onError`，即 `listFiles()` 抛权限拒绝 / IO 异常（`FilePickerViewModel.kt:65-68`）。**这是本机文件系统读取失败，不是网络离线**；界面沿用 OFFLINE 视觉档是既有口径，本单不改状态语义。
2. 改前用户能做什么：只能读错误文案；弹窗底部「取消」可关闭弹窗；面包屑可点 root / 上级，但文件列表停在错误态，没有任何入口主动重新列目录。
3. 改前做了会怎样：`InkEmptyState` 未传 `actionLabel` / `onAction`，按 `InkEmptyState.kt:62` 离线档默认渲「重试」按钮，`onAction` 落 `InkEmptyState.kt:41` 默认 `{}`——按钮可点、点击无下一步（Q-467 N1 登记的假接线）。

### 1.2 FileManageScreen 错误态（标签与动作错配）

1. 触发条件：`state.error != null`，同构来自 `FileManageViewModel.upFiles` 的根目录不可用 / `onError`（`FileManageViewModel.kt:33-35`、`FileManageViewModel.kt:49-52`）。
2. 改前用户能做什么：看到标签为「重试」的按钮；其余回退入口（面包屑 root、列表「..」行、系统返回键）走的是 `onPop`。

### 1.3 DictRichContent 词典图片失败态（无重试出口）

1. 触发条件：Glide `onLoadFailed`（`DictRichContent.kt:277-280` 改前位置）：远程图 404 / 超时 / 解码失败、`data:` 协议畸形数据、资源已移除。条目内图片块与大图查看器两条链共用同一个 `DictImageFailure`。

## 二、逐处接线方案与选择理由

### 2.1 FilePickerDialog：接 VM 重读当前目录

1. `FilePickerViewModel.kt:72` 新增 `fun retry() = upFiles(lastDir)`——错误态重试重读当前所在目录；注释写明「失败态的真恢复入口，不是返回上级」。
2. `FilePickerDialog.kt:112` 宿主（DialogFragment 壳）经 `onRetry = viewModel::retry` 传入；`FilePickerDialog.kt:153` `PickerContent` 形参补 `onRetry: () -> Unit`；`FilePickerDialog.kt:188-195` 错误态 `InkEmptyState` 补 `actionLabel = "重试"`、`onAction = onRetry`。
3. 本地兜底口径：本弹窗全程读本机文件，无网络也无远程缓存列表可切；已访问过的路径由面包屑（`state.subDocs`）保留可点，不可恢复场景（根目录为 null）由「取消」关闭弹窗兜底，不新造无意义动作。

### 2.2 FileManageScreen：选「真重试」，不改标签

二选一裁决（锚点卡 §二.2）：
- 方案 A：补真重试入口，标签维持「重试」，动作接重读当前目录。
- 方案 B：标签改成与 `onPop` 同义的「返回上级」，另补一个真重试入口。

**采方案 A。理由：**
1. VM 已具备 `upFiles(lastDir)` 重读链（`FileManageViewModel.kt:32-53`），真重试零新增协程路径；方案 B 要在 `InkEmptyState` 单动作槽里塞第二个入口，组件槽位不支持，等于强行扩组件接缝。
2. 返回上级已有三个既有入口：面包屑 root（`FileManageScreen.kt:67-71`）、列表「..」行（`FileManageScreen.kt:103-115`，父级分支 `FileManageScreen.kt:109`）、系统返回键（`FileManageActivity.kt:55-61`）。方案 B 把错误态按钮改成「返回上级」只是重复既有入口，却仍不给目录读取失败留下恢复路径，违反 C3 不允许空白态边界。
3. 按判据「写『重试』就只能重试」：改标签掩盖接错动作被禁止；正确收口是把错配动作换成同义真动作。

落地：`FileManageViewModel.kt:56` `fun retry() = upFiles(lastDir)`；`FileManageActivity.kt:39` `onRetry = viewModel::retry`；`FileManageScreen.kt:61` 形参补 `onRetry: () -> Unit`；`FileManageScreen.kt:87` `onAction = onRetry`。

### 2.3 DictRichContent：失败态加重试钥匙 + 占位可放大原文

1. 条目内图片 `DictRichImage`：`DictRichContent.kt:263` 新增 `retryTick` 重试计数；`DictRichContent.kt:265` `DisposableEffect(block.src, retryTick)` 以双钥匙挂加载副作用；点重试时 `DictRichContent.kt:340-344` 清空位图、置 `failed = false`、`retryTick++`，副作用重跑即强制 Glide 重新解码 / 重新取图；旧目标在 `onDispose` 经 `Glide.clear` 回收，不留泄漏。
2. 失败占位 `DictImageFailure`（`DictRichContent.kt:401-431`）形参补 `onRetry: () -> Unit` 与可选 `onOpenOriginal: (() -> Unit)?`；`DictRichContent.kt:430` 补「重试」`InkButton`（GHOST 档）；`DictRichContent.kt:409` 占位区在 `onOpenOriginal` 非空时可点，走既有 `onTap(block)` 契约——图片带 `click` 脚本时执行脚本，否则打开大图查看器（口径对齐 `DictDialog.kt:197-206`）。
3. 大图查看器 `DictImageViewer`：`DictRichContent.kt:444` 同构 `retryTick`；`DictRichContent.kt:446` 双钥匙副作用；`DictRichContent.kt:482-489` 失败态接 `onRetry`；查看器内已是大图层，`onOpenOriginal` 传 null，占位区不重复响应点击。
4. 重试仍失败的兜底：落回占位图（文案 + 原文 URL），重试按钮仍在、占位仍可点放大原文；查看器自身失败态同样可重试。`data:` 畸形数据这类不可恢复边界停在占位 + URL，不崩溃、不吞异常（异常仍由 `AppLog.put` 落档，条目图 `DictRichContent.kt:279`、查看器 `DictRichContent.kt:459`，口径沿用）。

## 四、动作 → 点下去发生什么 → 失败再怎么兜

1. **Picker 重试**：点「重试」→ `retry()` → `upFiles(lastDir)` 在 IO 线程重新 `listFiles()` 当前目录 → `onStart` 清 error / selectFile，`onSuccess` 落文件列表，`onError` 再落错误文案并 toast。重读仍失败：错误文案保留，按钮可再点；根目录为 null 这类不可恢复项：面包屑回退 / 「取消」关闭弹窗兜底。
2. **Manage 重试**：点「重试」→ `retry()` → `upFiles(lastDir)` 重读当前目录 → 成功落列表；失败保留 error 文案可再试。返回上级走既有面包屑 /「..」/ 返回键，错误态按钮不再冒充返回。
3. **Dict 图片重试**：点「重试」→ 清位图 + `failed=false` + `retryTick++` → `DisposableEffect` 重跑，Glide 按可用宽度（查看器按屏宽）重新解码 / 取图 → 成功按宽高比显示。再失败：回占位（文案 + URL），重试按钮仍在，占位区可点经 `onTap` 进大图查看器；查看器失败态独立可重试。

## 五、自查反例（最强反对者视角）

1. 反例：「Picker 是离线态，重试应该切到『已下载』筛选或刷本地缓存。」驳回：本弹窗全程读本机文件系统（`Environment.getExternalStorageDirectory()` / `initPath`），不发网络请求，不存在在线列表与下载缓存之分；当前目录就是本地口径。已访问路径由面包屑保留，即本场景下的「本地已缓存路径交互」。
2. 反例：「Manage 把标签改成『返回上级』更省事，不用加 VM 方法。」驳回：返回上级已有三个既有入口（§2.2 第 2 条），改标签只是重复入口；目录读取失败将永久失去重读出口，等于用文案掩盖错配动作，违反锚点卡 §二.2。
3. 反例：「Dict 重试应该回 VM 重拉整条释义。」驳回：图片失败是单图解码 / 取图边界，整段释义重拉代价过大且会丢掉用户当前浏览位置；钥匙式局部重载只重跑该图 Glide 请求，失败再落占位 + 可放大原文，边界内闭环。
4. 反例：「`retryTick` 自增会不会导致副作用反复重跑、位图泄漏？」驳回：每次钥匙变更先 `onDispose` 走 `Glide.clear(target)` 回收旧目标再建新目标（`DictRichContent.kt:289-291`）；位图复制为可变副本的既有口径（`DictRichContent.kt:268-269`）未动。
5. 反例：「新增必填表参数 `onRetry` 会不会漏掉别的调用方？」排查：`grep -rn "FileManageScreen("` 全仓仅 `FileManageActivity.kt:31` 一处；`PickerContent` 为 `FilePickerDialog` 私有 Composable，仅内部调用；`DictImageFailure` 私有，两处调用点同文件已改。无第二调用方漏接。
6. 反例：「失败占位整区可点，会不会和「重试」按钮双击触发两个动作？」静态排查：`InkButton` 自身消费点击；`Column.clickable` 只在非按钮区域响应，按钮点击不冒泡到占位区。观感层涟漪 / 按压反馈未真机实测，登记 §六 D5。
7. 反例：「是不是为消缺口给 data: 畸形 URL 编造了重试动作？」驳回：重试是既有权重路径的重放，不是新造事项；畸形数据重试不成功即停在占位，符合「重试失败有兜底」而非「重试必然成功」。
