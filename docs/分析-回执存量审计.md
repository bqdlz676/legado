# 分析 · 回执存量审计（229/230 执行类报告无回执）

> 结论先说：这是长期存量债，不是一夜之病。用"批量补回执"来掩盖等于伪造，正确做法是**分批重读 + 顺带复核结论**，回执里写明"补录，原交付无回执，本代理现读并复核 N 条"。

## 一、实测数（2026-11-26 夜，`python3 data_scripts/check-onboarding.py --audit`）

- 执行类报告总数 230 份（`docs/修复-*.md` / `验收-*.md` / `实现-*.md` / `组装-*.md`）。
- 缺回执或不合规 229 份，合规 1 份（本夜刚补的那份留档报告，且它是用"留档豁免"标记过的）。
- 老账不是"没写守则"造成的：三份必读在 11-25 就已成文，只是**没有任何机检要求出示读过它**——写与读之间断了链。

## 二、损失定级（为什么必须返回去消除，而不是从今天开始算）

1. **结论不可信面大**：229 份报告里，凡"已查验/已复核/已逐条核对"一类措辞，都无法证明是照着守则的判据做的；其中已累计沉淀 872 处余项、18 份硬 FAIL 判定的历史，事后追因要靠重读。
2. **复核成本随时间上升**：报告越老，回源所需的代码版本越远（`git log` 回溯 + 行号漂移），每晚一轮成本更高。
3. **规则被绕开有先例**：事故一至五全部发生在"规则在册、无人执行"的窗口里——不回填这段历史，下一棒有充分理由说"以前也没人贴"。

## 三、处置方案（分批、可验、不伪造）

- 新报告：即日起强制（`check-onboarding.py` 已入推送体检 3.7 步）。
- 存量：按域分 5 批（搜索与书架 / 战役与回放 / 阅读器与贴皮 / 地图与名物 / 机制与文档），每批派**机制-文档子代理**执行，动作固定三步：
  1. 读当前四份必读，贴真实指纹与三条逐字引用（标注"补录"）。
  2. 对该批每份报告**抽查 3 条关键结论回源**（结论 → 原始 `文件:行` / commit / 报告锚），不一致的记缺陷立案。
  3. 报告头统一加一行：`回执补录：原交付无回执，本代理 <日期> 现读并复核 N 条`。
- 不做的：不许原样复制模板回执贴到 229 份（那是伪造）；不许把历史报告批量改写成"已合规"。

## 四、判据（批次完成的定义）

- 该批每份执行类报告都有可回源的三条引用与真实指纹；
- 抽查结论回源率、发现的结论漂移条数、新增缺陷编号都写进批次报告；
- `check-onboarding.py --audit` 对该批域的计数归零（或剩余项全部带"作废/留档"标记并在台账挂号）。
