## 五、反向推演（先假设本方案错误，找反例与边界）

- 反对论点一：「回放栈枚举为什么不直接扩成 19 条，把 16 种动作都写上拒绝分支？」否证：回放棋子模型无 `alive` / `surrendered` / `exposed` / `target` / 兵力结算位，拒绝分支只能是空壳；且会形成第四份动作标签表，验收报告 §六 已记口径漂移认知债。枚举不扩、else 兜底，既能拦住未来静默空转，又不复制语义；模型补齐列入合并单。
- 反对论点二：「supply 字段加到回放棋子上，会不会驱动渲染层改出一堆断粮 UI？」否证：本单 supply 仅落模型与派发，`PieceVisual.kt` / `BattleArrow.kt` 未读 supply（已 grep 核对），渲染零改动；断粮视觉提示属后续 UI 单，不在本单范围。
- 边界穷举：
  - 目标 id 不存在：回放 `:246-250` 告警 + 登记已点燃；活栈 `CampaignController.kt:348-351` 同口径。
  - 目标已出局 / 溃散：回放断粮保留 ROUT 守卫（`:259`）；活栈 `:353-357` 除 `MORALE_CHANGE` 外不再重复结算。
  - 重复触发：回放 `appliedEvents` 集合（`:240`）；活栈 `firedEvents` 集合（`:97` / `:341`）。
  - 未知动作字符串：活栈解析层 `CampaignJsonParser.kt:239-241` 跳过 + warning；回放枚举类型系统构造不出未知值，else 为防御性兜底。
  - 非法 value：回放 `Morale.fromLabel` 未知值兜底 STEADY（`BattleModels.kt:27-32`）；活栈 `fracOf` / `toDoubleOrNull` 回落默认值（`CampaignController.kt:471-472`）。
- 反例挂账：意图型四分支事件写入的意图，同回合即被 `resolveIntent` 覆写（`CampaignController.kt:283-284`），测试只能守日志落位、守不住意图字段；若规格要求脚本意图压过规则裁决，需另立单在 resolver 加事件意图优先档位（沿用验收报告 §九 交接 2）。
