## 三、逐维对照（12 维，每条给判断与理由）

**1. 数据深度与真实性**

A：实测 Tycho-2，mag ≤6.5 内置全量约 9,100 行，金字塔到 11.5 等约 250 万行候选，局部放大真的长出暗星。
B：程序化密度场顶到"视觉约 9 等"，星官成员星约 1,700 颗有换算坐标，其余是生成的。
判断：A 完胜。理由：用户已拍板 11.5 等，B 在这一项已知不满足（B 自己在第 0 节与第 12.11 条都承认）。

**2. 许可风险**

A：Tycho-2 为 CC-BY-NC-3.0 IGO（非商用），需首启可选下载 + 许可页 + 数据台账；商业化即整体换源。风险中。
B：古籍 + IAU 事实 + 程序化，零外部许可依赖，可商用。风险零。
判断：B 完胜。这是 B 唯一的绝对优势，也是它作为回退方案的全部价值。

**3. 体积与分发**

A：内置 <2MB；金字塔按需 <60MB、可删可重建；NC 数据不进 APK/CI artifact。
B：全部 <300KB 内置。
判断：B 胜（体积小两个数量级）。但 A 的按需层不进包，APK 增量其实也只有 <2MB，差距对安装包影响有限。

**4. 精度与诚实性**

A：坐标实测，星等/距离/光谱对精选子集逐条有出处，其余留空。
B：星官坐标由古籍度数换算，偏差 1–2°，必须标"位置示意"，`precisionTier` 分 tier 1/2。
判断：A 胜在精度，B 胜在"零编造"同样彻底（它干脆不提供外国星表字段）。两份的诚实性设计都成立，A 的可用信息更多。

**5. 可落地性（外部依赖）**

A：依赖 CDS/HEASARC 抓取可达、行数校验通过、抽 3 行人工核对；任一环断则整候选回退 B。
B：零外部依赖，古籍文本已在项目内可查。
判断：B 胜在确定性。A 需要数据代理先做验证（第 3.13–3.16 条），这笔前置成本是硬成本。

**6. 性能**

A：可见实体星 ≤700 + 密度底图 1 张 + 连线单 Path；投影 <4ms、整帧 <16ms。
B：星官星 ≤1,700 + 密度场 1 张 + 连线单 Path；同四项 bench。
判断：持平。两份都压成 3 pass、都用 sprite atlas，draw call 结构一致。A 的 700 是"视场内可见上限"（视场外不画），B 的 1,700 是全量但大多在视场外，实际渲染量接近。

**7. 验收可测性**

A：判据全部可截图/可 bench/可 grep，地上观用单星方位判（误差 ≤1°）。
B：地上观**只能用星官整体方位判**（误差 ≤3°），单星判不了——这是 B 的验收弱项，也是它精度的直接后果。
判断：A 胜。可测性更强，判据更硬。

**8. 与全 App 一致性**

A/B：两份的 ⑧ 节同构（12 类卡片复用、77 图标不新增、12 色零裸 hex、内容色走 `SkySpecColor`、派生色集中 `GlobeTokens`、动效 spring、热区 48dp、字号 14sp）。
判断：持平。差异只在 A 多一层"金字塔加载态"需要命中 `UX-05` 关键词，B 的"加载态"是进程内一次性、几乎不可见。

**9. 离线韧性**

A：线框全内置、亮星全在、暗星缺则低层底图兜底、完全无缓存则程序化 `StarField` 兜底。
B：全内置，离线与在线等价。
判断：B 略胜（无"部分可用"状态），A 的兜底链更长但也更复杂、更容易出"降级域污染"这类 bug（A 第 11.8 已列为必改项）。

**10. 成本（工期 / 工具预算）**

A：4 单里数据单最重（抓取 + 校验 + 金字塔打包 + 三族表），估计占整条链一半工具预算。
B：数据单是"古籍度数提取换算"，纯文本工作，工具预算低。
判断：B 胜在成本。但 A 的成本大头是一次性的数据工程，做完不复用性低（数据可长期用）。

**11. 回滚与切换成本**

A→B：删金字塔与 Tycho 实体层，保留四表与全部 UI，切换成本中（数据层重写，渲染层不动）。
B→A：补数据层 + 金字塔，UI 层不动，成本中。
判断：持平。两份的契约层（`SkyParams`/`SkyFrame`/`SkySpecColor`/`StarProjector`）完全同构，这是刻意的——保证任何一份选中后，另一份都能低成本接上。

**12. 扩展性（二期行星 / 彗星 / 岁差 / 大气折射）**

A：有实测星表与 J2000 坐标，二期加行星/彗星只需补轨道根数；岁差可算。
B：坐标本身是换算值，二期加行星会与"非实测"口径冲突，需先补真实星表——等于回到 A。
判断：A 完胜。B 的架构在二期会逼你换源。

## 四、我方自认的最可能被判低点（不当已过关）

候选 A 的三条：

1. **石青用于"天赤道基准线"**。`ComponentPalette.kt:54-59` 登记石青用途为"Toast 提示态专用"，`GlobeTokens.kt:51` 又扩为"敌方灰青势力色块"。第三次用途会不会被判"语义污染"？我方认为"基准线"是中性测量语义、不承载情绪，可接受，但**必须由选型代理判**，并在切片-26 显式声明。若不接受，替换方案是 `textTertiary` alpha 0.30（代价：赤道与星座线同色，分层变弱）。
2. **"内容色"分类是否被接受**。我方依据 `GlobeTokens.kt:55-62` `GlobeSpecSurface` 先例（"地貌数据色，不是 UI 配色"）主张星色同类。若选型代理认为"星色不属于规格表格给定的数据色"，则 `SkySpecColor` 的四个锚点会变成"新造裸色值"，直接判低。这一条是 A/B 共有的结构性风险。
3. **视觉连续 ≠ 几何连续**。用户要"不设档"，A/B 都只做到"三档常驻 + 连续权重"，几何仍是三档。若选型代理按"必须几何连续"判，两份都不合格。我方主张：软渲染（C3 裁决）下几何连续的收益远小于成本，且用户可感的是"无跳变"；但这条必须由审验方裁，不能由设计方自证。

候选 B 的三条：

1. **已知不满足 11.5 等拍板项**。这不是"弱点"而是"定性"，B 的正当性只在"回退"。若选型按用户拍板项一票否决，B 应判淘汰。
2. **地上观只能用整体方位判（≤3°）**。判据比 A 软，验收代理可能判"不可测"。
3. **程序化密度场的观感天花板**。约 9 等的密度是"看起来像"，放大后不会长星；若验收要求"放大有新增星点"，B 直接 FAIL。

两份共有的一条：

4. **"跟随相机的 2D 投影"模型**。两份都推翻了"固定球壳"模型（第 8.4–8.7），理由是固定球在相机推到 9R 时会看到球外表面。这是技术判断，若验收代理认为"偏离切片-19 的 SphereGeometry 口径"，需按 C8（用户最新口令优先于旧规格）裁；旧口径本身在软渲染下也跑不通。

## 六、两条分支的落地前提

**若选 A（推荐路径）**，前置四项必须完成，缺一项不得进写码：

1. `docs/规格冲突清单.md` 增行：S-19 DoD 三档判据 vs 用户 2026-11-27 线性口令 → 按 C8 裁"连续为准，三档仅资源上限"，S-19 加作废标记不改原文。

3. NC 边界确认：非商用声明入数据台账；首启许可页文案定稿；Tycho 派生素材不进 APK/CI artifact 的构建规则写入 CI 配置说明。
4. `SkySpecColor` 与"石青基准线"两处口径由选型代理书面认可，否则按第四节给替换方案。

**若选 B（回退路径）**，前置三项：

1. 古籍度数覆盖率盘点：多少星官有可靠度数（可落坐标）、多少只能"示意"。这个数字决定 B 的可用度，未盘点前 B 的"1,700 颗"是估算。
2. 用户书面确认"接受 9 等、接受位置示意"——因为这与已拍板的 11.5 等直接冲突，不能用"未否决"推定。
3. 同样登记 S-19 冲突行（B 也改连续缩放）。

## 七、倾向（仅作参考，不构成结论）

按用户 2026-11-27 的三条拍板（11.5 等、线性不设档、精致），**A 是唯一能满足"深度"这一项的候选**，且二期扩展性明显更好；B 的全部价值在"零许可、零下载、零依赖"，适合作为 A 链断掉时的整链回退，不适合作为主选。

但 A 有两条真实成本：NC 边界（商业化即换源）与数据工程（抓取校验金字塔）。这两条若不接受，B 是唯一可走的路径，代价是深度降到 9 等。
