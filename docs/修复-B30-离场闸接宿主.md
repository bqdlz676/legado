## 二、落码方案与取舍

### 2.1 抽纯 JVM 阶段机基类，收敛 `isComposed`（第二件事）

新增 `app/src/main/java/io/legado/app/ui/book/read/ink/SheetExitPhaseGate.kt`：

- 枚举 `ReaderSheetExitPhase`（OPEN / EXITING / REMOVED）收归基类文件，全仓单一来源。
- 抽象基类 `SheetExitPhaseGate` 持有 `phase`，迁移规则 `enterOpen / beginExit / finishExit`
  与三份派生属性 `visible / isComposed / canOpen` 只在此写一份。
- `isComposed` 唯一派生口径：`phase != ReaderSheetExitPhase.REMOVED`（基类 :86-87）。
  B21 守卫不再读 `retainedRequest` 派生；负载槽位只负责登记 / 清存，不参与组合判断。
- 钩子 `onFinishedExit()` 供子类在收束时清存负载；无负载子类留空实现。
- 新增 `tryOpen(): Boolean`：仅 REMOVED 段放行并登记新会话，OPEN / EXITING 段返回 false
  且不改阶段、不登记负载。供宿主打开点一次性完成「先问闸、再 open」。

两个既有守卫改为继承基类，公开 API 全部保留：

- `ink/ReaderSheetExitGate.kt`：保留 `open(request)`、`beginExit(request)`、
  `finishExit()`、`retainedRequest`、`phase`；`onFinishedExit()` 清空保留请求。
  离场段重复 `beginExit` 仍按旧口径空操作，不替换保留请求（:49-53 守卫阶段）。
- `NoteDialogExitGate.kt`：保留 `open()`、`beginExit()`、`finishExit()`、`phase`
  及三份派生属性；自身不再写任何阶段判断。

两个 Compose 薄控制器（`config/settings/SheetExitController.kt`、
`book/source/SourceSheetExitController.kt`）本就只做 `get() = gate.xxx` 透传，判断逻辑
仍在守卫侧；本次只更新 KDoc 指向基类，透传体不动。

取舍：未把 B21 守卫泛型化为 `SheetExitGate<T>`。理由见 §3.1 被否决方案 A。

## 三、二阶影响推演

### 3.1 被否决的替代方案与反例

- 方案 A：把 B21 守卫泛型化为 `SheetExitGate<T>`，B26 直接复用同一泛型类。
  否决：泛型化要改 `ReaderSheetState`、`ReaderSheetGuard` 调用链与 B21/B26 既有单测签名，
  牵连超出本单红线；且两守卫差异仅在一个负载槽位，抽无负载基类已消除派生分叉。
  反例：泛型类仍需「带请求 / 不带请求」两个 open 入口，并未减少判断逻辑，只是把分叉挪进
  类型参数。
- 方案 B：宿主不另持闸，直接读弹窗实例内 `exitGate`。
  反例：每次 show 新建 Fragment 实例，宿主在 show 前拿不到旧实例引用；实例内闸对下一次
  show 不可见，无法解决 B26 §8 缺口。
- 方案 C：宿主用 `findFragmentByTag` 判现存实例代替阶段闸。
  反例：只能挡 OPEN 在场态，挡不住「节点已摘除、离场收束延时未到」的残余窗口；且把阶段
  语义散落成宿主判空，等于第二套判断。现方案闸 + 类型回调镜像，阶段口径仍归基类。
- 方案 D：保留 B21 `retainedRequest != null` 口径，给 B26 硬造一个 dummy 负载对齐。
  反例：无负载弹窗凭空多一个状态槽位；两套派生仍然不同源，分叉未消除。

### 3.2 离场期（EXITING 约 450ms）再次点击打开

- 弹窗仍挂在 FragmentManager 上时，宿主闸处于 OPEN，`tryOpen()` 返回 false，第二次
  点击不触发 `showDialogFragment`，不产生第二个 Fragment 节点。
- 节点摘除后镜像把闸切到 EXITING，延时收束前 `tryOpen()` / `canOpen()` 均为 false；
  收束到 REMOVED 后才放行下一次打开。拒收窗口略宽于弹窗内动画（多一段摘除后的残余
  延时），方向偏保守：宁可晚放行，不可叠节点。
- 弹窗实例内 `submitted` 单点出口与内部 `exitGate` 仍照常工作，宿主闸是外层第二道闸，
  不替代实例内写库副作用防重。

### 3.3 宿主 Activity 重建（旋转 / 配置变更）

- 宿主闸字段随 Activity 重建复位到 REMOVED；被系统保留的 `HighlightNoteDialog` 恢复时
  `onFragmentResumed` 回调把闸同步回 OPEN，不会出现「Fragment 在场但闸放行」的叠节点窗口。
- 若系统连 Fragment 一并销毁，无回调触发，闸保持 REMOVED，不存在幽灵节点。
- 弹窗内部 `exitGate` / `exitingState` 不跨重建存活，属 B26 已披露边界（验收-B26:268），
  本单不扩大处理范围。
- 重建前挂起的收束 Runnable 随旧 Activity handler 消息清空，不回调新 Activity 的闸。

### 3.4 `isComposed` 误判的后果与不变量

- 误判为 true（REMOVED 段仍组合）：离场收束后子树不摘，节点泄漏，留下不可见幽灵浮层。
- 误判为 false（EXITING 段提前摘树）：离场动画播到一半子树被摘除，动画截断、树提前拆。
- 新口径不变量：`retainedRequest` 只在 `onFinishedExit()`（即 `finishExit` 切 REMOVED
  的同一迁移）清空，不存在「phase 已 REMOVED 但负载非空」或反向的窗口；负载槽位不再
  参与 `isComposed` 判断，两条路径不会再漂移。

### 3.5 对既有控制器与单测的二阶影响

- 两个薄控制器透传 `gate.isComposed / canOpen / visible`，基类收口后取值矩阵不变，
  B29 既有 `SheetExitControllerTest`、`SourceSheetExitControllerTest` 断言不破。
- `ReaderSheetState.open` 仍走 `exitGate.open(request)` + B20 守卫判重；新增 `tryOpen()`
  只服务宿主入口，不改 B20 快照比对与异字拒收语义。
- 基类 `beginExit / finishExit` 标 `open`，子类可按需要 overload（B21 带请求重载保留
  阶段守卫）。
