# 落文 · 规矩总纲（做任务前必读）

> 唯一重读入口。上下文被压缩后，先读本文件再动手。
> 翻轨迹铁律：要同时理解「用户说过的话」+「我(agent)说过、用户未否决的话」——二者都是约定，未否决=默认接受。

## 一、目的 vs 手段（最高优先级）
- 灵魂闭环只是冒烟用例，**验收是手段、不是目的**：打开书→竖排读→点字出气泡→点「晋」命中春秋晋国→点「鲁隐公元年」出前722干支辛酉。
- 真正目的是：把整套规格做对、做好看、好用、所有边界兜底，不降级、不砍功能、不允许空白态或崩溃。
- **铁律 #34（做任务前先 Read 规矩总纲）与 #31（逐条调用全部铁律）为最高优先级**：任何任务/派单/验收/交付，第一步先执行这两条，再谈其余铁律。

## 二、四条硬规则（读对话/派单/验收的根本纪律）
1. 锚点强制可回源：每条结论必须能回到原文行号/切片/文件。
2. 规格、契约、验收三类**禁止压缩**，只压缩已完结过程。
3. 子 AI 禁止自行摘要——只读小段原文照做，靠索引+完整覆盖核对。
4. 三层分离：
   - 导航层：可有损，只答"在哪"。
   - 执行层：无损，原文切片逐字。
   - 验收层：逐字对照原文全文。

## 三、铁律（来自用户长期偏好）
> 每条规则都必须带「简短注释」（为什么/适用条件），防上下文压缩后丢失推理依据。
> 每次派单/验收/交付前，必须逐条调用全部铁律自检（本环节是否满足/已覆盖），未覆盖即补齐；只写不执行=未遵守。
1. 落文只保留 Legado 排版引擎，界面全部原生自绘重写。（改动边界：只动 UI，不碰排版引擎）
2. 编译通过只代表语法过，不代表功能可用，未验证必须明说未验证。（防"假绿"）
3. 交付前必须自我模拟跑一遍关键路径并逐项自查，再报完成。（防空口交付）
4. 每个项目先做单项自检，再做一次整体自检，才可交付。（两层自检缺一不可）
5. 目标真机是荣耀 WIN，12GB 内存，安卓手机（用户语境"win"指手机，与电脑无关）。（性能与平台口径）
6. 规格未覆盖的边界情况自行判断并兜底，不允许空白态或崩溃，不降级不砍功能。（兜底是硬要求）
7. 每完成一个模块必须自测验收，跑不通不交付。（模块级验收）
8. 规格超上下文时分段读、记结论继续读，不许跳读。（长规格必须全读完）
9. 改代码要推演二阶三阶影响，不只考虑改动直接效果。（看连锁反应）
10. 做方案先假设自己方案错误，找反例边界重新评估再定。（反证法定案）
11. 改动后必须先 grep 确认代码真的写入，未生效不许编译更不许报完成。（落盘验证）
12. 分析代码库历史和遗留包袱，识别可安全移除的历史代码。（清历史包袱）
13. 以新人工程师视角评估代码认知成本，简化命名与职责不清的代码。（降低接手成本）
14. 复盘 Bug 返工回滚的共同根因，沉淀为项目规则或自动化。（防同因复发）
15. 质量优先，交付前自检，不好全部返工；已有实现绝不复用只做参考。（质量>速度，防带病续命）
16. 每个模块配可跑的单测和 bench，性能指标跑过才算数，只过编译没真机验证的显式写进交付说明。（性能必须可度量）
17. 固定签名 keystore 收口，签名不一致会导致覆盖安装失败。（覆盖安装前提）
18. 并发默认放开（无固定上限），仅在沙箱真正高负载时才临时降低、负载回落即回升；质量优先、时间放宽。（负载来自编译非代理数，见铁律30）
19. 用户原文规格必须逐字保留、不蒸馏不改写；子 AI 读全靠索引+完整覆盖核对，不靠压缩浓缩。（原文无损）
20. 派单任务尽量划小范围，每个子 AI 只读小段原文照做，减少其自行编造或摘要。（小切片防编造）
21. 每次出 APK 必须 JDK17 先 clean 再 assemble 全量重编，禁止增量编译。（见下方「已定决策」：工程 toolchain 钉 21 已让位于实际，改 JDK21）
22. 排查问题用穷举法：列全部嫌疑点后一次性全改，不逐点试。（穷举防反复试错）
23. 用户提出修改意见时先读相关源代码再动手，不许凭感觉改。（先读源码再改）
24. 改动前先对比旧版 APK 借鉴好用实现，再自己重新研究重写。（先借鉴再重写）
25. 新逻辑先接好再删旧，不留旧格式兼容层，及时清理废旧代码。（接新再删旧）
26. 每次交付 APK 前必须把整个 APK 完整模拟跑一遍再报完成。（整包模拟）
27. **验收 AI 独立把关**：每模块/派单完工后交独立验收 AI（非写码的项目 AI）逐字对照规格原文+验收标准判质量；判质量低 → 换掉项目 AI、废弃其代码、重新派单重做，做完再交验收 AI，直到通过；项目 AI 禁止自评代替验收 AI。（独立验收防自评放水）
28. **翻轨迹双向理解**：读对话历史要同时理解用户的话 + 我(agent)说过、用户未否决的话，二者都算约定。（未否决=默认接受）
29. **指令冲突以后面与实际为准**：指令前后冲突时，以后面（最新）的指令、以及实际（工程现实/史实）为准；例：JDK 按工程实际 21、干支按史实己未、距今按后说 1950。（后令+事实优先）
30. **沙箱内禁止一切编译（gradle + kotlinc）**：负载来自子 AI 在沙箱跑编译（吃 CPU/内存），不是代理数量；编译+单测+bench 的真跑全部走云端 CI；子 AI 只写代码+测试代码+grep 静态确认。（编译离沙箱，并发才可放开）
31. 【最高优先级】**工作时调用全部铁律**：每次派单/验收/交付前，逐条过一遍全部铁律，确认本环节满足或已覆盖，未覆盖即补齐；禁止只写规则不执行。（规则不落地=空文）
32. **跨模块问题交接**：子AI发现不属于自己文件域的问题，必须记录（问题/归属模块/发现者/证据）并由总控交接给对应子AI；不属当前任何切片的问题进待派清单，不漏交不甩锅。（跨域问题闭环）
33. **写完一个就验收一个、编译一个，不攒批**：子AI写完 → 独立验收AI静态验收 → 通过才 push 仓库 → 云端编译 → 编译后再验收；两道验收都过才算完成；不干等编译，写完先存本地/仓库、边写边推边编。（单模块流水线闭环，编译仍离沙箱）
34. 【最高优先级】**做任务前第一步先 Read 铁律全文 + 总控必读**（用户 2026-11-23 改定）：任何一件事（派单 / 提交 / 推送 / 判 CI / 改台账 / 改状态页 / 回用户）开工第一步固定是两读——
   ① Read `docs/落文-规矩总纲.md`（铁律 1–77 全文，不是摘要）；
   ② Read `docs/机制-总控必读.md`（职责边界 / 槽位 / 派单 / 提交链 / CI 判读 / 门禁 / 落盘）。
   两读做完才允许调第一个工具。长会话里每换一个动作类别（写码 → 判 CI → 收尾落盘）都重读一次对应节。
   > 为什么：这是抗上下文丢失的唯一锚点，且本轮实证「读了没当锚点」＝没读——派单不引 §、备案当装饰、流水漏追加，全是少读一步造成的。适用：总控每一轮的第一动作；子代理读各自机制文件（三份不混用）。
35. **数据字段 schema 先行、示例数字是下限非上限**：先抽每类数据的字段 schema，再按规则拉满全覆盖；规格里的示例数字（8/120/2000）只是举例和下限，不因示例截断。（数字是模式不是配额）

38. **细节唯一事实源落磁盘，不靠主控口述**：子代理开工前从磁盘重读契约与原文；进度用 git status + 交接文档 + 任务板三重兜底，防主控上下文压缩丢细节。（磁盘是事实源）
39. **手势分区：点中字永远优先于翻页**：边缘点击先判是否命中字，命中字先出气泡，点空白才翻页；正文区点/长按归 Compose、滑动翻页归 View、底栏 60dp 归 Compose 全吃。（字优先于翻页）
40. **3D 资源离开可见区必须 dispose，背景粒子静置 3 秒暂停**：离开即销毁 geometry/material/texture；阅读背景粒子静置 3 秒后暂停动画循环，滚动恢复，不白烧 GPU。（省 GPU 不白烧）
41. **落盘原文/资产须逐字符比对自检**：与源文件逐字符核对一致、UTF-8 无乱码无截断；原文保留磁盘 + 云链接双重保险。（落盘无损双备份）
42. **长任务等待期间代理不得自行关闭**：跨小时等待期持续盯进度、不空转不自停，直至交付。（长等不停机）
43. **时间紧张时落地优先级**：先保证代码全部落地 + 编译通过 + APK 产出，细节打磨放最后；交付物须附各模块验收清单（标明自测通过 / 仅过编译未验证）。（先落地后打磨）
44. **契约/索引随进展实时更新，不攒批**：任一模块接口变更或验收状态变化，总控即时回写 `docs/落文-模块契约索引.md`（bump 版本号、只通知下游重读受影响条目），不等到交付末尾批量补。（索引随动防漂移）
45. **火力全开、满编 5 个子代理、固定留 1 个验收槽、代码槽永不空、写完即送审（随时提效）**：满编 5 个并发里固定留 1 个槽专职独立静态验收，其余 4 个槽给写码代理；**4 个代码槽任何时候都不许空**——一个写码代理完成就立即补派下一个写码模块，绝不让写码槽空着等验收或等编译；每个写码/验收子代理一律一次性使用、完成即废弃、绝不复用，下一模块或下一次验收一律派全新子代理；写码代理一完成就立即送验收槽审查（不攒批、不等批），独立验收代理每次换新、加强审查防止惯性盲区，同时立即补派下一个写码模块保持满编；验收报错就派新的子代理重写修复（不退回原代理、不让 organizer 自己下场修 bug），再送验收；任何等待空档都用换岗/补派填满，只有确无可独立并行的任务时才允许少于满编。质量优先、并发不缩水。（满并行 + 固定验收槽 + 代码槽永不空 + 写→验流水线，不停摆）
46. **金字塔式分层组装验收（每10小模块→1大组装验收，每2大组装→1更大组装，逐级向上）**：单个写码代理写完一个模块送独立验收（铁律45）的同时，按「10 个小模块 = 1 个组装单元」聚合成一次**大组装编译验收**——由云端 CI 把该组装单元连同其上已通过模块一起 clean 编译 + 跑测试，专验模块间接口咬合，不只验单模块；每 2 个大组装验收再聚合成 1 次**更大组装编译验收**，依此类推逐级向上，直到整仓全量组装验收。契约索引必须同步登记「模块 → 所属组装单元 → 所属更大组装」的层级归属，每次验收状态变化实时回写（呼应铁律44）。任何一级组装验收报错，退回该级对应模块、派新子代理重写修复（铁律45），不降级不砍功能、不允许空白态。（分层组装防「单模块各自绿、拼起来接口红」的咬合盲区）
47. **push 不阻塞于验收：验收未过也先推云端，只做区分标记，有空位即调下重写**：代码写完 commit 即 push 存档，不因「验收还没过」就藏着不推；验收 PASS/FAIL 只做区分标记（PASS=可用、FAIL=待重写），标记随 commit 记录；FAIL 的模块一旦写码槽有空位就立即调新的子代理重写（铁律45），不留「本地藏着没推」的空窗，保证云端始终有全量代码、CI 复验始终能跑到最新提交。（推与验解耦、区分标记、FAIL 即调下重写）
48. **写码/验收代理一律一次性，用完即弃，禁止唤醒复用**：写码代理交付即废弃，不复用同一代理续跑；验收有误 → 派全新代理重写；验收无误 → 派全新代理写下一个模块。（用户原话，16:00 后 L1597 / L1630："一个代码写完之后那写那个代码的子代理就完全废弃不要了，换新的来，如果验收有误就让新的重写，无误就让新的子代理写下一个代码，验收完成的代码就推上云"）。为什么：复用会带惯性盲区与自评放水的温床；适用：所有写码/验收/抢救类子代理。
    **最严口径（用户 21:25 原话「最严口径」，对 48 的收口，优先于任何"顺手/高效"理由）**：
    - 一次派单 = 一条命，**任何已派出的子代理不许二次派活**——即使它还在跑、即使追加的只是"顺带修几条编译错"，也算违规；
    - 结合铁律 54 带来的自然诱惑（想让旧代理继续干）必须抵抗：**organizer 对本会话子代理的 `send_message` 目标数恒等于 0**（唯一例外是叫停/终止，那不是派活）；
    - 需要补活 → 先终止在飞代理（避免双写），再派全新代理，并把"上一代理留下的未提交半成品"作为事实交底给新代理（产物可继承、代理不可继承）；
    - 自检方式：定期从自己的轨迹里数 `send_message` 目标，非 0 即违规、当场纠正并登记。
49. **调度层禁止休眠与空转**：只要有子代理在跑，就必须轮询其进度并推进编排，不许以"等结果""等编译"为由停摆；无子代理在跑时也必须先把可并行的下一包派出去。（用户原话 L1654："你不能休眠，你要对子代理工作进度进行轮询"）。为什么：停摆等于让代码槽空转；适用：调度层每一次等待间隙。
50. **代码槽永不空 + 验收未过也先推 + 区分标记**：写码槽任何时候不许空着；完成一个立刻补派下一个；验收未通过的代码也先 push 云端存档、只在标记上区分 PASS/FAIL，一旦有空位立即调新代理重写。（用户原话 L1701："不能空代码槽，这样，验收不通过的也先推上去只是要做区分，有空位了就及时调下来重写"）。为什么：云端要始终能跑到最新全量代码；适用：每轮派单与提交。
51. **索引与规矩随新口令即时重整；索引契约必须写入"美化与感官引导"**：用户每提一条新规矩/新口径，当场更新规矩总纲与契约索引，不攒批；契约索引必须持续携带美学与感官引导条款，使每个子 AI 不看指令也按"好看"的标准做。（用户原话 L1722"索引和规则也要重新整理" + L1868"索引契约也要更新出美化与感官的引导，让每个子ai都按好看的做"）。为什么：索引漂移会导致下一代代理照着错的干；适用：每次用户新指令后。

## 八、调度八律（铁律 67–74；用户 2026-11-23 定，全部来自本轮真实故障）

> 一句话：把记忆、判断、交付从 Agent 身上剥离，落到文件 / CI / 脚本上；Agent 只做执行，任何时刻可被替换。

### 铁律 67 调度去状态化
状态实时落盘到 `docs/落文-模块契约索引.md` + `docs/当前状态.md`，调度器可随时被杀、随时换人。
> 为什么：本轮发生过上下文爆掉导致加载失败——记忆留在 Agent 脑子里等于随时归零。适用：每次 commit 后必须更新续命页，不许攒到最后。

### 铁律 68 进度只报三布尔
只报：HEAD commit / CI 绿不绿 / 有没有 APK。**禁止报百分比**。
> 为什么：报 55% 时实际 8 连红且没有任何包——百分比是自我安慰，三布尔是可核验事实。适用：对用户的一切进度汇报。

### 铁律 69 P0 单列通道（红灯优先）
CI 红或没包时，**停发新功能派单**，全队先修红；修复最小改动**立刻 push**，CI 本身就是验收。
> 为什么：修一行 30 分钟能出包的事，曾拖了十几个小时。适用：任何时刻 CI 非绿，功能单一律排队；已在飞的允许收尾，不许再开新功能单。

### 铁律 70 验收与执行彻底分离
验收不排队、不串行等待；判低即换人重做，**禁止自评代验收**。
> 为什么：自评+两道验收串行曾把出包拖死。适用：每个包提交后立即起独立验收单，验收与下一包开发并行。

### 铁律 71 子任务无状态
用完即弃、带产物、**超时熔断**（超 40 分钟无产物或无报告即判废 kill）。
> 为什么：字体代理卡死空转直到人工发现；DetailSheet 代理 47 分钟零改动零报告。适用：派单时写死交付物，超时即 kill 重派。

### 铁律 72 流水逐字只增不改
`docs/落文-对话流水-2026-11-23.md` 只追加；抢救上下文按时间锚抽原文，**禁止转述**。
> 为什么：重启后只能靠 git 重建过程。适用：每轮收尾追加一段，不许改写历史段落。

### 铁律 73 出包闸门脚本化
CI 绿 → 取 artifact → 校验 → 交付，固定由 `data_scripts/release.sh` 执行，不靠任何人记得。
> 为什么：交付动作依赖记忆就容易漏（曾漏 aapt 断言、漏 versionCode bump）。适用：每次交付 APK。
