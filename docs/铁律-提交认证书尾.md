# 铁律 · 提交认证书尾（F-111）

## 一、由来（两条纪律打架，K-20 实证）
1. 纪律 A「代码槽永不空、验收未过也先 push 云端只做区分标记」：未验收的产物也要上云留槽，不能压在本地。
2. 纪律 B「攒批一次推、CI 在飞不推、等终态」：一次 push 会触发主 run + 截图 run 两个 run，CI 中再 push 会把在飞 run 打成 cancelled（本棒 3 分钟连推 3 次打掉两对，记 K-20 / 事故清单）。
3. 两条纪律过去都靠人记：记成 A 就连环推红，记成 B 就空槽停工。冲突的根因是——**"这个 commit 到底验没验"没有写在 commit 本身里**，只能翻台账、翻回执、靠记忆对。

## 二、为什么要有 trailer
- 让"推了什么、验没验"能被 `git log` 机械查：脚本扫 commit message 末尾的认证书尾即可分流，不靠人记、不靠翻对话。
- 验收证据随 commit 走：以后任何一棒 `git log --format=%B` 就能看出每条提交是独立验收通过、还是未验收保槽、还是纯文档，回源不依赖台账是否同步。
- 与 F-108（写码/验收分人）衔接：`Verified-by` 必须是独立验收代理的 id，写码代理自评无效。

## 三、trailer 规范（每个进 main 的 commit 有且只有一行）
commit message 末尾空一行后，写且仅写一行下列认证书尾之一：

| trailer | 含义 | 适用 |
| --- | --- | --- |
| `Verified-by: <验收代理id>` | 独立验收代理逐字对照锚点卡判通过的证据；id 须能回查到验收报告 | 代码/接线/实现类提交，验收已过 |
| `Wip: <未验收原因>` | 未过验收、但按纪律 A 仍要保槽上云；原因一句话写清缺什么验收 | 未验收提交，走 wip 分支承载 |
| `Docs-only: <说明>` | 纯文档 / 规则 / 台账 / 流水单，无代码产物，免验收代理 | 文档与规则类提交 |

判据细则：
- **有且只有一行**：一个 commit 不得同时出现两种及以上 trailer；出现多行判不合规。
- trailer 必须在 message 末尾（git trailer 习惯：正文与 trailer 之间空一行）；写在标题行或正文中间不算数。
- `Verified-by` 不许自评：写码代理给自己签的 `Verified-by` 无效，按缺 trailer 处理。
- 缺 trailer 一律视为不合规：main 不推、wip 也不推，打印 commit 短号让调度层补 trailer 后再走入口。

## 四、push 分流判据（`data_scripts/pre-push.sh`，唯一 push 入口）
取 `git log origin/main..HEAD` 每条 commit message 逐条认证书尾：
1. **全部带 `Verified-by:` / `Docs-only:`** → 推 `main`（仍受已有 CI 窗口守卫：在飞 run 时暂缓）。
2. **存在任何 `Wip:`、且无不合规项** → 不推 main，改推 `origin HEAD:wip/<YYYYMMDD-HHMM>`；main 保持绿，未验证提交由 wip 分支承载；stdout 打印分流原因与分支名。
3. **存在缺 trailer 或多行/自评 `Verified-by:`** → 两种推法都拒绝，打印该 commit 短号与建议补的 trailer，交调度层补齐。

## 五、机械守卫
- 门禁 ㊴ `data_scripts/check-commit-trailer.py`：扫 `git log origin/main..HEAD`（远端 ref 不可解析时回退最近 5 条，回退窗口只告警不拦历史）；任何 commit 缺 `Verified-by:` / `Wip:` / `Docs-only:` → FAIL，打印短号与建议 trailer。
- 分流执行在 `data_scripts/pre-push.sh`：门禁 ㊴ 与 CI 窗口守卫都过之后，再按第四节三分支落推。

## 六、二阶 / 三阶自查
1. **wip 堆积会不会让 main 落后太多，导致"HEAD 不是最新"误判？**
   会。wip 分支长期不回并，本地 HEAD 与 origin/main 分叉越拉越长，调度层容易把 wip HEAD 当成 main 最新。
   防法：pre-push 分流时打印当前 main 与 wip 的分叉提示（领先 main 的提交数），并把 wip 分支名、短号、主题登记进 `docs/台账-wip分支.md`；验收通过后必须合并回 main 再销账；判"HEAD 是否最新"一律以 `origin/main` 为准，不以 wip HEAD 为准。
2. **`cancel-in-progress: true` 会不会让红反馈变慢？取舍结论。**
   不会变慢，反而更快：true 时同一 ref 后推的 commit 自动取消排队/在跑的旧 run，runner 不堆积，最新一轮红反馈最先出。代价是会打断在飞验证（K-20 实证 push 会 cancelled 在飞 run）——这个代价由 push 侧兜底：pre-push.sh 的 CI 窗口守卫 + trailer 分流保证不在飞时才推、未验证不进 main；workflow 内 concurrency 保持 true，不为"保在飞"而关闭取消。

## 七、不适用
- 纯文档 / 规则 / 台账 / 流水改动：用 `Docs-only:` 代替验收 trailer，不派验收代理。
- 紧急回滚：可先推 main 再补 trailer 与事故登记（沿用 F-109 豁免口），事后必须回填认证书尾。
