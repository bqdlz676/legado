# 验收单模板（验收机制优化，2026-11-26）

## 为什么要模板化

105 份验收报告实测：PASS 20 份、有条件通过 23 份、FAIL 18 份，52 份非 PASS 报告里散着 872 处余项标记（N/D/R 编号）。余项之所以越滚越多，是因为每张验收单的判据口径现写现编，写码方与验收方对"什么叫过了"理解不同。模板把通用部分固化，派单只写差异。

## 一、机器可读头（每份验收报告开头四行，固定格式）

```
被验 commit：<sha>（区间 <from>..<to>）
总结论：PASS | 有条件通过 | FAIL
判据：通过 <n>/<m>
新缺陷：<n> 条（编号 D1..）
```

要求：结论只许这三个枚举值，禁"基本可用""大致通过"这类模糊词。余项必须带编号（N1、D1、R1），不许写成一段话——编号才能被统计与追踪。

## 二、验收单开工固定动作（写进派单，不必每次重写）

1. 先跑四条机检，结论直接贴进报告：`check-report-fields.py`（本轮报告字段）、`cross-module-guard.py`（编译面）、`debt-ratchet.py`（债务）、`check-combo-coverage.py`（组合矩阵，若涉组装）。
2. 读来源判据原文与写码报告，逐条对照；对照表用「原文判据 → 现状证据 `文件:行`」两列。
3. 做改坏推演：至少挑 4~5 条断言，写出"把实现改坏到哪里、哪条会红"。
4. 独立复核写码方自述的分类结论，不许照抄。

## 三、通用硬判据（每个验收单都适用，派单不再重复写）

H1 只读：不许改 `app/**`、既有 docs、脚本；不许 git 写操作。
H2 回源：每条结论必须有 `文件:行` 或命令输出；没有回源的结论视为未判。
H3 不越级：低层未过不许拿高层结论放行（见 F-92 R4）。
H4 不替写码方论证：发现测试空转，判 L1 不合格并打回，不自己补论证。
H5 分类复核：写码方的"共有 N 种、其中 M 种…"这类结论必须数一遍。
H6 夹带核对：`git show --stat <被验 sha>` 确认只碰声明范围。

## 四、派单只需写四样差异

来源（哪个修复单/哪份判据原文）、被验 commit 区间、本单专属判据（3~8 条）、禁区（哪些文件有其它在飞单）。

## 五、结论回填（机器）

验收报告落盘后由 `land.py --verified-by <报告>` 回填队列，未带该参数修单一律标"未验·待验收"，防止把写码完成当成验收完成。
统计口：`acceptance-stats.py` 输出各域 PASS/有条件/FAIL 分布与余项密度，用来找薄弱域。
