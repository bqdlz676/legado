# 修复-g66 改动面路径口径（--changed 空转）

## 一、缺陷原文与审计方复现数据

- 被验件：`data_scripts/check-member-override.py`（g66 同签名实现成员缺 override 静态判据闸，入库提交 e42bae7，非工作树新件）。

- 本单逐字读码复核（不凭行号猜）：建模侧 `build_model` 旧码用 `rel = os.path.relpath(f, root)`（旧 `data_scripts/check-member-override.py:561`），`root` 来自 `collect_roots()` 的 `ROOT/app/src`、`ROOT/screenshot/src`，所以 `Decl.file` 存的是源码根相对名（形如 `main/java/io/legado/.../X.kt`）；改动面侧 `git_kt_diff()`（`data_scripts/check-member-override.py:737`）返回仓内相对名（形如 `app/src/main/java/io/legado/.../X.kt`）；主判定 `evaluate` 旧过滤点直接做 `d.file not in judge_files` 等值比对（旧 `:711` 附近），两侧无归一，dirty 树里改动的 .kt 直配 0 条，改动面判定空转。
- 改前镜像复现命令：在仓外镜像仓提交非改动样本对后，未跟踪两个改动样本文件，执行 `python3 data_scripts/check-member-override.py --changed`。
- 改前镜像复现末行（rc=0，应红未红）：`MEMBER-OVERRIDE: PASS（改动面 0 个实现声明；缺 override 0；已配对 override 0；放行 ）`。
- 改前镜像全仓对照末行（同一份代码 audit 口径能判红）：`MEMBER-OVERRIDE AUDIT: 全仓清单（接口/抽象类 131 个 / 实现声明 230 个 / 候选缺 override 4 处 / 已配对 override 516 处；存量只登记不判红）`，INFO 行路径为源码根相对名 `main/java/a/g66probe/ProbeBad.kt:4` 形态。

## 二、根因

- 路径命名空间错位：模型侧按各自源码根取相对名，改动面侧按仓根取相对名，两套命名空间在过滤点做等值比对，必然全部落空；`impl_count` 计 0，`fails` 计 0，`--changed` 空转。
- 放行计数器缺口一（SKIP:COMPANION）：旧码伴生对象分支配平后整段丢弃，块内 fun/val/var 成员没有登记进 `decl.members`，`COMPANION` 计数器永不递增。
- 放行计数器缺口二（SKIP:TOPLEVEL）：类/接口体外的顶层 fun/val/var 不进入任何 `Decl` 体，旧模型没有文件级收集位，`TOPLEVEL` 计数器永不递增。两条缺口只影响可审计性，放行行为本身正确。

## 三、修法选择与被拒的另一条路

- 采用方案：模型侧 `Decl.file` 统一存仓内相对根名（`os.path.relpath(f, ROOT)`，`data_scripts/check-member-override.py:617`），与 `git_kt_diff()` 返回的改动面文件名同一命名空间；过滤点保持等值匹配。
- 被拒方案（judge 侧剥 `app/src/`、`screenshot/src/` 前缀，归一到源码根相对名）及拒绝理由：
  1. 路径命名空间的生产者是模型。归一放在消费侧过滤器后，判红/INFO 输出行仍带源码根相对名；两个源码根（`app/src`、`screenshot/src`）下都有 `main/java/...` 段，打印路径无法唯一定位，也与 g65 消费方反查闸的输出口径、`git status` 口径不一致。
  2. 消费侧要重复掌握源码根表并按根剥前缀；将来新增第三个源码根，就要再改一遍剥前缀表；两个根共享同名前缀段时，剥离归属还会产生歧义。模型侧一次取 `ROOT` 相对名，没有逐根剥离逻辑，后续加根不动过滤点。
  3. 模型侧归一后，等值匹配不引入子串包含或前缀放宽；judge 集本身已过滤 `.kt` 且要求文件真实存在，模型侧只收 `SOURCE_ROOTS` 下的 `.kt`，不会把 `.java` 或非源码目录卷进改动面。

## 七、主构造参数内 override 属性建模判断

- 结论：本单不纳入主构造参数属性建模，列为待裁后续项。
- 仓内实例：`app/src/main/java/io/legado/app/lib/dialogs/AndroidAlertBuilder.kt:13` `internal class AndroidAlertBuilder(override val ctx: Context) : AlertBuilder<AlertDialog>`，覆写 `app/src/main/java/io/legado/app/lib/dialogs/AlertBuilder.kt:17` 的 `val ctx: Context`；当前闸只扫类体一层成员，主构造参数位不建模。
- 不做的理由：
  1. 主构造参数是第二解析曲面：多行参数表、函数类型、嵌套括号、注解、vararg、默认值、解构声明都要处理，保守解析的误伤面大于本单收益。
  2. 基线四元数冻结 527；纳入构造参数位后，已配对计数必然上移，违反本单「四元数不变」口径。
  3. 仓内该唯一实例已带 `override`，没有活红漏判；缺口属覆盖度留痕，不挡当前 push。
  4. 后续迭代补这一位时，必须 prove 不误伤：全仓 `--audit` 候选缺 override 保持 0，且双向夹具（构造参数缺 override 判红 / 带 override 配对）齐全；与匿名对象体、具体类 open 成员两条旧缺口同批评估。

## 八、自查反例（改坏推演）

- 反例一：若走 judge 侧前缀剥离归一，新增源码根或共享前缀段会让剥离归属歧义，输出路径也无法唯一定位（理由见第三节）。
- 反例二：若 TOPLEVEL 统计只看花括号深度，无类体 data class 的主构造参数跨多行、没有类体花括号，会被误判成顶层声明；实测 `Book.kt` 一度误计 35 处、全仓 TOPLEVEL 虚高到 4370。补圆括号深度口径后，`Book.kt` 归 0，全仓 TOPLEVEL 回落 413。
- 反例三：若本单顺手把构造参数 val/var 纳入建模，解析面扩大且基线配对计数上移，违反四元数不变口径；故留待后续专项并带双向夹具验收。
- 反例四：若路径归一改成子串包含匹配，非改动文件可能被卷进改动面造成反向误报；实现保持仓内相对名等值匹配，不做包含判定。
- 反例五：若为过样本给缺 override 成员加白名单，判据被放宽，真事故会漏；本单未加任何白名单，未放宽既有判据。
