# 断言范式（写码与验收共用）

## 为什么写这份

2026-11 的两轮验收返工里，返工原因几乎都不是业务逻辑写错，而是**断言没牙**：源码子串回证（`assertTrue(src.contains("foo"))`）改了实现也不红、缺调用记录桩、只测正向不测反向。验收方每次都要人工推演"改坏会不会红"，代价比写码还高。所以把有效断言归纳成四种范式，写码方派单时点名使用，验收方按范式核对。

适用范围：`app/src/test`、`screenshot/src/test`、`modules/**` 下的 JVM 单测。Compose/Paparazzi 快照只做视觉基线，不承担逻辑锁。

## 一、行为锁（首选，占比应 ≥60%）

构造输入 → 调到公开入口 → 断输出/状态。断言对象必须是**返回结构、状态流、可见元素**，不是源码文本。

要求：一条断言只锁一个行为；期望值从外部契约（规格/枚举/KDoc）推出来，不从实现抄回来。

反例：`assertEquals(3, list.size)` 当 list 由被测函数自己造时，等于抄实现。

## 二、结构锁（用于"注册表/分支全集"类）

对穷举型问题（动作注册表、状态机分支、槽位仲裁），锁**结构完整性**而不是某一跑法：
- 断言枚举全集条数与被测表条数相等；
- 断言每个非默认分支都有独立用例（以 mock 的调用记录反证"走到了这支"）；
- 断言"无 else 兜底"这类缺失会红：删掉 else 分支，用例必须失败。

这是替代"源码子串回证"的正确手段——源码回证只在**删除类/接口必须零引用**这类静态事实用，且必须标为兜底回证。

## 三、调用记录桩（替代"看源码判断短路"）

凡是"命中即早退 / 优先级仲裁 / 拦截链"逻辑，必须用桩记录每次调用的实参顺序，断言**调用序列**。只断最终结果时，早退和兜底产生的同一结果无法区分。

要求：桩记录 `callCount` + `recordedArgs`；正向用例断言"后位未被调用"，反向用例断言"前位未命中时后位确实被调用"。

## 四、反向可红自查（每张写单必须交）

报告末尾必须有「自查反例」节：列出至少两处"我把实现改坏到这里，哪条断言会红"的具体位置。没写这节的报告，验收方第一动作就是补推演，等于把成本转嫁。

已知踩过的坑：写码方自述"某功能模型无状态位"这类分类结论，只要没附反例，一律按可疑处理——回放栈就是这样把 6 种"有位未接"误报成"缺字段"的。

## 硬约束

- 禁用 `Thread.sleep` 等时序等待，统一 `withTimeout(5_000)` + 流式 `first`。
- 禁一个用例断 6 条无关事；用例名必须能读出被锁行为。
- 不许为过测放宽既有断言；要改就写明原因与等价证明。
- 断言数不是目的，**"改坏会红吗"**才是验收唯一的判据。
