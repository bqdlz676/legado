# 机制 · 守则回执规范（解决"写了不等于读了"）

> 一句话：**读守则这件事必须留下机器可验的痕迹**，否则"文件里有这条规则"只证明它存在过，不证明任何人照着它干活。
> 立此规范的直接诱因：2026-11-26 夜，三份必读早已成文（写码方该跑哪些门禁、验收方该验哪些陷阱都写在里面），我却在同一天连犯四类错；用户一句「为什么即使写了也不是实际就读了」把问题点破——**没有回执，就没有阅读**。

## 一、回执是什么（报告头固定四行块，逐字照抄规范格式）

```
守则回执：
- 指纹：docs/机制-子代理必读.md=<sha256 前 12 位>；docs/机制-总控必读.md=<sha256 前 12 位>（按角色取，机制/文档类加 docs/机制-文档子代理必读.md）
- 逐字引用 1：「<从该文件逐字抄的一整句>」（文件:行）
- 逐字引用 2：「…」（文件:行）
- 逐字引用 3：「…」（文件:行）
- 适用条款：本单实际照做了哪几条（编号或小节名，逐条写）
```

- 指纹取**当前磁盘版本**的 sha256 前 12 位。文件一改，旧指纹立刻失效 → 逼下一棒重读，不许吃老本。
- 三条引用必须是该文件里**真实存在的一整句**（机检会回源比对子串），且要覆盖本单实际约束（如写码单必须引到"≤600 行"与"禁 git"类条款）。
- 只有汇报、没有回执的报告，一律视为**未开工**：门禁判 FAIL，不推。

## 二、机检入口

```
python3 data_scripts/check-onboarding.py            # 查本轮新增/改动的报告
python3 data_scripts/check-onboarding.py --emit     # 打印当前指纹块，派单时直接贴进任务书
python3 data_scripts/check-onboarding.py --audit    # 扫历史报告，列出缺回执/缺三节的老账
```

已接入 `data_scripts/pre-push-check.sh`（3.7 步）。为什么接在这里：推送前是最后一道不会漏的关卡，事后补回执的成本比开工时贴四行高一整轮。

## 三、派单侧义务（总控）

1. 派单第一行固定写前置：`【开工前必读】先 Read <角色必读文件>，把 sha256 前 12 位与三条逐字引用填进报告头「守则回执」，否则整单不通过。`
2. 派单时把 `check-onboarding.py --emit` 的输出（当前指纹块）直接贴进任务书，减少代理自己查的成本。
3. 总控自己在每一轮收口报告里也要贴同一块（总控必读的指纹），别只要求别人。

## 四、为什么这样能"以后不再犯"

1. **从"应该读"变成"必须出示证据"**：没有回执 = 机检 FAIL = 不推，代理没有绕过路径。
2. **从"读过一次"变成"每次重读"**：指纹随文件变化失效，吃老本会被当场抓出来。
3. **从"行数很多的守则"变成"三条引用"**：代理必须真的定位到具体句子，泛泛"我读了"不算数。
4. **可追溯**：回执留在报告里，事故复盘时能回查"那一单到底读没读到关键条款"，而不是靠回忆。

## 五、边界（不制造新负担）

- 纯查证/只读类小单（预算 ≤10 次工具调用）可只贴指纹一行，免三条引用；写码与验收单一律四条齐全。
- 引用必须逐字，抄错一个字机检就红——这正好也是"逐字引用禁转述"铁律的机检化。
- 回执不许写"参考了""了解了"一类含糊词，机检按子串比对，含糊词过不了。
