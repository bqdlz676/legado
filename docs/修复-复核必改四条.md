## 第 1 条（最严重）：取包闸把 `skipped`/`neutral` 计入 GREEN

### 原缺陷证据

- 复核件 7 / G-1：`data_scripts/fetch-apk.py:46` 旧值 `GREEN = ('success', 'neutral', 'skipped')`；合成探测 Verify `completed / skipped` 时 `verify_gate` 判 **green**，被跳过、根本没执行的 Verify 也能放过取包闸，直送交付链，破「不接受任何不完善 APK」红线。
- 复核实测：`ff9c20c` / `49cc659` 两个 `cancelled` Verify 旧口径能拦（rc=1），唯独 `skipped` / `neutral` 漏网。

### 改法（为什么这么改、适用条件）

- `GREEN` 只留 `'success'`：只有 `status=completed 且 conclusion=success` 才算绿。适用条件：GitHub check run / workflow run 的 `conclusion` 字段全部走这张归类表。
- 新增 `NON_GREEN_REASON` 表，把 `skipped` / `neutral` / `cancelled` / `timed_out` / `action_required` / `stale` / `failure` / `startup_failure` 逐条翻成带原因的人话；非绿输出区分「没跑 / 取消 / 超时 / 失败」，不许笼统归 `red`。
- `verify_gate()`：已完成但非 `success` 的 run 一律进坏集合；返回状态取首个坏 run 的 conclusion，detail 逐条带原因；在跑 / 无 run 仍走 `running` / `none`。
- Package run 闸同口径：旧 `conclusion not in GREEN` 改为 `!= 'success'`，原因同样查表。
- `--selftest` 补两个夹具：E `completed/skipped` 必须非绿且原因含「未执行，禁止取包」；F `completed/neutral` 必须非绿且原因含 neutral。原 4 条结构夹具不动，末行由 `PASS 4/4` 改 `PASS 6/6`。

### 反例推演：success 但 artifact 未生成，会不会被重新放过？

不会。绿闸只放行「进入取包流程」，artifact 存在性在下载前、下载后、解压后分四层二次确认，任一层缺失即非 0 退出：

1. Package run 必须查得到；查不到 → rc=1「未找到 Package Debug APK run」。
2. Package run 必须 `status=completed` 且 `conclusion=success`；未结束 / 非 success → rc=1。
3. artifacts 列表为空 → rc=1「Package run 无 artifacts（构建未上传产物）」；列表里无 `debug` 变体 → rc=1。
4. 下载后 zip 为 0 字节 / HTTP 非 200 / 404 过期 → InfraError rc=2；解压后 `validate_extracted` 再判 0 个 apk（`NO_APK` rc=1）、多于 1 个变体（`MULTI_APK` rc=1），单包再查 Manifest / `resources.arsc` / `classes*.dex` / v1 签名三件。

即「Verify success」只过第一道闸，包本体不存在到不了 `RESULT=PASS`。残留边界：v2/v3 签名在 Signing Block、zip 目录不可见，无 apksigner 环境不可判定，脚本以 NOTE 行声明，不冒充已验。

## 第 2 条：种子 `CI=unknown` 不传导 + 三件自测漏进种子

### 原缺陷证据

- 复核件 8 / A-1：`data_scripts/seed-check.sh` 内嵌 python 任何异常（凭据缺 / 网络断 / API 错）都 `print('unknown')`；旧终判只看 `FAIL` / `MISS`，`unknown` 不入任一计数，种子可在 CI 状态不可知时仍报 `SEED: READY`，两布尔的 CI 腿是空的。
- 复核 H-1 / H-2 / H-3：`scan-blocking-hazards.py --selftest`、`fetch-apk.py --selftest` 未进种子；`check-design-tokens.py` 只跑 verify 未跑 `--selftest`（verify 绿不能证明负样本能判红）。

- 补三行 `need`（三件均已自带 `--selftest`，逐一核实过入口存在，未把无自测门禁塞进种子）：

  - `scan-blocking-hazards.py --selftest`。
  - `fetch-apk.py --selftest`。

### 反例推演：收口单本身没人写（历史欠账），`closing_report_check` 会不会又悬空？

会有残余风险，但本单做了三层兜底，不把补偿单压在「记得写收口单」上：

1. **双渠道互备**：挂 `closing_report_check` 的 audit 项绝大多数同时挂 `full_gate_round`——每轮收口跑全量 `bash data_scripts/rule-gate.sh`（不带 `--blocking-only`），audit 项照常出结论，不依赖人工写收口单这一动作。
2. **渠道背后是机器闸，不是人工勾选**：`closing_report_check` 的证据是 `check-evidence.py` / `check-unpushed-reports.py` / `check-problem-finding.py` 三道在册脚本；报告不落盘、缺 E1/E2/E3 证据、缺「新发现问题」节，由 ⑭ / ㊽ / 55 阻断在提交前，不需要有人事后想起来核对。
3. **校验器在岗**：`--check-compensation` 进种子 `need`，渠道证据文件被删 / 补偿引用未注册键 / blocking 误带补偿，下一次种子自检即红；渠道字典本身被掏空也会被顶层字典非空校验抓住。

如实记录的残留边界：若整轮既不开收口单、也不跑全量 gate，audit 项仍是流程纪律盲区；这一点写进了 `full_gate_round` 渠道的 `description` 触发时机，不属于本单能机械消灭的范围。另外 `reason` 字段里历史降级理由仍有「夜间」字样（如 g03/g13/g41 等），那是「为何不拦 push」的理由描述，不是补偿渠道引用；本单按边界未改写 reason 文案，补偿字段已全部收敛在册。
