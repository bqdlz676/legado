## 1. 落点定位（grep 证据）

### 1.1 任务书假设与实际落点

任务书列了四个候选域：词典规则 / 替换规则 / 自动任务 / 文件。改前全量 grep 与旧版历史比对结论：

- 仓内**不存在** `ui/tools/` 目录；四域实际落点为：
  - 词典规则：`ui/dict/rule/`（`DictRuleScreen.kt` / `DictRuleListViewModel.kt` / `DictRuleModels.kt`）
  - 替换规则：`ui/replace/`（`ReplaceRuleScreen.kt` / `ReplaceRuleListViewModel.kt` / `ReplaceRuleModels.kt`）
  - 自动任务：`ui/autoTask/`（`AutoTaskScreen.kt` / `AutoTaskListViewModel.kt` / `AutoTaskModels.kt`）
  - 文件：`ui/file/`（`FileManageScreen.kt` 等）
- 旧版（`e012b36^`，重写前）全仓检索 `lastRunAt / lastRunTime / runTime`：**仅** `AutoTaskRule` 实体、其 DAO、模型层、调度策略与 `AutoTaskAdapter` 使用；词典 / 替换 / 文件三域的旧实体、旧 Adapter、旧 item 布局均无任何运行时间字段。
  - 旧实体字段核对：`DictRule`（name/urlRule/showRule/enabled/sortNumber）、`ReplaceRule`（id/name/group/pattern/replacement/scope…/timeoutMillisecond/order）均无运行时间。
  - 旧布局核对：`item_replace_rule.xml`、`item_dict_rule.xml`、`item_file.xml` 无 time/date/run 控件。

**结论：本单实际落点 = 自动任务列表行**；其余三域旧版本就没有「最近运行时间」列，本次不补造（理由见 §4）。

## 3. 时间来源：真实执行记录，不造假

### 3.1 记录写入链路（改前已存在，本次复核确认）

```
AutoTaskJobService.kt:47
  → AutoTaskRunner.runDueTasks(context, now)          // 调度到期任务
  → runTask(context, task, persist = true)
      ├─ 成功：AutoTask.updateRunState(id, finishedAt, resultText, null, log)   // Runner.kt:66
      └─ 失败：AutoTask.updateRunState(id, finishedAt, null, message, log)      // Runner.kt:82
         （空脚本等前置失败走同一 failure 分支，persist=true 时同样落 finishedAt）
  → AutoTask.kt:230-238 → AutoTaskRuleDao.updateRunState(...)                // DAO.kt:51-67
```

- `lastRunAt` 由执行完成时刻 `System.currentTimeMillis()` 写入 DB 字段，非 prefs 估算、非默认值；
- 成功与失败**都会**落记录（失败行的时间同样是真实最近一次执行时刻）；
- 调试运行 `AutoTaskDebugActivity.kt:120` 以 `persist = false` 调 `runTask`，**不写** `lastRunAt`——与旧版行为一致（调试是试跑，不计入正式执行记录），本次保持不改。

### 3.2 无记录态

- 实体默认 `lastRunAt = 0L`（`AutoTaskRule.kt:43-44`）；新建任务、在线导入的新任务均为 0；
- `clearRunLog`（`AutoTaskRuleDao.kt:40-49`）只清 `lastResult/lastError/lastLog`，**不清** `lastRunAt`——清日志后仍显示最近一次真实运行时间，与旧版语义一致；
- 0 / 负数 → 行内显示「未运行」，不回退到 1970-01-01 或空串。

## 4. 其余三域为何不加时间列（含反方假设复核）

| 域 | 是否存在离散「执行完成」事件 | 结论 |
|---|---|---|
| 替换规则 | 规则在正文渲染链路逐条匹配替换，是**每页渲染热路径**，无独立「一次运行」概念；旧实体无时间字段、旧列表行无时间列 | 不落记录。若每次替换都写 prefs/DB，将在阅读翻页路径上引入高频写库，属明确性能回退（见 §5.4）；旧产品亦无此列 |
| 词典规则 | 取词是按需单次查询（用户点词触发），旧实体无时间字段；新 UI 无「运行/测试」动作入口 | 不落记录、不显示 |
| 文件管理 | 目录浏览界面，无任务执行概念；列表里的文件修改时间是文件系统 mtime，不是「规则最近运行时间」，两回事 | 不混入本列 |

> 反方假设自查：是否应给替换/词典补一个「最近测试时间」？旧版编辑弹窗虽有预览（`ReplacePreview`），但预览不落库、不进列表；本单口径是补齐旧版被移除的列，不新增旧版没有的功能。若后续要做「最近测试时间」，应另立单子并先定热路径写入策略。

## 5. 格式与配色决策

### 5.1 绝对时间，不用相对时间

**选绝对时间**（`AppConst.dateFormat`，`yyyy/MM/dd HH:mm`），理由：

1. **移植对齐**：旧版行内就是 `AppConst.dateFormat.format(lastRunAt)`，本单是补齐被移除的列，口径保持一致；
2. **静态列表不失真**：列表由 Room Flow 驱动重组，不会随墙上时钟定时刷新；相对时间（「3 分钟前」）停留数分钟后即失真，绝对时间恒定准确；
3. **既有相对工具不适用**：`StringUtils.dateConvert(source, pattern)` 入参是**格式化后的字符串** + 格式串，需先 format 再 parse 回日期，往返有损且对 `HH:mm` 精度不友好；直接吃 Long 的既有工具就是 `AppConst.dateFormat`；
4. 任务书允许二选一，本单选绝对时间并在此说明。

### 5.2 配色

仅使用既有 token：副标题行 `ComponentTokens.textTertiary`（与改前同行副标题同一 token），未在 `ComponentTokens` / `ComponentPalette` 新增任何色值。

## 6. 二阶 / 三阶推演

### 6.1 备份 / 恢复

- **WebDAV 备份**：`help/storage/Backup.kt:306` 将整份 `AutoTaskRule` 列表序列化进 `autoTask.json`，`lastRunAt` 随实体一起备份（既有行为，本次未改）；恢复时 `Restore.kt:628-631` 整实体 upsert，时间戳随备份回流。二阶影响：换机恢复后展示的是备份时点的真实记录，不会凭空生成当前时间；三阶影响：若备份很旧，行内时间偏旧——属忠实还原，非缺陷。
- **分享 / 导出 JSON**：`AutoTask.exportJson`（`AutoTask.kt:132-144`）已剥离 `lastRunAt / lastResult / lastError / lastLog`，导出文件不含运行态；导入时 `prepareImportedAutoTasks`（`AutoTask.kt:251-273`）对已存在 id 保留本地记录，新 id 沿用导入实体（导出件中为 0）→ 新导入任务显示「未运行」。本次展示改动不改变上述契约。
- 未新增实体字段、未改 Room 表结构，无迁移脚本影响。

### 6.2 排序 / 过滤

- DAO 排序键为 `customOrder, name COLLATE NOCASE, id`（`AutoTaskRuleDao.kt:13,17`），`lastRunAt` 不参与排序；本次未加「按最近运行排序」入口，列表顺序与改前一致。
- 搜索过滤只匹配名称（`AutoTaskListViewModel.visibleRules()`），时间文案不参与匹配；副标题追加一段不影响过滤命中率。

### 6.3 性能

- 每行仅一次 `FastDateFormat.format(Long)`：`dateFormat` 是 `lazy` 单例，`FastDateFormat` 线程安全；`LazyColumn` 只对可见行求值，无新增 DB 查询、无新增 Flow 订阅。
- 记录写入仍只发生在任务执行完成时（调度路径），列表渲染不触发任何写库。
- 三阶：长列表（数百条）下格式化成本与一次字符串拼接同量级，无可观测卡顿风险；未做缓存（时间文案在重组时重算，避免快照过期）。

### 6.4 调度策略 / 并发

- `AutoTaskSchedulePolicy.kt:54` 用 `lastRunAt` 做首次运行宽限判定；本次只读取展示，不改写字段时序，调度语义不受影响。
- 展示层派生属性只读 `lastRunAt`，不跨线程写状态；VM 仍走 `conflate()` 的 Room Flow，重组粒度不变。

### 6.5 持久化契约 / 测试债

- `AutoTaskUi` 构造器签名未变（仅加派生属性），既有 `toEntity()` 回写链路不变；`AutoTaskImportContractTest` / `AutoTaskImportMergeTest` 等既有用例不受构造器变动影响。
- 新增纯函数无 Android 依赖，可在 JVM 单测直接覆盖；生产路径对 `AppConst.dateFormat` 的调用留在派生属性内，测试不触碰 AppConst 对象初始化。
