# 诊断：机制在转，功能没走（2026-11-26）

## 一、现象与实测

用 `python3 data_scripts/progress-meter.py 24` 直接量，不靠感觉：

- 近 24 小时提交 202 次：碰 `app/src/main` 的 51 次，碰 `app/src/test` 或 `screenshot` 的 24 次，`docs/` 116 次，`data_scripts/` 6 次，其它 5 次。
- 队列共 162 条，PENDING 6 条，其中 Q-124、Q-130、Q-134 三条**实际早已完成**（报告与代码都在），状态仍写 PENDING。

也就是说：一半以上的提交产出是报告与台账；而台账本身已经和事实脱节。机制在自我复制，功能推进被挤到次要位置。

## 二、根因（四条，都不是执行者的态度问题）

R1 KPI 错位：我把"门禁绿、报告齐、验收走完一轮"当成进度信号。于是每张单都本能地先满足报告/证据/锚点/交接，功能码排在最后。可量化的后果就是 docs 提交数压过 main。

R2 机制单占功能槽：并发上限 5，我这两天派了 Q-164（机制脚本）、Q-165（文档与 watchdog）、Q-169（缝合怪盘点）三张非功能单，等于把 3/5 的产能锁在机制上；同时 Q-152、Q-168、B4/B8/B10/B12/B13 五条判低返工长期 PENDING 无人认领。

R3 串行等验收：写单 → 等验收单（单次 10~22 分钟）→ 等结论 → 再派下一单。同域明明可以按文件切片并行，我却为了"怕撞文件"整域串行，实际吞吐等于 1.5 张单在跑。

R4 判低率高导致返工翻倍：近两天 16 份修复报告对应 19 份验收报告，其中十余份判"有条件通过"或 FAIL，直接生成返工单。根因集中在断言空转与"写码方自述分类不可信"——这既是质量问题，也是工期问题。

## 三、解决（已落地 / 立即执行）

F1 状态不再手写：队列与台账的状态改由事实派生。巡检脚本把「报告文件存在 + 代码已提交」的 RUNNING/PENDING 行车标为"疑似已完成待确认"，我只需确认一次，不再靠记忆改格子。已补 `progress-meter.py`；本轮已把 Q-124/Q-130/Q-134 三条陈旧行改正。

F2 机制单让槽：功能槽保底 4 张常满，机制/文档/盘点类最多占 1 槽。本轮已停发机制单，空出的槽立即给了 Q-152（搜索翻页收口，D1 阻断项）。

F3 同域切片并行：域内按文件边界切片（如 D16 四片、缝合怪按批），允许"A 片验收"与"B 片写码"同时在跑，冲突面用文件清单写进派单，不再整域串行。

F4 返工前置拦截：写码单交付前必须自带「自查反例」节（按 `docs/断言范式.md`），缺节不进验收槽。这一条直接砍掉"断言空转→判低→返工"的最大来源。

## 四、类似问题（同类，不同形状）

S1 报告长度通胀：同一件事被写成三份文档（修复、验收、台账）还不够，还要追加证据节。根因同上——把文档量当工作量。对策：报告只保留"判据→证据→结论"三块，追加证据一律进附录一行。

S2 门禁反复罚同一类格式错：⑤（一条单里出现两个缺陷号）踩过三次，⑭（报告缺结论标记）多次。人写格式必然漂移。对策：格式由脚本生成，人只写内容。

S3 积压老化无报警：五条判低返工挂了超过 24 小时只在门禁里以 INFO 出现，等于没提醒。对策：`progress-meter.py` 输出最老 PENDING 年龄，超过 6 小时必须"派或作废"，不许继续挂着。

## 五、杜绝（写进调度纪律，不增加门禁条目）

1. 每轮调度第一动作跑 `progress-meter.py`，只看三个数：main 提交数、PENDING 条数、最老 PENDING 年龄。
2. 连续两轮 main 提交为 0 → 停发一切机制/文档/盘点单，只准派功能单。
3. 机制单不计入功能槽，最多占 1 槽。
4. 队列状态以报告文件与提交事实为准，不靠记忆。
5. 派单模板固定"冲突面清单"，界内切片并行。

为什么不做成门禁条目：门禁已经 40+ 条，再加规则只会让机制继续膨胀——这正是本次事故的病理。所以这五条只落在调度纪律与仪表输出里。

## 六、串行验收的全部机制与拆解（2026-11-26 追加）

"串行验收"不是一条规则，是六条机制叠出来的结果。逐条列出并给出拆法，凡是拆不掉的都说明理由。

M1 调度习惯链（我的问题，不是铁律）：写单完成 → 等验收结论 → 才派下一张写单。后果是同域吞吐恒等于 1 张单。拆法：写单一交付就三连——提交、派验收、立刻从 PENDING 取下一张写单派出去；验收结论晚到不影响写码继续。

M2 一单一验收被误读：铁律要求的是"一个 W 只对应一张 V、必须换代理、不许自验"，从没要求 V 必须在 W 之后独占时间轴。拆法：W 与 V 一对一关系保留，"V 期间不许派新 W"这条自加的约束删掉。

M3 并发池混计：上限 5 把写单与验收单算在同一个池里，写单一完成槽子就被 V 占走。拆法：显式分工——功能槽 4（写码/修单）+ 验收槽 2（只读），总并发仍受 5 约束，但验收永不吃功能槽。

M4 我的等待语义：`wait_agent` 是"任何子代理有动静就返回"；我却按"等这一张单的结论"来用，等于把并行退化成串行。拆法：等待返回后第一动作固定为"查 PENDING 表 → 有槽就填"，而不是"读刚完成那份报告"。

M5 验收要"干净 HEAD"：验收必须对着确定提交判，于是我倾向等到没有在飞改动才派 V。拆法：V 单固定"被验 commit 号 + 只判该区间 diff"，其它提交视为无关漂移（本轮 Q-162/Q-163 已实证可行）。

M6 尾部串行：台账、交接快照、门禁刷新都等验收结论落盘后才做，等于每张单后面拖一条尾巴。拆法：状态派生交给 `queue-sync.py`，交接交给 `update-handover.py`，我只确认差异，不再手写格子。

不可拆的两条（外部约束，保留）：
- 推送单飞：CI 的 `cancel-in-progress` 会把上一轮 Verify 取消，连续快推等于白跑，这条只能串行。
- W/V 换代理且禁自验：这是质量底线，与工期无关，不参与任何加速。

落地口径（写进调度纪律，不进 门禁）：
1. 功能槽 4 + 验收槽 2，验收永不吃功能槽。
2. 写单交付三连：提交 → 派 V → 派下一张 W。
3. 等待返回先查 PENDING，再看报告。
4. V 单必须写"被验 commit"，只判该区间。
5. 台账/交接由脚本派生，人只确认差异。
