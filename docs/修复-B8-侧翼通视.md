### 1.2 缺陷定性（改前现状）

`Pathfinder.kt` 改前：`flankPath` 把 `enemyPositions` 直接传入私有 `astar` 的敌军位参数；
`stepCost` 对候选格只做 `enemyPositions.any { map.visible(enemy, next) }` 命中后乘
`VISIBILITY_PENALTY = 1.8` **加价**，不排除该格。后果：

1. 路径仍可踩进敌军视野核心区（加价 1.8 倍在长路径上完全可能被地形差价抵消）；
2. 敌军所在格本身也可被选入路径（原代码没有任何 `next == enemy` 排除）；
3. 与规格「**强制**绕开敌方视线」不符——规格是排除口径，不是加权口径。

### 1.3 视线口径核对（grep 签名确认，未自造 API）

- `app/src/main/java/io/legado/app/ui/map/crossing/terrain/TerrainMap.kt:110`：
  `fun visible(a: Cell, b: Cell): Boolean`——语义为**两点山脊通视（LOS）**，方法体内只做连线
  采样遮挡判定，**不携带任何半径**；越界两点返回 `false`。
- 现有半径口径在 `app/src/main/java/io/legado/app/ui/map/crossing/engine/CampaignController.kt:328`：
  `val visible = distCells <= corps.visionRadiusCells && map.visible(corps.position, enemy.position)`
  ——即「距离 ≤ 半径 **且** 两点通视」两段式。兵种半径表在同文件 `:107-112`
  （骑兵 6 / 精锐 5 / 常规 4 / 民兵 3 格）。
- 结论：`visible` 是两点通视而不是半径，故本单在 `Pathfinder` 内补齐半径闸门
  （八向格距 ≤ 半径），与情报口径保持一致；未在 `TerrainMap` 新增 API。

#### 2.1.2 新增 `flankRoute`（`Pathfinder.kt:60-90`）——三级兜底，逐级放宽，绝不返回空

```kotlin
fun flankRoute(
    from: Cell,
    to: Cell,
    type: ArmyType,
    enemyPositions: List<Cell>,
    visionRadiusCells: Int = radiusFor(type),
): FlankRoute {
    if (from == to) return FlankRoute(listOf(from), degraded = false, reason = "起点即终点")
    val target = nearestPassable(to, type)
    if (target == null) {
        return FlankRoute(
            straightPath(from, to, type, enemyPositions.toSet()),
            degraded = true,
            reason = "目标周边无可通行落点，已退化为直线折线兜底",
        )
    }
    val strict = astar(from, target, type, emptySet(), enemyPositions, visionRadiusCells, strictView = true)
    if (strict.isNotEmpty()) return FlankRoute(strict, degraded = false, reason = "")
    val penalized = astar(from, target, type, emptySet(), enemyPositions, visionRadiusCells, strictView = false)
    if (penalized.isNotEmpty()) {
        return FlankRoute(
            penalized,
            degraded = true,
            reason = "敌军视野封锁全部绕行通路，已退化为视野代价最小路径（仍可能暴露）",
        )
    }
    return FlankRoute(
        straightPath(from, to, type, enemyPositions.toSet()),
        degraded = true,
        reason = "视野与地形双重封锁，已退化为朝目标钳制的直线折线兜底",
    )
}
```

退化口径（KDoc 已写明）：① 严格 A* 剪枝视野内格 → ② 无路则放宽为视野代价最小路径
（加价，`degraded = true`）→ ③ 仍无路则直线折线钳制（`degraded = true`）。

#### 2.1.4 新增纯函数 `watchedBy`（`Pathfinder.kt:148-152`）

```kotlin
fun watchedBy(enemy: Cell, cell: Cell, viewRadius: Int): Boolean {
    if (cellDist(enemy, cell) > viewRadius) return false
    return map.visible(enemy, cell)
}
```

口径：八向格距 `cellDist` ≤ 半径 **且** `map.visible` 两点通视；半径外短路，不调 LOS。

## 四、二阶三阶影响（连带影响逐个点名）

### 4.1 直接效果

侧翼候选格处任一敌军「半径内 + 通视」即剪枝；敌军格任何模式不入路；绕不开时有可断言的
退化标志与三级兜底。

### 4.2 连带影响（全量 grep 逐个说）

1. **AI 进攻路线 —— `CampaignController.kt:355`**：`Intent.FLANK` 仍调 `flankPath` 四参形态，
   第 5 参 `visionRadiusCells` 走默认 `radiusFor(type)`，源码兼容、无需改该文件。二阶：严格绕路
   使侧翼路径变长；`:363-369` 回合移动按 `minOf(budget, route.size - 1)` 逐步推进，路径变长意味着
   单回合抵达格数不变、抵达目标所需回合数可能增加——这是「包抄绕侧」的预期行为，不是卡顿；
   路径非空保证军队不会原地僵死。三阶：若多支军队同时绕远，回合推进节奏整体后移，调度层无需
   改逻辑，`route.size` 只作遍历上限。
2. **动画插值 —— `CrossingShell.kt:245-247`**：`corps.route.map { geoToOffset(...) }` 按路径格 〔W-451 重贴锚：corps.route.mapNotNull { geoToOffset(…) } 现行第663-667行〕
   逐点映射；路径变长只增加插值点数，现有代码无固定长度假设，不爆数组。三阶：长路径动画帧数
   增多，单帧渲染量仍与路径点数线性相关，32×32 栅格上限内不构成性能风险。
3. **回合预算 —— `CampaignController.kt:365`**：`steps = minOf(budget, route.size - 1)`，
   严格剪枝不改变预算口径；退化路径（加价绕行 / 折线兜底）长度可能大于最短路，同上只影响
   抵达回合数，不影响预算计算。
4. **退化分支是否导致路径长度暴涨**：三级兜底逐级放宽，最坏情况退化为直线折线
   （`straightPath`，守卫上限 `gridN * 2` 步，`Pathfinder.kt:203`），不会出现死循环或指数级路径；
   加价模式仍是 A* 最短路（仅视野格加权），不是枚举绕行。
5. **情报口径一致性 —— `CampaignController.kt:328`**：情报用「`distCells <= visionRadiusCells &&
   map.visible(...)`」，本单 `watchedBy` 同两段式；两处半径表目前各持一份（见 §8 交接 1）。
6. **`help/sim/` 旧模拟包**：`app/src/main/java/io/legado/app/help/sim/Pathfinder.kt`、
   `SimEngine.kt:234-235` 是另一套独立旧实现（静态 `Pathfinder.flankPath(terrain, ..., scratch)`），
   与本类无继承 / 调用关系，本次改动不触及；是否同病属别单判定（见 §8 交接 2）。
7. **`VISIBILITY_PENALTY` 消费面**：全仓仅 `Pathfinder.kt:166` 一处使用；严格分支已不再消费它，
   常量保留给退化加价，未删（删除会破坏退化模式的代价诱导）。

### 4.3 对用户行为 / 系统复杂度 / 维护成本的后果

- 用户侧：包抄意图不再「贴着敌军视野走」，暴露概率下降；极端被封锁时仍有路线可走，UI 不空白。
- 复杂度：新增 1 个结果数据类 + 1 个纯函数 + 1 个半径表函数；A* 内部多一个 `strictView` 布尔分支，
  概念上限可控。
- 维护成本：半径表双份是已知漂移点（§8-1）；退化原因字符串 `reason` 供日志 / 调试断言，未进 UI。

## 五、反例与边界（含假设错误时的兜底）

### 5.1 清单要求的五类边界，逐条对应实现

| 边界 | 实现兜底 | 对应用例 |
|---|---|---|
| 无敌军 | `enemyPositions` 空列表：`watchedBy` 短路不命中，严格 A* 等同普通最短路，`degraded = false` | `无敌军时侧翼路径不退化` |
| 敌军在起点 | 起点格由 A* 无条件入队（路径无从第二格起步），属输入自相矛盾；不崩溃、路径非空；KDoc 已写明起点 / 目标格不受视野剪枝 | `敌军在起点时不崩溃且路径非空` |

### 5.2 其它反例压力测试

- **半径外但 LOS 通视**：`watchedBy` 先判格距短路，距离 > 半径即使无遮挡也不算被看见，
  与情报口径「距离 < 可视半径」一致。
- **半径内但山脊遮挡**：`map.visible` 返回 `false`，候选格不算被看见，可通行——与规格
  「无山脊遮挡 AND 距离 < 可视半径」一致；平地测试栅格无山脊，该分支由 `TerrainMapTest` 覆盖。
- **敌军坐标越界**：`map.visible` 对越界返回 `false`；`enemySet` 相等判定不受影响，不会抛异常。
- **全军被视野封死（全图封锁）**：严格 A* 空 → 加价 A* 出视野代价最小路径，`degraded = true`；
  用例 `全图视野封锁时退化为代价最小路径并置降级标志` 固定该口径。
- **若我的判断错了（严格剪枝过严）**：反例是「视野格本可强行通过」，此时退化链第二级就是
  加价放行，不会把军队困死；`degraded` 标志把「这次走了暴露路线」显式暴露给上层，便于后续
  接暴露状态结算。

### 5.3 已知口径豁免（KDoc 已写明）

起点 / 目标格不参与视野剪枝：若把起点也判为视野内，路径无从起步；若把目标格判死，严格模式
永远无法落点。敌军所在格不在豁免范围内，任何模式都排除。
