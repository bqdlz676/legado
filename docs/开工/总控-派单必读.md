# 开工守则 · 总控（派单必读，本文件是调度层唯一的开工文案）

> 用途：每个调度层开工第一份读的文件。它管的是"怎么派、派给谁、什么时候不许派、派完怎么收口"，具体一单做什么写在任务单里。
> 为什么必须有这份：2026-11-26 夜，三份子代理守则已经成文，但调度层自己没有守则——结果是子代理被管住了，总控这边仍连犯四类错（未验即入库、CI 红还发新功能单、锚点卡给错、台账滞后一轮）。管住被管理者不等于管住自己。

## 一、开工三条命令（任一 FAIL 不许开工）

```
cd /home/user/Doubao/chats/38454122521460994/legado
bash data_scripts/rule-gate.sh          # 末行必须 GATE: PASS
bash data_scripts/pre-push-check.sh     # 末行必须 PRE-PUSH: PASS
python3 data_scripts/progress-meter.py 24   # 看 main/docs/scripts 提交结构，main=0 会打 ALERT
```
为什么先跑：GATE 会当场告诉你有几单挂着、台账新鲜不新鲜、积压深度多少；不跑就是凭记忆调度，而记忆是本项目最不可靠的东西（实测队列状态手写漂移、报告在盘却仍标 RUNNING）。

## 二、派单前六查（缺一条就会返工，逐条给结论）

1. **锚点卡存在性**：`ls docs/锚点/<缺陷号>-*.md`。不存在先建卡；派单里写的锚点必须是**本单主对象编号**的那个卡（实例：B10 单被我挂了 D16 的卡，⑲锚点卡门禁判 FAIL，白跑一轮补卡）。
2. **在飞改动面认脸**：`GIT_OPTIONAL_LOCKS=0 git status --porcelain`；派单里写明"不碰这些在飞文件"，避免两个代理同时改一棵文件树。
3. **删除/改道类先给 sweep 结论**：任务要求写码方先做全通道 sweep 并分三类命中（代码引用/测试编译锁/注释提及），只有零引用零锁才可删。实例：B1 按文件名判死 5 件，实测 4 件有活引用。
4. **量化约束写死**：新增文件 ≤600 行；测试函数名反引号内不许有 `/`；断言必须"改坏会红"。这些不是提醒而是硬约束（事故四：731 行面板顶出棘轮）。
5. **引开工守则**：每份派单第一句写"开工先读 `docs/开工/<角色>-开工守则.md` 并按它执行"，本单只写差异。为什么：共性纪律抄在每份派单里必抄漏。
6. **验收预置**：写码单派出的同时，心里要有对应的验收单号（不能写码方自验）；写码单交付后 4 小时内必须进验收，否则积压门禁㊸会亮红灯。

## 三、并发与节奏（今晚实测出来的数）

1. 并发上限 5（门禁 ⑨）；少于 2 个在飞单要说清为什么不分（碎片化派单比并行更慢）。
2. **CI 红时只派两类单**：修红的最小改动单、独立验收单。**禁派新功能单**（铁律：CI 红或无包时停发新功能派单，全队先修红）。
3. 推送节流：一轮 CI 在跑时不要连推第二个 SHA（`cancel-in-progress` 会取消上一轮，实测白烧一次 Verify）；等到当前 run 结论出来再推。
4. 调度层不许休眠：等 CI 或等子代理时用 `wait_agent` 或带 timeout 的查询，不许"什么都不做地挂着"，也不许用短轮询刷 token。

## 四、落地纪律（顺序不许颠倒）

写 → 独立验收 → push → CI → CI 后再验收。两道都过才算完成。

- **未验即入库是欠账，必须登记**：确因 CI 阻塞要抢先修红的，允许 push 但必须在队列里立一张"补验"单（实例：Q-196/Q-197 就是给夜间未验入库的改动补的账）。
- 落地用 `python3 data_scripts/land.py --q Q-xxx --title ... --code ... --test ... --report ...`，它自带预检；手工提交必须 docs 与 code 分两个 commit（门禁㊵ 会查）。
- `git add` 只点具体路径，禁 `git add docs/`（会把别的在飞代理改动一起带走）；提交前 `rm -f .git/index.lock` 仅限 0 字节且无 git 进程。

## 五、派完必做的四件同步（滞后一轮就会被门禁⑯抓住）

1. `docs/派单队列.md`：新单立行、在飞写实际 agent id、交付后在盘即收口。
2. `docs/派单台账.md`：每批提交与 CI 红/绿按时间序登记，含根因一句话。
3. `docs/问题清单.md`：验收结论回写到对应行（✅已验 / 🟢待验证 / 新缺陷编号）。
4. `docs/索引-文档.md`、`docs/索引-机制.md`：新文档入册后重跑生成器，否则索引本身过期即算未完成。

## 六、事故沉淀（每一类都必须落到三件套）

出事当场记事实（可回源的 `文件:行`、命令输出、commit）→ 写根因（至少三层：机制口径 / 派单约束 / 自检缺口）→ 处置分两路：立单修当下 + 加机检防复发（脚本规则 + 守则条例 + 台账编号 M-xx）。

已沉淀的四次：事故一（机制吃产能）、事故二（缝合怪与串行验收）、事故三（自造七层金字塔＝机制双轨）、事故四（731 行新文件顶出债务棘轮）。

## 七、调度层自身的红线

1. 不许自评代验收（自己写的代码自己判 PASS）。
2. 不许把"报告在盘"写成"已完成"（DONE 只是"待确认结论"）。
3. 不许报百分比、不许报 APK；进度只报两布尔：HEAD commit、CI 绿红（含单测全绿）。
4. 不许把在飞的机制活算成"功能进展"——判定口径就一条：`app/src/main` 的提交是不是在涨。
