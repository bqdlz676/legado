# 开工守则 · 机制与文档子代理（每单必读，逐条执行）

> 用途：凡任务产物是"机制/脚本/台账/索引/复盘/规划"，而不是产品代码时，读本守则。
> 为什么单独成文：2026-11-26 夜实测，机制类工作最容易犯的错不是做不对，而是**自造第二套**（实例：自造"七层金字塔"与仓库既有 F-92 组合验收五层 + 铁律#46 + 三件套重复，被判机制双轨）。所以机制方开工第一件事永远是"先找现成事实源"。

## 一、开工前（先证明不是重复造）

1. 读 `docs/接手/00-入口.md` 的机制索引段，确认有没有既有机制覆盖本需求；有则扩展它，不许新建平行件。
2. `grep -rn` 扫 `data_scripts/`、`docs/` 找同名/近义脚本与文档；报告里写"我找到了哪些既有件、为什么不能直接用、我要扩哪一处"。
3. 读 `docs/经验库.md`、`docs/台账-机制缺陷.md`（M 编号）、`docs/规矩总纲` 对应段；已有结论只标注"同因已见 `文件:行`"，**不重复论证**（语料级重复论证是纯浪费）。

## 二、写机制时（三件套缺一不可）

1. **总账**：任何要长期维持的东西必须有台账承载（`docs/派单队列.md` / `派单台账.md` / `问题清单.md` / 专项台账）。只写脚本不写台账等于没人知道它在跑。
2. **门禁**：判据必须能机检，落成 `data_scripts/check-*.py` 或 `rule-gate.sh` 里一项；写完必须跑一遍并贴输出，另做**反向自测**（故意造一个违规样例，确认它会红，再删掉样例确认恢复绿）。
3. **溯源**：报告写清"这条判据对应原始事实的哪一行/哪份报告"，锚点可回源。

## 三、脚本类硬约束

1. 误杀优先消灭：新规则上线前拿全仓跑一遍，凡命中既有合法写法（`InkText` 一类自定义壳、`SpanStyle`、注释里提到文件名、模板串跨行）就收窄判据，并写注释说明"为什么这样收窄"（实例：guard F1 因注释误杀拦掉一次 land；lint S3 只对 BasicText/Text 判死以免误杀 InkText）。
2. 判据宁缺不误杀：不能确定判死的先打 WARN + 人工核，不进 FAIL。
3. 脚本改动后先 `grep -n` 回证改动写入，再跑，再报告；未生效不许报完成。
4. 涉及推送顺序的（`cancel-in-progress`），脚本里不加速连续 push；CI 在跑时等它结束再推。

## 四、收尾（报告口径）

1. 报告路径按类型：`docs/机制-…md` / `docs/诊断-…md` / `docs/事故复盘-…md` / `docs/索引-…md`，首行锚点卡。
2. 机器头四行 + 变更清单带 `文件:行` + 反向自测输出 + 二阶三阶影响（对既有流水、其他代理并发、CI 时长、维护成本的影响）。
3. 复盘类必须写到"共同根因 + 已成文的对策（规则/自动化/Skill）+ 未落地部分立单"，只统计现象不算复盘。
4. 索引类产出后必须重跑生成器（`docs-index.py` / `mechanism-index.py`），否则索引本身过期即算未完成。
5. 禁 git 写操作；禁唤醒续跑（机制/文档代理允许 ≤3 次复用，但每轮只做本单范围）。
