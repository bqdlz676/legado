## 三、裁决一：CI-4 走 B，两条边界封口

B 口径即"墙钟不进规则"：不用 30 分钟上限兜底，也不用 5 分钟最小间隔，全部改状态量——待推批次达到阈值即强制推，上一次 run 进入终态才允许下一次 push。

两条边界已经写死，目的都是堵 B 自身的空子：

一、"待推批次"只计已闭环批次：批次内全部 V 卡状态为"过"，且该批次静态门禁全绿（按 F-109 口径，除 ① 待提交态必红豁免口外全绿）。状态为待取、在写、已交活但验收未结、不过、缺锚点、待拆卡的批次，以及门禁有红的批次，一律不计入强制推计数。不这样卡，B 就等于给 C11"全过才推"开旁门，没验完的卡会被当成积压货推进去。

二、"run 不再处于 queued"改判为"run 已进入终态"。终态白名单只有 success 与 failure；queued、in_progress 不满足，cancelled 也不视为满足。按字面"不在 queued"判定，被 cancel 的 run 反而满足条件，连环推照样能打掉在飞 run，K-20 会原样复发。脚本落点上规定只能用白名单正向匹配，禁止写"状态 ≠ queued"这类反向排除。

## 六、归因验证去人工：dry-run 双批 diff

落盘文件 `docs/规则-归因机械验证.md`（88 行），三条规则：

一、F-113 归因判定链条上禁止出现人工环节。能机械判的一律机械判，判断依据只能是文件逐行 diff。理由是人工判读不可回源、不可复跑，口径会随人漂移，进不了批次登记与卡状态回写。

二、F-114 归因脚本必须带 dry-run 模式，用两个已结批次回放——单卡批次作对照、多卡批次作样本，产物与预落盘的期望归因文件逐行 diff。"两轮验证"就是跑两次 diff，且必须是两个不同批次样本。

三、F-115 期望归因文件由调度层一次性写定落盘，带批次号与时间戳，此后只 diff 不人眼，版本随批次事实更新。

两条反例边界也写进去了，这是这套机制唯一可能自欺的地方：其一，期望文件本身错误时，diff 只证"脚本与期望一致"，不证"期望正确"，所以期望文件必须由同批次已知事实生成，禁止为了变绿事后改期望；其二，同一样本跑两遍只证幂等，不证泛化，所以第二轮必须换批次。

## 十一、CI 拆分带来的两处结构性变化（必读，下一棒要盯）

一、跨 workflow 的 `needs` 无法保留。GitHub Actions 不允许一个 workflow 的 job `needs` 另一个 workflow 的 job，所以 `build-shard` 原本对 discover/test-shard/test-aggregate 的等待关系，改由 package.yml 顶部的 `workflow_run`（verify completed + conclusion success）承担。代价是打包起跑多一个调度间隙（约十几秒到几十秒），换来的是打包长作业不再被新 push 取消。

二、baseline 手动链路由一次入口变两次。原来一次 `workflow_dispatch` 能把 test-baseline 跑完再串到 build-baseline；拆分后 verify 跑 baseline 测试、package 手动出包要分别入口。这是行为变化，不是能力丢失。若要恢复一次入口，下一轮可在 package.yml 加一个输入参数与 verify 联动，属可选优化。

三、这两条都未在真 CI 验证。push 后必须按顺序看三件事：verify 跑绿 → package 被自动触发 → APK artifact 正常产出；三件齐了才允许删 `build.yml.bak`。在此之前旧配置是唯一回滚路径，不能动。
