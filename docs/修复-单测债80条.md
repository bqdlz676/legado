## 七、反例与边界（铁律 61：先假设本方案错误）

1. **反例：B 类迁移是否把「行为覆盖」偷换成「字符串存在」？** 本批多数契约测试本身就是源码字符串/结构断言（旧架构遗留形态），迁移保持了同等粒度；风险是 main 重构改了写法但字符串仍在时会假绿。缓解：关键行为（保存回写、顺序守卫、鉴权先于路由）断言的是**调用顺序/回调关系**，不是单纯标识符。下一轮 CI 若绿，仍建议后续把高价值契约换成真正的 JVM 行为测试。
2. **反例：#73 会不会是测试期望值错了，而非实现错了？** 复核规格 §三 L80：天候在速度侧是 ≤1 折减，坏天气只拖慢。旧 rain=1.30 与规格直接冲突，实现错配；测试 `clear > rain` 符合规格，不改测试。
3. **边界：宿主 JVM 性能基准**。#30 的 2ms×500 在无 AOSP 框架的本机 JVM 上数字不可比；warmup、GC、CI 负载都会抖动。不能据此判定 Pathfinder 回归，也不能放宽预算。
4. **边界：E-ink / 旧壳并存**。RSS 编辑、RSS 调试、存活 Adapter 仍是旧 View 壳；本批断言新旧两套并存，后续 Compose 化这些壳时，对应 B 断言要再次迁移。
5. **边界：schema 历史**。`BookSourcePart` 投影断言绑死 schema 93；后续 Room 迁移若改投影列，需同步该用例。
6. **反例检查：有没有为变绿而 `@Ignore`/空实现/放宽断言？** 全批未加 `@Ignore`；未出现 `assertTrue(true)`；负向断言（旧对象不存在、旧 import 不残留）全部保留；C 类只改实现未改测试。

## 八、认知成本复盘（铁律 63：这批测试为什么烂掉，以后怎么防）

### 8.1 根因

1. **架构切换与测试不同批落地**：Fragment/Adapter/XML 壳被 Compose 重写拆除时，指向旧壳细节（Binding 字段、menu id、弹窗方法名）的契约测试没有同批改写，先堆积成债。
2. **契约测试绑死实现细节而非行为**：大量用例断言 `binding.xxx`、`R.menu.xxx`、方法签名字符串，UI 壳一换即失效；它们本应断言行为（守卫顺序、回调关系、数据口径）。
3. **跨层口径漂移**：编排从 Fragment 迁到 ViewModel/Section 后，旧测试不知道新落点，也没有一张「旧对象→新落点」映射表可供改造。
4. **重写期未跑全量单测**：编译归零后未即时转红单测，80 条失败积累到一次性清偿。

### 8.2 防复发规则草案（建议入总纲）

- **规则 R-测试同批**：删除/替换任何 main 类、布局、菜单、Adapter、Binding 时，同一改动批次必须同步改完指向它的测试；CI 以「编译绿 + 单测绿」双闸门，不许只收编译。
- **规则 R-行为断言优先**：新增契约测试断言行为关系（顺序、回调、数据不变量），不断言私有 Binding 字段 / menu 资源 id / 方法内字符串；实现细节可自由重构。
- **规则 R-落点映射**：每次壳层迁移在报告/索引中登记「旧对象 → 新落点」对照表，供后续测试改造回源。
- **规则 R-债单可见**：单测失败按 A/B/C 当场分类入账；CI 红或有失败用例时，不派发新功能（沿用既有 CI 铁律）。
- **规则 R-定期清负向断言**：负向「旧类不存在」断言在旧类彻底删除一个版本周期后可移除，避免测试树堆积历史考古。
