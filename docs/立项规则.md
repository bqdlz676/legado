# 落文 · 立项规则（唯一权威）

> 本文件是"立项"这件事的唯一规则。**立项 = 把用户的一条要求，登记成一条可追踪、可验收的规格。** 目的：保证整个项目不漏项、每项都有人做、做完都有人验收、且不被误读。
> 其它文件（铁律 E13、`docs/规格登记册.md` 头部、`spec-check.sh`）只指向本文件，不复制规则——防止两处各写一套、一处漂移。

## 1. 术语（先定义，防止子 AI 各读一段时误读）

- **规格**：用户的一条要求（一个功能 / 一次规则修改 / 一次治理动作）。
- **立项**：给规格登记唯一编号，并定"由哪个缺陷号做 + 做到什么算完成"。
- **缺陷号**：`docs/问题清单.md` 里一行一缺陷的编号，格式 = 大写字母分区 + 数字（例如 D14、B1）。它是"这件事交给谁做"的唯一标识。
- **完成定义（DoD，Definition of Done）**：一句话说清"做到什么 = 这条规格完成"，让验收的人能据此判"过 / 不过"。
- **验收级别（五级，数字越大越严）**：L0=静态（grep/读代码对得上）、L1=接线（符号存在且真被调用）、L2=编译（CI 绿 + 单测全绿）、L3=契约（冻结签名/边界逐字对上）、L4=运行（真机/整包冒烟）。**L4 用户已定"不用真机"，不作强制门禁**。
- **验收档位（A/B/C，源自 F-73/F-77 与批次草案；D 档：规则与四份草案均未定义，不使用）**：硬内容四项＝尺寸/色值/状态/边界（F-77②③④⑤）。
  - **C（规格齐全，可直接派单）**：尺寸/色值/状态/边界四项齐全，按切片/原文对片验收。
  - **B（规格可复用，补条款/选型）**：边界降级条文或时代口径缺口未齐；既有切片/草案/契约原文有出处，先补条款再派单。
  - **A（需先设计规格）**：缺尺寸/色值/状态/边界任一项且文档无出处，须先出 ≥2 份方案候选 → 独立选型 → 再派单。
  - **B 与 A 的差异判据**：看缺口能否在既有切片/草案/契约原文找到出处——找得到出处、补条款即可闭环 → B；无出处、须新设计并走 F-73 三段流水线选型 → A。
- **落地物**：治理动作改出来的东西（规则文档 / 脚本 / 目录），用它的 commit sha（git 提交哈希，8 位短号）当证据。
- **执行进度**：问题清单缺陷号那行的标记，🔴=未做、🟡=进行中、🟢=已修待验。

## 2. 规格分两类（立项动作不同）

- **功能规格**（要写代码 / 做产品功能）：立项 = **在 `docs/问题清单.md` 立一个缺陷号 + 写完成定义 DoD**。
- **治理规格**（改规则 / 文档 / 机制本身）：**不在问题清单立缺陷号**；直接改出落地物，验收 = 落地物 + commit sha。

## 3. 规格分四种来源（编号前缀不同，登记册按此分四区）

| 来源 | 编号 | 位置 |
|---|---|---|
| 切片规格 | S-01 ~ S-20 | `docs/落文-规格切片/切片-*.md` |
| 原文规格 | Y-03 ~ Y-09 | `docs/落文-规格切片/落文-原文-*.md` |
| 契约规格 | Q-01 ~ Q-07 | 主项目目录 `落文-*-契约.md` / `落文-名物库档案.md` 等 |
| 新增规格 | N-001 起递增 | 用户后续每轮新要求 |

## 4. 立项粒度（一个规格立几个缺陷号）

- **默认：一个规格 = 一个缺陷号**，缺陷号的"问题"列承载完整规格描述，登记册"验收档位"列写 DoD。
- **拆多缺陷号**：仅当规格大到必须拆成多个"可独立验收的单元"时才拆（例：D14 人物关系力导向图，若"NER 抽取"与"力导向 UI"是两个能各自独立验收的单元，才拆成两个缺陷号）。拆后每个缺陷号各自有 DoD，登记册"立项缺陷号"列写多个。
- **合一缺陷号**：多个小规格可共用一个缺陷号（缺陷号"问题"列分条写），但登记册里每条规格仍各占一行、指向同一缺陷号。

## 5. 每轮动作（用户说完一句话后，当轮必做）

1. 用户**新增**要求 → 当轮：① 抽成一条规格（照抄用户措辞，不改写、不压缩）；② 判功能/治理；③ 给唯一编号；④ 登记进登记册对应分区；⑤ 功能规格 → 立缺陷号 + 写 DoD，状态改 `[已立项]`；治理规格 → 改出落地物，状态改 `[已验收]`。
2. 用户**修改**既有规格/铁律/契约 → 找到对应行，更新描述并标注"变更 + commit sha"，**不新建一行**；改的是铁律/规则（登记册没登记过的）→ 当作治理规格新增一条登记。
3. 每轮结束前 + 每次 commit 前跑 `bash data_scripts/spec-check.sh`；还有 `[待立项]` 就当场立项或否决，不许留着。

## 6. 状态机（每项规格只能是这 4 个状态之一）

- `[待立项]`：已登记，但还没立缺陷号、还没写完成定义。
- `[已立项]`：已立缺陷号 + 已写完成定义，可以派单。（此后做到哪一步，看问题清单该缺陷号那行的 🔴/🟡/🟢）
- `[已验收]`：验收代理给出结论，**必须写"级别 L0~L4 + 证据（报告路径或 commit sha）"**，不许只写"已验收"三个字。
- `[已否决]`：这条规格作废，不再做。

## 7. 立项 → 派单 → 验收 的闭环（三者分工，不互相替代）

- **立项**（本文件）：只管"登记 + 立缺陷号 + 写 DoD"。
- **派单**（`docs/机制-子代理必读.md`）：管"怎么派"——任务分型（执行/探索）+ 工具预算 + DoD + 止损动作。
- **验收**（`docs/机制-验收代理必读.md`）：管"怎么判过不过"——L0~L4 分级结论。
- 验收通过后，回写登记册：状态改 `[已验收]` + 级别 + 证据。

## 8. 完整性判据（`spec-check.sh` 机械判断 5 项，不是人看）

① 切片编号连续、无跳号；② 本册没有 `[待立项]` 遗留；③ 每个 `[已立项]` 的缺陷号都能在问题清单找到；④ 问题清单缺陷数 ≥ 已立项规格数；⑤ 每个 `[已验收]` 都写了验收证据（非空）。

## 9. 反模式（什么算漏项 / 误读，见到就纠正）

- 用户提了新要求，没当轮登记 → **漏项**。
- 登记了却一直 `[待立项]` 不立项 → **拖项**。
- `[已验收]` 只写"已验收"、无级别无证据 → **空口验收**。
- 改铁律/契约不登记、不标 commit sha → **改而不记**，后面读不到来龙去脉。
- 同一规则两处写、一处漂移 → **误读**（所以本文件是唯一权威，其它处只指向本文件）。
