# 修复-g64 lazy 绑定盲区与种子表 SpringSpec 同名多源

## 总结论

两项门禁加固在静态层通过：g64（单测判据真值闸）已把 readText 绑定识别扩到 `by lazy` 委托形态，双向自测全过，新增 lazy 坏样本可独立跑红；种子表 `SpringSpec` 已登记为双源白名单，包名比对闸在两个仓内合法来源之间放行、第三来源仍判死。编译面与 JVM 单测绿红未在本机验证（沙箱无编译链），以 CI 为准。

改动文件域仅限 `data_scripts/` 下两个脚本与一份种子表，外加本报告与对应锚点卡；未改 `app/src` 业务代码，未做 git add / commit / push。

## 一、A 项：g64 的 by-lazy 绑定盲区

### 1.1 盲区与根因

g64 脚本 `data_scripts/check-test-assert-truth.py` 拦三类「文本层合法、运行期打不出真值」的单测写法：反射取成员（REFLECT）、整份源文件直接 contains（RAWSOURCE）、空断言（EMPTYASSERT）。

RAWSOURCE 旧正则只认普通赋值 `val src = File(...).readText()`。测试里把 readText 包进 lazy 委托时——`val src by lazy { File(...).readText() }`——绑定名 `src` 抓不到，后续 `src.contains(...)` 断言就漏判。这是 2026-11-27 加固前的已知盲区。

### 1.2 改法

- 绑定识别拆成两条正则（`data_scripts/check-test-assert-truth.py:37` 赋值形态、`:43` lazy 委托形态），收集循环在 `:144` 对两条正则统一过白名单。
- 赋值形态的 RHS 截面截到下一条声明（val/var/fun/private/import/@/注释）为止，续行链式调用留在截面上。旧版只截到 `readText()` 本身，`filterNot` 写在续行时白名单看不见，会把已剥注释面的合法写法打成假红；本次把截面放宽后该假红路径一并兜住。
- 白名单原样保留：RHS / lazy 块内出现 `filterNot`、`filter {`、`strip_comments` 即放行；块内没有 `readText` 的绑定不进本闸。
- 断言侧判据未动：仍按括号配平取断言实参，命中绑定名 `.contains(` 才记 RAWSOURCE。

### 1.3 自测证据（双向，逐样本独立跑）

`--selftest` 退出码 0。坏样本逐条在独立临时目录单独跑红，放行样本逐条单独跑绿，不靠聚合结果一次性盖住：

- 坏样本独立 FAIL：REFLECT 反射取成员；RAWSOURCE 赋值整文件 contains；RAWSOURCE lazy 委托整文件 contains（本次新增）；EMPTYASSERT 空断言。
- 放行样本独立 PASS：赋值 + 续行 filterNot 剥注释面；lazy 块内 filterNot 剥注释面；普通字符串断言（无 readText 绑定）。

lazy 坏样本夹具正文：`val src by lazy { java.io.File("x.kt").readText() }` 接 `assertFalse(..., src.contains("mastered"))`，单目录单文件运行命中 `RAWSOURCE`，绑定行号回指 lazy 声明行。

### 1.4 存量面复核

门禁口径仍是只判相对 `origin/main` 的改动面（`--changed`），全仓存量属历史债务、走 audit 补偿通道，不挡 push。

- 改动面闸门实跑：`TEST-ASSERT-TRUTH: PASS（扫描 2 个测试文件，REFLECT/RAWSOURCE/EMPTYASSERT 三类 0 命中）`，rc=0。
- 全量扫描对照：加固前旧版命中 306 处，加固后 983 处。逐条归一化比对文件级命中集，旧 306 处零漏抓；新增 677 处是旧正则单行匹配漏掉的多行持有人（readText 在续行、链式调用跨多行），与已登记债务同一性质，不是新造的假红。抽样复核 `ImageDecoderContractTest.kt:13`、`AudioReadTimeTrackerTest.kt:101` 等新增命中，声明面确为整文件 readText 持有人。

## 二、B 项：种子表 SpringSpec 同名多源

### 2.1 消费方排查结论

全仓 grep `import-pack-map` / `PACK_MAP` / `pack_map`，唯一读取方是 `data_scripts/kotlin-syntax-lint.py`：表路径常量 `:388`，加载函数 `:391`，包名比对判据函数 `check_import_package` 在 `:410`。其余脚本（含依赖符号闸、pitfalls 闸）均不读该表。

包名比对闸原比对行逻辑：取 import 行的包名与符号名，`pmap.get(name)` 命中后与登记包名做等值比对，不符即 FAIL；未知符号不判，交 CI 编译兜底。

### 2.2 两源实证

仓内确有两个同名 `SpringSpec`：

- Compose 泛型版：存量 `app/src/main/java/io/legado/app/ui/map/crossing/shell/CrossingShell.kt:4` `import androidx.compose.animation.core.SpringSpec`。
- 契约层 data class 版：`app/src/main/java/io/legado/app/ui/motion/contract/MotionSpec.kt:25` `data class SpringSpec(stiffness, dampingRatio, label)`，包 `io.legado.app.ui.motion.contract`。

旧表只登记 compose 一条：新文件写短名 import 契约版会被包名比对闸误判包不符；写全限定名绕行又未经编译器在静态层证实。

### 2.3 修法选型：双源留登记 + 白名单对象（方案一），不选多源全跳（方案二）

落地修法：`data_scripts/import-pack-map.json:69` 的 `SpringSpec` 由字符串包名改为对象，`pkgs` 数组列两个已核实来源，`note` 写明两源身份与出处；判据侧 `data_scripts/kotlin-syntax-lint.py:434-442` 按集合成员比对——对象条目取 `pkgs` 白名单，字符串条目走原等值路径，`pkg not in allowed` 才判不符。

为什么不选「同名多源时不硬判并计 skipped」：包名比对闸的存在目的是拦手抄错包。多源即整名跳过，等于这个名字无论 import 到哪个包都无人拦，把闸在该符号上的判死能力整片让渡；而白名单方案只在两个已核实合法来源之间放行，第三来源（错包）仍 FAIL，判死能力保留，且两源出处写进 `note` 可回源。代价是判据多一个对象分支，约 6 行，不伤既有 151 条字符串条目。

### 2.4 定向矩阵结果（临时夹具单文件跑）

- import compose 源 `androidx.compose.animation.core.SpringSpec`：PASS（存量 CrossingShell 不被误伤）。
- import 契约源 `io.legado.app.ui.motion.contract.SpringSpec`：PASS（新文件短名 import 不再误红）。
- import 第三来源 `androidx.compose.foundation.SpringSpec`：FAIL，提示基线两源。
- 单源错包回归：`Arrangement` 抄成 `androidx.compose.foundation`：仍 FAIL（原判死能力未放松）。
- 未知符号：不判，PASS（原口径保留）。

### 2.5 反例与边界

- 第三个合法来源日后出现，必须补进 `pkgs` 数组，否则会假红；闸不自发现新来源，新依赖合法与否交 CI。
- 集合成员比对分不出「同名不同类型用错」：compose 泛型 `SpringSpec<T>` 与契约 data class 互串，静态文本层无类型推断能力，仍归 CI 编译兜底。
- 对象条目缺 `pkgs` 键时判据按未知符号跳过、不硬判，避免种子条目自身残缺把整闸带崩。
- 其余 151 条单源条目值形态未动，等值比对路径字节级保留。
- 种子表无写入脚本，条目为人工维护；本次未重生成容忍集与其他种子。

## 三、自查反例（改坏推演）

- 不能被误杀的合法写法一：`val code = File("x.kt").readText().lines().filterNot { ... }.joinToString("\n")` 后续 contains 断言——已在放行样本独立跑绿。
- 不能被误杀的合法写法二：`val code by lazy { File("x.kt").readText().lines().filterNot { ... }.joinToString("\n") }`——已在放行样本独立跑绿。
- 不能被误杀的合法写法三：断言对象是普通字符串或非 readText 持有人（如 `val code = "x".trim()`）——独立跑绿。
- 推演二阶影响：g64 收集循环对两条正则共用同一白名单与同一断言匹配，新增 lazy 形态不会改变 REFLECT / EMPTYASSERT 两条既有判据的命中集；赋值截面放宽只影响 RHS 文本范围，不改变断言括号配平逻辑。
- 推演三阶影响：种子表值形态从纯字符串扩成「字符串 + 对象」两种，唯一消费方已做类型分支；若后续有新脚本接入该表，必须先认对象形态，否则会把 dict 当字符串比对出错——此点记入新发现问题。
