## 九、推演 BGM（战时配乐，2026-11-24 新增口径）

- **F-26 阶段配乐（五段，不循环一首到底）**：部署(回合0，太鼓+古筝单音，开场15s) / 行军(琵琶轮指+二胡急促短弓，随回合持续) / 交战(大鼓+镲+琵琶扫弦，爆开+弦乐骤停0.5s→急板3-5s) / 战后(胜:低音鼓渐慢渐弱+箫，败:弦乐骤停→静2s→琵琶单音低沉，收尾8s) / 剧场收尾(鼓全静，一声极长箫渐弱到无；定格瞬间全静，6s)。
- **F-27 不打断原则**：配乐永远低于音效；交战朱砂冲击环爆发那一声"砰"的瞬间，BGM 自动降到 30%，音效过后恢复（这是硬要求，不是建议）。
- **F-28 用户音乐优先**：优先级＝用户音乐 > 推演BGM > 无音乐；用户已在落文播放器放歌（如古琴曲）时**不打断**，BGM 只在"用户没在听任何音乐"时才启动。
- **F-29 音源合规**：只用 5 段自编 MIDI + 公版/CC0 采样合成（VSCO Community 管弦、FreePats 中国民乐、MuseScore 公版 MIDI 导出），总时长 <60s；**不用完整古人录音**（版权），成品版权自有。
- **F-30 通道隔离**：推演 BGM 用 `SoundPool` 或 `AAudio` 直出，**不与 ExoPlayer 音乐播放共通道**；选 SoundPool 的理由＝可同时播多片段 + 可实时调音量（交战爆音要立刻压鼓点），ExoPlayer 单轨不适合实时响应。
- **F-31 接线链路**：`SimEngine.tick() → turnResult → AnimationController.animate() → BgmController.checkPhase(turnResult)`；遭遇→`play(CLASH_SFX, HIGH)` + 鼓点降到 0.3；溃退→`crossfade(DRUM,0,800ms)` + `play(SOLO_XIAO)`；剧场结束→`stopAll()` + `play(ENDING_XIAO)`。
- **F-32 开关位置三态**：沙盘页**右上角喇叭小图标**，三态 🔊 开（默认）/ 🔈 低音量 / 🔇 关，点一下切态；**不放设置页里藏**。
- **F-33 落地归属**：新增 N-015 → **D26「推演BGM」**（音频资产 + BgmController + 三态开关 + ducking），不并入 D23/D24。

## 十三、卡片/图标验收期口径修正（2026-11-24 20:0x，独立验收反馈后拍板）

> 来源：独立验收代理 `docs/验收-卡片12类.md` 判 PARTIAL/FAIL 后的裁决。每条都写"为什么/适用条件"，避免下一位接手者再判一次。

- **F-53 判据 1 的设置行卡豁免**：切片-25 判据 1 写「12 类全部复用 `CardBase`」，但同文档「十二、设置行卡片」原文明确「**无卡片框**、只靠云灰细线分隔」。二者冲突 → **以具体卡类原文为先**（更具体的条款优先于总则）。落地口径：11 类走 `CardSurface` 五态基座；`SettingRowCard` 只复用 `CardTokens`（色值/字号/间距），不套阴影与圆角。适用条件：仅设置行卡；其余 11 类不得援引本豁免。
- **F-54 判据 2 的例外边界**：组件内 `grep -c "0x"` ≤2 的例外只认「该卡类原文点名的边框色 / 朱砂进度线 / 金点」。分享卡四套背景（暗色/护眼/宣纸/纸白）不在例外内 → **必须从 `CardTokens` 派生**（`lerp(cardPaper, stoneBlue, …)` 等），实测 `ShareCard.kt` 的 `0x` 计数已归 0。适用条件：新增卡类若要自带色，先在 `CardTokens` 立 token，再引用。
- **F-55 判据 8 的可判证据链**：颗粒＝`res/drawable-nodpi/paper_noise_tile.png` 单张平铺（64×64、实测 638B ≤ 64KB）；「滚动零新建 Bitmap」以三层论证：资源加载器缓存 → composition 级 `remember` → draw lambda 内零分配。为什么要求证据而不接受"应该没问题"：判据原文写的是「grep 证明」。适用条件：任何性能类判据都要给可回源证据。

## 十四、CI 修红期口径（2026-11-24 首次全绿，run 45404217394 / commit a978f15）

> 来源：九连红→全绿复盘 `docs/复盘-CI连红到全绿-根因清单.md`。每条写"为什么/适用条件"，避免下一位接手者把编译绿当完成态。

- **F-62 修红完成判据＝三同时**：`BUILD SUCCESSFUL` 且 `e: file` 计数为 0 且 `tests failed` 为 0；编译绿只是中间态，不许报完成。为什么：本轮 `2ff867d`/`82e1afc` 编译清零后仍各有 8 个运行期失败，编译通过不等于逻辑通过；适用条件：任何"修红/修 CI"派单的验收口径，L1 静态自检不算完成，必须跑到 test 阶段真绿。
- **F-63 HOLD 意图豁免**：规则 7（兵力三倍→ADVANCE 压迫）与规则 9（未持关隘+敌远→SEIZE 抢关隘）对 `Intent.HOLD` 不生效；据守军只在相邻接敌/溃散/被围等生存威胁下易地。为什么：驻点归属/计数是分支存档的核心状态，被机会主义机动拖走会让 `pointHolders`/`captureHold` 快照空表；适用条件：`IntentResolver` 新增机动/抢占类规则时同样先过 HOLD 闸门。
- **F-64 士气降级回合节流**：一回合每军至多降一级；事件直置 BROKEN（`moraleChange` 等）不受此限。为什么：同格 2v1 两场遭遇叠加会把士气连降两级当场解散，部队掉出感知集造成"凭空消失"假象；适用条件：所有遭遇/交火引发的降级走回合级 `moraleDowngradedThisRound` 集合（`step()`/`restoreBranch()` 清零），事件直置路径不经过该节流。
- **F-65 短 base64 内联图签名探针**：长度阈值不是判定唯一依据；短串 base64 解出后命中 PNG 八字节签名（89 50 4E 47 0D 0A 1A 0A）即认内联图，字节按无符号 Int 比对。为什么：1×1 等极小图天然短（实测 92 字符 < `BASE64_MIN_LENGTH=200`），纯长度阈值会误判为 ASSET；适用条件：`classify` 探不出签名仍走 ASSET 兜底，探针只放宽短串分支。
- **F-66 源码扫描型测试的失效模式**：断言资源/文件路径时，资源可能被"清孤儿"删除、文件可能搬迁；失效必须二选一——实现补回引用 + 测试同步更新，或明确放弃资源化并改断言，禁留空断言/死引用。为什么：本轮 JS 角标资源被清孤儿删掉后扫描型测试落空，实现侧却硬编码 `"JS"`；适用条件：写扫描型测试前先确认被测资源/路径仍在册，清孤儿扫描前后都要 grep 扫描串。

## 十五、子代理派单与回执取证口径（2026-11-24 空转事故族复盘）

> 来源：`docs/复盘-子代理空转与假完成.md`（375 个带轨迹代理扫描，10 例零工具调用 + 1 例证据缺档）。每条写"为什么/适用条件"，验收只认仓库实证，不认回执文字。

- **F-67 回执零工具调用即判未交付**：轨迹中工具调用数为 0（无 Read/Edit/grep/ls 等任一执行痕迹）的代理，无论回执文字多像完成汇报，一律判未交付并重派；禁止以回执文字判完成。为什么：事故族 10 例全部返回了一段文字，其中 6 段像完成汇报，但文件系统零改动；回执通道与产物通道解耦，文字不携带产物证据。适用条件：所有写码/改文件/落报告类派单；纯咨询类问答不在此列。
- **F-68 回证三条硬要求**：任何写码/改文件类派单，回执必须同时含 ≥1 条 `grep -n` 命中行、≥1 个 `文件:行` 落点、≥1 个括号配平数（或等价词法计数）；缺一即判未交付并重派。为什么：承诺句/拒答句/编造句在无取证格式时都是低成本通过路径，三条证据分别锁死"符号真被引用 / 落点可回源 / 文本未写残"。适用条件：机械修复、测试改写、文档回写各类派单；报告类派单至少给报告路径 + 一节标题命中行。
- **F-69 机械改动短句派单**：同一批机械修复，指令 ≤200 字，只给「文件 / 行 / 原文 / 改成什么 / 三条自证」，不附大段背景与日志；长篇多段派单只用于需要判断（口径权衡、反例推演）的活。为什么：对照实验 `s_0007oNQJnkb`（长派单空转）vs `s_0007Qc68H0S`（≤60 字机械指令＋三条 grep 自证成功）证明，长派单首 turn 即退化为重复/拒答/计划倾倒；机械活不需要背景推理。适用条件：import 补齐、参数名订正、计数对齐、单图标规范补齐等可逐条枚举的修复。
- **F-70 重派不复用空转代理**：空转 / 拒答 / 乱码 / 幻觉回执的代理一律不再唤醒续跑（其工作记忆已被污染，复用会把退化状态带进新单）；同域任务新派代理，并在新单里重申 F-68 三条自证。为什么：事故族中 0 行 / 1 行空壳轨迹与重复退化回执都出现在被长上下文压垮的代理上，续跑无法清掉已污染的上下文。适用条件：F-67 判定未交付后的重派动作；仅"产物待补证据"的代理不在此列。
- **F-71 派单前置核验（现状原文≠回执证据）**：派单前调度层自己 grep 一次目标现状，把「现状原文 3 行」写进派单以降低子代理发现成本；但现状原文只是派单侧输入，不能替代回执侧取证——回执仍须按 F-68 交证据。为什么：`修红-卡片三处API` 派单已含现状原文，代理仍零工具空转，证明预塞现状防不住不执行；核验动作保护的是"改错地方"，防不住"不动手"。适用条件：所有修红/修缺陷派单；现状原文与回执证据分两栏记账，不得互相顶替。
- **F-72 全量盘点节奏与三类分账**：每完成一个大模块，调度层扫一次"零工具调用 ＋ 零产物路径"的子代理，列入问题清单；盘点必须分三类记账——①**零工具调用（未执行）**→ 重派；②**回执产物路径缺失（执行了但无证据）**→ 补档；③**承诺句/拒答句（未执行且无证据）**→ 重派＋缩短派单。为什么：三类失败补救动作不同，混账成一条"失败"会导致补错动作（该补档的去重派、该重派的只补文档）；事故族 4 例证据缺档即属第②类，功能已落地但验收无从回源。适用条件：模块收口验收与每轮派单前的台账核对；"仍漏"只计功能/产物真缺失，文档缺档单独标类不算功能漏洞。

## 十六、无规格功能三段流水线（2026-11-24 新铁律）

> 来源：用户 2026-11-24 原话「需要一个代理去专门设计最最符合的几份规格，然后交给一个验收代理去审验选出最符合全app的方案（可以全部判低），新派子代理去重做，然后交由另一个子代理去写代码走正常流程，此前未按此操作流程进行的，正在进行的或已交付的实现全部废除，重新来」。每条写"为什么/适用条件"，与 F-67~F-72 同体例。

- **F-73 可循环四段流水线（本铁律主干）**：功能要求存在但**无具体规格**时，禁止直接派写码。流程分可循环四段：①**规格设计**：规格设计代理产出 **≥2 份**候选规格，每份都必须是"最最符合"的强候选，禁止交凑数弱稿（各含尺寸/色值/状态/边界/验收判据，硬内容见 F-77）；②**独立验收选型**：独立验收代理审验全部候选，**允许全部判低**，选出最符合全 App 的一份（写选型理由与淘汰理由）；③**判低回炉（双换）**：若验收代理**全部判低**，则**设计代理与审验代理两者都换新**（不是只换设计代理）：由新设计代理重出 ≥2 份强候选，由新审验代理重审，回到②循环，直至选出一份；④**写码**：另一写码代理按选中规格走正常流程（写→独立验收→push→CI→CI 后复验）。废除范围同时覆盖**在飞与已交付**两类：一旦发现某功能**在飞**但无具体规格，立即**停工并作废**（不是让它做完再作废），已写代码标作废、不许继续合入，回到第①段重新设计规格。为什么：无规格直接写码＝让写码代理同时当设计师，规格漂移不可回源（本轮已发生"凭记忆转述规格导致两张卡返工"）；允许全部判低＋回炉循环，防止弱稿被"矮个子里拔将军"；同一审验代理连审两轮会锚定自己上轮判低理由，换审验才能重新看全 App 契合度；在飞单若放任做完，作废成本随代码量线性放大。适用条件：只要"功能要求"里缺尺寸/色值/状态/边界中任一项且文档无出处的，都算无规格；**仅当"全部判低"触发双换**；若只是选出了但有一份贴近，仍走正常选型；在飞、已交付一体适用。
- **F-74 三段必须三个不同代理 + 判低留档**：设计规格的代理**不得**同时做验收选型，验收选型代理**不得**参与写码；三者都要验收报告落盘（设计稿、选型结论、实现验收各一份）。被判定低的规格文档**不删、标作废留档**：写明为什么低（缺哪几项 / 与全 App 哪处冲突）；新一轮规格必须写明"相对上一轮被否稿改了什么"，防止重复踩同一坑。每轮必须留下**流程审计四要素**：设计代理 id / 审验代理 id / 是否触发了双换 / 本轮判低份数与理由；缺项即视为流程未走完。为什么：自评代验收会让"最符合全 App"退化成"最省事"；删稿会丢掉判低理由，下一轮无从避坑；四要素留痕才能复核双换是否真执行、判低是否有据。适用条件：一次功能只走一条链，禁止一人跨段；F-73③ 回炉循环中本口径同样适用，双换轮次须记清新两代代理 id。
- **F-75 废除的语义与顺序（两档）**：不合规实现分两档处置，**两档都不要"为了清干净而直接删代码"**。①**在飞档**：立刻冻结（停止派单/停止合入）、代码就地标作废 KDoc、从分支上不再推进，留在原地等新链路替换，不做物理删除；②**已交付档**：标作废→重做→新链路验收通过→再物理删除，顺序必须遵守既定铁律"新逻辑先接好再删旧"：先标记作废（问题清单 + 契约索引 + 代码文件头 KDoc 作废声明）→ 新链路交付并验收通过 → 再物理删除旧实现。为什么：直接删会让 App 中途无可用实现、也可能删掉别处仍在引用的东西；在飞单提前删代码则会丢失已写部分可参考的事实交底。适用条件：任何"重做"都适用，包括卡片/图标/图标启动图这类已验收过的。
- **F-76 作废的判定口径（谁能免于废除）**：判定对象集合＝**已交付 ∪ 在飞**；**只有**"功能要求逐项都能在指定规格切片里找到原文出处、且实现与原文一致"的实现才算合规；"参照了某文档、细节靠代理补充"的一律判不合规。在飞的按"缺规格即停工"（F-73/F-75 在飞档），已交付的按"缺规格即作废重做"（F-75 已交付档）。为什么：本轮卡片 12 类、图标 77 有 `切片-25`/`切片-24` 原文支撑，属合规；而"App 图标/音效/分享卡四背景"这类只有方向没有具体规格的，属不合规；适用条件：判定必须给"要求项 → 原文出处 文件:行"的对照表，给不出出处即不合规。
- **F-77 规格候选的硬内容**：每份候选规格必须含 ①目的与用户可感效果 ②尺寸/间距/圆角/字号 ③色值（引用既有 token 名，禁新造裸色值）④全部状态（默认/悬停/按下/加载/禁用/空/错误/离线）⑤边界与降级（无数据/断网/超长文本/低帧率/无权限）⑥与其它模块的接口 ⑦逐条可测的验收判据 ⑧与全 App 既有资产的一致性对照：逐项写"复用 X token / 不冲突 Y"，对照既有 12 类卡片、77 图标、12 色 token 色板。缺②③④⑤任一项的候选规格直接判不合格，不进选型；缺⑧一致性对照的，验收代理有权判低（F-73③ 回炉）。为什么：本轮事故的返工都出在这几项缺失；不对照既有资产会新造第二套色板/卡片样式，与全 App 串味。适用条件：含视觉的新功能必带②③⑧，纯逻辑功能至少要④⑤⑦。
- **F-78 三段流水线的门禁化**：任何"实现/交付类报告"必须首行给出**规格锚点**（逐字：`规格：docs/…`）与**选型结论锚点**（`选型：docs/验收-选型-….md`）与**实现验收锚点**（`验收：docs/验收-….md`），三者缺一即视为未走流水线，门禁 FAIL。选型锚点指向的选型文档必须含**明确的"选中第 N 份 + 判低份数与理由"**；只有"看过了/差不多"、没有选型结论的一律 FAIL。若选型文档出现"全部判低"结论，则**必须**同时能查到下一轮的设计代理/审验代理记录（新的 `docs/规格候选-*-v2.md` 与新的选型报告），否则 FAIL——防"判低了就悄悄按旧稿开工"。例外口径：若报告正文写明"该功能无规格→已按 F-73 退回设计"（退回第①段），则该报告不要求 `规格：` 锚点，但必须显式带退回声明；既无 `规格：` 锚点、又无退回声明却声称新功能实现的，FAIL 并提示应退回第①段重新设计规格。为什么：靠人记流程必然漏（F8 已证明回执文字不可信）；选型无结论等于第二段空转，写码代理拿到的仍是口头方向。适用条件：门禁只校验本次 `git status` 新增/修改的这类报告，历史留档不追改。

## 十七、并发机制接线与分档（2026-11-24 台账空转事故复盘）

> 来源：`docs/复盘-并发机制空转-台账未接线.md`。事故：台账 14:23 冻结、HEAD 23:08，当晚派出 20+ 单零登记，门禁 ⑥/⑨ 恒绿；另一漏改：用户 14:21 原话三档配比只落地最低档，后两档被摘要吞掉且"待升档"状态未入库。每条写"为什么/适用条件"。

- **F-79 派单台账是并发的唯一事实源**：派单当轮必须登记 `docs/派单台账.md`（一行一代理，状态列严格写 `在飞` 才能被 ⑥/⑨ 正则统计）；create_agent 之后不登记，⑥/⑨ 就读不到真实在飞数，并发约束等于不存在。为什么：事故当晚台账冻结 8h45m，在飞计数恒为 0，门禁每次必过，同期实际派出 20 余个代理；规则只落文档+脚本、未接进派单动作链路，机制即被架空。适用条件：所有写码/验收/选型/审计/复盘类派单；纯咨询问答不在此列。
- **F-80 台账新鲜度门禁**：`data_scripts/check-dispatch-ledger.py`（门禁 ⑯）机械判：HEAD 提交时间比台账 mtime 新 >60 分钟 → FAIL（有提交/派单未登记）；`在飞` 行数超硬上限 → FAIL；台账无当日行 → WARN 不 FAIL。为什么：把"派单即登台账"从靠记忆变成机械判据；60 分钟是登记动作必须在同一轮内完成的宽限，超出即判定被当成"事后动作"漏掉。适用条件：每次 commit / push / 派单前随 rule-gate.sh 跑一遍。
- **F-81 工具预算入派单模板（E10 落地）**：总纲 R3 三份派单模板（规格设计 / 选型验收 / 写码）每份硬写两行：工具预算 ≤40 次（写/修）或 ≤60 次（验收/查），超预算即判失控；独立工具调用必须一条消息内并行发，禁串行单发。为什么：E10 原只写在总纲正文，模板不带预算，派单时预算字段被省略；请求率失控（49 次中位 vs 失控代理 6894 次）才是限流主因，预算必须进模板才会被写进每一单任务书。适用条件：所有新派单；切片超上下文需分段读的，派单书显式上调预算。
- **F-82 并发分档表（用户 14:21 原话落地）**：三档与配比写死在册——档 1（基线）`5 = 4 写 + 1 查`；档 2 `6 = 4 写 + 2 查`；档 3（上限，硬顶）`8 = 5 写 + 3 查`。升档条件：连续 3 轮（每轮 ≥10 次派单）实测请求率中位 < 6 次/分钟且期间 0 次 429/限流 → 升一档；降档条件：出现 1 次 429 或连续两轮请求率中位 > 12 次/分钟 → 立刻降一档并落快照（快照沿用 watchdog 现有格式）。档位状态唯一事实源＝`docs/并发档位.md`（单行：`当前档位：N（写 a + 查 b）；最近升降档：<日期 原因>；下一档条件：…`），⑨ 与调度层都读它，禁在脚本里写死配比；`load1 ≥ 1.5` 饱和仍降到档 1 写槽减半（2 写 1 查）。为什么：用户原话"能提到五个就按 4 个写一个审查来，提到 6 个就按 4 个写两个审查来，提到八个就按 5 个写 3 个审查来"，即按实测能到几档就用几档；旧队只落最低档，"待升档"状态未入库，新会话只看到 5，永久停在基线。适用条件：档位升满 3 后不再上调（8 是硬顶，避免再触发限流）；台账暂无写/查分列，⑨ 先判总数 ≤ 档位总数，写查分判待台账补列。

- **F-84 有效并发＝双约束取小 + 槽满不丢单 + 四杠杆**（2026-11-24 用户令「根据实际约束，在不触发限流情况下把并发尽可能提高，并修改机制」）：
  ① **有效并发 = min(框架硬顶 F, 请求率档 N)**。F 实测＝**5**（框架硬顶、无队列：第 6 个 `create_agent` 直接返回 `sub-agent concurrency limit reached. You already have 5 running sub-agent(s) (limit: 5, configurable). THIS sub-agent was NOT created, and there is NO queue — the framework never defers creation`，丢了就是丢了；只有平台放宽才动 F）；N 按 F-82 分档表实测（裕度 5~8，旧队实测 5~8 个轻代理请求率安全）。当前 **N ≥ F**，机制按 **F=5 满槽 = 4 写 + 1 查** 跑；F-82 档 2（6 = 4 写 + 2 查）/档 3（8 = 5 写 + 3 查）**保留为"F 放宽后自动生效"的预留档**，档位文件必须写明 `预留（受 F 钳制）`（禁写"暂缓"，防后档再丢进虚空——⑰ 已管三档在册）；请求率档在 F=5 下永远不会成为约束，旧 E10/E11 的请求率杠杆是保险不是瓶颈。`load1 ≥ 1.5` 饱和照旧降到 2 写 1 查。
  ② **槽满不丢单（本轮最关键机制改动）**：`create_agent` 返回并发已满**不算失败**，必须立刻把该派单**原样**写入 `docs/派单队列.md`（列：序号 | 派单标题 | 创建时间 | 状态 PENDING/RUNNING/DONE | 依赖 | 文件域），不许改成"以后再定"、不许合并进别的派单、不许降级缩小范围；任一槽释放（子代理完成/终止）→ **立即**按队列顺序取队首重派，禁止空槽待料；PENDING 项存活 **>1 轮调度**（≈一次 `wait_agent` 返回）即视为丢单，门禁 ⑱ FAIL。
  ③ **四杠杆（F=5 内把吞吐顶满）**：a. **同域串行多件**——一个代理承担同一文件域内 2~3 件相邻小任务（串行做，保文件域互斥），跨域绝不合并；b. **零发现成本派单**——派单自带绝对路径锚点、已知坑、验收判据，避免子代理重复探索（每代理省 3~10 次调用＝省请求率）；c. **wait 不 poll**——调度层用 `wait_agent` 阻塞，禁 `peek_agent_progress` 反复短轮询（空转烧请求还拖慢槽周转）；d. **长任务异步 + 短任务填缝**——长任务先派，槽一空立刻补队首短任务，禁止"等一个长任务完成再派下一个"。
  为什么：实测瓶颈是框架槽位而非 API 请求率；无队列意味着满槽即丢单，必须由仓库队列兜底。适用条件：F 随平台放宽时重算 min(F,N)；依赖未解除的 BLOCKED/PENDING 不计丢单；队列与台账分工＝台账记已派代理在飞状态，队列记待派/待补派单。旁证：`落文-全量交接文档.md:15`「子 agent 并发上限 5，完成一个补一个」。

- **F-85 前置设计费（锚点卡）**（2026-11-24 用户令「那你换吧」；原话语境：「新铁律本身会拉长单包、压缩返工——上一批 12 张卡片里有 2 张因"凭记忆转述规格"返工，这类成本今后应转成前置设计费」）：
  ① **事实依据**：12 类卡片中 **2 张**（BookCard、TopicCard）返工，根因＝执行代理**凭记忆转述规格**（分享卡三背景 lerp 比例 `0.35/0.12/0.10` 记岔），不是能力问题，是派单没给可逐字引用的原文锚点。成本对比：一张锚点卡 ≈ 轻代理 5~10 分钟；一次返工 ≈ 写码+验收+CI 复位 30~60 分钟 + 重读上下文——锚点卡是"用小钱买断返工"。
  ② **锚点卡（前置设计费）**：派写码单之前必须先产出 `docs/锚点/<缺陷号>-<主题>.md`（≤30 行），三件套：a. 逐字原文引文（带 `文件:行`，从切片原文复制，禁改写）；b. 参数表（数值/单位/来源 token 逐项列）；c. 可测判据（P1…Pn + FAIL 条件）。
  ③ **无锚点卡不许开工**（门禁 ⑲）：写码类回执必须含"锚点卡路径 + 从锚点卡逐字抄的参数段（标明行号）"；验收类回执必须**逐字对照锚点卡**验收，禁止"按记忆里的规格验收"。
  ④ **适用范围与豁免**：仅对"有规格来源的功能"生效；无规格功能走 F-73 三段流水线（候选规格本身即锚点，不重复付两次费，`验收-选型-*` 同属 F-73 链豁免）；纯机械改动（改一行 import、补一个 `strokeLineJoin`）豁免，豁免须在派单里写明"机械改动"。
  ⑤ **记账验证净收益**：`docs/台账-前置设计费.md` 每次返工记 5 列（缺陷号 / 根因类 / 返工实际耗时 / 若前置设计预估耗时 / 是否本可避免）；**若某类返工率 < 5%，该类锚点卡可降级为"参数表版"（≤10 行）**——用数据决定投入强度，不搞一律加码。
  ⑥ **承认代价**：F-85 会拉长单包（设计与写码分离，多一次派单和一次收单），这是**已知成本**，不许把"单包变长"当失败；判成功看返工率与 CI 连红次数下降。
  接线：与 F-73 分工——F-73 管"没规格怎么造规格"，F-85 管"有规格怎么把规格递到执行者手里不丢字"，两条不合并；锚点卡由**设计/查证代理**产出，写码代理不许自己写锚点卡（F-74，自己做锚点＝自证规格，等于又回到凭记忆）；已交付但无锚点卡的功能，返工前先补锚点卡，不许直接派修（F-75/F-76）；R3 三份派单模板带强制字段 `锚点卡：docs/锚点/<缺陷号>-<主题>.md（无则先派查证/设计代理）`。

- **F-86 缝合怪清理**（2026-11-24 用户原话「把清理缝合怪的工作也要写进铁律机制」）：
  ① **六种可机械判定形态**（判定命令与豁免条件逐条见 `docs/铁律-缝合怪清理.md`）：1. 双轨并存——同能力新旧两套实现都活着且主链路同时可达；2. 规格一套代码另一套——切片要求 A 技术栈/数据结构，代码是 B；3. 兼容层残留——`*Compat/*Legacy/*Old/*V2/*_old*` 仍在主链路被调用且新实现可用；4. 职责混装——单文件跨 3 个以上域或行数超阈（阈值依据普查分位数：1368 个 kt 文件 p95=565、p99=1196，≥600 候选、≥1200 重点）；5. 贴皮实现——只改外观不改结构，旧逻辑+新皮肤靠 flag 切换；6. 半成品分支/文件残留——`wip/*` 未合并、标 FAIL 未收口、`@Deprecated` 仍被调用。框架 API 自带的 `Deprecated in Java/Drawable` 注解不算形态 6。
  ② **四步清理工序（写死不许跳）**：a. 普查建档 `docs/台账-缝合怪.md`，字段固定——位置（`文件:行`）/ 形态 / 成分 / 风险 / 处置（拆/合/迁/删/留+理由）/ 状态（待处理/处理中/已清/留档）；b. 定序——阻断交付 > 影响性能 > 影响观感 > 仅整洁，同序按影响面排序；c. 执行顺序硬约束——先接新实现（可运行、被调用）→ 切所有调用点 → 组合验收与单测过 → 再物理删旧；禁止先删后接、禁止留旧格式兼容层兜底、禁止 `@Suppress` 掩盖；d. 回填证据——已清条目附证据三件：`grep -rn "<旧符号>"` 0 命中、CI run 绿、受影响组合验收/单测通过。
  ③ **机械门禁 ⑳**：`data_scripts/check-frankenstein.py` 扫 `app/src/main/java` 与 `app/src/main/res`，自动判形态 1/3/4/6 中可机械判定部分，输出五类命中计数 + 逐条 `文件:行` + `FRANKENSTEIN: PASS/FAIL`；形态 2/5 由台账人工定级，门禁反查在册。豁免反查：任何"留档/已清"必须能在台账找到对应条目，代码或台账自报豁免而无条目者仍判 FAIL（防自己给自己豁免）；`--selftest` 造夹具跑通 FAIL/PASS 两条通路后自删。
  ④ **为什么**：缝合怪是 CI 红灯、口径漂移、返工的三重源头；它还让"规格逐字对照"失效——代码里根本没有规格那套实现，验收无从回源。与铁律 57 分工：57 防"一个代理做多件"（横向打包），本条防"一件里拼多套"（纵向双轨）。
  适用条件：扫描范围限主源码与主资源；`app/src/test/**`、`.github/`、F-88 巡检脚本域不在本闸；为兼容旧数据必须保留的解析层可留档，但台账必须写明理由与下线条件。

- **F-88 规格流入与完整性持续巡检**（2026-11-24 用户原话「现在需要一个新机制，就是不断的去检查完整性，而后续我又会有新的要求规格填入，你要解决一下」）：
  ① **持续巡检**：`data_scripts/check-spec-flow.py` 做四向双向对齐——切片文件↔登记册行 / 登记册行↔问题清单缺陷号 / 登记册行↔契约索引模块条目 / 登记册行↔派单踪迹（台账或队列）；任一断裂判 FAIL 并逐条打印漏项；门禁 ㉒ 随 `rule-gate.sh` 在每次 commit / push / 派单前跑，每轮调度开始时总控先跑一次。
  ② **新规格入库流水线**：用户贴入的新规格必须先走 `docs/流程-新规格入库.md` 六步——原样落盘 → 自包含切片 → 登记册连续编号 → 立项定档位/缺陷号/DoD → 入队注明文件域互斥 → 巡检 PASS；巡检不过不许把该规格当作「已入库」。
  ③ **禁止跳过登记直接派写码单**：未切片、未登记、未立缺陷号的要求，不许直接派写码代理（与 F-73 三段流水线、F-85 锚点卡同口径，防贴皮与凭记忆转述返工）。
  为什么必须自动：完整性靠人「想起来才查」必然漂移——旧 `spec-check.sh` 不反向校验切片↔登记册，切片 21~25 五片漏登记长期无人发现；机械巡检把「每片有登记、每号有清单、每模块有索引、每立项有踪迹」变成提交前硬门禁，不靠记忆兜底。为什么禁跳过登记直接派单：没有登记行就没有缺陷号、档位、DoD 与原文锚点，写码代理只能凭记忆转述规格（12 类卡片中 2 张返工即此根因），验收也没有逐字对照对象。
  适用条件：巡检只判结构对齐，不替代 L1~L3 分级验收；治理项 / 内部新立号 / 归档吸收 / 已否决 / 已验收行按脚本豁免口径不要求活踪迹；积压在问题清单在册的 🔴/🟡/🟢 项不算悬空立项，队列只装调度批次。

## 十八、通用工作模式与规则总账机制（2026-11-25 用户令）

> 来源：用户 2026-11-25 原话「我不再靠记忆补规则，改成总账加门禁两条腿，这个也弄成一个工作模式的规则」「我说的是工作模式，是门禁加总账的核对，可以应用到任何场景」「不是当他不存在，是要你特殊处理」「这么多规则你都漏掉了，再回去找找，清理一下」。

- **F-89 门禁+总账+溯源工作模式（通用，非规则专用）**：
  ① **三件套定义**：总账＝唯一事实源（结构化、脚本可读、单点权威、禁口头禁记忆）；门禁＝机械判据（必须双向自测：违规必 FAIL、合规必 PASS，`--selftest` 造夹具跑通两条通路后自删）；溯源＝逐字锚点（`文件:行`/run_id/sha256，禁转述）。
  ② **适用范围**：任何需长期维持的状态——口径、规格、任务、代码状态、进度、验收、事实、资产、基线、时间预算。
  ③ **缺件特殊处理（不是当它不存在）**：缺哪件登记 `docs/台账-三件缺项.md`（缺哪件/责任/期限/补齐前效力限制/状态），默认一轮内补齐，逾期升级阻断；补齐前限权——缺门禁的规则不得用于验收判定、缺总账的状态不得作为决策依据、缺溯源的结论不得引用；同一事项二次登记缺件即 FAIL。
  ④ **三条特殊通道**：人判门禁（审美类，独立验收代理+第二人复核，判据落成可截帧/可量像素/可单测硬指标）；历史豁免（一次性留档报告标"不进任何新判定"，门禁只校验本次新增/改动产物）；外部门（真值在 GitHub/用户真机，改为"取外部真值比对"）。
  ⑤ **既有实例**：派单台账/规格登记册/契约索引/作废冻结台账/前置设计费台账/问题清单三件齐备；观感基线缺门、组合验收矩阵三缺、空转盘点缺门、CI 转绿登记半缺门，逐条见 `docs/台账-三件缺项.md`。
  ⑥ **落地节奏**：新规则进门四步＝原话落盘 → 入账 → 写门禁 → 双向自测 → 才允许派单。
  为什么：靠记忆维持的状态必然漏，今晚已证三次（三档配比只落最低档、台账冻结 8h45m 在飞计数恒 0、切片 21~25 漏登记长期无人发现）。适用条件：本模式套用于一切跨轮交接的长期状态；一次性当场结论不强制入账。
  接线：总账 `docs/规则总账.md`；冲突裁决 `docs/规则冲突清单.md`；模式条文 `docs/工作模式-门禁总账溯源.md`；门禁 ㉓ `data_scripts/check-rule-ledger.py`（总账结构/编号覆盖/冲突裁决/缺项逾期/否决串裸奔）、㉔ 同脚本缺项台账判据。
