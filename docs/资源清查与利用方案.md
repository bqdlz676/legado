## 三、资源利用方案

### 1. 定性：本机只做"轻活"，重活全部外置

**本机允许**（秒级、低内存）：
- git 操作（status/diff/add/commit/push/log/show）
- 静态分析：`rg`/`git grep`/`git show`、词法配平 python 脚本
- 小文件文本/数据脚本（流式读，不整读大文件）
- ImageMagick 小图（图标 1536 以下）处理
- curl 拉 CI 状态与日志（只 grep 错误行，不整份下载）

**本机禁止**（会打满 2 核 / OOM）：
- gradle / kotlinc / assemble（铁律 30、88，双保险）
- LLM 本地推理（无 GPU、4G 内存跑不动）
- 大图批量渲染、大数据一次性载入

### 2. 编译/单测/出包：100% 走 GitHub Actions

GitHub Actions 免费 runner = 4 核 / 16G / 有网络，远强于本机。落文已钉死"云端 CI 编译"，继续即可，**不因本机盘大就试图本地编译**。

### 3. 并发策略：2 核 → 硬上限 2 个代理

- 原"满编 5 槽"在 2 核机器上不成立（5 个代理同时 grep/python 就会互相抢 CPU，叠加失控代理即打满）。
- 定案：**落文在飞代理 ≤ 2**（建议 1 写 + 1 验，或 2 写；重扫描串行）。
- 与铁律 74（负载高降到 2）、铁律 86-89（限流防护）一致，并把它从"临时降"升级为**本机默认值**。

### 4. 静态扫描加速：用 rg / git grep，别用 find+grep

- `rg` 已装，全仓扫比 `grep -r` 快一个量级、CPU 更低。
- 大文件扫描用 `git show <sha>:<path>` 定向读，不扫工作树。
- CI 日志只 `curl → grep 'e: '`，超过 30 行 `head`/`cut` 截断（铁律 11 §4 已有）。

### 5. 磁盘纪律（10TB 很够，但别堆垃圾）

- 落文中间产物（CI 日志、`/tmp` 校验脚本、下载的 APK、`models_tmp` 之类）用完即清。
- `/tmp` 当前 33M（phantomjs 23M 等），可安全清理。
- 备份（zip+bundle）属用户要保留的，不删。

### 6. 把"重数据/重渲染"迁移到 CI（可落地优化）

本机 2 核跑得慢的重活，改成 GitHub Actions 的一个 job，产物上传 artifact 或 commit 回仓库：
- 图标渲染 `icon_v/apply_icon.py`（PIL 批量生成 mipmap）
- 数据批量生成脚本（字典/人物/纪年/图层）
- 词法配平、双口径删资源扫描这类纯 CPU 静态检查，也可挂 CI 每周跑一次。

> 收益：把 2 核机器从"偶发重活打满"里彻底解放，只剩秒级编排；CI 4 核白嫖且可并行。

### 7. 跨项目隔离（同机多项目共存）

- 落文只动 `legado/` 与它自己的 `docs/`、`backup/`。
- 用户的 AI 模型/知识库 APK 一律只读不碰；若要跑本地大模型推理，建议外置云 GPU 或用户本地机器，本机 2 核 4G 无 GPU 是硬瓶颈。

1. 落文并发硬上限降为 **2 代理**（写进铁律，替代"满编 5"）。
