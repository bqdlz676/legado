## 二、四条判据实现口径与既有边界

- 判据① PENDING 悬挂：队列主表 PENDING 行创建时间早于当前 30 分钟以上，且台账无对应 RUNNING/DONE 记录即红并点名队列号（`::run` 判据①，快照 :298-309）；台账在飞/收口词表见 `::ledger_done_ids`（:124-138），待派/待验/作废/待裁不算收口记录。创建时间不可解析的 PENDING 行，从严判红（不可证明在 30 分钟内），边界只对 PENDING 行生效。
- 判据② 空转空槽：在飞数 < 5、PENDING = 0、距最近一次派单（队列最新可解析创建时间）或 HEAD 提交超过 30 分钟即红（`::run` 判据②，快照 :311-320）。
- 判据③ 调度层休眠：只取本轮活跃控制器（轨迹 mtime 最新的 o_/m_ 目录，`::active_controller`，:178-195）。「本轮」两层收窄口径，均在 `::scan_controller_sleep`（快照 :198-268）：(a) 行级锚定——以轨迹里最近一条 `role=user` 消息为界，只扫其后的 tool_calls，user 之前的挂起属上一轮留档跳过并留 INFO 痕；轨迹一条 user 行都没有时整条从严按本轮判定（:225-231）。(b) 接续过滤——只认本轮最后一次工具调用上的挂起，其后再有任何真实工具调用，即视为被工作接续的历史留档跳过（:254-267）；挂起若是当下末条调用仍判红，仅 tool_result 不算接续。命中三类：`wait_agent` 任何一次调用（:238-239）；`Wait` 工具 time/timeout/timeout_ms > 60 秒（:240-246）；Bash `sleep <秒>` > 60 秒（:247-252）。只解析 JSON tool_calls 真实调用，Read 到的脚本文本里出现字样不算。
- 判据④ 空集不可判定：队列主表 0 行 / 台账 0 行 / 轨迹目录不存在 / HEAD 取不到，任一即红并写「输入为空不可判定」（`::run` 判据④，快照 :279-287；固定文案 `::EMPTY_MSG`，:81）。

边界（脚本头注 `:20-38` 写死谁优先）：

- ㊹ `check-dispatch-compliance.py`：RUNNING 与轨迹一致、僵尸 RUNNING、在飞超时归它；本项不复核在飞代理轨迹新鲜度。
- 57 `check-slot-full.py`：有 PENDING 而槽不满归它；本项判据②只在 PENDING = 0 时空转触发，两者触发条件互斥，同一行不重复计红。
- ㉙ `check-no-idle.py`：HEAD 时间戳停滞归它；队列悬挂/空转/轨迹休眠归本项。
- ㊳ `check-agent-timeout.py`：单个在飞代理 15/60 分钟熔断归它；本项不算单个代理时长。
- ㊾ `check-vacuous-pass.py`：静态扫描检查器空集 return 0 的假绿结构；本项判据④是其运行态同族落地。
- ㊿ `check-no-wait-rule.py`：规则文本残留 wait_agent 条款归它；本项扫真实轨迹行为。
- 子代理 s_ 前缀轨迹不在判据③范围（§17 适用条件：子代理内部允许阻塞式调用）。

## 三、规格三反例结论（docs/待做-主AI空等门禁.md:29-31）

1. 阈值 30 分钟改 5 分钟，会不会把子 AI 正常跑 10 分钟误判成空等：不会由本项误判。判据①只看 PENDING（未派/台账无在飞记录），不看 RUNNING 子代理；判据③只扫控制器轨迹；在飞子代理跑多久归 ㊳ 15/60 分钟熔断，不进本项任何判据。但 5 分钟线会误杀调度层正常短间歇——派单间隙、等子代理首轮回执、等 CI 回执都可能落在 5 分钟内，判据②会把正常节奏误判空转。结论：30 分钟保留；子代理 10 分钟不受本项阈值影响。
2. 轨迹路径在别的机器/别的会话下不存在时为什么必须判红而不是跳过：跳过等于把「证据缺失」表述成「合规」，与 ㊾ 空集假绿同族；没有轨迹就无法证明主控未休眠，放行即假绿。故判据④判红并写「输入为空不可判定」，待轨迹证据补齐再判，不静默跳过、不 continue-on-error。
3. 与 ㉙ 停工守卫口径冲突（一个看 HEAD 时间戳、一个看在飞与 PENDING）时以谁为准：HEAD 时间戳停滞归㉙；队列悬挂/空转/轨迹休眠归本项。两门禁结论打架时各自报红、互不覆盖；人工裁决以外部可观察的队列与轨迹事实优先于单一 HEAD 时间戳（HEAD 新鲜可能只是被无关提交顶新，队列事实不会骗人）。

## 六、二阶三阶影响（B3）

- 直接效果：g60 在 blocking 位拦截四类主控空等——悬挂 PENDING、空转空槽、末条挂起、空集输入。
- 二阶连带（误红方向）：接续过滤把判据③从「本轮曾等过一次」收窄为「此刻在等」，历史挂起不再压门禁，commit/push 不会被一条旧 sleep 永久卡死；代价是③不再为「本轮历史等待」背书，长期静默改由判据②兜底。② 与㉙ 在 HEAD 停滞区可能同一条事实两边各红一次，分工已在脚本头注写死，各自报红、互不覆盖。三档边界夹具 A/B/C 对应三层留档口径（旧控制器不选中 / user 前留档 / 被接续留档），后续改轨迹解析须同步这三处。
- 三阶后果（放宽与调参的传导）：若接续过滤再放宽（如按时间戳衰减、把琐碎工具调用也算接续），长期静默可能从③漏到②；②只取队列行与 HEAD，不看轨迹活动，该共有盲区登记在 N2 与验收单 A1。若①② 的 30 分钟阈值被调松，空等停摆会在用户不可见状态下多停留一个阈值周期；阈值是模块级常量且带注释，调参必须同步本报告反例节。若前缀白名单漏放新控制器族，③ 会扫不到真控制器而落到「轨迹 0 条」空集红，方向是从严不漏放，但会误报。
- 维护成本：新增「末条工具调用」一个口径概念；轨迹解析链路上锚定、接续、前缀白名单三处耦合，改其一须复核另两处。

## 七、跨领域同类对照（B5）

对照外域三类同类空转/挂起检测机制，写清采纳面与不采纳面。

1. CI watchdog / 任务队列 liveness probe（K8s liveness probe、Celery heartbeat 一类）：周期性探活，无心跳即判死重启。采纳面：判据②与之同族——30 分钟无新派单/提交即空转判红，相当于调度层的心跳超时。不采纳面：liveness probe 靠外部常驻周期轮询进程状态；本项门禁是事件后离线扫描轨迹与队列，不另起常驻心跳进程，避免在调度层之上再加一个监控自己空等的递归节点。
2. 分布式 leadership 选举（Redis/ZK lease、Kubernetes leader lease 一类）：靠租约心跳加任期过期判定主节点失联。对照取舍：本项不引入租约/任期概念——会话内控制器唯一性由 `::active_controller` 取 mtime 最新的 o_/m_ 目录近似，不做选主；主备切换不是本仓场景。若未来出现多控制器并行，需补任期/租约校验，当前判据③只审单条活跃轨迹。
3. 看门狗喂狗（hardware/software watchdog）：必须定期喂狗，久不喂即复位。接续过滤与喂狗表面相反，实则同构：被接续的旧等待放行，不等于没喂狗——其后的真实工具调用就是喂狗动作；只有末条调用仍是挂起，才是久未喂狗。该对应关系写在 `::scan_controller_sleep` 接续过滤注释（快照 :254-259）。

豁免说明：本单为机制 Python 门禁，无组装/组合矩阵对照面；以上对照仅用于取舍定位，不引入外域依赖。

## 十二、口径修订（2026-11-27，调度层实测触发）

- 问题（已处置）：行级锚定后，「本轮」可能持续数小时（没有新 user 指令），一次历史 sleep/wait 会永久判红并把 commit/push 永久卡死。实测触发：调度层一次 `sleep 100` 之后判据③ 全轮变红，且无任何机制可在本轮内清除。
- 修订（已修）：`scan_controller_sleep` 尾部加「接续过滤」——只认本轮**最后一次工具调用**上的挂起；若其后还有工具调用，视为被真实工作接续的历史留档，按留痕跳过。判据③语义回到「此刻是否在空等」；长期空转仍由判据②（30 分钟无新派单/提交）兜。
- 为什么这样定：判据③原本的红点是「调度层正在挂起等待」，不是「本轮曾等过一次」；两条判据互补，不重复。
- 适用条件：本过滤只对**已结束**的挂起生效；若挂起是当下最后一次调用，仍判红并点名行号。
- 证据（已闭环·已验证）：`--selftest` 边界夹具 C（挂起→后接 `Bash echo work` → PASS，留痕「已被其后工具调用接续」）；2026-11-27 本棒基线实跑 `IDLE-EMPTY: PASS`，留痕「挂起 3 次已被其后工具调用接续…最后工具调用行 @442」。轨迹行号是快照，随行轨迹增长漂移，回源以 `::scan_controller_sleep` 符号为准；次数以当次实跑为准。
- 验收状态（已闭环·已验证）：本修订已经独立验收单 `docs/验收-复核-主AI空等门禁.md` 项 1/项 5 按新口径复验通过；残留盲区登记在该单 A1/A2/A5。
