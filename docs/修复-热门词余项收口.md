### 2.2 处置选择与理由

处置二选一的裁决：**删除字段，binder 改为 `observeHistory()` 内的临时构造对象**，不改为显式持有 + 手动取消。

- 取消语义已由作用域保证：两路收集协程在 `SearchHotBinder.start()` 内 `scope.launch(dispatcher) { ... }`，生产侧传入 `viewModelScope`（`InkSearchViewModel.kt:266`）。`viewModelScope` 是 androidx 标准作用域，`onCleared()` 调 `super.onCleared()`（`InkSearchViewModel.kt:158-161`）时随 VM 生命周期取消，子协程一并取消；binder 不需要 VM 另存句柄去手动 `cancel()`。
- hot 不依赖该字段：热门档由 binder 内部收集循环经 `publishHot` 原子回填到 `_uiState`（`SearchHotBinder.kt:78-84`），VM 从不回读 binder 实例。删字段不触碰热路径，也不存在「hot 依赖字段所以不能删」的约束。
- 不引入 `binder.cancel()` / `onCleared` 显式收口：binder 当前没有也不需要独立于作用域的取消 API；再加一层手动取消句柄是冗余抽象，两路收集器的取消已经被 `viewModelScope` 覆盖（见第六节二阶推演）。

## 三、N3 补断言：单条删除后热门行同步剔除（两种情形）

### 3.1 情形一：被删词来自历史档（HISTORY），删后从热门行剔除

用例：`removing a history-only word drops it from the hot row`（`SearchHotBinderTest.kt:113-144`）。

- 前置构造：`timeFlow = [春秋, 左传]`，`usageFlow = []`。频次路为空，resolver 落第二档 HISTORY，`hot == history == [春秋, 左传]`。选词「春秋」刻意不在 `SEED_KEYS`（`SearchHotResolver.kt:48-51`：论语 / 诗经 / 楚辞 / 庄子 / 左传 / 孟子 / 老子 / 尔雅 / 尚书 / 礼记）内，删后不会被种子兜底重新带出，剔除结论不会被兜底词表掩盖。
- 删词动作：`timeFlow.value = listOf(keyword("左传"))`（`:136`），等价 DAO `delete(SearchKeyword("春秋"))` 后时间序 Room 流重发「少了一条」的新快照；频次路本就为空，不补发。
- 断言清单（谓词等待点是收敛手段，不计入末尾断言条数；条数只数 `assertEquals` / `assertFalse` / `assertTrue`）：
  1. `:130` 等 `hotSource == HISTORY` 收敛；`:131` `assertEquals(HISTORY, before.hotSource)`。
  2. `:132` `assertEquals(listOf("春秋", "左传"), before.hot)`。
  3. `:133` `assertEquals(listOf("春秋", "左传"), before.history)`。
  4. `:138-139` 等新快照收敛：`history == [左传] && hotSource == HISTORY`。
  5. `:141` `assertEquals(HISTORY, after.hotSource)`。
  6. `:142` `assertEquals(listOf("左传"), after.hot)`。
  7. `:143` `assertFalse(after.hot.contains("春秋"))`——被删历史档词不得残留在热门行。

### 3.2 情形二：被删词与种子兜底重合，删空后档位必须记为 SEED

用例：`removing last history word overlapping seed keeps fallback source marker`（`SearchHotBinderTest.kt:146-175`）。

- 前置构造：`timeFlow = [论语]`，`usageFlow = []`。「论语」是 `SEED_KEYS` 第 0 位，先以历史档出现；此时 `hot == [论语]`、`hotSource == HISTORY`。
- 删词动作：`timeFlow.value = emptyList()`（`:168`），等价删空最后一条历史；频次路本就为空，两路皆空。
- 断言清单：
  1. `:163` 等 `hotSource == HISTORY`；`:164` `assertEquals(HISTORY, before.hotSource)`。
  2. `:165` `assertEquals(listOf("论语"), before.hot)`。
  3. `:170` 等 `hotSource == SEED`。
  4. `:171` `assertEquals(SEED, after.hotSource)`——删空回落兜底，档位标记必须是 SEED，不得记成 HISTORY / USAGE。
  5. `:172` `assertEquals(SEED_KEYS.take(HOT_LIMIT), after.hot)`。
  6. `:174` `assertTrue(after.hot.contains("论语"))`——兜底词表仍收录「论语」字样，但来源标记是 SEED 兜底；锁定「词形可以被兜底重新带出，档位不许冒充真实日志」。

### 3.3 反向推演（摘掉哪一环会红）

- 情形一反向：若 binder 时间路漏接 / `start()` 未启动时间收集，`:130` 等不到 HISTORY，`withTimeout` 内超时转红；若删词后快照未随流重发回填，`:139` 的 `history == [左传]` 谓词永不命中超时转红；若回填路径仍把旧词留在 hot，`:143` `assertFalse` 直接红。
- 情形二反向：若删空后 resolver 误把残留历史档标记带到 SEED 帧，`:171` 档位断言红；若兜底词表被写空或截断错误，`:172` 顺序断言红；若来源标记错误降级为 USAGE / HISTORY，`:171` 同样红。
- 两情形刻意分开：情形一锁「历史档词同步剔除」，情形二锁「种子重合词删空后的兜底档位标记」，避免只测一种路径。既有三条断言（USAGE 真实档 / 双空 SEED / 清空回落 SEED）未改未删，断言强度未放宽。

## 六、二阶 / 三阶影响推演

### 6.1 N1 生命周期与泄漏

- 存活持有：删字段后，binder 实例的强引用来自两路 `scope.launch` 协程闭包（闭包捕获 binder `this` 调用 `snapshot` / `publishHot`）。VM 存活期间协程存活，binder 不被误回收；`viewModelScope` 取消后协程结束、闭包释放，binder 随之下一轮 GC 回收。与旧字段持有方案在 VM 存活期内的保留时长等价，作用域死亡后释放路径一致，不新增泄漏。
- 热路径：hot 回填只经过 binder 内部 `publishHot` → `uiState.update`，VM 字段从未参与读取；删字段对收集频次、回填延迟、状态写入路径零改动。
- 冷启：少一个可空字段的实例挂接，分配影响可忽略；`observeHistory()` 仍只在 `attach()` 首次初始化分支调一次（`InkSearchViewModel.kt:57-60`），不产生重复订阅。
- 三阶风险（未来扩展）：若后续需要独立于 VM 生命周期的 binder 暂停 / 重启（例如页面 `pause` / `resume` 也要停订热门流），当前设计没有句柄可用；现状是 `pause` / `resume` 只挂起 `searchModel`，不重建 binder（与改前逻辑一致），该扩展点属于未来批次决策，不在本单预埋冗余 API。

### 6.2 N3 断言对生产行为的约束面

- 两条新断言锁的是流接线层（binder 收集 + 快照合并 + resolver 档位 + 状态回填），不替代 `SearchHotResolverTest` 既有 6 条纯函数断言；resolver 签名与行为零改动。
- 快照语义沿用 `AtomicReference` 不可变快照（`SearchHotBinder.kt:50/:59/:68/:79-80`），单删重发只改一路快照，另一路沿用最近一次值，最坏一帧级陈旧按设计残留（验收判据 3 已登记），本单不扩大修复面。

### 6.3 N4 超时对测试稳定性的影响

- 5 秒超时不改变调度模型：仍是 `Unconfined` 单线程，既有用例的顺序耦合前提（验收 N2，时间路先于频次路启动）未被触动；若后续换成多线程分发器或 `runTest` 虚拟调度器，超时值与顺序耦合需重新评估。
- 超时失败栈会定位到具体 `state.first` 等待点，比挂死在 CI 全局超时更易归因；不存在超时吞掉真实断言失败的路径——断言仍在谓词命中后的状态上逐条执行。

### 6.4 最强反对者复核（反例与边界）

- 反例一：情形一删掉的词会不会恰好也是种子词？已核 `SEED_KEYS` 十词，「春秋」不在其中；若将来种子表扩词纳入「春秋」，情形一的剔除断言会被兜底词表破坏——届时应换一个确定不在种子表内的历史词，该边界已在测试注释 `:117` 标明选词依据。
- 反例二：情形二删空后 usage 路会不会补发旧帧？`MutableStateFlow` 不向新订阅 / 重发未变更值；usage 路初始空表，删历史动作不动 usage 路，快照 usage 恒为空。
- 反例三：谓词会不会命中中间帧误绿？情形一删后谓词同时要求 `history == [左传]` 与 `source == HISTORY`，单路旧帧无法同时满足；情形二谓词等 `SEED` 终态，档位单调回落不回退。
- 反例四：删字段后 binder 会不会在 `start()` 返回、局部引用消失后被提前 GC？协程闭包持有 binder `this`，JVM 可达性分析以 GC Roots（活动协程）为准，不存在提前回收；`publishHot` 内访问的 `snapshot` 为 binder 成员，同被闭包持有。
