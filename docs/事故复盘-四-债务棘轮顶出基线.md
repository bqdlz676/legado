# 事故复盘（四）· 新写码单把债务棘轮顶出基线

> 记录时间：2026-11-26 夜。等级：机制级事故（阻塞交付链）。
> 一句话：一张"做新功能"的写码单交付了一个 731 行的新文件，把 `oversized_warn` 从 50 顶到 51，推送体检当场 FAIL，全队停摆等拆分。

## 一、事实（可回源）

- 产物：`app/src/main/java/io/legado/app/ui/book/read/ink/InkContentEditSheet.kt`，731 行。
- 拦截点：`bash data_scripts/pre-push-check.sh` → `RATCHET: FAIL（债务只许减不许增）`，`oversized_warn 由 50 增到 51`；`GATE` 因此 FAIL，推送被停。
- 阈值出处：`check-frankenstein.py` 的 `LINE_WARN=600`（p95 口径），`debt-ratchet.py` 只做"基线比大小"，不解释阈值。
- 写码方自述：收尾跑了 `check-frankenstein.py`（PASS，因为它对既有/新增都只"提示"不 FAIL）与 `kotlin-syntax-lint`（当时只有 S1~S3，不看行数），**没有跑 `debt-ratchet.py`**。

## 二、损失

- 直接：推送停摆一轮；需要另派一张"只拆不改"的单；拆分期间 CI 红（4 例测试失败）无法先行推送修复。
- 间接：把"修 CI 红"和"还债务"两件本该独立的事串成一条串行链，最慢的一环决定全队速度（本次最慢环是拆分单）。
- 隐性：如果当时选择"上调基线"，会在历史上留下一次债务虚增，后续每轮验收都要多解释一次。

## 三、根因（三层，缺一层都不成立）

1. **机制分层错位**：两个脚本对"超长文件"口径不同——`check-frankenstein.py` 对超长只 `[3] 提示不单独 FAIL`，`debt-ratchet.py` 才把它当硬债务。写码方按守则跑的是"提示级"的那个，看起来是绿的。
2. **派单没给量化上限**：派单只写"做面板，能力覆盖旧页"，没写"单文件 ≤600 行，超了先拆"。写码方按功能完整性写满 731 行，是合理选择。
3. **交付前自检清单缺一项**：守则要求跑三个脚本，但没要求"新增文件行数"这一项，也没有工具在看它。

## 四、处置（已落地）

1. 拆分单已派（零行为变化，只拆文件 + 挪 import；拆完必须 `debt-ratchet` 回到 50 或更低）——债务不走"上调基线"这条路。
2. `kotlin-syntax-lint.py` 新增 **S4**：新增文件 ≥600 行 → FAIL，并在文案里直说"会顶高债务棘轮（先拆再交）"。只判"不在 HEAD 的新文件"，既有 50 个历史超长文件不误杀（反向自测：700 行探针文件被判 FAIL，删除后恢复 PASS）。
3. 写码守则补一条量化上限（600 行，超了先拆再交），并把"跑 `debt-ratchet.py`"从建议改成收尾硬步骤。
4. 台账登记 M-24：两个脚本对"超长"口径不一致，属"机制口径分裂"遗留，待后续统一（合并到 `check-frankenstein.py` 一处出判据、棘轮只读结论）。

## 五、为什么不是"一次偶发"

同一晚已经出现过同构的两次：`check-report-fields` 与 `check-evidence` 对"证据锚点"口径不同；`guard F1` 与 `land` 预检对"删除残留"口径不同（注释被当引用）。共同模式是：**同一件事有两个机检入口，判据不同，取绿的那个就能过关**。对策统一为：一件事只留一个判死入口，其余降为提示并注明"提示不可作为通过依据"。
