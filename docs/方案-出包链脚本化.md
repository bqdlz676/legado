# 方案 · Q-279 出包链脚本化（CI 绿闸 → 取包 → 结构校验 → 签名口径报告）

- 新增文件：`data_scripts/fetch-apk.py`（一条命令固化整条出包链）；本报告；锚点卡 `docs/锚点/Q279-出包链.md`。
- 未触碰：`.github/workflows/verify.yml`（有别的单在改）、既有 `check-*.py` 门禁、`app/src/**`；无 git 写操作；沙箱无 JDK / 无 Android SDK / 无 apksigner，未跑 gradlew / kotlinc / apksigner，只做 Python `py_compile`、离线夹具自测与 zip 结构校验。
- 锚点卡：docs/锚点/Q279-出包链.md

## 一、背景与事实锚点

- 现状是「人肉出包」：CI 绿了以后靠调度器记忆去 GitHub 取 artifact、解压、核对签名与资源、再交付。调度器换人或上下文一断，这条链就断。历史两类事故：
  - 「CI 绿但没有包」：绿跑没有被回查 artifact 是否真的存在 / 可下载，交付侧拿到的是空口结论。
  - 「报了 APK 实际没校验签名」：签名核对只发生在人工交付文档里（见 `docs/交付-APK-98ee6d0-静态自检.md` §3，当时用 `keytool -printcert -jarfile` 人工比对证书指纹），脚本层不查签名件。
- 既有旧链 `data_scripts/release.sh`（bash）已把部分动作固定化，但存在缺口：
  - 轮询默认开：`for i in $(seq 1 40); do … sleep 20; done`，调用方会被阻塞在脚本里，违反主控不等待纪律。
  - 变体不判：`ls -t dist/*.apk | head -1` 取最新一个，debug / release 混拿没有闸；多 apk 变体不报错。
  - 校验薄：只在 `aapt2` 存在时断言 versionCode；缺 aapt2 时跳过且无 manifest / resources.arsc / dex / 签名件结构校验。
  - 失败面不区分：无 artifact、artifact 过期 404、zip 损坏、0 字节 apk 共用笼统报错；无整体超时熔断。
- 现行云端事实（只读核对，未改）：
  - Verify 工作流名 `Verify (unit tests)`（`.github/workflows/verify.yml:1`）。
  - 出包工作流名 `Package Debug APK`（`.github/workflows/package.yml:1`）。
  - 上传产物：artifact 名 `legado-debug-apk`、`legado-release-apk`（`.github/actions/build-apks/action.yml:37`、`:44`），debug 路径 glob `app/build/outputs/apk/**/debug/*.apk`，`if-no-files-found: error`。
- 本单所补：把「绿闸 → 取包 → 解压 → 结构校验 → 签名口径报告」整条链固化进 `fetch-apk.py`，任何人任何时刻一条命令可重现；每一步失败都有明确输出与退出码，不允许 silent。

## 二、脚本能力与用法

脚本：`data_scripts/fetch-apk.py`。

入口参数：

- `--sha <head>`：指定提交；默认取 `git rev-parse HEAD`；短号自动 `git rev-parse --verify` 补全 40 位（GitHub `head_sha` 服务端过滤只认全号，短号会假阴性）。
- `--run-id <id>`：直连指定 Package run；仍先按该 run 的 `head_sha` 过第一道 Verify 绿闸。
- `--wait`：可选；默认关闭。开启后轮询 Verify 直到 completed，受 `--timeout` 总时限约束。
- `--timeout <秒>`：整体超时，默认 300s；超时打印停在哪一步，退出码 3。
- `--selftest`：`/tmp` 造四类假夹具跑判定，跑完夹具自删。

产物目录：`dist/<sha前7>/`，下载的 artifact zip 与 `unzip/` 解压目录都落在其下。

退出码：

- `0`：包结构按本脚本口径校验通过。
- `1`：CI 未绿（red / running / none）或结构校验 FAIL。
- `2`：基础设施错误：凭据缺失 / 401 / 403 / run 不存在 / artifact 404 过期 / zip 损坏。
- `3`：整体超时熔断。

## 三、三步链与判据

### 3.1 第一步：Verify 绿闸（未绿绝不取包）

- 按 `head_sha` 查 Actions runs，挑出 Verify run（名含 `Verify`，排除 `Shadow` 影子单测工作流）。
- 判序：已完成的红优先判红（不被「还有在跑」藏住）；无红但有在跑 → `CI=running`；全绿 → `CI=green`；无 Verify run → `CI=none`。
- 非绿一律明确输出 `CI=red|running|none …` 并以退出码 1 结束，**不进入取包步骤**。
- `--wait` 开启时才轮询（每 10s 一次），直到 green / red / none 或超时熔断。

### 3.2 第二步：Package Debug APK run 与 artifact 下载

- 查同一 sha 的 `Package Debug APK` run；run 未结束 → `CI=running` 退出 1；结论非绿 → `CI=red` 退出 1。
- 取该 run 的 artifacts 列表并逐条打印（id / 名称 / 大小）；按名优先选含 `debug` 的变体（`legado-debug-apk`）；无 debug 变体时列出全部并判红，不静默拿 release 包。
- 下载端点 `/repos/<repo>/actions/artifacts/<id>/zip`，落盘 `dist/<sha前7>/<artifact名>.zip`。

### 3.3 第三步：解压与结构校验（逐项 PASS / FAIL / WARN）

- apk 数量闸：递归统计 `*.apk`。恰好 1 个才进单包校验；0 个 → `NO_APK`；多于 1 个 → `MULTI_APK` 并逐个列出名称（说明取到的是别的变体），判红。
- `AndroidManifest.xml`：存在优先调 `aapt` / `aapt2 dump badging` 解析；工具缺失时降级为 zip 目录结构检查，显式打印 `WARN: MISSING: aapt`，不许静默 PASS。
- `resources.arsc` 存在；`classes*.dex` 至少 1 个。
- 打印 apk 字节大小与 `sha256`。
- v1 签名判定：`META-INF/` 下证书（`*.RSA|*.DSA|*.EC`）+ `*.SF` + `*.MF` 三件齐全 → `已签名（v1）`；有 `META-INF` 占位但无三件、或完全无签名件 → `UNSIGNED` 判红。
- 每条签名结论附 NOTE：v2/v3 签名只在 APK Signing Block 里，zip 目录看不到；无 apksigner 环境无法判定。本脚本只保证不漏 v1 存在性与 `META-INF` 矛盾态。

## 四、失败面穷举（每条都有明确输出，不许 silent）

- 凭据缺失：`~/.git-credentials` 无 github token → 退出码 2。
- token 401：`AUTH=401 token 无效或过期` → 退出码 2。
- token 403：`AUTH=403 权限不足或触发限流` → 退出码 2。
- run 不存在：API 404 → `NOT_FOUND=404 资源不存在`；Verify / Package 名单内无对应 run → 分别按 `CI=none` / 「未找到 Package run」退出 1。
- artifact 过期：下载端点 404 → `ARTIFACT_EXPIRED=404 artifact 已过期或不存在（GitHub 默认保留 90 天）` → 退出码 2。
- zip 损坏：`testzip()` 命中坏条目或非 zip → `CORRUPT_ZIP`；apk 本体非 zip / 条目损坏 → `CORRUPT_APK` → 退出码 2。
- 解压出 0 个 apk → `NO_APK`，退出码 1。
- apk 0 字节 → `ZERO_BYTE`，退出码 1。
- 多于 1 个 apk → `MULTI_APK`，列名，退出码 1。
- 整体超时：在任一网络调用 / 轮询前检查剩余时限，超时打印 `TIMEOUT: … 停在步骤「<步骤名>」`，退出码 3。

## 五、三个口径说明

### 5.1 这条链与「CI 即验收」的关系：为什么第一步必须等绿，而不是先取包后补验收

- 现行纪律是 CI 即验收：Verify 绿红本身就是代码能不能编译、单测过没过的验收结论；出包链是验收通过之后的「搬运 + 复核」环节，不是第二道验收。
- 先取包后补验收的二阶风险：包一旦先落到本地 / 交付侧，后续验收红了，已经有人可能拿这个包去装、去测、去汇报；「先拿下来再说」会把不完善包流出的窗口拉开。历史「报了 APK 实际没校验签名」正是环节顺序倒挂——交付结论先于复核动作。
- 因此脚本把绿闸硬接在取包之前：非绿在第一步就退出，根本不请求 artifact 端点；Package run 自身非绿 / 未结束同样不取。绿闸与取包在同一进程顺序执行，不靠调用方记得「先查 CI 再下载」。

### 5.2 `--wait` 为什么不默认开

- 主控 / 调度层纪律是禁止阻塞空等：主控不许休眠，必须轮询进度；阻塞在一条出包命令里等于把调度层挂起。
- 默认不带 `--wait` 时，脚本只查一次当前状态：在跑就明确报 `CI=running` 退出 1，调用方（主控）可以稍后再来跑一次，链路上不挂死。
- `--wait` 只给人手动盯包用：人在终端等一个明确的包，开启后轮询到结束或超时熔断；它不进入主控自动化路径。

### 5.3 一版能覆盖到什么程度的「签名可信」，以及接 apksigner 的前提

本脚本当前口径能覆盖的：

- v1 签名存在性：`META-INF` 下证书 / SF / MF 三件是否齐全；`META-INF` 有占位却无签名件的矛盾态能抓出并判红。
- 包结构完整性：单 apk 变体、Manifest 条目、`resources.arsc`、dex、大小与 sha256；zip 完整性 `testzip()`。
- 缺 aapt 时的降级口径：Manifest 只做 zip 目录条目存在性检查，打印 `MISSING: aapt`，不声称解析过二进制 Manifest；该行是 WARN 不是 PASS 背书。

本脚本当前不能覆盖的（必须明说，不许当已验证）：

- v2 / v3 / v4 签名方案判定：签名块在 APK Signing Block，不在 zip 中央目录，纯 zip 检查看不到。
- 证书身份比对：不能确认签名证书是否等于既定 `luowen.jks` 指纹；v1 三件齐全只证明「走了 v1 签名流程」，不证明「是目标证书签的」。
- Manifest 二进制解析：applicationId / versionCode / minSdk 等字段在缺 aapt 时读不出。

后续接入 `apksigner verify` 需要的环境前提：

- JDK 运行环境（apksigner 是 Android SDK build-tools 里的 Java 程序）；沙箱当前无 JDK，本单不装。
- Android SDK build-tools ≥ 30（含 `apksigner`）；或在 CI 镜像内调用（现行 `build-apks/action.yml:26` 已通过 `$ANDROID_HOME/build-tools/*/aapt2` 取工具，镜像里已有 build-tools 路径）。
- 校验命令口径：`apksigner verify --print-certs <apk>` 判 v1/v2/v3 方案与证书指纹；再把证书 sha256 与既定 keystore 指纹比对（对齐 `docs/交付-APK-98ee6d0-静态自检.md` §3 的既有指纹）。
- 落地位置二选一：CI 出包 job 内加一步 `apksigner verify` 把结论写进 artifact / 日志；或在带 SDK 的本机侧跑本脚本后追加 apksigner 复核。沙箱侧继续只做结构与哈希口径。

## 六、与既有 `release.sh` 的关系

- 本单不删 `release.sh`（边界：不改既有脚本）。两者口径差异：旧 bash 链轮询默认开、变体不判、签名不查、失败面不区分；新 Python 链绿闸前置、变体闸、结构校验、签名存在性口径、退出码与超时熔断齐备。
- 后续收口建议（已入队，见 §八）：要么把 `release.sh` 改成薄壳转调 `fetch-apk.py`，要么退役旧链；双轨并存期间以 `fetch-apk.py` 的输出为准。

## 七、自检记录

- 单项自检：`python3 -m py_compile data_scripts/fetch-apk.py` RC=0；`python3 data_scripts/fetch-apk.py --selftest` 末行 `PASS 4/4 fetch-apk selftest`，RC=0；夹具目录 `/tmp/fetch-apk-*` 跑完自删，`/tmp` 无残留。
- 四种假数据判定（selftest 实测）：
  - A 正常单包 + v1 三件：`overall=True`，`signature=v1-signed`，reasons 空。
  - B 双 apk 变体：`overall=False`，`reasons=MULTI_APK`。
  - C 0 字节 apk：`overall=False`，`reasons=ZERO_BYTE`。
  - D 仅 `META-INF/` 占位、无签名三件：`overall=False`，`reasons=UNSIGNED`。
- 补充边界实跑：外层 zip 无 apk → `NO_APK`；外层 zip 非 zip 字节 → 抛 `CORRUPT_ZIP` InfraError。
- 降级口径实跑：本环境 `which aapt aapt2 apksigner` 均为空；正常夹具 Manifest 行打印 `WARN: MISSING: aapt —— AndroidManifest.xml 仅做 zip 目录结构检查，未解析二进制 Manifest`，不静默 PASS。
- 整体自检：脚本未引用任何 JDK / SDK / 系统包；网络路径只在真实取包时触发，selftest 全程离线；未改 `verify.yml`、既有 `check-*.py`、`app/src/**`；无 git 写。

## 八、新发现问题

1. **旧 bash 出包链双轨并存（已入队）**：`data_scripts/release.sh` 仍在仓内，轮询默认开、不判变体数量、不查签名件，与新脚本口径不一致。处置：后续单决定把 `release.sh` 改薄壳转调 `fetch-apk.py` 或退役；本单边界不改既有脚本。归属：出包机制收口。
2. **`dist/` 未入 `.gitignore`（待裁）**：实跑后 `dist/<sha7>/` 会在工作区留未跟踪产物目录。处置：后续单评估补 `/dist` 忽略规则；本单边界不改 `.gitignore`。归属：工作区卫生。
3. **v2/v3 签名与二进制 Manifest 在本沙箱不可判（待裁）**：需 JDK + Android SDK build-tools 的 `apksigner` / `aapt2` 环境；接入前提见 §五-c。处置：优先在 CI 出包 job 内加 `apksigner verify` 步骤，沙箱侧维持结构与哈希口径。归属：签名复核链。
4. **GitHub artifact 90 天保留期（已闭环）**：过期 run 回取不到包；脚本下载端点 404 明确报 `ARTIFACT_EXPIRED`，不静默当空包。处置：口径已在脚本内，无需额外动作；超期历史包只能重跑 CI 出新 artifact。
5. **artifact 变体名耦合（已入队）**：脚本按名含 `debug` 选包；若日后出包 workflow 改名、新增 abi 拆分变体或多 debug 产物，选择规则需同步复核。处置：变体清单打印在案，改名时先核本脚本选择逻辑。归属：出包 workflow 联动。
