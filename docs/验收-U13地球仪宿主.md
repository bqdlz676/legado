## 六、FAIL 级违规点

### F1 · 帧循环把纳秒帧时间戳当作 UTC 毫秒传入门面，太阳方位不按真实 UTC 走

- 文件：`app/src/main/java/io/legado/app/ui/map/globe/host/GlobeScreenHost.kt`
- 行号：**第 84 行**（缺陷代码）；关联：第 78–87 行帧循环；`host/GlobeHostController.kt:27-28`；`scene/GlobeScene.kt:73`；`astro/Sun.kt:42-55`
- 缺陷代码：
  ```kotlin
  // :81
  withFrameNanos { now ->
      val dtSec = ((now - lastFrameNanos).coerceAtLeast(0L)) / 1_000_000_000.0
      lastFrameNanos = now
      // :84  ↓ now 是帧纳秒（since boot, ns），却作为 utcMillis 传入
      snapshot = host.frame(dtSec.coerceAtMost(0.1), now)
  }
  ```
- 原因（逐层回源）：
  1. `withFrameNanos` 回调参数 `now` 是**帧纳秒时间戳**；`dtSec` 用纳秒差 ÷1e9 折秒是正确口径，但同一 `now` 被原样传给 `frame(dtSec, utcMillis, ...)`。
  2. `GlobeHostController.frame`（`:27-28`）→ `GlobeController.nextFrame(dt, utcMillis, ...)` → `GlobeScene.update`（`:73`）`sunDir = Sun.direction(utcMillis)`。
  3. 门面契约与全部上游测试均以 **UTC 毫秒 epoch** 为口径：`SceneSnapshotTest.kt:20/34/53/61`、`SunLightTest.kt:17/23` 传 `System.currentTimeMillis()`；`SunLightTest.kt:96` 用 `1_721_000_000_000L`（毫秒级 epoch）；`Sun.kt:43-45` 按 `utcMillis/1000` 再 `% 86400 / 365.25` 推小时与年积日。
  4. 纳秒值被当毫秒后：`utcSec = now/1000` 实为微秒量级，epoch 基准与速率全错。按 16ms/帧估算，`now` 每帧增约 1.6×10⁷ 纳秒，`utcSec` 增约 1.6×10⁴ 秒 ≈ **4.4 小时日照角/帧**，太阳方位盘在帧间高速乱转；不满足切片 19 第 52 行「太阳位置根据真实 UTC 时间自动算——你手机上几点，地球就转到对应的光照位置」。
  5. 首帧口径正确：`GlobeScreenHost.kt:66` 用的是 `System.currentTimeMillis()`；问题仅出在帧循环。
- 影响面：太阳方位盘方向错误且帧间漂移；昼夜/晨昏线门面逻辑（`Sun.dayFactor/terminatorSide`）若后续接线，会继承错误输入。不崩溃、不空白，但属规格功能错误。
- 修复方向（本验收不代改）：帧循环内另取 `System.currentTimeMillis()` 作为 `utcMillis` 传入 `host.frame(...)`；`now` 仅用于 `dtSec` 差分。补一条单测：连续两帧传入同一 UTC 毫秒时 `sunDir` 不变，避免回归。
- 判定：**FAIL**。
