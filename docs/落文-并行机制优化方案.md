# 落文 · 并行任务机制优化方案

> 生成：2026-11-23。依据：本轮 26 组并行真实运行中暴露的全部故障（上下文爆、进度虚报、8 连红、调度器被 kill、子代理卡死空转），逐条对应优化。
> 每条格式：问题事实 → 优化措施 → 为什么（理由）。

---

## 一、调度层去状态化（本次最大教训）

**问题事实**：调度 Agent 把 20+ 子任务的往返消息、验收报告、代码片段全部堆在自己的上下文里，加上 76KB 常驻规格，最终加载失败；被 kill 后，进行中的判断全部丢失，只能靠 git 日志重建。

**优化措施**：
1. 调度层只持"索引 + 状态"，不持代码、不读规格全文、不回灌子任务过程。
2. 一切状态实时落盘：`docs/落文-模块契约索引.md`（模块状态）+ `docs/落文-进度续传快照.md`（任务状态）。
3. 调度器自身设计为**可随时被杀、可随时换人**：换人只读两个文件即可续跑，无需任何对话记忆。

**为什么**：Agent 上下文是易失资源，磁盘是唯一能跨进程存活的记忆。把"记忆力"从 Agent 挪到文件，调度器就不再是单点故障。

---

## 二、进度上报改三指标，废除百分比

**问题事实**：调度器报"总进度 55%"，但当时 CI 连续 8 次全红、一次都没走到出包、没有任何可安装的 APK。百分比完全失真。

**优化措施**：进度只报三个布尔量，不报百分比：
- **代码点**：当前 HEAD commit（哪笔提交）
- **编译态**：最近一次 CI 绿/红、跑通多少测试
- **包态**：有没有从 CI artifact 取出的 APK、校验过没有

**为什么**：百分比是估算，三个布尔量是事实。用户判断"能不能装"只需要第三个；判断"有没有坏"只需要第二个。

---

## 三、P0 单列通道：出包优先于一切新功能

**问题事实**：8 连红期间调度器还在继续派 UI 新模块，导致"没有包"的状态持续了十几个小时；修好一行编译错之后 30 分钟就有了包。

**优化措施**：
1. 任何时刻，只要"没有绿 CI + 没有 APK"，新功能派单一律停发。
2. 全队资源先压到修红上；修红任务单列，不排队、不经过验收流程的排队区。
3. 修红由最小编码单元做（往往是单行），做完立刻 push，不等验收——CI 本身就是验收。

**为什么**：没有包，用户无法验证任何东西；后续功能做得再多都是悬空的。修复代价极小（一行），拖延代价极大（整个交付链停摆）。

---

## 四、验收与执行彻底分离，验收不排队

**问题事实**：部分验收由执行者自己顺带完成（自评代验收），且"两道验收"串行等待把出包拖死。

**优化措施**：
1. 执行 AI 只写码；验收 AI 独立组，只读"原文切片 + 模块代码 + 判据"，不看执行过程。
2. 验收判低 → 换执行者、废代码、重做，不讨价还价。
3. 验收未过也先 push 云端（区分标记），CI 绿优先于验收结论。

**为什么**：自己写自己审等于没有审；CI 是全仓库唯一中立的编译器，它比任何静态验收都硬。

---

## 五、子任务无状态、用完即弃、带熔断

**问题事实**：一个字体消费子代理因反复 `ls/find` 探测卡死空转，直到被人工发现才废弃；子代理复用唤醒导致上下文复用不清。

**优化措施**：
1. 每个子 AI 只拿"一个切片 + 自己文件域"，写完回写一行状态即终结，禁止复用、禁止唤醒续跑。
2. 给每个子 AI 设熔断：固定轮数内无产物（无 commit、无文件写入）即自动废弃重派。
3. 调度层不许休眠：必须轮询子 AI 进度，不能等它自己报。

**为什么**：子 AI 挂掉的方式是空转而非报错，只有"产物超时"能识别它死了。

---

## 六、对话流水只增不改，抢救按时间锚

**问题事实**：调度器重启后，我重建上下文只能靠 git 和文档转述，过程性信息（为什么放弃某个方案）丢失。

**优化措施**：
1. 每轮对话即时逐字追加进对话流水文件，只增不改。
2. 抢救死掉的上下文时，只按时间锚点逐字抽原文，禁止转述。
3. 流水文件本身就是"过程记忆"的磁盘形态，不再依赖任何 Agent 的记忆。

**为什么**：转述会失真；逐字原文加时间戳是可审计、可回源的唯一可靠形式。

---

## 七、出包闸门脚本化

**问题事实**：取 artifact、解包、校验包内资源、上传、交付这一串动作目前依赖调度器记得做，容易漏。

**优化措施**：把"CI 绿 → 取 artifact → 校验（签名/关键资源在不在）→ 拷贝到会话目录 → 上传交付"固化成一条固定脚本流程，每次 CI 绿后自动走一遍。

**为什么**：流程固化成脚本就不再依赖任何人的记忆力，这是本次所有故障的共同根因——**依赖 Agent 记忆的一切都会以某种方式坏掉，落盘和脚本才不会**。

---

## 八、负载自适应与并发纪律

**问题事实**：默认满并行在沙箱高负载时互相踩踏，队列无序。

**优化措施**：默认并行、负载高时降到 2；任务按依赖入队，不无脑全开；每次只并发"文件域互不重叠"的子任务。

**为什么**：并行度的收益曲线是倒 U 型，超过资源承载力后，加人就是加冲突。

---

## 结论（一句话）

**机制优化的总原则：把记忆、判断、交付从 Agent 身上剥离，落到文件、CI、脚本上；Agent 只做执行，且任何时刻都可被替换。**
