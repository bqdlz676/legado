# 规则结构优化 · 报送 CI（无墙钟版）

> 口径：**墙钟不进规则。** 不用分钟做门槛、不做时间窗、不设"多少分钟内跑完才算合格"。全部控制改用**状态量**——在跑几个 run、排队几批、卡在什么状态、批次是否全过、失败重开几张。目标是"顺畅"：报送永远不堵在关键路径上，写码与验收永远有空槽。
> 历史墙钟数字只当事故档案（主 run 曾 25–27 分钟、打包 job 曾占 15 分钟），不作任何判定依据。

## 一、为什么不能拿墙钟当闸门

1. **墙钟不可控**：机器负载、缓存命中、runner 排队都变了，同一份代码今天 20 分钟明天 40 分钟，用时间判定等于把"合规"交给运气。
2. **墙钟会把人逼成赌徒**：定了 30 分钟窗口，就会算"还差 5 分钟能不能塞一单"，最后必然贴边撞车（本仓已有先例）。
3. **墙钟掩盖真问题**：慢只是表象，真问题是"长作业占住了验证车道"和"后推取消在飞验证"。这两件都能用状态解决，不需要时间。

## 二、度量换算：所有时间量换成状态量

| 原来用时间量表达 | 改成状态量 | 怎么读 |
|---|---|---|
| "窗口 30 分钟才能推" | 验证车道是否空闲（在跑 run 数 = 0）+ 待推批次队列为空 | 读 run 状态与队列文件 |
| "run 要 26 分钟，太慢" | 验证车道被几个作业占着；打包是否挤在同一车道 | 看 job 构成，不看时长 |
| "一批要在 X 分钟内验完" | 一批里 V 卡是否全 `过`、失败重开了几张 | 读卡表状态 |
| "节拍多久推一次" | 待推批次堆积数（>2 就说明验证车道成瓶颈） | 读队列 |
| "写码等 CI 等了多久" | 写码槽空闲轮次数（有空槽却无卡可取 = 真堵） | 读卡表与槽位 |
| "判废率多少" | 判废次数 / 重开卡数 | 计数，不做比率外推 |

## 三、顺畅的三条不变量（任何时候都必须成立）

1. **写码槽不空**：只要存在"前置已过且状态待取"的卡，就要有写码代理在跑。
2. **验收槽不空**：只要存在"已交活待验"的卡，就要有验收代理在跑。
3. **报送不在关键路径上**：push 只在批次攒够、车道空闲时发生；写码与验收**不等** CI 结果——CI 绿红只决定"这批能不能收尾"，不决定"下一张能不能开工"。

这三条成立，系统就顺畅；任何一条破了，先修不变量，不修速度。

## 四、报送控制律（判据全部是状态，无一条是时间）

推一批，必须同时满足四条：

1. 批次内所有 V 卡结论 = `过`（批次纯度）。
2. 验证车道在跑 run 数 = 0（不打断在飞验证）。
3. 待推批次数 ≥ 1（有货才推，不空推）。
4. 工作区干净，且没有别的批次的 commit 混在同一区间。

任一条不满足 → **排队，不等待**：把批次挂在待推队列，写码与验收继续跑。排队不是阻塞，排队是"把报送从关键路径上摘下来"。

反例（明确禁止）：为了"当天推完"而在车道忙时硬推；为了"少一条红灯"把两张未验的卡塞进批次。

## 五、双车道：不是为省时间，是为腾车道

- **验证车道**：编译 + 单测分片 + 汇总断言（含 ≥3185 基线）。只做判定，不产出交付物。
- **打包车道**：APK 与资源校验。只在交付出包、打 tag、手动触发时跑。
- 理由不是"打包慢"，而是**长作业不能与判定共用一条车道**：一旦共用，任何一次打包都会把验证顶到后面，排队立刻堆积，第三条不变量就破了。
- 打包产物不参与批次判定；批次判定只看验证车道。

## 六、取消策略：把"取消在飞"换成"互不相撞"

- 并发组 = 批次号，不同批次互不取消；同一批次重推才取消旧的自己。
- 这样"后推"不再是"打断"，而是"排队"；K-20 那类"连推三次打掉两批"在结构上不可能发生。
- 判定不是"取消次数多少"，而是"任何时候验证车道在跑 run 数 ≤ 1"。

## 七、失败处理：只重开受影响的卡

1. 失败先归因到 job：编译红 / 某分片红 / 汇总断言红 / 资源校验红。
2. 再按批次内卡序对 commit 区间二分，定位到具体卡。
3. 只对该卡起 `W-0NN-R1` 与 `V-0NN-R1`，其余卡保持 `过`，不许整批重来。
4. 编译红例外：编译红会让整条链停摆，按既有纪律"最小改动立刻修、修完马上推"，不等独立验收——这一条是唯一的抢修通道，且必须在该批其余卡上标"批次暂停"。

## 八、卡表要补的三列（状态量都在这里落地）

| 列 | 取值 | 用途 |
|---|---|---|
| `批次` | `B-0NN` / `—` | 同一批卡的归属，批次纯度按它算 |
| `车道` | `待推` / `在验` / `已验` / `暂停` | 报送状态，替代原来的时间窗 |
| `失败归因` | `编译` / `分片-N` / `断言` / `资源` / `—` | 只重开受影响卡 |

## 九、验收判据（全部机械可判，无一条含时间）

1. 任一时刻，验证车道在跑 run 数 ≤ 1。
2. `cancelled` run 数 = 0（连续 10 次报送窗口内）。
3. 每次 push 都带 `Batch:` trailer，且批次内 V 卡全为 `过`。
4. 一次失败重开的卡 ≤ 2 张。
5. 写码槽空闲轮次 = 0（只要还有待取卡就有代理在跑）。
6. 待推批次数 ≤ 2（超过说明验证车道成了瓶颈，按第一条不变量处理）。

## 十、明确不做

- 不设任何时间阈值、时间窗、超时判定（除代理存活熔断这类与报送无关的机制）。
- 不为了"当天推完"硬推；不把未验卡塞进批次。
- 不关掉取消就了事，也不靠"人手少推几次"来避免撞车——撞车要用批次组消除，不靠纪律。
- 不用本地编译替代 CI（本机无 JDK21，编译只会假绿）。
- 不把打包塞回验证车道"图省事"。

## 十一、落地顺序（不改代码，随时可回滚）

1. 改 `pre-push.sh` 与 `check-push-window.py`：判据从"时间戳"换成"run 在跑数 + 待推队列"。
2. 卡表补三列（批次 / 车道 / 失败归因）。
3. 拆 `verify.yml` 与 `package.yml`，并发组改批次号；旧 workflow 保留一天对照。
4. 改三个读数脚本（在飞计数、台账新鲜度、计数单源）指向卡表。
