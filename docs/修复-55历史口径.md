## 二、背景与根因（复跑取证，不凭转述）

- Q-257 收口后，现行判据三条：① 报告内有「新发现问题」小节；② 节内 ≥1 条带列表前缀的问题；③ 每条正文自身含处置状态词（已修／已入队／判废／待裁／已闭环／已处置）。三条任一不成立即红（`data_scripts/check-problem-finding.py:254 judge`）。
- 复跑旧脚本全仓：判红集中在规则上线前交付的存量报告，缺小节是历史写作格式，F8 规则当时尚不存在；旧机制只能把个别报告登记进 `problem-finding-baseline.json` 洗白，存量面太大，基线不可能也不应该逐份收编。
- 根因：旧脚本只看正文合规性，不看报告进入仓库的时间；用生效后的判据回溯生效前的产物，等于让历史存量永久挂红，门禁失去告警新增违规的本意。

## 五、时间口径判定规则

- 首现时间探针：`git log --follow --diff-filter=A --format=%ct -1 -- <path>`（批量表未命中时单查）；取最早一次 A 事件的 committer time。

- `post`（ct ≥ 1795685975）：规则生效后进入仓库，按现行三条判据重判，一条不放宽。
- `unknown`（未跟踪 / git 不可用 / 改名链断，探针返回 `None`）：默认从严，先进 `judge()`；仅当路径在册且正文 sha256[:12] 双匹配时走基线豁免。

## 十、自查反例 / 改坏推演

- 反例 1（复制旧报告改名绕过）：把规则前旧报告复制成新文件名落盘，新路径首现 ct 为当前时刻，必然进 post 桶按现行判据重判，复制改名不能继承旧报告的历史豁免；只有 `git mv` 纯改名才可能沿改名链回溯首现时间，见反例 2。
- 反例 2（R100 改名链断裂）：`:152 _first_add_ct` 先查批量 A 表，未命中再 `--follow` 单查；若改名链跨多次重命名、follow 仍断链，探针返回 `None` 归 unknown，从严判 + 基线双匹配兜底，不会误放 pre。
- 反例 3（边界相等误判）：首现 ct 恰好等于分界 ct 时归 post（`:169` 注释），规则同批产物不享受历史豁免；若反向归 pre，F8 当批夹带的新报告就会漏网。
- 反例 4（中文路径键失配）：批量表若漏 `-c core.quotepath=false`，中文路径变八进制转义串，全部键失配、251 份存量被误判 unknown；夹具未直接覆盖该分支，`:133` 注释与实跑中文仓结果已回证。
- 反例 5（基线洗白改坏）：在册文件内容被改坏后 sha 不符，`:188-191` 判 `rehash` 转重判，豁免不能只按路径命中；空基线时该分支不触发，但机制保留。
- 反例 6（空集假绿）：无报告可判仍走 `:401-404` EMPTY rc=2，历史口径不改变空集不许 PASS 的口径。
- 改坏推演：将来条目出现新前缀（`▪`/`– `/`· `），`_split_items` 会把整节并入一条，状态词在整条内查找反而漏判；状态词表是封闭集，新增处置措辞不命中会误红，扩词表须同步补夹具。

## 十一、二三阶影响

- 一阶（直接效果）：251 份规则前存量不再永久挂红，门禁 55 只对规则后产物告警；现行三条判据代码路径未改严也未改松。
- 二阶·复制旧报告改名：新建路径首现即 post，无法继承豁免；风险点在 `git mv` 纯改名——follow 链把首现时间回溯到旧路径的 pre 时刻，若改名时夹带内容改写（R90/R80 非满格相似度），改名后产物实际已是新交付，却可能沿链落 pre。当前兜底：follow 断链归 unknown 从严；后续可在改名判定时叠加相似度校验，非 R100 不带历史豁免。
- 二阶·R100 改名怎么判：批量 A 表只认 A 事件，R100 改名在 A 表无记录，由 `--follow` 沿链回溯到原始 add 提交取 ct；链上任一环节断链（跨目录改名、历史压缩、force-push 改写）探针返回 None，归 unknown 从严 + 基线双匹配。现仓两例实测：`修复-Q244-导入分组与死行摘除.md` follow 回溯到 `4904d9b` ct 1795693335（post）；`修复-名物库判低收口.md` follow 回溯到 `d745e63` ct 1795626007（pre，历史豁免）。
- 二阶·时钟依赖：探针取 committer time（%ct），不取 author time（%at）。author time 随提交者本地时钟走，可被 rebase / commit --date 改写；committer time 记录对象入库时刻，门禁锚的是「报告何时进入仓库」。残留坑：本地时钟整体偏移会影响 ct；历史被 force-push 重写后 ct 链不可信；跨时区提交 %ct 为 UTC 秒，比较时两边都是秒级时间戳，不涉时区换算。快照常量 `:56` 只在 git 不可用时回落，正常启动以 `git show` 实测为准。
- 三阶·基线沉淀风险：基线新口径收窄到 unknown / 改名边界，但在册条目仍可能只增不减；棘轮闸门是 sha 双匹配——内容一改坏指纹即失效重判。若长期不销账，需在基线维护环节定期核对在册条目是否仍属边界情形。
- 三阶·词表封闭性：处置措辞超出词表即误红（首轮 3 份、收尾快照 1 份判红，全是同义词问题）；扩词表要跟报告用语同步，否则值班代理会向词表内挤措辞、掩盖真实处置状态。
- 跨模块观察：`审计-` 前缀报告不受 55 约束（第七节 7.2）；evidence 门禁历史三件套欠账不归本单；`check-commit-split.py`、`selftest-baseline.json` 等其他代理在飞文件本单未触碰。
