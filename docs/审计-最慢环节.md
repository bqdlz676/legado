## 1. CI 时长

### 1.1 三句结论（铁律 64）

1. **慢在哪一步**：最近 10 次 run 墙钟 **130–234s（中位 181.5s）**，耗时集中在名为「Run all module unit tests and benches」的 Gradle 步骤，中位 **135.5s（84–172s）**；前置供给（setup/checkout/JDK/SDK/cache）中位 27s，`clean` 步骤中位 12s，`assembleDebug/assembleRelease` 在 10 次 run 中**全部 skipped，时长取不到**。
2. **为什么慢**：该步骤名义上是跑单测，实际 10 次全部在**编译阶段失败**，`:app:testAppDebugUnitTest` 任务一次都没执行；135.5s 主要花在资源合并 → KSP → 主源码 Kotlin 编译 → 测试源 Kotlin 编译链路上，不是测试用例慢。叠加 `--no-daemon` 每次冷 fork JVM、`org.gradle.parallel=true` 被注释、配置缓存关闭，编译期没有增量/并行/缓存收益（证据 §1.4）。
3. **怎么优化**：先把 A 区编译阻断修绿，让单测任务真正跑起来、拿到任务级基线；再开 `--profile`/build scan 定位 KSP 与主 Kotlin 编译的真实占比，评估开 parallel、保留 daemon 温热、拆分 compile/test/assemble 为独立 job。**不能归因于「机器不行」**——runner 规格未变，波动来自编译失败点、缓存命中与任务编排。

### 1.3 「全量 clean 编译 / 单测 / assemble」分解

工作流原文（`.github/workflows/build.yml`，本单只读未改）：

```yaml
- name: Clean (full rebuild, no incremental)
  run: ./gradlew clean --no-daemon --stacktrace
- name: Run all module unit tests and benches
  run: ./gradlew testAppDebugUnitTest --no-daemon --stacktrace
- name: Build debug APK
  run: ./gradlew assembleDebug --no-daemon --stacktrace
- name: Build release APK
  run: ./gradlew assembleRelease --no-daemon --stacktrace
```

- **clean 全量清理**：中位 12s（step 10–15s）。Gradle 自报 `BUILD SUCCESSFUL in 9–14s`（10 份日志逐一抽取）；抽样日志中 4 个 clean 任务（`:clean`、`:app:clean`、`:modules:book:clean`、`:modules:rhino:clean`）均 `UP-TO-DATE`——fresh runner 上本就没有 `app/build` 产物，clean 实际删不到东西，主要是 Gradle 冷启动开销。

## 5. 可自动化建议（只给方案，不落改；禁区 `.github/workflows/**`、`app/src/**`）

### 5.1 建议一：CI 接入 Gradle `--profile`，把任务级耗时打进 summary（首选）

- **改哪个文件**：`.github/workflows/build.yml` 的「Run all module unit tests and benches」与「Build debug APK」两步，命令追加 `--profile`：
  ```yaml
  run: ./gradlew testAppDebugUnitTest --no-daemon --stacktrace --profile
  run: ./gradlew assembleDebug --no-daemon --stacktrace --profile
  ```
  新增一个 `upload-artifact` 步骤，路径 `app/build/reports/profile/`；再加一个步骤用脚本解析最新 `profile-*.html`（或其内嵌 JSON），把 Top 10 耗时任务写进 `$GITHUB_STEP_SUMMARY`。
- **为什么**：当前 plain console 只能拿到任务开始时间戳（§1.3 口径警告），KSP / Kotlin 编译 / 资源合并 / 测试执行各占多少没有官方数据；`--profile` 产出任务级 wall 时间与依赖阻塞，是后续一切编译优化的基线。
- **怎么验证**：转绿后的 run 中，artifact 可下载到 `profile-*.html`；summary 页面出现逐任务秒数表；本表 §1.3 的相位近似值能被官方任务时长替换或证伪。
- **边界**：`--profile` 本身有少量开销；配置缓存开启后 profile 报告口径会变化，需在同一次基线里记录。

### 5.2 建议二：静态性能门禁脚本（不依赖编译，可随 CI 或 pre-commit 跑）

- **新增脚本**（建议落点 `data_scripts/perf-static-audit.sh`，本单未创建）：只读统计并打印——
  1. `runBlocking` / `Thread.sleep` / 数字字面量 `delay(` 计数与文件清单（对照 K1/K2/K3 基线 53/2/21）；
  2. `app/src/test` 文件数、行数、`@Test` 数、含 `Thread.sleep`/`runBlocking` 的测试文件；
  3. `du -sh app/src/main/assets` 与 Top N 大资产，超红线项（字典 >15MB、字体子集 >200KB）标红；
  4. 输出可贴入 `$GITHUB_STEP_SUMMARY` 的 Markdown 表。
- **怎么验证**：本地 `bash data_scripts/perf-static-audit.sh`，数字应与本报告 §1/§2/§4 实测一致（549 / 60391 / 3030 / 116M / 53 / 2）；阈值超限即退出非零，防止后续提交把阻塞原语或大资产重新堆回启动链。
- **边界**：静态脚本只能数原语与体积，不能证明主线程卡顿或帧率；运行时指标仍需真机/模拟器埋点（§9）。

### 5.3 建议三（依赖 A 区转绿后再做）：编译/测试/打包拆 job + 缓存温热

- 当前单 job 串行 `clean → test → assemble`，`--no-daemon` 三步冷 JVM；转绿后可评估：compile 与 test 分 job、保留 Gradle 缓存键覆盖 wrapper/modules/`.gradle` 变换、复核 `org.gradle.parallel=true` 与 configuration-cache 的收益。
- **前置条件**：A8–A11 与主源码编译错误先清零；在红 CI 上拆 job 只会放大失败面，不解决问题。

## 6. 二阶三阶影响

- **CI 红污染时长基线**：10 次 run 全失败，§1 测到的 135.5s 是「编译到失败点」的时间，不是全量编译+测试+打包时间。二阶影响：若直接拿这个数字做优化目标，会误删测试或跳过编译来「变快」；三阶影响：出包链（`release.sh` 取 artifact）持续无包，性能优化失去真机验证载体。
- **资产按需下载的连带面**：把 `books/`、大词典移出 APK，二阶需要版本化资产清单、下载/校验/解压、缓存淘汰与断网兜底（L131 要求）；三阶影响：存储权限、后台下载调度、字典升级与 App 版本的兼容矩阵，以及弱网/断网首启空态体验。只搬文件不建这套链路，会直接违反「不允许空白态/崩溃」的规格。
- **动画闸门缩短的交互连锁**：2800ms splash 若压到 1.8s 红线内，二阶影响墨滴/金粉/扫光/竖排字的编排节奏（`SplashChoreography` 各 `*_END_MS` 相位）；三阶影响品牌识别度与设计验收口径，需设计侧确认哪些相位可裁剪，不能单纯改 `TOTAL_MS` 常数。
- **`offscreenPageLimit=3` 的内存交换**：预载全部 tab 换滑动流畅度，二阶抬高启动后内存峰值（红线 ≤180MB，规格 `:184`）；三阶影响低端机型被杀后台、重载频率回升，反而拖慢二次启动。
- **KSP/编译耗时优化的模块边界**：开 parallel / 拆模块前需先确认 `modules:book`、`modules:rhino` 与 `app` 的依赖方向是否解耦；二阶若存在循环依赖或共享可变态，并行会暴露顺序依赖问题。
- **测试体量**：549 文件 / 3030 用例一旦在 CI 跑起来，单测步骤时长会显著超过当前编译失败点的 135.5s；三阶影响：需要测试分片、超时熔断与慢用例归集（对应建议二的慢测试清单），否则绿 CI 的反馈周期会过长。

## 7. 反例与边界（先假设本报告判断有误）

1. **「测试/编译步骤 135.5s = 单测慢」不成立**：10 次 run 测试任务均未执行，该数字主要是编译。反例边界：若未来绿 CI 显示测试本身占大头，§1.3 的相位归因需重写；本报告已把单测执行时长标为取不到。
2. **静态 grep 不能证明主线程真卡顿**：`runBlocking` 链上 0 命中，不代表首帧前无阻塞（§3.3 列了同步 init）；反过来，grep 到 `delay(1000)` 也不代表卡 UI——它在后台池。边界：无运行时 trace（`traceview`/`perfetto`/`Looper` 消息时长）前，所有线程归属判断都是静态推断。
3. **日志时间戳 ≠ 官方任务耗时**：plain console 任务行是开始时刻，并发任务交错；§1.3 区间是上界近似。反例：某任务日志行早但实际最晚结束，区间会被低估。
4. **空数据 / 断网边界**：书架空态（`EMPTY`）、离线态（`OFFLINE`，`InkShelfFragment.kt:121`）与有书在线态的首帧路径不同；粒子场在空态仍 compose，本报告未分态测量。
5. **缓存命中波动**：cache 步骤 9–15s，runner 镜像与 `~/.gradle` 缓存命中情况会改变前置时长；10 次 run 同属一个 runner 镜像系列，不能外推到冷缓存全新环境。
6. **数据时点差**：本地 HEAD `d8cbf06` 与 CI 窗口最新 SHA `741b1e1` 不同步；§2/§3/§4 的静态数字基于本地工作树，§1 的 CI 数字基于远端 run。若工作树有他人未提交改动，计数可能与远端略有出入（复核以 `git grep` 仓库快照为准）。
7. **字典红线口径**：「字典 ≤15MB」未注明是单文件还是字典合计；本报告按单文件判定两项超限，若口径为合计，结论需相应调整。

## 8. 认知成本

- **链路双轨口径**：任务书写 `App → ui/main → bookshelf`，实际入口是 `WelcomeActivity`；新人易只查 `ui/main` 而漏掉 welcome 动画闸门与字体阻塞预载。建议后续在模块契约索引里写死 launcher 链路：`Application → WelcomeActivity → MainActivity → InkShelfFragment`。
- **步骤名误导**：CI 步骤叫「Run all module unit tests and benches」，实际卡在编译；交接时必须显式说明「步骤名 ≠ 已执行测试」，否则接手人会去优化测试用例而不是编译。
- **全局计数 vs 链上命中**：53 处 `runBlocking` 集中在 JS/网络桥（`JsExtensions` 6、`BookController` 6、`AnalyzeUrl` 5、`BottomWebViewDialog` 4、`AnalyzeRule` 4、`ReadRssActivity` 3…），**没有一处在启动链**；看全局总数容易误判启动阻塞，必须按链路过滤。
- **资产分层术语**：core / dup / bulk、按需下载 / 预缓存 / 断网兜底（`App.kt:113-126` 注释、总纲 L131）是新引入的分层概念；本报告只标注了每个大头的现状归属，core/dup/bulk 的最终划分需数据域确认，接手人不要按文件名自行归类。
- **本报告未新增抽象或命名**：纯审计文档，不改代码；唯一建议新增物是 §5.2 的脚本，命名建议 `perf-static-audit.sh`，与既有 `selfcheck-*.py/sh` 同族。
