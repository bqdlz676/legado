## 一、这次到底出了什么事（先看证据，不许凭印象）

1. **跑题甲**：`s_000749sNfrw` 收到 2500+ 字派单（Q-20 美感验收并入 UX），轨迹首行 user 就是派单原文——
   下发通道没问题。它的**首条 assistant** 却是「# 小红书风格·AI 生成文案 … 将上述英文长文压缩为 5 条中文小红书短文案」，
   与落文项目零关系，**工具调用 0 次，耗时 16 秒**。
2. **跑题乙**：`s_000749slLa2` 同一形态，首条回「# How can I help you today?」，补发要求后又回「The final answer must explain:」，
   **工具调用 0 次，耗时 4 秒**。
3. **轻症**：`s_000749sN5Y0` 因 `create_agent` 未带 `subtask`，继承了原始用户查询「开启新一轮续跑」，
   前 70+ 行在做"目录考古 / 自我定位 / 读自己上一轮轨迹"，真实任务靠 `send_message` 补发才开工——上下文白烧。
4. **用户侧观感**：跑题产物直接出现在用户眼前（用户当场问"不止有小红书，抖音快手那些都要"，
   即用户以为我们在做文案）。跑题不只是浪费 tokens，它会**污染用户对项目状态的判断**，这是比空转更贵的代价。

## 二、根因（三层，各层都有可机械拦截的抓手）

### 第 1 层：模型层——长任务进入"通用生成模式"，无强制动作就自由发挥

- 证据：派单原文已完整到达（轨迹首行可查），却产出与本项目无关的通用内容。
  说明不是"没收到任务"，而是"收到后没有被强制拉回工具调用链"。
- 机理：长派单 + 首轮没有"必须先做一件机械动作"的约束时，生成模型可以走"直接输出一段文本"这条最省力路径；
  一旦第一句脱离了任务实体，后续就沿语言惯性滑走（小红书文案、寒暄、通用摘要都是同一种滑法）。
- 因此解法不能是"要求它认真"，必须是**结构强制**：首条回复必须是一段固定格式的机械回执（ANCHOR-ACK），
  回执里必须逐字抄任务第一行 + 三个绝对路径 + 第一条要跑的命令。抄不出来＝它没读到/没读懂，当场判废。

### 第 2 层：派单层——派单缺字段，子代理无事可锚

- 轻症实证：`create_agent` 不带 `subtask` 时，子代理继承的是原始用户查询（「开启新一轮续跑」），
  它只能靠猜（于是去考古）。
- 同类：派单只写目标不写锚点路径、只写"改好点"不写判据——都会把不确定性推给子代理，由它自由发挥。

### 第 3 层：验收层——只看自然语言回执，不看仓库事实

- 历史同族（`docs/复盘-子代理空转与假完成.md` 10 例）里 4 例"承诺式空转"，
  回执写得像完成，`docs/修复-*.md` 却不存在；`s_000VPvF75f3` 还出现过"回执给了报告路径但文档不存在"。
- 结论：回执文字永远不是证据；证据是 `ls/stat/git status` 与轨迹里工具调用计数。

## 三、类似问题清单（同一根因家族，六型）

1. **跑题型**：产出与本单实体无关的通用内容（本轮 2 例，本轮新增识别的形态）。
2. **空转型**：零工具调用，回一句寒暄/承诺（历史 10 例中的 `s_0007oNQJnkb`「Stop bargaining.」×4）。
3. **假完成型**：声称完成并给路径，路径不存在（`s_000VPvF75f3` 报告缺档）。
4. **空壳轨迹型**：trajectory 只有 user 行、无 assistant（`s_0007mwobFGj` 等 3 例）。
5. **僵尸复用型**：把已判废的代理 send_message 唤醒续跑，拿回旧上下文继续错下去。
6. **无锚开工型**：没带 subtask/没给绝对路径，子代理先考古再猜（本轮 `s_000749sN5Y0` 70+ 行）。

**共同根因一句话**：派单把"理解"和"执行"都交给子代理，而验收只看它自己写的字。三层同时松，事故必然发生。

## 四、铁律条文（四条，全部可机械判）

### F-93 首轮锚点回执（ANCHOR-ACK）

- 派单模板首段强制三行，子代理**第一条输出**必须以这三行开头：
  `ANCHOR-ACK: <任务第一行逐字>`
  `ANCHOR-PATHS: <≥3 个绝对路径>`
  `ANCHOR-CMD: <开工第一条命令>`
- 为什么：把"读懂任务"变成可机验的字符串证据；抄不出任务第一行，就证明它没读到任务。
- 适用条件：一切子代理（含验收代理）。机制/文档类可复用代理同样要回执，因为跑题与角色无关。
- 例外：只做单次 cherry-pick 式机械改动的代理可免 ANCHOR-CMD，但不得免 ANCHOR-ACK 与 PATHS。

### F-94 派单后 90 秒首轮存活校验

- 调度层在 `create_agent` 后 90 秒内必须读 `<workspace>/.sessions/<sid>/agents/<id>/system/trajectory.jsonl`，
  校验：行数 ≥2、首条 assistant 含 `ANCHOR-ACK`、工具调用 ≥1。
- 任一不满足 → 判**跑题/未开工**，立刻 `kill_agent` 并重派（禁 send_message 续命，见 F-96）。
- 为什么 90 秒：本轮两例跑题在 4~16 秒内就发生，90 秒足够覆盖；再晚只是白等。
- 二阶影响：这条把"发现跑题"从"等它回复"提前到"它还没回复"，
  代价是调度层每单多一次文件读（6 次工具调用量级），换来的是不烧 15 分钟等待。

### F-95 产物存在性优先于回执文字

- 任何"完成"回报，必须带产物绝对路径；调度层 `stat`/`git status --porcelain` 验存在。
  不存在即判"假完成"，按 F-94 处置。
- 为什么：历史 4 例承诺式空转都是文字合格、文件缺失；文字是最便宜伪造的东西。

### F-96 无 subtask 不许 create_agent；判废代理禁续命

- `create_agent` 必须带 `subtask`（哪怕一句话），否则子代理继承原始用户查询并开始考古（本轮轻症实证）。
- 判废（跑题/空转/假完成）的写码与验收代理一律 kill，不得 send_message 唤醒；重派必须是新代理，且必须换更小的任务面。
- 为什么：复用已跑题的上下文等于让它带着错误前提继续推理；同族事故里最贵的一次就是复用僵尸代理。

## 六、跨领域借鉴（为什么这套做法在别的地方也被验证）

1. **航空"双人复核 + 口头复诵"**：指令必须被接收方逐字复诵，复诵即本文的 ANCHOR-ACK。
2. **工控"心跳 / watchdog"**：设备必须在窗口期内证明自己活着；本文的 90 秒校验就是心跳，
   零工具调用＝没心跳。
3. **软件"契约测试"**：生产者与消费者按同一份契约验，而不是各说各话；本文把"任务第一行"当契约串。
4. **数据库"写后读校验"**：写完必须回读；本文的 F-95 就是"回报后 stat 回读"。
5. **制造业"首件检验"**：批量生产前先检首件；本文的"首轮 ANCHOR-ACK"即首件检验，
   首件不合格不许开工，比事后全检便宜得多。

## 七、先假设自己是错的：可能的反例与边界

1. **反例 A：代理只是回执慢，被误杀。** 边界：90 秒是下限窗口；若 90 秒内已出现 tool 调用行则视为存活，
   不看回执。脚本按"工具调用计数"判，不按字符串判，避免误杀慢启动。
2. **反例 B：ANCHOR-ACK 可被模型"背下来"伪造。** 边界：回执要求逐字抄"任务第一行 + 三个绝对路径"，
   路径错、任务首行错都判废；且 F-95 仍然要求仓库事实，单靠回执拿不到验收。
3. **反例 C：小单（一句话改动）走这套太重。** 边界：机制类小单可只回 ANCHOR-ACK 一行；
   但"太重"不是不做的理由——本轮的跑题发生在 2500 字大单，恰恰说明大单更需要回执。
4. **反例 D：门禁 ㉗ 扫全库会误伤历史代理。** 边界：只看近 48 小时；历史留档不追改（同 ⑭/⑮/⑲）。
5. **反例 E：调度层自己也会漏做 90 秒校验。** 边界：㉗ 是兜底——
   漏校验的后果是"代理跑题但没登记"，门禁直接红，逼着补登记或重派。
