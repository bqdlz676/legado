> 优先级排序依据：条目频次 × 返工成本。下列脚本均为只读静态检查，退出码 0/1，不猜业务结论；误报宁可 WARN 不 FAIL。

### 方案 1（优先级 P1）· 零消费符号扫描器 —— 对应 N 类，兼补 E 类
- 输入：`app/src/main/java` 本轮新增/改动的公开符号（`fun`/`val`/`class`/`object` 名），以及 `app/src/main/res` 引用串。
- 判据：符号在 main 非 contract/非 declaration 目录零引用（测试引用单列标注，不算生产消费）；命中输出 `符号名 · 定义文件:行 · 零引用证据 grep 命令`。
- 误报风险：接口/契约声明、预留 Provider、序列化字段本就允许暂不消费 → 这类须带「契约/预留」注释或在缝合怪台账在册才豁免；否则 WARN。
- 落地脚本：新增 `data_scripts/check-zero-consume.py`，挂 rule-gate ㉑ 之后作为 WARN 型守卫。
- 预计行数：约 120 行（符号提取 30、引用计数 50、豁免与输出 40）。
- 频次依据：N 类 53 份 / 97 条目行；E 类零消费残留 36 份 / 56 条目行。

### 方案 2（优先级 P1）· 断言强度扫描器 —— 对应 A 类
- 输入：`app/src/test`、`screenshot/src/test` 全部 `*Test.kt`。
- 判据：① 断言仅用源码子串 `contains(`/`== "文本"` 锁实现文本；② 测试体无调用记录桩/无参数捕获；③ 恒等水断言（`assertTrue(true)`、断言对象与自身比较）；④ 夹具字段缺失导致被测分支早退（夹具 JSON/Map 缺被测分支必需键）；⑤ 某判据章节在测试中零断言覆盖（对照报告判据编号）。
- 误报风险：纯结构快照测试、不可变值对象的等值断言属合法 → 按文件名/注解白名单降为提示。
- 落地脚本：新增 `data_scripts/check-assert-strength.py`；④⑤ 需配合报告判据编号解析，首期只做①②③。
- 预计行数：首期约 150 行；④⑤ 二期再加 80 行。
- 频次依据：A 类 41 份 / 73 条目行；M-18 字面串锁在册。

### 方案 3（优先级 P1）· 兜底守卫与降级覆盖扫描器 —— 对应 K 类
- 输入：main 源码解析/桥接/数据层函数；测试清单。
- 判据：① 裸 `getAsXxx(`/`!!`/`first()` 无空值守卫且所在函数无 catch；② `catch` 块未包住解析/解码调用；③ 枚举/降级分支在测试中无对应用例（分支枚举名 vs 测试用例名模糊匹配）；④ 数值钳制缺失（增量/兵力/半径等可负或越界量无 `coerceIn`）。
- 误报风险：契约层已声明非空、上游已守卫的函数会被误报 → 以可空类型标注与上游守卫链做负向后顾。
- 落地脚本：新增 `data_scripts/check-guard-coverage.py`，③ 出 WARN，①②④ 按置信度分级。
- 预计行数：约 140 行。
- 频次依据：K 类 38 份 / 91 条目行；B13R1、D16、B8R 系列多起 FAIL 源于此。

### 方案 4（优先级 P2）· 文档内嵌源码分叉检查器 —— 对应 D 类增量
- 输入：docs 报告/切片/手册中以代码块或 `文件:行` 引用的源码片段。
- 判据：抽取被引 `文件:行` 区间文本，与磁盘现行源码比对；行号漂移、片段缺失、函数签名不一致即 WARN。
- 误报风险：历史留档报告允许分叉 → 只校验本次 git status 新增/修改的文档（同 ⑭/⑮ 边界口径）。
- 落地脚本：新增 `data_scripts/check-doc-source-drift.py`。
- 预计行数：约 100 行。
- 频次依据：D 类 17 份 / 23 条目行；`验收-校验脚本可移植化.md:219` 实证。

### 方案 5（优先级 P2）· 自述与事实一致性比对器 —— 对应 B 类
- 输入：验收/修复报告中的自报计数（断言数、测试数、改动文件数）、备案状态（未 commit / 已 push）。
- 判据：① 报告自报 `@Test`/断言数 vs grep 实测数偏差超阈值；② 报告称「未提交」与 `git log` 历史矛盾；③ 自报改动文件清单 vs `git show --name-only` 不符。
- 误报风险：报告引用的是历史提交快照 → 以报告 HEAD 锚点时间为准比对。
- 落地脚本：新增 `data_scripts/check-claim-fact.py`，WARN 型。
- 预计行数：约 90 行。
- 频次依据：B 类 16 份 / 21 条目行；单条返工成本高（失实自述直接判 FAIL）。

### 方案 6（优先级 P2）· 行号↔引文回源校验器 —— 对应 G 类增量
- 输入：报告中 `文件:行` 定位串与其相邻 `「…」` 引文。
- 判据：按行号读磁盘对应行，做引文子串包含比对；行号漂移或引文对不上即 FAIL；行号在文件末尾之外直接 FAIL。
- 误报风险：引文跨多行、注释被删改 → 允许行号 ±3 行窗口，窗口外才判红。
- 落地脚本：扩展 `check-evidence.py` 新增 E4 子规则，不另起脚本。
- 预计行数：约 70 行。
- 频次依据：G 类显式判低 3 份 / 4 条目行，但格式打回散见多份。

### 方案 7（优先级 P3）· 同域夹带检查器 —— 对应 I 类增量
- 输入：最近 N 条 commit 的 `--name-only` 名单 + 队列/台账单号归属。
- 判据：同一 app/src 目录内出现两个不同单号的文件改动；测试 commit 夹带非本单测试文件；同一 docs commit 混两个以上单号报告。
- 误报风险：公共工具类/共享资源改动属合法跨单 → 以单号文件域清单做白名单。
- 落地脚本：扩展 `check-commit-split.py` 增加同域夹带规则。
- 预计行数：约 60 行。
- 频次依据：I 类 33 份 / 97 条目行。

### 方案 8（优先级 P3）· 注释口径一致性抽查器 —— 对应 J 类
- 输入：main 源码 KDoc/块注释中的「全部/唯一/同源/豁免/不受/不参与」等过满词。
- 判据：被描述函数内实际分支数/调用点与措辞冲突（如注释称唯一出口，代码存在第二调用点）即 WARN。
- 误报风险：注释描述的是设计意图而非现状 → 首期只出清单交人工复核，不 FAIL。
- 落地脚本：新增 `data_scripts/check-kdoc-claim.py`，只读清单型。
- 预计行数：约 80 行。
- 频次依据：J 类 49 份 / 102 条目行，但语义判据模糊，放 P3。

### 方案 9（优先级 P3）· 线程/性能静态嗅探器 —— 对应 L 类
- 输入：main 源码。
- 判据：① `runBlocking` 在主线程可调路径；② 跨收集器可变 `var` 无 `@Volatile`/锁；③ 超时用真实时钟 `System.currentTimeMillis` 可被测试控制；④ 解码/IO 重 API 直接在 Composable/主线程函数调用。
- 误报风险：工具类/测试替身合法使用 → 按目录与调用链过滤。
- 落地脚本：新增 `data_scripts/check-thread-sniff.py`，WARN 型。
- 预计行数：约 110 行。
- 频次依据：L 类 30 份 / 55 条目行。

### 5.1 Top3 最该补的机检
1. 方案 1 零消费符号扫描器（N/E 类，153 条目行量级，纯静态可落，第一批组装与多份验收已用手工 `grep -rl` 反复做同一件事）。

## 6. 经验库补丁（建议追加到 `docs/经验库.md`，本单不改文件）

> 下列条目均不与在册 L1~L10 重复；格式沿用经验库「症状 / 根因 / 对策 / 机检入口 / 适用条件」。

### 新条目 E-1 · 备案状态与 VCS 事实不一致
- 症状：报告自述「未 commit / 本单落码」，但 `git log` / `git show --name-only` 显示改动已在别的收口单落地，或归属提交粒度对不上。
- 根因：写码/验收方凭记忆写备案，未用 Git 事实回查；过程状态与代码状态分成两处手写。
- 对策：回执提交归属必须附 `git log -S` 或 `git show --name-only` 证据；状态以 VCS 为准。
- 机检入口：方案 5 `check-claim-fact.py`（②③）。
- 适用条件：所有修复/验收/判定类报告；历史留档不追改。

### 新条目 E-2 · 引文真实但行号错位
- 症状：`「…」` 引文在源码里确实存在，但标注的 `文件:行` 指到相邻行或另一处，验收无法按行回源。
- 根因：行号靠抄录记忆，改动后未刷新；证据形态合规但落点失真。
- 对策：引用前按行号重读目标行；行号随代码改动必须同步复核。
- 机检入口：方案 6（`check-evidence.py` E4 子规则，±3 行窗口）。
- 适用条件：所有带 `文件:行` 定位的报告。

### 新条目 E-3 · 契约/模型符号备好但生产零消费
- 症状：Provider、桥接、派生值、字段在契约层/数据层齐备，全仓 main 非 contract 目录零引用，UI 与控制层均未接管。
- 根因：分层先行、接线单滞后；「字段存在」被误当成「功能接通」。
- 对策：组装/接线单必须附生产消费点 `文件:行`；零消费符号入待接线台账，不许计完成。
- 机检入口：方案 1 `check-zero-consume.py`。
- 适用条件：名物库、气泡、地图回放、搜索等分层接入模块。

### 新条目 E-4 · 夹具正向不覆盖被测分支
- 症状：测试全绿，但夹具缺被测分支必需字段/形参，被测分支早退或走兜底，改坏行为也不红。
- 根因：夹具按 happy path 构造，未按分支条件逐项配齐；断言与夹具脱节。
- 对策：每个分支用例先核夹具条件字段齐备；反向改动该分支应能使对应用例变红。
- 机检入口：方案 2 `check-assert-strength.py` ④。
- 适用条件：JSON/Map 夹具驱动的引擎、规则、解析测试。

### 新条目 E-5 · 跨收集器可变状态无同步 / 帧级错配
- 症状：两路收集器/两帧之间共享普通可变 var，无锁无 `@Volatile`；或缓存/订阅在开合、回放、存档切换时不复位，产生跨周期残留。
- 根因：状态生命周期按单页面设计，未推演跨收集、跨回合、跨开合的共享窗口。
- 对策：共享可变状态收口到单一持有者；订阅随生命周期降级；缓存键含周期/会话维度。
- 机检入口：方案 9 `check-thread-sniff.py` ②；人工核生命周期释放链。
- 适用条件：ViewModel、回放栈、热门/历史流、地图渲染态。

### 新条目 E-6 · 同域夹带别单文件 / 测试 commit 夹带
- 症状：docs/app 路径已分离，但同一 app 目录内夹带别单代码，或测试 commit 带入无关用例，单号与文件无法一一回源。
- 根因：攒批提交时 `git add` 粒度粗；测试与代码同目录未拆单。
- 对策：提交前列 `--name-only` 逐文件对单号；共享改动单独成单并在台账注明跨单。
- 机检入口：方案 7（`check-commit-split.py` 扩展同域夹带规则）。
- 适用条件：所有代码 commit 与测试 commit。

### 新条目 E-7 · KDoc/注释口径过满与实现不符
- 症状：注释称「唯一出口 / 不受影响 / 全部同源 / 豁免」，代码存在第二调用点、未豁免目标格或分支口径不同。
- 根因：注释随旧版本写下，实现演进后未回改注释；措辞强度超出实际分支。
- 对策：改分支必同步复核相邻注释；过满词改为可证伪的具体表述。
- 机检入口：方案 8 `check-kdoc-claim.py`（首期清单型）。
- 适用条件：引擎规则、路径/视野、仲裁、兜底口径相关源码。

### 新条目 E-8 · 文档内嵌源码分叉现行脚本
- 症状：手册/报告/切片内嵌的源码片段、命令路径、常量口径仍是旧版，与现行脚本/源码分叉，照文档操作会复发旧缺陷。
- 根因：文档一次性抄录，脚本演进后无回刷机制；文档与代码成双事实源。
- 对策：内嵌代码优先引 `文件:行` 而非整段抄录；脚本改动同步刷文档引用。
- 机检入口：方案 4 `check-doc-source-drift.py`。
- 适用条件：校验脚本、构建脚本、管线命令相关文档。

### 新条目 E-9 · 多批次/跨词竞态收口标记丢失
- 症状：分批收口的特性，后一批改动把前一批的已收口标记/缓存键/复位点覆盖或遗漏，跨词/跨页状态串味。
- 根因：收口按批次独立验收，未做跨批次回归核对；标记位没有统一注册表。
- 对策：收口标记/缓存键集中登记；跨批次改动跑一次全量状态复位核对。
- 机检入口：暂无；先入人工复核清单，后续随方案 9 扩展。
- 适用条件：搜索翻页、热门/历史、回放告警复位、高亮批次收口。

### 新条目 E-10 · 工程兜底阈值无冻结规格出处却写成既定规格
- 症状：每页条数、末页算法、兜底半径、降级口径等为工程推定值，规格/切片/登记册无原文，报告却按既定规格描述。
- 根因：规格缺口期先落地兜底，事后未回填规格，推定值升格成口径。
- 对策：工程兜底值必须显式标注「工程兜底，待规格回填」；规格补齐后回写数值出处。
- 机检入口：`check-spec-flow.py` 四向对齐 + 人工核数值出处。
- 适用条件：所有规格缺口期落地的阈值、枚举、文案。

### 6.1 补丁统计
- 建议新增经验库条目：10 条（E-1~E-10）；其中 6 条对应 §5 可落地脚本，3 条先入人工复核，1 条挂靠现有 spec-flow 守卫。
