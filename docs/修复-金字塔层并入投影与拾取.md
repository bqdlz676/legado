## 二、缺口与根因

- 现象（上一单交接）：`host/SkyCanvasRenderer.kt` 的 `projectStars` 只扫内置 L0（8920 颗）；金字塔 L1/L2（+108,067 颗）经 `StarStore.ensurePyramid` 并入扁平数组后，既不参与投影也不参与拾取，暗星永远不上屏。
- 根因：投影遍历循环硬编码 `catalog.size`，未读 `catalog.pyramidSize`；拾取器本身是缓冲驱动的通用实现，断链点在投影出口没把金字塔星写进 `ProjectedStars`。
- 处置：投影遍历下沉到新建 `StarProjectionSource`，按 L0 → 已加载金字塔顺序双层合并；`ProjectedStars` 实现投影出口接口；渲染器只保留帧参数装配。

## 六、二阶 / 三阶影响

- 内存：投影缓冲 `ProjectedStars` 256 起步、2 倍扩容；最坏深景可见约十万颗时数组扩到约 131k 槽位，四枚 FloatArray + 一枚 LongArray + 一枚 DoubleArray 合计约 3MB 量级，帧间复用、不每帧 new 列表（§十二.2 零分配口径延续）。金字塔数组本身由 `StarCatalog` 持有，本单未复制星表数据。
- 首帧卡顿：金字塔加载完成后第一帧进入深景才会遍历增量层；缩览帧经 `:74` 层级短路不扫金字塔。低电模式 `SkyCanvasRenderer.kt:81` 把 magLimit 压到 6.5，金字塔整组跳过。
- 低端机风险：116,987 颗遍历 + 逐颗投影算子在弱机上的帧耗未实测；现有层级短路只挡 magLimit ≤6.5 的帧，深景帧仍全量遍历。该风险登记在未验证项，待真机 / CI bench 数据决定是否再做前缀截断。
- 后续第 3 层扩展：源按 `store.pyramidSize` 循环，新层并入目录数组后投影自动生效；访问器随 `StarStore` 既有金字塔槽位口径追加即可，投影循环无需改分支。
- 拾取下游：选中金字塔暗星后 `pickStar` 返回主键，`SkySheet.byId` 已支持金字塔索引解码（`StarStore.kt:128`）；暗星无中文名时名称回落空态，属关系层后续补齐项。

## 七、最强反对者反例（自查反例）

- 反例 1：「为什么不做按需分块投影（按天区 / 视场切块，只投影当前可见天区对应的星块）？」
  - 不做的理由：相机姿态每帧连续变化，天区切块边界要与视场球心对齐，需要 RA/Dec 球面空间索引；现有目录是扁平数组，无切块索引结构。一期软渲染下引入球索引的复杂度与内存代价高于收益，且规格 §八.4 定调软渲染 2D 投影背景。分块投影列为后续优化方向，不在本单范围。
- 反例 2：「为什么不做层内星等升序索引 + 前缀截断（排好序后从暗端截断，达标即停）？」
  - 本单先落全量遍历 + 层级短路；前缀截断是任务书允许的超标后备手段，不是首选。原因：L0 / 金字塔数组当前都未按星等排序，建排序索引要在加载期额外排序或落盘序；4ms 预算是否被 116,987 全扫突破，要等 CI / 真机 bench 数据。若实测超标，优化方向是按星等分段索引后前缀截断——截断只停止遍历、不移除达标星点，也不抬高下限星等；不允许用砍星数或提星等下限凑预算。
- 反例 3：「层级短路阈值 6.5 是否会误放 / 误裁？」
  - L1 星等带 (6.5, 9.0]、L2 (9.0, 11.5]（`StarCatalog.kt:307-310`）；magLimit ≤6.5 时所有金字塔星必被逐颗裁剪，整组跳过不改变结果。magLimit 由 `SkyParams.magLimitFromBlend` 连续算出、非有限回落 6.5，不存在阈值跳变。
- 反例 4：「合并后并列命中口径是否被改成近者优先？」
  - 未改。拾取器仍是半径内取最亮（mag 最小），星等并列取索引靠前（`StarPicker.kt:87`）；任务书「近者优先」按沿用既有实现理解，本单未动拾取比较口径。
- 反例 5：「会不会把未加载的金字塔空数组扫出脏坐标？」
  - `pyramidSize == 0` 时循环不进入；访问器越界回 0 / NaN / -1，与目录既有兜底口径一致。

## 十三、CI 首轮红诊断与回滚补丁
