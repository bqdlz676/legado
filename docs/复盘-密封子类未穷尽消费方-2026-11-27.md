# 复盘 · 密封子类未穷尽消费方（0ba8adc 双红根因）

## 一、事实链（逐条陈述，不转述）

- `0ba8adc`（其后一个 docs 提交）触发 CI：Verify 的 `Discover test classes` job 与 Screenshot 的 `Render screenshot frames` job 同时在 `:app:compileAppDebugKotlin` 失败。
- 两个 job 的失败日志指向**同一行**：`app/src/main/java/io/legado/app/ui/book/read/ink/InkReadActivity.kt:356:13` — `when expression must be exhaustive. Add the 'Conflict' branch or an 'else' branch.`
- 修复 `1c3165a`：在该 `when` 补 `EditSaveResult.Conflict ->` 分支（提示语用新增双语字符串 `content_edit_conflict`），并同步 `values/strings.xml` 与 `values-zh/strings.xml`。
- 影响面：一个密封子类漏接，导致**两个 job 同时红**，本轮从红到修复推回约 25 分钟（含取日志与最小改动）。

## 二、根因（不是「忘了写」，是机制缺口）

- 本项目密封类型（`sealed interface` / `sealed class`）与枚举被大量 `when` 消费，Kotlin 要求穷尽；但**沙箱禁编译**，穷尽性只能靠编译器在云端发现。
- 写码单在验收里被要求「推演二阶三阶影响」，但「新增密封成员 → 必须枚举全部 `when` 消费方」这一条没有被写成可机检的动作，于是只落在纸面推演。
- 更深一层：`EditSaveResult` 是 B4-04 单**自己新增**的结果态集合，消费方 `InkReadActivity` 属旧壳域（不在该单白名单），写码代理按白名单约束不去改它 —— **白名单边界把「必须同步的消费方」挡在了单外**，这是本轮真正根因。

## 三、二阶 / 三阶影响

- 二阶：任何「新增密封成员 / 枚举成员」的单，只要消费方在白名单外，就必然复现同类红；B4-06/B4-07 接线期还会再遇到（`InkActionDispatcher` 的 `OpenArtifact` 契约当前就在密封层里无路由）。
- 三阶：若继续用「白名单内改代码」的硬约束而不开「消费方同步例外」，写码单会系统性地把编译红外推给 CI，调度层被迫反复做同样的人工修红，吞吐被拉低。

## 五、反例与边界（先假设本复盘结论是错的）

- 反例 A：编译器已经会拦，加门禁是冗余。反驳：本仓沙箱禁编译，编译器只在云端回合生效，每漏一次就是一次 25 分钟级往返；门禁的价值是把它从「云端回合」提前到「工作树落盘前」。
- 反例 B：给 `when` 加 `else` 分支最省事。反驳：加 `else` 会让后续新增成员**静默**走同一分支，属降级；本单只用具名分支，不用 `else`。
- 边界：若某个 `when` 消费方本意就是「其余一律同一处理」，允许 `else`，但必须在 KDoc 写明「此 else 声明承接全部未来成员，新增成员须复核」。
