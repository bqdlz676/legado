## 六、反例推演

### 6.1 反例 a：两个同名常量在不同文件，未来有人 import 错源

- 风险：`PROGRESS_LINE_WIDTH_DP` 同名存在于 `ShelfParams`（2.0）与 `VerticalReaderParams`（1.0）；后续写码若 `import ...ShelfParams.PROGRESS_LINE_WIDTH_DP` 却用在阅读页，或反向 import，线宽就串域。
- 处置：选择「同名不同值 + 注释区分」，**不改名**。理由：改名（如 `SHELF_PROGRESS_LINE_WIDTH_DP` / `READER_PROGRESS_LINE_WIDTH_DP`）牵动两个转发链（InkTokens、VerticalTokens）、契约 symbol 字段、单测断言与既有引用面，本轮边界内收益不抵风险；同名不同值的防串靠三处：① `ShelfParams.kt:59-65` KDoc 写明两线语义差异与「禁止合并 / 统一」；② 契约两条 name 已拆 `reader-` / `shelf-` 前缀，锚点各自独立；③ 报告本节明示语义差异。
- 残留风险：import 错源在编译期不报错（两个常量类型同为 Double）。若后续出现第三处消费方，应在那时改名为带域前缀的符号，并同步转发链与契约。

### 6.2 反例 b：契约拆两条后，`--emit` 重生成会不会又合并回一条

- 现状：`check-design-tokens.py:269` `emit()` 按源码声明逐条抽取，`name = _kebab(symbol)`，每条记录 `aliases: []`，不做同名合并。两个文件同名符号会生成两条同名 `progress-line-width-dp` 草稿记录（当前 `docs/契约-设计token.emit.json:7908`、`:8193` 正是两条同名草稿）。
- 结论：自动 emit 不会把两条合并成一条带 aliases 的单 token；旧的合并结构是人工建档时手工并到一起的。
- 风险：① 下次人工整理 emit 草稿时，可能再次凭同名把两条并回一个 token——一旦合并，书架 2.0 与阅读 1.0 必然在别名锚点互相判 FAIL，门禁会当场红，不会静默放过。② emit 输出默认写 `契约-设计token.emit.json`（draft），覆写锁定契约需 `--force`（脚本 :271 守卫）。
- 处置：锁定契约两条已带 `ruling_ref` 指向本报告；emit 草稿残留同名记录列入 §六 N3，下次重生成后人工按 reader / shelf 拆分命名。

### 6.3 反例 c：2dp 在低密度屏是否出现非整数像素模糊

- 换算（px = dp × density）：mdpi 1.0 → 2px；hdpi 1.5 → 3px；xhdpi 2.0 → 4px；xxhdpi 3.0 → 6px；xxxhdpi 4.0 → 8px，均为整数。仅 tvdpi 1.333 一类非常规密度下 2dp ≈ 2.67px，存在亚像素抗锯齿柔化。
- 判断：书架竖线由 `Box.width(dp)` 布局确定宽度，Compose 测量阶段会把宽度吸附到设备像素网格；非常规密度下的亚像素余量由抗锯齿消化，不会出现硬边错位。阅读页 1dp 在 1.333 密度下 ≈1.33px，比亚像素余量更大且早已在线上，本轮裁决明确阅读线不变。
- 措施：本轮**不**加 `ceil` / 像素取整。理由：2dp 在全部标准密度下都是整数像素；为 tvdpi 边角密度引入取整会改变布局测量口径，属于凭直觉改代码。若后续真机在低密度屏观测到竖线发虚，再单独立项评估 `Box` 宽度像素取整。
