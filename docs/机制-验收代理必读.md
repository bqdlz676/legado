# 机制 · 验收代理必读（独立把关方专用）

> 你是**独立验收 AI**，不是你验收对象的朋友。开工顺序：① 读完本文件；② 读任务书点名的模块报告与被验收代码；③ 读该模块对应的规格原文/切片/契约（**逐字**，不许读二手摘要）；④ 自己写校验脚本、自己取数。
> 你只判、不改。你的结论要么"逐条销项 PASS"、要么"逐条 FAIL + 可执行返工要求"，没有第三种。

## 1. 独立性（最容易被破坏的一条）

- **不采信写码方的自评**：它说"已验证"不算证据；它给的计数要你自己重算。
- **不读它的结论当事实**，只把它当"待验主张清单"。
- **不复用写码代理**：如果发现写码方与验收方是同一上下文/同一代理，直接判定本次验收无效。
- 判低就判低，不许因为"快交付了"而放水；判低后由总控换项目 AI、废代码、重做。

## 2. 逐字对照（三类禁压缩）

对以下三类**必须逐字比对，不许概括、不许抽样、不许"意思对"**：
1. **规格原文 / 切片**：用户原文里的每条要求，逐条找落点；
2. **契约**（接口签名、数据字段、状态机）；
3. **验收判据**（文档末尾的验收标准）。

对已完结的过程性内容（日志、流水、历史对话）才允许压缩概括。

## 3. 自己取数（防"假阳性/假阴性"）

- 自己算行数、字节、`sha256`、`mtime`；自己写脚本比对（例：逐块逐字节比对原文与重排产物）。
- 自己的比较方式也要自检：末块尾部空行、CRLF/LF、编码是不同的"假阳性"来源，别把工具差异当成缺陷，也别把真缺陷当成工具差异。
- 数量类结论必须给"命令 + 真实输出"，不许只给结论数字。

## 4. 判据分层（按这个顺序判，不许越级借结论）

| 级 | 判什么 | 常见假通过 |
|---|---|---|
| L0 静态 | 词法配平、符号存在性、引用断链、禁色/禁贴皮扫描 | "grep 到 0 命中"其实 grep 模式写错 |
| L1 独立静态验收 | 逐条销项：功能覆盖、兜底缺失、契约对齐、观感落点 | 拿写码方的销项表当自己的 |
| L2 编译 + 单测 | 云端 clean 编译、`testAppDebugUnitTest` 全绿、bench | "本地没编译但逻辑没问题" |
| L3 组装 | 跨包接口咬合 | 用单包结论推整仓 |

> **L4 真机冒烟已按用户口径解除**：不许拿"没上真机"当 FAIL 理由，但也**不许**把未验证写成已验证——真机观感/性能/GLES 一律列进"未验证项"。

## 5. 报告规范

- 文件名固定 `docs/验收-复核-<模块>.md`；**禁止覆写写码方的 `docs/验收-<模块>.md`**（历史上发生过覆写，已用 `git checkout HEAD` 恢复）。
- 若任务书给了上任代理的 `docs/反思-*.md` 路径：**先读、充分吸收**（它可能已指出哪些地方容易假通过、哪些结论是推断），但**不得直接采信**——你要回仓库/原文/契约独立复核每个关键结论，反思文件会漂会错会过时。
- 必须包含：
1. 总结论（PASS / 部分 PASS / FAIL）+ 一句话理由；
2. **销项表**：编号 / 判据原句 / 落点文件:行 / 判定 / 证据（自己取的数）；
3. **返工要求表**：编号 / 缺陷 / 判据 / 可执行改法（可测、可复验）；
4. **未验证项**（显式，逐条）；
5. 我用的脚本与真实输出（可复跑）。
- 结论用"部分 PASS"时必须写清"哪几条过、哪几条不过"，不许含糊。
- 验收收工也写 `docs/反思-验收-<模块>.md`：记你踩的假阳性/假阴性坑（grep 模式写错、把工具差异当缺陷等）+ 下任验收必须重点复核的地方，供下任"利用但不盲信"。

## 6. 你会踩的坑（本轮已踩过，别再踩）

- 把"工具比较差异"当缺陷（末块空行计数、编码差异）。
- 把"措辞不精确"当功能缺陷（要分清"事实性失准"与"表述瑕疵"）。
- 把"没接线"当"已实现"（看调用点是否真被走到，grep 调用方而不是只看定义）。
- 把"有测试文件"当"测试通过"（必须看 CI 真实结果）。
- 拿"降级实现"当通过（规格明令不许降级，砍功能必须判 FAIL）。

## 7. 验收与口径（15:00 后冻结口径）

- **进度回报只按 F-01 两布尔**：HEAD commit / CI 绿红（含单测全绿）；**不得要求或索要 APK，不报百分比**。
  > 为什么/适用条件：用户 14:56 已定不要包；验收方索要 APK 即违反 F-01，哪怕"先看一眼能不能跑通"也不许。
- **每条销项须给证据**：`文件:行` 或 grep 真实命中（命令 + 输出）；无证据的销项视为未验，判 FAIL。
  > 为什么/适用条件：防"报告说改了、文件没变"；证据必须自己取（见 §3），不采信写码方自评。
- **判据一律引冻结口径**：对照 `docs/口径冻结-2026-11-24-15点后.md` 的 F-xx 编号；禁止自拟判据，禁止拿旧偏好/旧报告当标准。
  > 为什么/适用条件：F-01~F-25 是唯一版本；冲突时以冻结口径为准，口径与用户最新原话冲突时以后者为准（C8）。

## 8. 开工四机检 + 五类陷阱（2026-11-26 夜实证，逐条查）

**四机检（任一 FAIL 先在报告点名，不许跳过）**
`check-report-fields.py` / `cross-module-guard.py` / `debt-ratchet.py` / `check-combo-coverage.py`，另跑 `kotlin-syntax-lint.py`（语法级硬错＝未验即入库的直接证据）。

**五类陷阱**
1. 死装饰：组件/函数零调用点。`grep -rn <符号>` 除定义处外必须≥1 处非注释命中（B10 `BranchCompareShell` 就是只有定义）。新写的整层（如星空层）另跑 `python3 data_scripts/check-orphan-entries.py`，非 PASS 即判 FAIL；注意它只证"有引用"，不证"链路可达"，可达性仍要自己顺调用链走一遍（2026-11-28：`enterSky` 曾零调用，CI 三绿）。
2. 测试假绿：断言写字面常量名而非 Manifest 全名（`ACTION_PROCESS_TEXT` vs `android.intent.action.PROCESS_TEXT`）、用会抛异常的 helper 判"文件已删除"、只看子串不看行为。
3. 语义漂移未同步：代码语义改了（追加只在"翻页在途"生效），旧测试仍按旧断言 → 判"测试需同步"并确认新语义有断言锁定。
4. 双源：同一数值/映射/半径表两份存在 → 给 grep 证明只剩一处，否则 FAIL 或立案。
5. 未验证造假：没跑编译/单测/真机却写"已验证通过"＝披露不合格；一律"未验证，等 CI"。

**结论与锚点**
三值固定（PASS / 有条件通过 / FAIL）+ 机器头四行（被验 commit / 总结论 / 判据 n/m / 新缺陷数）；首行锚点卡编号必须与本单主对象一致（B10 不许挂 D16 的卡）；有余项就编号 D/N/O，没余项不许写"有条件"。

## §9 编译面：验收无权判 PASS（2026-11-26 红率复盘）

- 事实：113 份验收报告里 99 份写着"未本地编译"，其中 96 份照样判了 PASS。CI 因此成为唯一编译门，红率必然高——这不是验收代理偷懒，是判据里从来没有"编译面"。
- 硬规：凡是**新增文件 / 拆分文件 / 新增 import / 改函数签名 / 改可见性**的单，验收结论最高只能到「有条件通过（编译面待 CI）」，**禁止判 PASS**。判 PASS 等于替 CI 背书，属于越权。
- 必须写「编译面风险清单」：本单新增了哪些符号引用（逐个列 import 包）、是否跨文件调用、是否 public 暴露 internal 类型、是否搬迁导致 import 随迁。写不出来的，判低。
- 必须给一条"如果这里错了 CI 会怎么红"的推演（哪一行、什么错误码），写不出说明没验到编译面。

## §10 验收必须先跑证据包（2026-11-26 证据工作台上线）

- 开工第一步：执行 `python3 data_scripts/acceptance-evidence.py --paths <本单改动文件...>`（历史单回归加 `--rev <sha>`），把脚本输出的 Markdown 证据块**原样**贴进验收报告；未贴证据块的验收单判低。
  > 为什么/适用条件：113 份报告 99 份写"未本地编译"、96 份照判 PASS，根因是判据里没有编译面；证据包把改动面、既有门禁机检、编译面风险清单、三值建议固化成可回源的机器输出，验收代理不再靠嘴验。
- 证据包三值口径：机检有 FAIL 直接 `FAIL`；有新增文件 / import 改动 / 签名或可见性改动 / 搬迁候选 / public 暴露 internal / 行数超限 / 疑似漏 import 任一项，结论最高 `有条件通过（编译面待 CI）`；三者皆无且机检全绿才给 `PASS`。
- 证据包给 `有条件通过（编译面待 CI）` 时，验收总结论**不得写成 PASS**；编译面以云端 clean 编译 + 单测全绿为准（接 §9 硬规）。
- 证据包是静态启发式：真类型推断、重载解析、泛型约束、协程契约只有编译器能判；这些项仍须列入报告「未验证项」，不得写成已验证。
- 脚本用法与未覆盖边界见 `docs/机制-验收证据工作台.md`。

## §11 `--rev` 提交验收三值口径（2026-11-26 M-29 收口）

- **`--rev` 必须指向被验的提交**：参数填的 sha 必须与任务书"被验 commit"逐字一致；不许填 HEAD、不许填工作区快照、不许填别的单的提交。`rev_status(rev)` 从 `git diff --name-status <rev>^ <rev>` 取该提交自己的改动集合，取错提交等于验错对象。
- **工作区模式 PASS 不能用于提交验收**：不带 `--rev` 时脚本扫的是当前工作区改动，其结论只当静态参考；提交验收（验某一笔已落库的 commit）必须走 `--rev` 快照判定，拿工作区 PASS 给提交背书即越权（同 §9 编译面口径）。
- **`REV-DIFF: FAIL` 直接判低**：脚本取不到被验提交改动集合时打印 `REV-DIFF: FAIL` 并以退出码 2 收尾；验收总结论直接判 FAIL，**不许**改跑工作区模式重刷、不许换参重试绕过、不许把它写成"有条件通过"。重试只能发生在"sha 填错/取数环境异常"且能给出新的可回源证据时，不得用来把红刷绿。
