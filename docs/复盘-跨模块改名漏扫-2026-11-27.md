# 复盘 · 跨模块改名漏扫（2026-11-27）

## 一、发生了什么

Q-311 把卡片基座 `CardSurface` 改名为 `CardBase`（14 个卡片文件 + 1 个单测，36 插入 / 36 删除，纯同词替换）。写码方自检第 6 条写「全仓 `grep -rn "CardBase" app/src/main/java --include=*.kt` = 35」，独立验收 Q-317 复核后判「有条件通过（编译面待 CI）」，其结论里明写「二阶三阶：全仓 `CardSurface`（kt+xml）0 残留；其它包无 `import ui.card`」。

CI 实测（run 45885405578，ee229f4 的 Screenshot 工作流）：

```
e: file:///home/user/runner/work/legado/legado/screenshot/src/test/java/io/legado/app/ci/screenshot/CardFoundationSnapshotTest.kt:17:30 Unresolved reference 'CardSurface'.
e: ...CardFoundationSnapshotTest.kt:53:17 Unresolved reference 'CardSurface'.
e: ...CardFoundationSnapshotTest.kt:57:21 @Composable invocations can only happen from the context of a @Composable function
> Task :screenshot:compileDebugUnitTestKotlin FAILED
BUILD FAILED in 2m 50s
```

即：改名后 `screenshot` 模块（独立的 Gradle module，源码在 `screenshot/src/`，不在 `app/src/`）仍引用旧名，Screenshot 工作流编译失败。修复落点 `4fd2d29`：`CardFoundationSnapshotTest.kt:17/53` 与 `CatalogCardsSnapshotTest.kt:32` 三处同步为新名，`grep -rn "CardSurface" --include=*.kt screenshot/` 归 0，`kotlin-syntax-lint.py` 两个文件 PASS。

## 二、根因（不是手滑，是判据口径）

1. **扫描域写死成 `app/src/main/java`**：写码方与验收方都把「全仓」当成了「app 模块主源集」。这个仓是多 module 结构（`app`、`screenshot`、以及若干 test-only 模块），改名类改动的爆炸半径天然横跨所有 module 的 `src`。
2. **没有把「改名」当成跨模块事件**：改名与「改一个函数的实现」不同，前者是**符号在全仓的引用面收敛**，后者只影响本文件。判据应随改动类别切换，两人都沿用了「本包内自检」的旧模板。
3. **验收是静态复核，不是编译复核**：`grep` 只在被扫描的目录里为真，扫描域外的引用它看不见，于是「0 残留」成了可被扫描域操纵的假绿——这与 ㊾「空集判 PASS 就是假绿」同族。
4. **CI 才是最终判据**：本仓沙箱禁编译，编译面结论只能由 CI 给。写码方与验收方都标了「编译面待 CI」，方向对；错在没有把「跨模块引用」列为必须由 CI 兜住的清单项，于是漏项无人认领。

## 三、沉淀成规则（可执行载体）

规则 R-跨模块改名（适用于任何「符号改名 / 签名变更 / 模块搬迁」类改动）：

1. **扫描域由 `settings.gradle(.kts)` 反推**，不许手写目录：先列出全部 Gradle module，再对每个 module 的 `src/` 做 `grep -rn <旧符号>`；单一目录的 grep 不作为「全仓 0 残留」的证据。
2. **报告必须贴扫描域清单**：把 module 名逐一列出、每条给出命中数（0 也要写），缺一个 module 即视为未验。
3. **验收方独立复算扫描域**：不许沿用写码方给的目录；发现扫描域小于 module 全集，直接判不合格而不是判「有条件通过」。
4. **CI 未绿前，「0 残留」只能表述为「在已扫描域内 0 残留」**，禁止写成「全仓 0 残留」——这是本单真正踩的那句话。
5. **改名的同一次派单里必须包含 test-only 模块**（`screenshot` 之类的快照测试也是代码，它引用的符号与主源集同等重要）。

## 四、二阶三阶影响

- 二阶：`screenshot` 模块的红会连带 52 视觉基线停摆——快照渲染不出帧，观感基线永远空，后续所有「看起来对不对」的判断都失去机器证据。
- 三阶：如果这类漏扫反复发生，团队会把「CI 红」当成常态噪音（本仓历史上就有过 8 连红无包），于是真红被忽略，制度退化。
- 反向：本次是 CI 先发现、人后补，说明「编译面交给 CI」的分工是对的，要保住的正是这条链，而不是把 grep 写得更长。

## 五、跨领域同类对照

- **编译器/链接器**：符号解析天生是跨编译单元的，任何「本地 rename 工具」都靠索引覆盖全工程；只扫一个目录的 rename 与只重命名本地变量的幼稚做法同构。
- **重构工具的 find-references**：IDE 的 rename 之所以安全，是因为索引包含所有 source root（含 test、含 sample），这与本规则第 1 条同构。
- **供应链清单（SBOM）**：只审一个仓库的依赖清单不等于全供应链安全；扫描域不全时，「0 漏洞」是伪结论。采纳它的报告格式——必须列全清单范围再给结论。

## 六、认知成本

- 新人接手时最大的坑不是代码复杂度，而是**不知道「全仓」在这个仓里指什么**。`settings.gradle` 是唯一事实源，建议在其旁边写一行注释指向本复盘。
- 本单留下的教训一句话可记：「改名要扫 module 全集，CI 未绿不许说全仓 0 残留」。

## 七、改坏推演（本复盘的判据会不会假绿）

1. 把扫描域写成 `app/src/main/java`（原错法）：`grep -rn "CardSurface" app/src/main/java | wc -l` 得 0，看起来「全仓干净」，但 `screenshot/src` 里仍有 3 处命中——扫小域就能产出假绿，这正是本单事故的复现路径。
2. 把判据 P1 改成只扫 `.kt` 不扫 `.xml`：仓内 `screenshot` 快照测试若以 XML 引用就会漏，故 P1 的 `--include` 白名单必须显式列出并接受复核。
3. 把「CI 绿」从判据里删掉：静态 grep 全绿但 Screenshot 工作流仍可能因 test-only 模块编译失败而红，删掉 CI 判据即把唯一能看见跨模块引用的那张网剪掉。
