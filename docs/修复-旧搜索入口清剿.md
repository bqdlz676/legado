2. `external share routes plain text to shelf overlay and stays exported`：`SharedReceiverActivity` 文本分支调用 `ShelfSearchRouter.openShelfSearch(this, text)` 且不再引用壳类；Manifest 中分享 Activity 仍 `exported="true"` 且保留 `PROCESS_TEXT` / `SEND` 双过滤器；`MainActivity` 声明两个 extras 常量并 `handleSearchIntent` 切书架 Tab。对应派单断言「分享入口改道后仍能打开搜索（Intent 构造锁定）」。
3. `discover page entries route to shelf overlay through request handoff`：`ExploreInkFragment` 两处调用点计数为 2；Fragment 暴露 `openSearchRequest` 并在建栈时消费 handoff；画面层接收 `searchRequest` 并按 `seq` 挂 effect 打开浮层。对应派单断言「浮层入口在发现页可触发（入口函数存在且被调用的源码回证）」。
4. `handoff enqueues consumes and sequences requests`：纯 JVM 语义——入队可消费、消费即清空、后到覆盖先到、`seq` 随入队自增；用例首尾各 `consume()` 隔离单例残留。
5. `scoped routes pass SearchScope string through router`：书详情标签 / 书源管理 / 书源编辑 / RSS JS 桥单源重载均经 router 透传 `SearchScope(...).toString()`；作者 / 书名入口只传关键词走全书库。

### 6.1 反向推演（先假设本方案错误，找反例与边界）

- 反例 A：跨页拉起 `MainActivity` 时它不在前台任务栈，会不会再起一个主壳？——不会。`MainActivity` Manifest `singleTask`，router 另加 `SINGLE_TOP | CLEAR_TOP`；`startActivity` 工具自带 `NEW_TASK`，singleTask 复用既有任务实例，走 `onNewIntent`。
- 反例 B：冷启分享时书架 Fragment 尚未建栈，请求会不会丢？——不会。`handleSearchIntent` 先 `enqueue`；Fragment 缺失时单例保留，`InkShelfFragment.onFragmentCreated` 消费；Intent extras 双保险，进程死亡重建后仍能从 extras 落词。
- 反例 C：浮层打开后重复收到同一关键词请求，会不会不触发？——不会。`seq` 每次入队自增，`LaunchedEffect(searchRequest?.seq)` 键变化即重跑。
- 反例 D：单源检索改道浮层后，作用域会不会被全书库默认范围覆盖？——不会。`VM.attach(initialKey, initialScope)` 已初始化分支在 `initialScope` 非空时 `searchScope.update(..., save = false)`，单源范围不写回全局偏好（与旧 `SearchScope` 单源不缓存口径一致）。
- 反例 E：初始词非空会不会被提交两次（effect 一次、attach 一次）？——不会。`attach` 内部对非空初始词 `QueryChange + submit`；画面层 effect 只回填本地输入态并调 `onAttachSearch`，不再显式 `onSubmitSearch`。
- 反例 F：书源管理页局部过滤会不会被误删？——没有。被改道的是 Sheet「搜索」行的找书跳转；顶栏 `SearchField` 与 `vm.onQueryChange` 列表过滤链路原样保留。
- 反例 G：删除壳文件后，结果跳转分流会不会丢？——不会。本地 / 未藏书卷分流在 `InkShelfFragment.openSearchItem` 既有实现，入参键沿用旧页口径。
- 反例 H：死壳 `ExploreFragment` 清空函数体后会不会编译破接口？——不会。`override fun searchBook(bookSource: BookSourcePart)` 签名保留，仅函数体置空；接口声明在 `ExploreAdapter.CallBack:738` 未动。

## 七、二阶 / 三阶影响推演

- 二阶 1（外部分享冷启）：外部 App 冷启唤起时，`SharedReceiverActivity` 透明壳 `onCreate` → `dispose` → router 拉起 `MainActivity`；若文本含链接仍走原 `startActivity<MainActivity>()` 链接分支。分享入口不直接碰浮层组件，无 Compose 上下文依赖。未验证项：冷启首帧浮层弹出时机、IME 弹起遮挡（需真机）。
- 二阶 2（书内搜索体验）：书内查找走 `SearchContentActivity` 独立链路，词典走 `DictDialog`，均不路由本检索栈，本轮改动不波及其翻页 / 高亮口径。
- 二阶 3（Manifest exported 安全）：摘除的壳原本 `exported="false"`，本就不可被外部直接唤起；保留的 `SharedReceiverActivity` 导出属性与 intent-filter 未改。新 extras `shelfSearchKey / shelfSearchScope` 只在 `MainActivity` 内读取，未新增任何导出组件、未新增 deep-link。
- 二阶 4（作用域残留）：Fragment 作用域的 `InkSearchViewModel` 在 Tab 切换间保留；一次单源检索后，再从书架页眉按钮打开浮层走 `attach(null, null)`，已初始化分支不清空旧作用域。此为既有浮层行为延续，非本轮回退；若需「按钮新开必回全书库」，后续单可在无请求打开时显式重置 scope，记为挂账。
- 二阶 5（配置变更）：旋转重建 `MainActivity` 时 `onActivityCreated` 会重读 intent extras 再次排队，浮层可能在旋转后重新弹出；旧独立页旋转时保持原查询页，行为口径略有差异。边界保留，未在本轮加 extras 消费后清除逻辑（改动面会扩到 intent 变异），列入未验证项。
- 三阶 1（双栈收口）：壳拆除后，全书库 / 单源检索只有浮层一条生产路径，验收 N3 的两套并行检索栈在 UI 入口侧已并轨；`SearchScreen.kt` 整页 Composable 残留拆解留后续单（见第五节第 1 条）。
- 三阶 2（JS 桥兼容）：`searchBook` 两个重载签名不变，书源脚本无需改写；作用域串格式 `名称::url` / 逗号分组与旧页一致。
- 三阶 3（死壳对）：`ExploreFragment` / `ExploreAdapter` 整体仍属旧壳清理交接项（验收未验证项已记），本轮只清空其中搜索跳转，未拆除整对死壳及其布局菜单。
