## 二、根因与选型

- 根因：Q-497 把「四要素逐字落盘」当成完成，只渲染文本，未接打开链接的入口；g68 / g76 静态闸判不到「文本是否可交互」。
- 选型：`Modifier.clickable` + `LocalUriHandler.current.openUri(...)`，未选 `LinkAnnotation`。理由：
  1. 本组件每行是单一整行样式、一行对应一个 URL，整行热区与点击目标 1:1；`clickable` 挂在整行上，热区形状与 48dp 下限可控。
  2. `LinkAnnotation` 要先构造 `AnnotatedString` 并只在标注子串上挂点击，可点面收缩到链接子串，48dp 整行热区与 `Role.Button` 语义都要另补一层；当前两行文案是「名称 · URL」整行署名，整行可点更符合署名行的交互预期。
  3. `LocalUriHandler` 是 Compose 官方打开外链入口，不绑 Activity / Context，与组件「不绑 Context」的既有约束一致。
- 语义口径：`clickable` 同时带 `role = Role.Button` 与 `onClickLabel`（读屏标签）。`role` 用于把可点行播报为按钮；`onClickLabel` 给读屏提供中文标签（「打开 HYG 数据来源仓库」/「打开 CC BY-SA 4.0 许可页」）。二者均由 `clickable` 的具名参数直接写入 semantics，未另起 `semantics {}` 块。

## 六、反例与边界（最强反对者自查）

- 反例 1：「行文案被改了，映射会不会失配？」`urlForLine` 按整行字符串等值匹配；`sourceLine` / `licenseLine` 本身由常量拼接，测试直接拿这两个 val 做键，文案与键同源。若将来文案格式化调整，必须同步改 `when` 分支键；例 2 / 例 3 会在键失配时变红。
- 反例 2：「URL 为空或畸形会怎样？」两个常量在例 1 用 `java.net.URI` 解析并断言 https + 主机非空；`url?.let(...)` 对 null 安全，映射为 null 的行（衍生行 / 未知行）不会调 `openUri`。
- 反例 3：「热区 48dp 会不会把三行署名挤变形？」`heightIn(min = 48dp)` 只设下限，行高随 14sp 文案自然撑开；Column 既有 `padding(12.dp)` 与宿主 `padding(top = 56.dp, end = 12.dp)` 未动。
- 反例 4：「读屏会不会把两行都念成同一按钮？」两行 `onClickLabel` 分别写仓库名与许可名；`Role.Button` 标注可点语义，静态衍生行不带 role。
- 反例 5：「离线时点链接是否崩？」`UriHandler.openUri` 由系统处理外部 Intent；组件不捕获跳转结果，离线 / 无浏览器场景沿用系统兜底，本组件不抛异常。
