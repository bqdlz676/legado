## 四、复制成本量级估算（不拍脑袋）

口径：FloatArray 每格 4 字节；尺寸取解码器护栏常量与实测资产。

| 栅格形态 | 尺寸（格） | 单份副本体积 | 依据 |
| --- | --- | --- | --- |
| 合成回落场默认 | 32×32 = 1024 | 4096 B ≈ 4.0 KiB | `HeightMapDecoder.DEFAULT_GRID_N=32`（`:83`） |
| 实测真实 DEM | 1024×1024 = 1,048,576 | 4,194,304 B = 4.0 MiB | `assets/map/china_height.png` 实测 `PNG 1024×1024 8-bit grayscale` |
| 解码像素上限 | 4,000,000 | 16,000,000 B ≈ 15.3 MiB | `MAX_PIXELS=4_000_000`（`:70`） |

- 频次：门面 `decode` / `decodeInline` 每次战役装配走一次（`CampaignController.resolveHeightMap` 每 `load(…)` 一次）；缓存命中复用同一实例，不重复解码。
- 本单选型是**热路径零拷贝**：标量消费走 `valueAt` / `at`，不复制数组；只有调用方显式要自有数组时才付 `toFloatArray()` 一份副本。当前 main 侧唯一批量消费点 `toHeightRaster` 逐格标量读，不导出数组，故正常装配路径无额外栅格复制。
- 反事实对照：若改为「每次命中都返回防御性副本」，1024² DEM 每次命中瞬态多分配 4.0 MiB，4MP 上限单次 15.3 MiB；回放 / 沙盘二次命中越频繁，GC 压力随「命中次数 × 栅格体积」线性放大。这是本单不采用命中即拷贝的原因。

## 五、二阶 / 三阶影响与取舍

- 一阶：缓存源栅格无法经公开 API 被改写；共享副本写串味路径在类型层面封死。
- 二阶：
  - 既有消费点全部切到访问器；`HeightRaster`（0..255 IntArray 姊妹类型）不在本单范围，仍暴露 public `data`，同型潜在写口见 §七。
  - 未来需要整栅格数组的消费方必须显式调 `toFloatArray()` 取副本，拿不到活引用；少了「直接摸数组」的捷径，换安全性。
- 三阶（LRU 容量 2 的复用率影响）：缓存槽位上限 2（`HeightMapRasterCache.kt:19` `CACHE_CAPACITY=2`），第三种不同高程源入槽即逐出最久未用；本单零拷贝不改变槽位与复用率，但若改命中即拷贝，被逐出副本随 GC 回收、源栅格仍只占一份；容量 2 下连续切换三张 DEM 时复用率本就偏低，复制方案会在每次未命中后的首批命中上叠加拷贝开销。
- 并发：`getOrDecode` / `resetCache` 仍 `@Synchronized`；密封后返回实例内部状态不可变，并发读无需再加锁。

## 六、自查反例与边界（假设本方案错误的地方）

1. **空数据 / 坏栅格**：生产者返回 null 或抛异常仍只记未命中、不写槽位（缓存既有口径不变）；`valueAt` 下标越界由调用方索引保证，既有 `at(col,row)` 提供边缘钳制入口。
2. **类加载期静态初始化阻塞**：本单不改初始化链路；若挂死发生在静态装配阶段，类型密封不覆盖该面（沿用 Q-243 缺口口径）。
3. **反射 / 第三方库绕过私有字段**：Kotlin `private` 对同模块反射不绝对封闭；仓内当前无反射读栅格代码，该残余风险在报告显式声明，不夸大为「绝对不可变」。
4. **data class `copy` 形参改名**：`copy(pixels = …)` 形参名随主构造器改名；仓内除 `:472` 外无其它 `copy(data=…)` 调用（grep 已清零，见 §八）。
5. **降采样新数组**：`downsample` 产出独立 `out`，源栅格不被回填；未超护栏时原样返回源实例，密封后该实例也不会被外部改写。

### 11.1 红牌原文（三行 unresolved reference）

### 11.2 两条路线权衡（本轮唯一一次改这里，先权衡再二选一）

| 维度 | 路线 A：map 键保持 String 哈希，改读 `victim.value.key`（采纳） | 路线 B：map 键改 `CacheKey` 复合键（哈希+宽+高） |
| --- | --- | --- |
| 命中语义 | 入口 `getOrDecode(contentHash, producer)` 解码前拿不到栅格宽高，查找只能按哈希前缀；命中 = 同前缀槽位，尺寸不参与查找。贴合现有「解码前即可按哈希命中、免去二次 inflate」契约（`:35` 注释）。 | 复合键查找需要宽高，但宽高只有 producer 解码成功后才知道；入口签名无尺寸，解码前无法构造复合键。要成立须改双层结构（哈希前缀 → 尺寸子表 → 槽），或先解码再查，直接违背缓存目的。 |
| 碰撞面 | 16 hex（64-bit）前缀相撞才串味；本仓源为本地 PNG / Base64 确定性解码，同源同尺寸，不同源同 64-bit 前缀概率极低。尺寸差异在碰撞时只被台账记录，不拦查找。 | 尺寸纳入判重，可杜绝「同哈希不同尺寸」串味；但代价是嵌套 map、两级查找、命中路径复杂度上升。 |
| LRU 逐出失效口径 | 逐出按 `slot.lastUsed`；台账从 `victim.value.key` 读身份；`remove(victim.key)` 仍用 String 键，与插入键一致，失效口径不变。 | 逐出与插入都须换成复合键删除，`getOrDecode` 三条写路径（命中重插 `:69`、未命中入库 `:78`、逐出 `:86`）连锁改造。 |
| 改动面 | 仅 `evictIfNeeded` 内字段读取一处；入口签名、map 类型、命中流程不动。 | 类型签名 + 双层结构 + 全部写路径连锁改，编译面与单测面同步放大。 |
