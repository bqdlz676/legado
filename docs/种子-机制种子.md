# 种子：机制在岗自检（接手第一页）

> **口径已失效（2026-11-26，Q-282）**：`ReaderProvider`（含 `readerProvider` authority、`ReaderProviderRoutes` 路由表/分发、`ReaderProviderRoutesTest`）已封死并整体清除，详见 `docs/修复-清除ReaderProvider.md`；本段保留为历史记录，勿据以施工。

一句话：`bash data_scripts/seed-check.sh`

它输出三件事——每一块机制是在岗、还是缺了、还是红的；末尾两布尔 `HEAD=<sha>  CI=<green|red|running|none>`；最后一行 `SEED: READY` 或 `SEED: INCOMPLETE`。

## 为什么要有这一页

仓库里已经接线 50 个门禁。全量跑一次，稳定出现 3~6 项红，绝大多数与本次改动无关（历史文档欠账 118 份、别单在飞的队列抖动、历史混合提交 `e8ce4a8`、24 条 selftest 历史欠账）。接手者第一次跑全量，会看到一屏红，无法分辨「哪条是我造成的」，几次之后就开始忽略红——门禁退化成装饰，这比没有门禁更危险（它给出虚假的安全感）。种子只跑阻断级，并把缺失模块以 `MISSING` 显式记账，**缺失绝不静默跳过**：静默跳过就是假绿。

## 种子覆盖什么（9 项自测 + 2 项契约）

1. 门禁接线（孤儿基线 0）：保证没有门禁被悄悄摘掉。
2. 分片清单净化（自测 4/4）：保证 CI 分片喂给 Gradle 的清单里没有 `object`/`data class`/`interface`/无源残留/无 `@Test` 的伪条目——实测 644 条里剔除 19 条，伪条目会让 Gradle 空扫、分片负载不均。
3. 提交来源（自测 3/3）：保证每个新源码文件都有 `docs/` 里**文件级**回源，目录名不算回源。今晚 CI 两次编译真红就是目录级 `git add` 把未验收的在飞产物扫进提交，这条门禁的职责就是不让人再犯。
4. 提交分桶（自测双向）：保证一笔提交不混桶；生成器产物（`docs/索引-*.md`）只有在 `GEN:START…GEN:END` 区间内变更才豁免。
5. 空集假绿（自测 7/7）：保证「零命中」不会被当成「通过」。
6. workflow 契约（自测 3/3）：保证契约测试点名的路径与 workflow 里真实存在的一致。
7. 永远找问题（自测含历史口径夹具）：保证每份回执都逐条带状态词，且整节「一条待裁兜底」不再能骗过门禁。
8. 挂死 culprit 取证（自测 3/3）：一条命令从 job 日志点名「有 STARTED 无终态」的嫌疑用例，替代肉眼翻 830 行。
9. 挂死二分（自测 3/3）：161 条嫌疑 → 81/80 二分，最坏 8 轮定位到 1 条类。
10. 设计 token 契约（颜色/线宽/辉光半径/动画时长/内存预算 ↔ 源码常量）。
11. 阻断级门禁 `--blocking-only`（历史噪声只进审计，不拦 push）。

## 铁律（每条都注为什么）

- **禁目录级 `git add <dir>`**：会扫进未验收的在飞产物。今晚的代价是 CI 编译真红（`ImportSourceGroup.kt:40` 在 `java.net.URI` 上调 `lastPathSegment`）。逐个文件 add，add 完 `git diff --cached --name-only` 逐行核对。
- **一笔提交一个桶**（脚本 / 工作流 / 文档 / 业务代码）：混桶之后无法回滚单个意图，㊵ 会红，而且历史 commit 不可拆——只能长期挂账。
- **CI 红即全队停发新功能单，先修红**：红着往上叠功能，等于把红的归因成本无限放大。
- **修复最小改动立刻 push，不等验收**：CI 本身即验收；等验收只会让红的窗口变长。
- **分片 `timeout-minutes: 15`**：绿跑单片实测 268~320s，45 分钟只让静默挂死白等，且取消后仍取不到 culprit；15 分钟取消后日志可直接下载。
- **`testLogging { events "STARTED","PASSED","FAILED","SKIPPED" }` 四事件必须在**：这是挂死时唯一能定位的证据源，关掉它等于把盲区变黑箱；只开 STARTED+FAILED 时绿跑用例不进日志、配对失效（Q-277 已补齐四事件，commit `faa6d80`）。
- **禁 `sleep`/`wait_agent` 长阻塞轮询**：CI 轮询外置成后台脚本，主控不空转（平台会直接拦 `sleep 60`）。
- **只报两布尔**（HEAD、CI 绿红含单测全绿）：不报百分比、不报包；百分比在长链路上必然失真（历史上出现过"55% 时 8 连红无包"）。
- **门禁只能否定式**：它证明"没有已知的这类错误"，不能证明"东西好"。见下节。
- **每条报告带「新发现问题」并逐条带状态词**（已修/已入队/判废/待裁/已闭环）：否则"I think it's fine"会接管全部结论。
- **降级必须带补偿**：任何门禁从阻断降到审计，都要写明事后由什么发现（夜间 job / 收口单 / CI 侧等价检查）。没有补偿的不许降级——降级而不补偿就是悄悄取消报警器。
- **验收独立**：写码与验收不是同一个 AI，验收逐字对照原文，禁自评代验收。

## 已知坑（今晚踩过，别再踩）

- `git commit -m` 里带反引号会被 shell 展开，用 `-F <(printf ...)`。
- 提交前 `pgrep -x git` 确认无进程，再删 0 字节 `.git/index.lock`；多代理并发 `git status` 会持续占锁。
- GitHub job 日志：`curl -sL -H "Authorization: Bearer $TOK" .../actions/jobs/<id>/logs`，**不加 `--location-trusted`**（401）；在跑的 job 取日志返回 401，属正常，不是故障。
- 沙箱无 JDK：禁 `./gradlew`、禁 kotlinc。唯一能跑的是 `python3 data_scripts/kotlin-syntax-lint.py`。任何"我本地编译过了"的说法在本环境都不成立。
- 挂死源会随分片划分迁移：上轮挂死 shard1 与这轮挂死 shard2 的清单 161 条里重合 158 条——**别把"换了个片就不挂了"当成修好了**。

## 这套机制的质量上限在哪（必须先认清）

它保证的是**过程可信**：改动可回源、构建可复现、失败可定位、假绿被封。它同时保证**过程合规**：报告有字段、有状态词、有锚点卡、台账双源一致。

它**不保证产品好**。50 个门禁全部是否定式的，没有一个在检查"2dp 线宽是否还是 2dp"、"40dp 辉光是否还在"、"动画 320ms 有没有被改成 500ms"、"内存有没有胀过 100MB"、"分页翻页的手感有没有退化"。而这个项目的价值恰在这一层。所以：

- 设计 token 契约（种子第 10 项）是把"好看"从主观变可回归的第一块砖；
- 像素/帧率基线（截图 diff、Macrobenchmark）是第二块；
- 规格里不可判定的部分（"高级感"）只能靠人工裁决，必须有人拍板并留裁决行，不能让"待裁"长期堆积。

## 有了种子之后，一天怎么走

1. `bash data_scripts/seed-check.sh` 先看是否 READY。
2. 不是 READY：先补 MISSING（缺脚本）或修 FAIL（真阻断），不写新功能。
3. READY 后：派单（一人一域、一次一单、文件域互斥），派单书必须写死范围边界与验收标准。
4. 写码 → 独立验收 → 分桶提交 → push → 看 CI；红即停发新功能单，全队修红。
5. 每单收尾必带「新发现问题」；下一轮把它变成脚本 + 夹具 + 自测（三类齐才算沉淀完）。
6. 每周一次：统计门禁误杀率与历史欠账增速。欠账增速 > 销账速度，说明该收缩门禁而不是继续加。

## 当前机制实测基线（2026-11-26 夜，供接手者对照"是不是又退化了"）

这些数字都是当轮实跑/CI 真值取到的，不是目标值。接手时先对着看一眼，差得远说明机制被改动过。

- 门禁总量：59（`data_scripts/gate-levels.json` 口径：blocking 19 / audit 40）。`bash data_scripts/rule-gate.sh --blocking-only` 实测 2 分 44 秒、退出码 0；全量实测 3 分 54 秒。
- 分片清单净化：`644 → 保留 598（150/150/149/149）+ 分类打标 27（Rhino 18 + SlowBench 9）+ 剔除 19`；剔除分因 non-class-decl 14 / facade-no-test 4 / no-test-annotation 1。点名 6 个伪条目（`ComponentBenchmark`、`InkSlateBenchmark`、`SearchBenchReport`、`HalfSheetBenchmarkKt`、`RhinoEvalTest`、`SlowBenchTest`）已清。
- 设计 token 契约：`docs/契约-设计token.json` 共 70 项（color 13 / geometry 18 / motion 21 / perf 15 / memory 3），机检 67、spec-only 3。上线首日抓出 3 处**真漂移**：`ShelfTokens.kt` 卡片圆角 14f→16f（规格切片-25 `圆角 | 16dp`）、`InkTokens.kt` 旧 180MB 常量拆成 100/120 三档、`assets/ui_tokens.txt` 旧文本同步。
- 挂死取证实测（旧口径留痕）：早期 `testLogging` 只开 `STARTED","FAILED"` 时，真实日志只能给 `WARN_STARTED_ONLY`（一次 shard 日志 1873 行、STARTED 658 条、终态 0 条），只能靠"最后一条 STARTED"倒推。**现状（commit `faa6d80`，Q-277）：events 已补 `PASSED","SKIPPED` 四事件齐备，脚本走 STARTED↔终态精确配对；此后再出现 `WARN_STARTED_ONLY`，只说明日志被截断或任务未跑到测试阶段，未闭环条目是「末段未闭环候选（不可定罪，仅指向）」，不能当挂死嫌疑。**
- 挂死类已二次确认（不是偶发、不是分片玄学）：`SearchHotBinderTest > removing last history word overlapping seed keeps fallback source marker`。`ff9c20c` 轮在 shard 2 后静默 2410 秒；`49cc659` 轮在 shard 3 后静默 651 秒（14:06:14.960Z STARTED → 14:17:10.963Z `##[error]The operation was canceled`）。同轮 shard 1/2/4 全绿——**净化让 shard 2 不再挂，但挂点迁移到 shard 3 且命中同一个类，"换了个片就不挂了"永远是错觉。**
- 静态嫌疑扫描：`scan-blocking-hazards.py` 扫 632 个测试类，带命中 25 类、keep 桶 19 类；与上一轮挂死 shard 清单交集 4 条（`SourceLockTest`、`ReaderProviderRoutesTest`、`LoginUiScriptEvaluatorTest`、`ReplacePreviewTest`）。静态法只能当二分的加速器，不能单独定罪。
- 二分收敛（理论值）：161 条最坏 `ceil(log2 161)=8` 轮、单轮 8 分钟、a/b 并发 → 最坏 64 分钟；已净化 149 条同为 8 轮。
- 出包链：`fetch-apk.py` 四类假数据（单包 v1 签名 PASS / 双 apk MULTI_APK / 0 字节 ZERO_BYTE / 仅 META-INF 无签名件 UNSIGNED）全判对；无 aapt 时降级为 zip 条目检查并打 `WARN: MISSING: aapt`，**不静默 PASS**。

## 种子自身的维护

- 新增模块后，在 `seed-check.sh` 里加一行 `need`（文件 + 自测命令）。**没有 `--selftest` 的门禁不许进种子**——无法自证的门禁等于不可信任的门禁。
- 删除模块时同步删 `need`，否则 `MISSING` 会一直挂着，久而久之被当成噪声——这正是本节要防的事。
- 种子文件改动本身也要走分桶提交，并在报告里写清"为什么加这一项、它替人挡掉了哪类错误"。
