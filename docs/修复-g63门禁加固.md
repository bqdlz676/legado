## 四、自查反例与改坏推演

- 反例一（声明位放宽过头会回退成旧假阴性）：若 fun 分支保留 `.*?` 跨段匹配，探针 F 形态（错包源文件函数体同行提及同名）仍会被当成同包声明放行。本单 `FUN_DECL_POS_RE` 把名字锁在接收者段之后且紧接 `(`，坏样本四夹具即该反例的回归锁：函数体提及不再豁免，跨包错引必红。
- 反例二（声明位收太紧会误杀泛型接收者）：若接收者字符类只收字母数字点，`fun <T> HashMap<String, T>.get(...)` 认不出，存量两条 `utils.get` 会被刷成 PACKAGE 假红。本单接收者段保留泛型尖括号/逗号/空格/可空符，放行五夹具锁该放行通路；全仓复跑 PACKAGE 0，存量两条仍绿。
- 反例三（通配符整行放行会漏包级红）：若 `*` 路径在解析层就跳过，目标包不存在也不报警。本单先扩 `IMPORT_RE` 字符类再分通配符分支，坏样本六（包不存在必红）/ 放行六（包存在放行）双向锁住。
- 二阶影响：`analyze` 拆分只动返回结构，`main` 打印文案与退出码口径不变；规则编排器仍以子进程退出码为准。外部名表对通配符路径跳过，不会把 `*` 加进全局外部名集合污染同名判断。
- 三阶影响：自测夹具全部仓外 tempfile 自删，仓内 `data_scripts/fixtures/` 未新增持久夹具；分级表 g63 仍 blocking、compensation null，未把存量债降级成 audit 红墙。
