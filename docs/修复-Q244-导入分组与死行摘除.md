## 三、B34：书单导入按来源计算分组

### 3.1 现状缺陷（改动前回源）

- 旧 `FileAssociationViewModel.importData()` `"bookshelf"` 分支把组号硬编码为 `IMPORT_DEFAULT_GROUP_ID = 0L`；`importBookshelfJson(json, groupId)`（`ui/main/bookshelf/BookshelfViewModel.kt:20`）体内 `:40` `if (groupId > 0) book.group = groupId`，groupId = 0 时不写分组位，`Book.group` 保持实体默认值 0（`data/entities/Book.kt:78`）。书架分组是位掩码，0 即未分组。
- 导入 JSON 仅解析 `name`、`author`（`BookshelfViewModel.kt:21-29`），载荷本身不带分组信息。

### 3.2 来源标识字段取舍（回证）

选定字段：入口参数 `source`（分享/文件 URI 字符串）。该值由 `ImportDataDialog.kt:17-19` 经 arguments 传入，`:40-43` 交 `viewModel.importData(type, source)`；外部分享/文件入口是独立 Activity，Intent 只带数据 URI，无 groupId extra（`OnLineImportActivity.kt:57-61` 跳转 `FileAssociationActivity` 仅 `ACTION_VIEW` + data）。

否决的候选字段：

- 匹配书源 origin：书源要在 `importBookshelfJson` 内部 `preciseSearchAwait` 之后才知道；一份书单往往跨多个书源，按书源归组会把同一清单打散，与「同一来源归同组」的清单级语义不符。
- 当前可见分组：`FileAssociationActivity` 外部入口拿不到当前分组，`AppConfig` 无「当前可见分组」持久化（仅有书源导入分组记忆 `importLastGroup` 等），强行猜组属隐式行为，用户不可预期。

### 3.3 归一化与建组口径（行号 / 回证）

帮手文件 `ImportSourceGroup.kt`：

- `:15` `IMPORT_GROUP_NAME_PREFIX = "导入·"`：来源分组保留名前缀，与用户自建分组区分；复用匹配只认该前缀 + 指纹，不会误配用户组。
- `:30` `sourceImportGroupKey(source)`：来源键归一化。
  - http/https：host 小写 + 去尾斜杠的 path，剥离 query / fragment；同一清单带临时 token 的不同分享链接归同一组。
  - content：最后路径段 URL 解码后，取最后 `/` 与 `:` 之后的文件名。
  - file / legado / 其他 opaque scheme：身份不稳定（临时文件、内部跳转），返回 null，回落未分组。
- `:52` `importGroupTag(key)`：sha256 前 8 位十六进制指纹，避免长 URI 直接进分组名。
- `:60` `matchesImportGroupTag(groupName, tag)`：保留前缀且含本指纹才算既有来源分组。
- `:64` `importGroupDisplayName(key)`：折叠空白后截断 40 字符，长路径不顶宽分组名。
- `:71` `allocateFreeGroupBit(idsSum)`：从现有正组位掩码分配下一个空闲位（2 的幂，覆盖到 2^62）；63 个正组位耗尽返回 null。

ViewModel 解析 `FileAssociationViewModel.kt:206-221` `resolveImportGroupId(source)`：

1. `:207` 键为 null → 回落 `IMPORT_DEFAULT_GROUP_ID`（0）。
2. `:208-210` 按指纹在 `appDb.bookGroupDao.all` 中复用既有来源分组，命中即返回其位。
3. `:211` `canAddGroup` 为假（正组位 ≥ 63）→ 回落 0。
4. `:212-213` 位分配失败 → 回落 0。
5. `:214-220` 插入新 `BookGroup`：groupId = 空闲位，groupName = 前缀 + 指纹 + 显示短键，order = `maxOrder + 1`（与 `GroupViewModel.addGroup` :27-38 建组先例同口径）。

接线点 `:168-176`：`importData` 内先 `resolveImportGroupId(source)` 得 `importGroupId`，再传入 `importBookshelfJson`；`:186-191` 成功 toast 按 `importGroupId > 0` 分流：归组走 `import_bookshelf_source_group`，回落未分组走旧 `import_bookshelf_default_group`。

### 3.4 旧 0 组兼容与迁移口径

- 旧有 group = 0 的书籍仍走未分组视图：`BookGroupDao.kt:32` 正组匹配条件为 `group & book_groups.groupId > 0`，0 不匹配任何正组；`BookshelfViewModel.kt:40` 守卫 `if (groupId > 0)` 原样保留，回落组号 0 不写分组位。
- 已在书架的书由 `appDb.bookDao.has(name, author)` 跳过（`BookshelfViewModel.kt:36`），其既有分组位不被本次导入改动；不做强制数据迁移，旧 0 组数据照常可用。
- 固定负号组（IdAll/IdLocal/IdAudio/IdNetNone/…，`BookGroup.kt:33-40`）不参与位分配，帮手只在正组位内分配。

## 七、自查反例（改坏推演）

- 反例 1（按书源 origin 归组）：若把分组依据取成搜源命中的书源网址，一份跨多书源的书单会被拆进多个组，违背「同一来源归同组」的清单级语义；故来源字段定在入口 `source` URI（§3.2），书源 origin 方案否决。
- 反例 2（来源哈希直映位掩码）：若把来源哈希直接映射成组位，会撞上用户已有组位或产出非 2 的幂的非法掩码；故改走 `allocateFreeGroupBit` 在 `idsSum` 之外分配空闲位，建组口径对齐 `GroupViewModel.addGroup:27-38`。
- 反例 3（位预算耗尽仍强写组号）：63 个正组位占满后若继续写位，会破坏位掩码互斥；故 `canAddGroup` 为假或位分配失败一律回落 groupId 0，不写出非法位。
- 反例 4（旧 0 组强制迁移）：若把存量未分组书按新来源规则回写分组位，会打断用户既有分组引用；本单只对本次新导入的书写位，存量 `group = 0` 书籍不迁移、不改写。
- 反例 5（临时文件被当成稳定来源）：分享文本落地的 `file://` 临时文件名带随机后缀，若入键会每次导入建新组；故 file / legado / opaque scheme 归一化为 null，回落未分组。

## 八、新发现问题

1. content URI 同文件名不同目录会归到同一来源组：当前 content 键只取文件名，`/A/list.json` 与 `/B/list.json` 指纹相同；若未来需要按目录区分，键应补全相对路径 —— 待裁。
2. 自动建组可能留空组：导入书籍后若书籍被移出/删除，来源分组行仍在册；书架展示查询（`BookGroupDao.kt:32`）对无书正组不显示，但行要用户在分组管理里手动删；位预算耗尽前不自动回收 —— 已入队观察。
3. 并发同来源导入：`importData` 入口有 `importingData / importedData` 守卫（`:166`），同一 ViewModel 内不会并发建两组；跨进程/多窗口并发未在本单建模，当前 App 书单导入为单通路 —— 已闭环（单 VM 守卫覆盖现存链路）。
4. 多语种文案：新文案补齐默认英文与简中、繁中（HK/TW）、西、日、葡、越共 8 份；其余资源走 Android 回退 —— 已处置。

## 十、编译真红修复（Q-249，远端 CI run 45810466813 Discover 步）

- 原文报错（CI 真机编译，逐字）：
  - `e: .../ui/main/bookshelf/ImportSourceGroup.kt:40:26 Unresolved reference 'lastPathSegment' on receiver of type 'URI'`
  - `e: .../ui/main/bookshelf/ImportSourceGroup.kt:41:15 Cannot infer type for type parameter 'T'`
- 根因：帮手 `sourceImportGroupKey(source: String)` 内部按 `java.net.URI`（`import java.net.URI`）解析来源串，content 分支却写成了 `android.net.Uri` 才有的成员 `lastPathSegment`；`java.net.URI` 无此成员，故 :40 解析失败，:41 的 `?.let { ... }` 链因接收类型未定而连带报类型参数 T 无法推断。调用方 `FileAssociationViewModel.importData(type: String, source: String)` 实参就是 `String`，帮手签名也是 `String`，不存在跨类型接线；问题只在帮手内部取值写法与所选 URI 类型不一致。
- 改法（与实参 / 所选类型对齐，保持纯 JVM 可测定位）：
  - content 分支弃用 `uri.lastPathSegment`，改取 `uri.rawPath`（未解码原始路径）先 `substringAfterLast('/')` 切出末段，再 `URLDecoder.decode` 解码，之后保留原有的切斜杠 / 切冒号、去空白、空串判空口径。
  - 全文件复核其余 URI 访问：`uri.scheme`、`uri.host`、`uri.path`、`uri.rawPath` 均为 `java.net.URI` 合法成员；未引入 `android.net.Uri`，http/https、file/legado/opaque 分支一行未动；帮手签名 `source: String` 未变，调用方 `resolveImportGroupId(source)` 无需改动。
  - 为什么选 `rawPath` 而非 `path`：`getPath()` 会先把 `%2F` 等百分号序列解码，解码出的 `/` 会被当作路径分隔，末段可能错位；`rawPath` 保留原始转义，先切段再解码，行为与原 `android.net.Uri.lastPathSegment` + 手动解码的口径一致。
- grep 回证（改后真实输出）：
  - `grep -n "lastPathSegment\|android.net.Uri" app/src/main/java/io/legado/app/ui/main/bookshelf/ImportSourceGroup.kt` → 零命中。
  - `grep -n "uri\.\|URI\|Uri" .../ImportSourceGroup.kt` → 仅 `scheme`/`host`/`path`/`rawPath` 四处合法成员与 `java.net.URI` import。
