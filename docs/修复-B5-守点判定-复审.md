**1.1.2 `check()` KDoc 写清两形参「为什么需要、适用条件」**（`:31-40`，改写）

- `pointHolders`：为什么需要——DEFEND 是「守点」而非「歼灭」，只看有生力量无法判断目标点是否已被突入，引擎层不掌握归属推导，必须由调用方每回合显式传入；适用条件——仅 DEFEND 消费，其余类型忽略；表中缺该点视为「未被任何方持有」，不按「未知」挂起成僵局。
- `alliedSideIds`：为什么需要——盟友协防不算失守、盟友不计入 ROUT blockers，友敌身份由外交关系推导后显式传入；适用条件——DEFEND 判占据方、ROUT 筛敌军；空集即无盟友，谓词有空值守卫不崩溃。

**1.1.3 DEFEND 分支兜底注释**（`:89-94`，新增两行注释）

- `def.point == null` 或表中查不到 key → `holder == null`，视为未被任何方持有，不按未知挂起；仅存在非友方占据记录时才判失守。
- `alliedSideIds` 空集即无盟友；`isFriendlySide` 空值守卫保证此处不抛 NPE。

行为表达式（`:95`）沿用既有收口口径：`val lost = holder != null && !isFriendlySide(def.side, holder, alliedSideIds)`；档位顺序仍为 **失守 → 防御方全灭 → 撑满回合判胜 → Ongoing**。

## 四、反例与边界（先假设方案错误，逐条找反例）

1. **同点两方持有**：`buildPointHolders()` 己方优先、其次任一可战他方（控制器 `:513`），每 key 只存一个 holder；判定层只见单一占据方。若规格要求「敌我同点即算失守」，当前口径偏宽松——规格原文未细化混驻，沿用既有取舍，留交接。
2. **点不存在 / `def.point == null`**：`holder == null` → 非失守，回落有生力量 + 回合路径；不抛 NPE。空表语义是「未观测到占据」而非「己方守住」，中途状态为 ONGOING，不会既不胜也不负挂死。
3. **友军与敌军重叠**：若 `alliedSideIds` 混入某敌军 sideId，谓词会按友方放行；重叠应在控制器外交推导侧杜绝，判定层只消费传入集合，不做阵营好恶校验。空集 = 无盟友，除同阵营外一律保守判敌。
4. **据点 key 拼写漂移**：key 为 `%.4f` 经、纬度字符串，判定层 / 控制器 / 测试三处同口径；任一侧改格式需三处同步（既有注释已标）。
5. **极端回合值**：`duration <= 0`、回档后 `turn` 变小，`turn >= duration` 仅与当前回合比较；回档重算走快照逻辑，不产生跨回合串线。
6. **COMPOUND 子 DEFEND 多据点**：持有表只推顶层胜利条件一个点；子 DEFEND 落到空表兜底（既有取舍，见交接 3）。
