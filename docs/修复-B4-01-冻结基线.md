### 2. 失配判定

- 四包 diff 出现路径行、三 API 任一签名行哈希变化、paragraph 文件数或逐件哈希变化、引用集条目文件数或指纹变化，均记为基线失配。
- 函数体内部实现改动、vertical 包内非三公开 API 的可维护改动，不构成签名失配；目录内纯文档/README 类改动是否计入指纹，以重冻单登记口径为准。

### 3. 失配处置（谁重冻、留什么痕）

- 谁重冻：失配先由当单执行代理在回执内如实点名失配条目（路径、旧指纹、新指纹、归因），禁止自行改基线哈希掩盖；重冻只能由调度层指定的基线维护登记单执行，该单不改业务代码。
- 归因分流：若失配源于冻结区被越界改动，先回滚越界改动、恢复到基线状态，再谈重冻；若失配源于已批准的合法维护改动（含规格变更经任务书复核），才按新状态重冻。
- 重冻留痕：重冻单独成单或单独一笔提交，记录失配条目清单、旧指纹、新指纹、归因、重冻命令、重冻后 HEAD；报告内新增「基线重冻留痕」节，锚点卡同步更新指纹；重冻后四检复跑。
- 验收口径：验收代理按本基线旧快照比对签名与指纹；签名变化无对应冻结豁免单或重冻留痕的，判 FAIL，不接受口头说明。

## 七、二阶三阶影响（含反作用推演）

- 一阶：后续 30 个写码单开工前都有同一组静态可比对象；四包越界、三 API 签名漂移、paragraph 与引用集内容漂移可由 diff 与哈希在 L1 静态层抓到。
- 二阶连带：基线指纹把引用集目录整体锁住，后续单若需要在 ui/components 或 ui/card 内新增组件，属于新增文件而非改既有文件，目录指纹会变；这类新增须在回执内单列说明并走重冻流程，不能悄悄挂进只读目录。
- 三阶后果：基线一旦被随手重冻覆盖，门禁会退化为自证；故第六节把重冻权限收归调度层指定登记单，并要求旧指纹、归因、HEAD 三件留痕。
- 反作用：目录指纹粒度是整目录，单文件改动与整目录增删在指纹层面都表现为目录指纹变化；回执比对时须再下钻到逐件哈希定位具体条目，不能只凭目录指纹判责。
