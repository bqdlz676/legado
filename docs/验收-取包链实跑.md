## 五、`workflow_run` 触发条件原文与解释

### 5.1 触发层原文（`.github/workflows/package.yml:3-13`，逐字）

```yaml
on:
  # 由 verify 车道成功完成后触发：verify 全绿才进入打包，并行触发被此闸门排除。
  # 注意：workflows 里填的是被监听 workflow 的 name 字段（verify.yml 的 "Verify (unit tests)"），
  # 不是文件名 "verify"。填文件名不会报错，但闸门永远不触发——第 5 轮实测脚手架静默失效，故此处按 name 精确匹配。
  workflow_run:
    workflows: ["Verify (unit tests)"]
    types: [completed]
  # 保留手动入口（baseline 对照模式直接出包等场景）。
  workflow_dispatch:
    inputs:
      baseline_full_test:
        description: 'baseline 模式：单 job 跑全量单测对照（默认 false 走 4 分片并行）'
        type: boolean
        default: false
```

### 5.2 job 级闸门原文（`.github/workflows/package.yml:38`，逐字）

```yaml
if: ${{ (github.event_name == 'workflow_dispatch' || github.event.workflow_run.conclusion == 'success') && (github.event_name != 'workflow_dispatch' || inputs.baseline_full_test != true) }}
```

并发配置原文（`.github/workflows/package.yml:23-25`）：

```yaml
concurrency:
  group: package-${{ github.ref }}
  cancel-in-progress: false
```

### 5.3 一句话解释与分支限制

1. 触发层只声明监听 `Verify (unit tests)` 的 `completed` 事件，**不在 `on:` 层过滤 conclusion**；`conclusion == 'success'` 的过滤落在 job 级 `if:` 表达式里。因此 Verify 非 success（cancelled / failure / skipped / neutral 等）时，Package workflow run 仍会被 GitHub 创建，但 job 被 `if:` 跳过，run 结论记 `skipped`——这正是 `49cc659` 三道 Package `skipped` 的机制。
2. 触发层**没有 `branches:` 限制**。上游 `verify.yml:4-7` 只在 push / PR 到 `main` 时触发；`workflow_run` 继承上游 ref。影响：若未来 Verify 在非 main ref 跑绿，Package 会同 ref 被触发；取包侧必须核对 `head_sha` 与目标分支，不能只看 run 结论 success。
3. baseline 路径 job（`package.yml:136`）仅 `workflow_dispatch` 且勾选 `baseline_full_test=true` 才跑；`workflow_run` 路径只走 `build-shard` job。

## 六、反例推演（必写三条）

### 6.1 上游被 concurrency 取消：会不会"绿了但没有包"，兜底是什么

1. 现状并发口径：`verify.yml:22-27` `cancel-in-progress: false`（排队不取消；注释记录 2026-11-26 晚 `f590b58` / `a10e0b3` 两轮 Verify 全 cancelled、零结论后由 true 改为 false）；`package.yml:23-25` `cancel-in-progress: false`，在飞打包不被新推打断。
2. 若上游 Verify 被取消：结论 `cancelled`，`workflow_run(types: [completed])` 仍会触发 Package；job `if:` 中 `conclusion == 'success'` 不成立 → Package `skipped`；`fetch-apk.py` 第一道闸判 `cancelled`，RC=1 拒绝取包。链路不会把取消态当成绿。
3. "绿了但没有包"的现存缺口与兜底：
   - Verify 绿但 Package run 缺失（`workflow_run` 事件漏发 / GitHub 事件延迟）：脚本 RC=1，输出 `FAIL: 未找到 Package Debug APK run`；本仓无对账 cron 补齐，恢复靠重推或 `workflow_dispatch` 手动触发。
   - Package success 但未上传 artifact：RC=1，`Package run 无 artifacts`。
   - Package job 自身失败：第二道闸按非 success 拒绝，RC=1。
   - `--wait` 只轮询 Verify 变绿，不等 Package 出包；Package 在飞时脚本查到 `status != completed` 即 RC=1 返回，不阻塞空等（符合调度层禁空等铁律）。
4. 二阶影响：若日后把 verify 并发改回 `cancel-in-progress: true`，在飞 Verify 被掐断后其 Package 不会出包；旧 run 结论可能被新 push 覆盖，台账必须按 run id 留证，不能只记 commit 号。

### 6.2 artifact 90 天过期后 `fetch-apk` 会怎样，失败面是否覆盖 404

1. GitHub artifact 默认保留 90 天；过期后列表接口仍可能返回条目（`expired: true`），下载端点返回 404。
2. 脚本覆盖：`download_artifact`（`fetch-apk.py:362-363`）显式判 `code == 404` → `InfraError('ARTIFACT_EXPIRED=404 artifact 已过期或不存在（GitHub 默认保留 90 天）')`，RC=2。404 失败面已覆盖，报错文案明确指向过期。
3. 残留缺口：选 artifact 阶段不读 `expired` 字段，可能先选中过期件、到下载步才 404；报错时点偏后但结论不变。另：下载后只查 0 字节（`:366-367`），不比对 `size_in_bytes`，截断要等到解压 / `testzip` 才暴露（本次弱网实测即此路径，RC=2 `CORRUPT_ZIP`）。

### 6.3 只有 v2/v3 签名、`META-INF` 为空时脚本会判什么，会不会误判永久红

1. 判定路径（`fetch-apk.py:292-304`）：证书 / SF / MF 任一为 0 → `signature = 'unsigned'`，reason `UNSIGNED`，`overall = False`，最终 RC=1。
2. 后果：一个只走 v2/v3 签名的包（minSdk 26 可正常安装）会被本脚本判成"未签名"，取包闸永久红；NOTE 行（`:306-307`）虽声明 v2/v3 不可判，但 `UNSIGNED` 仍是硬 FAIL，没有"v1 缺失、签名态 indeterminate"的中间档。
3. 当前为何暂不发作：`app/build.gradle` signingConfigs `enableV1Signing / enableV2Signing / enableV3Signing / enableV4Signing` 均为 true，固定测试签名 `luowen.jks`，CI 包当前带 v1 三件；本包实测 v1 齐全。风险只在构建配置摘掉 v1 时出现。
