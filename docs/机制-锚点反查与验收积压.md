# 机制 M-08 / M-09 收口报告：锚点卡编号↔反查 + 验收积压深度门禁

> 落地日期：2026-11-26 ｜ 范围：只改 `data_scripts/` 检查器、`rule-gate.sh`、本仓机制台账；未触碰 `app/**`、`docs/锚点/**` 已有卡片内容与其他报告。
> 关联台账：`docs/台账-机制缺陷.md` M-08（锚点卡门禁滞后）、M-09（验收积压无上限判据）。

## 一、M-08：⑲ 锚点卡判据扩为「编号↔锚点卡反查」

### 1.1 原有判据（原样保留，未改弱）

原有三条校验全部保留在 `data_scripts/check-anchor-card.py`：写码类回执（`修复-*`/`实现-*`）正文必须含 `锚点卡：docs/锚点/<编号>-<主题>.md` 且文件真实存在；验收类报告（`验收-*`）除锚点卡路径外还必须有逐字引文段（`「…」` 引文或 `文件:行` 定位串）；显式写明「机械改动」或「无规格→已按 F-73 退回设计」的报告豁免，`验收-选型-*` 属 F-73 链豁免。校验范围仍是本次 `git status` 新增/修改的报告，历史留档不追改。

### 1.2 新增三条反查判据

R1 主对象反查（FAIL）。写码报告的主对象缺陷号必须能在 `docs/锚点/` 按文件名前缀编号反查到对应卡，查不到判红。为什么需要这条：旧判据只认报告首行写没写卡路径，报告所属编号本身无卡也能先派先修（M-08 实证 B1、B8R2 长期无卡）；主对象无卡等于执行代理凭记忆开工，F-85 前置设计费被架空。

R2 次要提及（仅 WARN，不判红）。正文其余缺陷号缺卡只打提示。为什么降级：次要提及的号可能是「已收口并入别号」的旧号（实证 Q-82 并入 Q-89、Q-87 并入 Q-90），旧号不再单独立卡，硬反查会误红；同一行内出现「已并入 / 并入 / 作废 / 收口」字样的号直接豁免，不提示。

R3 孤儿卡扫描（仅 WARN，不判红）。`docs/锚点/` 下未被任何报告、派单队列、派单台账引用的卡列为孤儿提示。为什么不判红：前置设计费本来就要求卡先于写码单落地，新卡常先落卡、后写报告；判红会逼代理反过来先补报告引用再落卡，把顺序倒置。

### 1.3 主/次区分口径

主对象取号顺序写死在 `main_object_id()`：先剥掉文件名前缀（`修复-`/`验收-`/`实现-`/`清理-`）后取首个缺陷号；文件名无号时，取正文首个非引用（非 `>` 开头）、非标题（非 `#` 开头）段落的首个缺陷号；两处都取不到则本项跳过，不反查。

验收报告的主对象缺卡降级为 WARN：验收报告的锚点卡指向催生该缺陷的上游卡（实证 `验收-B17` 锚点卡是 `Q53-空态压淡.md`），被验缺陷号本身未必单独建卡，硬判红会误杀既有验收回执。

编号匹配做归一化：去横线、大写后整号相等比对，`B-2` 与 `B2`、`S-01` 与 `S01` 视同；token 边界保证 `B2` 不命中 `B12`。在册缺陷族写死为 A/B/C/D/E/F/N/P/Q/S/U/V，`JDK21` 这类三字母技术词不命中；`§八-D1` 这类章节引用号前接横线，lookbehind 排除。

### 1.4 接线

`rule-gate.sh` ⑲ 块保留原有「本次改动报告」逐份校验；新增仓库级孤儿扫描 `python3 data_scripts/check-anchor-card.py --orphan`，WARN 单列并标注「不影响 GATE 结论」。

## 二、M-09：㊸ 验收积压深度门禁

### 2.1 判据

新建 `data_scripts/check-backlog-depth.py`，双阈值任一超限即 FAIL（退出码 1）：

D1 积压行数：当前「可立即送验收」的待验单超过 `MAX_PENDING=10` 条判红。
D2 最老时长：可立即送验收的单子里，最老一条存活超过 `MAX_AGE_HOURS=48` 小时判红。

计数口径：`docs/问题清单.md` 状态格含 🟢 且带待验关键词（待验证 / 待验 / 待派验收 / 待独立验收 / 已判·待验证）；`docs/派单台账.md` 状态格含 🟢 或「已判·待验证」字样。✅ 已关闭、已收口、已落地、功能全补救、🟡 在飞、🔴 未派、⛔ 作废均不计。两源按归一化编号去重，同一号只计一次；台账首格形如 `11-26 00:1x Q-70 B17 标题`，Q-xx 是派单号，去重优先取非 Q 族缺陷号。

外部阻塞单列：状态/归属/级别格含「待 CI / CI 待绿 / 待云端 CI / L2 待 CI / 待 CI 转绿 / CI 待」的单归 CI 阻塞组，不计入 D1/D2，只在报告里单列条数。为什么单列：等 CI 的单不是验收槽欠账，算进积压会误逼调度层去抢验收槽。

### 2.2 阈值理由（冻结在台账 M-09 行与脚本顶部常量）

行数阈值 10 条：依据 F-02/F-84，框架并发硬顶 5 槽，档1＝4 写 + 1 查，验收槽仅 1 个；Q-22 单代理 >15 分钟 WARN、>60 分钟 FAIL，验收工具预算 ≤60 次。按一单验收约 30~60 分钟一轮估算，10 单 ≈ 一个工作轮次（4~5 小时）的验收槽周转量；超过即说明写码在堆、验收槽被挤占，调度层应先清验收再发新写码单。升档到档2/档3（2~3 查槽）后，行数阈值按查槽数同比上调，改脚本顶部常量即可。

时长阈值 48 小时：约两个完整轮次。一条待验单挂过 48 小时还没排上验收，基本是被遗忘的僵尸积压，必须亮红牌，不能继续混在待验堆里。

### 2.3 年龄回退口径

台账行年龄取首格日期（支持 `YYYY-MM-DD HH:mm` 与 `MM-DD HH:mm`，分钟缺失按 0 分；解析成未来时间回退一年）。清单行无行内日期，年龄回退到该行关联报告文件的 mtime（优先 `修复-/清理-/实现-` 报告，其次验收报告；路径已含 `docs/` 前缀，拼目录前先剥掉防 `docs/docs` 双前缀）。取不到日期的单计入行数但不参与最老时长判定，单列提示，不因缺日期误红。无单缺陷号的聚合行计入「未编号」桶，只提示，不参与年龄判定。

### 2.4 接线

`rule-gate.sh` ㊸ 块调用 `python3 data_scripts/check-backlog-depth.py`：退出码 0 回显 `BACKLOG-DEPTH: PASS`，非 0 进 `bad()`；INFO/WARN 行单列标注「不影响 GATE 结论」。

## 四、误判风险与兜底

M-08 风险一：编号写法差异（横线、R 轮次后缀、小写子号）。兜底：归一化去横线大写后整号相等比对，`B8R2` 正常命中 `B8R2-侧翼敌军半径.md`。

M-08 风险二：章节引用号、技术词被误当成缺陷号。兜底：族名写死在册字母族，三字母技术词（JDK21）不命中；横线前置的章节号（§八-D1）lookbehind 排除；单文件次要提示去重后最多列 5 条，防刷屏。

M-08 风险三：新卡先建后被引用期间被判孤儿。兜底：R3 只 WARN 不 FAIL，引用来源覆盖报告、派单队列、派单台账三处。

M-09 风险一：等 CI 的单被算成验收欠账。兜底：CI 阻塞关键词单列，不计入 D1/D2。

M-09 风险二：清单行缺日期导致最老时长算不出。兜底：回退关联报告 mtime；仍取不到则计入行数、排除年龄判定，unknown 单列。

M-09 风险三：台账同一缺陷号在清单与台账双源重复计数。兜底：归一化编号去重，同号保留更早日期。

M-09 风险四：阈值拍脑袋。兜底：阈值理由绑定 F-02/F-84 槽位结构与 Q-22 时限，写进台账 M-09 行；升档扩查槽后按查槽数同比上调，只改顶部常量。

## 五、未验证项

全量 `rule-gate.sh` 的末行 `GATE: PASS/FAIL` 本次未端到端截取：门禁后半段检查较慢，单次运行在 90 秒超时前未走到㊸ 行；㊸ 分支已通过直接调用 `check-backlog-depth.py` 实跑验证，`bash -n rule-gate.sh` 语法通过，分支写法与既有㊷ 块同构。
