### 6.1 把某条 heavy gate 从 blocking 降为 audit，能省多少、代价是什么

- 降 g34 ㉞Gradle语法：省约 34.6s（python 总耗时 31.0%，单条最重）。代价：Groovy 构建脚本行首 `#` 这类非法注释失去本地早警，只能等 CI 走到 Gradle 配置阶段才红（run 45525688582 先例，CI 一轮十几分钟）；且按 fail-safe 口径，降级必须在 `gate-levels.json` 补在册 compensation 渠道，否则 shell 侧仍按 blocking 处理。
- 降 g55 55 永远找问题：省约 16.4s。代价：报告缺「新发现问题」节 / 条目无处置状态的假绿失去 push 前拦截，补偿只能靠收口单人工复核；本轮 3 份红稿会直接流到收口轮才被发现。
- 降 g19 ⑬测试源码陷阱：省约 13.6s。代价：R1 反引号非法字符名 / R2 静态调实例方法直接造成编译红，本地静态闸撤除后只能靠 CI 单测编译任务兜底。
- 结论：省时最多的 g34 恰是编译硬判据；可降级空间主要在报告内容类（g48/g55），代码静态守卫六条不建议动级别。

### 6.2 若慢根因是「未提交文件多」，提交后同一命令会不会自动变快（预期数字）

会变快，但只快文档回执那部分。工作区干净后：

### 6.3 `timeout` 掐断与「gate 判红」在日志上如何区分

- 被掐断（rc=143 SIGTERM / 124 timeout）：脚本没跑完，**末行不存在** `GATE: PASS/FAIL` 汇总；输出停在某条 gate 扫描中途（半截 WARN/路径/计数）；`/tmp/.gate_failures` 只登记到中断前；没有逐条 `✗` 清单。
- 判红（rc=1）：所有 gate 跑完，末行必有 `GATE: FAIL —— 失败步骤清单（N 项…）`，下面逐条 `✗ <门禁>｜<原因>`；被点名的门禁自身输出 `FAIL` 行。
- 判定纪律：看到中断码 143/124 时，先 grep 末行 `^GATE:`；没有汇总行就是被掐断，**不得读成红**，更不得据此补门禁或改阈值。
