## 二、改法：三档分层数据源 + 来源标记 + UI 三态可区分

### 2.1 数据从哪来、为什么可信、断网怎么办

| 档位 | 来源 | 为什么可信 | 断网行为 |
| --- | --- | --- | --- |
| ① USAGE 高频榜 | 本地 Room 表 `search_keywords`，`flowByUsage()` 按 `usage DESC` 排序；每搜一次 `usage + 1`、刷新 `lastUseTime`（`InkSearchViewModel.saveSearchKey`） | 用户本人真实搜索日志，频次即热度；关键词随备份恢复（`Restore.kt:353`），非推断、非营销榜单 | 纯本地 DB 查询，断网照常出词 |
| ② HISTORY 历史回流 | 同表 `flowByTime()` 最近搜索词（已接的历史流） | 本机时间序真实日志；高频榜为空（新装 / 从未点搜过频次词）时回流最近词 | 纯本地，断网照常 |
| ③ SEED 内置精选 | `SearchHotResolver.SEED_KEYS`，10 个典籍短词，逐词对应随包 `assets/books/` 内书目（论语集注 / 诗经 / 楚辞补注 / 庄子集释 / 春秋左传 / 孟子 / 老子道德经王弼注 / 尔雅 / 尚书 / 礼记） | 书目随安装包携带，离线可用；仅作末档兜底，UI 标题标注「猜你想搜」，**不冒充实时热搜** | 内置常量，断网照常 |
| ④ EMPTY 防御态 | 三档清洗后皆空（理论不可达） | 防御分支，保证 resolver 永远返回非空结构，不抛异常 | 面板回落既有引导句，不留白 |

回落顺序：USAGE → HISTORY → SEED → EMPTY。任何一档出词即停；清洗 / 去重 / 截断统一复用 `SearchHistory.hot`，口径与历史行一致。

## 五、二阶 / 三阶推演

### 5.1 二阶（直接连带影响）

- **两路流异常隔离**：时间序流与频次流各自 `.catch { AppLog.put(…) }`，一路仓储异常只记日志，另一路仍可出词；resolver 对 null / 空入参安全回落，不把异常抛到 UI。
- **增删历史后热门自动重算**：删除单条 / 清空历史 / 新搜一词都会触发 Room 流重发，`historyKeys` / `usageKeys` 刷新后热门档随之重算，不会出现已删词仍挂在热门行的残留。
- **频次实时上浮**：同一词重复搜索 `usage` 累加，频次榜顺序在下次流重发时更新，热门行随用户行为自学习。
- **重复词抑制**：USAGE 档剔除历史行已展示的词；HISTORY 档与历史行存在同词（规格要求的历史回流形态），靠标题「搜索历史 / 最近搜过」与点色区分，不构成歧义。
- **无新增网络请求**：本特性全部读本地 DB 与内置常量，不申请网络权限，离线 / 在线行为一致；未改动检索编排 `runSearch` 与命令闸门。

### 5.2 三阶（长期演进与维护成本）

- **远程热搜可插拔**：后续若接书源搜索建议 / 远程热搜，只需在 `SearchHotSource` 增一档（如 `REMOTE`）、resolver 插一档优先级、ViewModel 注入远程结果；状态模型的 `hotSource` 标记位与面板标题 / 点色映射已留扩展点，无需改 UI 骨架。
- **清洗口径单一收口**：三档词表都走 `SearchHistory.hot` 归一化 / 去重 / 截断，脏词（空白、重复、超长上限）不会从热门行漏进高亮与 LIKE 查询。
- **认知成本**：解析逻辑集中在 `SearchHotResolver` 一个纯 JVM 对象，ViewModel 只做流接线与字段搬运；接手者读 resolver 即可看清三档优先级，不必翻 Compose 层。
- **历史包袱排查**：`flowByUsage()` 在改前为零引用死方法，本次激活；未发现可一并移除的废旧兼容层（DAO 其余方法仍被历史 / 备份链路使用）。
