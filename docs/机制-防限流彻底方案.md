# 防限流 · 彻底解决（三大根因的机械封堵方案）

> 根因（复盘结论）：这台云主机只有 **2 vCPU / 3.9G 无 swap**。三个"抢资源"根因是——
> ① **5 并发子代理**（2 核带 5 个代理互相抢 CPU）；② **历史本地 gradle 编译**（吃满 CPU/内存）；③ **失控子代理**（跑重 IO/死循环/吐垃圾，40–83 分钟空转）。
> 原则：规则靠"记得"必漂，**能机械判的必须机械判**（铁律 84）。下面四层全部落成脚本/门禁，不靠自觉。

---

## 第一层：能力封死（本地编译物理不可行）

- 本机**无 Android SDK、无 JDK21、`~/.gradle/jdks` 为空** → `./gradlew assemble` 即使被误触发也会因缺 SDK/JDK 失败，从能力上封死本地编译。
- 铁律 30/88 双保险：本地禁 gradle/kotlinc；编译/单测/出包 100% 走 GitHub Actions（4 核 16G）。
- **门禁**：`rule-gate.sh` 第 ⑩ 项机械自检——`which gradle` 为空、无 `ANDROID_HOME/ANDROID_SDK_ROOT`、`~/.gradle/jdks` 无 JDK、无 gradle/kotlinc/assemble 进程，四项全过才算"本地构建能力已封死"，否则 `GATE: FAIL` 禁提交禁派单。

## 第二层：并发封死（2 核 → 上限 5 = 4 写 + 1 查，负载动态）

- 落文**在飞子代理硬上限 = 5（4 写码 + 1 验收/查）**，替代原"满编 5"；按 1 分钟负载动态下调：`load1 < 1.5` 满 5，`≥1.5` 饱和降 2。
- **门禁**：`rule-gate.sh` 第 ⑨ 项机械自检——读 `/proc/loadavg` 的 load1 定上限（`<1.5` 满 3、`≥1.5` 降 2），再数 `docs/派单台账.md` 里"在飞"计数，超上限直接 `GATE: FAIL`，**不许再派单**。
- 台账 `docs/派单台账.md` 的"在飞"计数是唯一权威；每派一单 +1、每收一单 -1，即时回写。

## 第三层：失控熔断（超时 + 输出体积 + 进程回收）

- **超时**：派单任务书写死"超 15 分钟无产物或无报告即判废"（小模块 5–10 分钟内交付；大模块派单书显式声明更长超时）；总控用 `wait_agent` 阻塞等待，超时未回即 kill（不空转、不短间隔轮询）。
- **输出体积**：子代理回报 ≤ 约 4KB；一旦出现重复串/乱码/长篇填充，立即判废 kill（已写入 `机制-子代理必读.md` §5.1 与铁律 87）。
- **进程回收**：kill 返回 `no_task` ≠ 子进程已回收；`watchdog.sh` 列出孤儿/吃 CPU 进程，kill 后照单清。
- **门禁/工具**：`data_scripts/watchdog.sh` 每次等待期间/负载异常后跑一遍，输出「负载、内存、吃 CPU 前 8、构建进程、在飞超时、孤儿进程、请求率」七项。

## 第五层：请求率封顶（限流的真正开关）

- **依据（本会话实测）**：中位子代理 49 次工具调用；失控代理（网速插件任务）**6894 次**（4857 Bash + 539 Edit + 512 Write）。限流主因是"单位时间工具请求数"爆掉，不是稳定 CPU 高。
- **单代理工具调用预算**（铁律 E10）：派单书写死 **写/修 ≤ 40 次、验收 ≤ 60 次**，超过即判失控 kill（与 15 分钟熔断并列，先到先废）。
- **并行合并**：独立工具调用必须一次性并行发（一条消息多个 tool_calls），禁串行单发——把"请求数"压成"批次数"。
- **分段读长文不算刷请求**：切片仍超上下文时按 `offset/limit` 分段读、每段读一次、结论即落盘、不跳读；禁止的只是"同一段已读且已记结论后无进展重读"。
- **门禁/工具**：`watchdog.sh` 第 ⑥ 项列出各 agent 工具调用数，`>500` 标"失控嫌疑"；第 ⑦ 项记录请求率快照（时间戳 + 全会话工具调用总数），逐次算增量速率，用于回放限流临界点。
- **补齐五杠杆（铁律 E11）**：① 派单零发现成本（切片/路径/契约/陷阱全预塞，子代理不 search/不重读/不重推导）② 脚本合并（多文件加工一次脚本跑）③ 外置重活（编译/单测/批量数据/长文分段/交叉验证走 CI 或后台）④ 请求整形（错峰派发 30s~1min + wait_agent + 关键动作退避）⑤ 实测留边际（并发/预算压到实测阈值 60~70%）。

## 第四层：运行期监控（实时可见，不靠事后）

- `watchdog.sh` 第一项即打印 `uptime` + `free -h`，一眼看出是否被打满。
- 触发"负载较高/工具被拒"时按**铁律 89 标准动作**：停发一切工具调用 → 终止在飞代理 → 跑 `watchdog.sh` 清孤儿进程 + `df/du` 查盘清 `/tmp` → 每 ≥10 分钟一次低频探测 → 恢复后 `resume-state.sh` 重建基线。
- 调度层"实时轮询"只准用 `wait_agent` 阻塞等待（铁律 88），禁 <5 分钟短间隔探测。

> 一句话：**能力封死（不能编译）+ 并发封死（最多 3=2写+1查）+ 失控熔断（超时/体积/进程）+ 请求率封顶（工具预算/并行合并）+ 实时监控（watchdog）**——五层全是脚本/门禁，不靠"我记得"。
