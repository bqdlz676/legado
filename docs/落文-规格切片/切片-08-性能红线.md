落文 · 全端性能加强

一、阅读页（最核心，用户 90% 时间在这）
| 问题 | 方案 | 预期 |
| 翻页掉帧 | 预加载下一页排版数据，翻页前已经在内存里 | 翻页全程 16ms/帧 |
| 滚动气泡重绘 | 气泡按页面缓存 bitmap，滚动时贴图不重排 | 滚动 60fps 不抖动 |
| 竖排文字测量 | 首次分页后把每列每字的 x/y 缓存到 sparse array | 重排速度 ×3 |
| 章节切换白屏 | 预载前后各一章的排版缓存 | 章节切换 0 白屏 |




二、字典/数据加载
| 数据 | 当前 | 方案 | 预期 |
| zh_ci.txt (15.6MB) | HashMap<String,String> 28万 Entry | 紧凑 byte[] 数组，二分查找 | 内存 15MB→3MB，首查 ≤ 50ms |
| char_dict.txt (1.7MB) | 同上 | Java 原生 SparseArray 按 Unicode 码点索引 | 查一个字 O(log n) |
| allusion.txt (5.5MB) | 全量 HashMap + 首字分桶 | 首两字索引，桶数 ×30 | 扫描一页 ≤ 80ms |
| person.txt (CBDB 8.9万) | readText() 一次性全读 | BufferedReader.useLines 逐行流式 + SQLite | 加载内存 12MB→2MB |
| person_terms.txt (3万) | ArrayList + indexOf 全扫 | 首字分桶 + 排序，跟 allusion 同策略 | 匹配 ≤ 5ms |




三、3D 沙盘（WebGL，当前最大性能消耗）
| 问题 | 方案 | 预期 |
| 每帧重建所有 Path | 笔画完成时一次性硬化成 Path 缓存 | onDraw 耗时 ×10 |
| 22 个独立 Canvas 纹理 | 合并到 1 张 atlas，所有标签一张纹理 | draw call 22→1 |
| 地形 128×128 段全量上传 | 做视锥体外裁剪（只画可见格） | 顶点数 → 30% |
| 势力多边形每帧采样高度 | 地图加载时预采样高度，存为静态顶点 | 多边形开销 → 0 |
| 低端机掉帧 | 检测 hardwareConcurrency < 4 → 粒子减半、阴影关、fog 距离缩 | 50fps 保底 |




四、WebView 复用（画板/地图/沙盘三家共享一池）
| 当前 | 方案 |
| 每个页面 new WebView，打开 4s 白屏 | 在 Application 启动后 2s 后台预热 3 个 WebView 入池（沙盘/地图/画板各一个） |
| 离开页面 destroy | removeView + 重置状态 回池，不销毁 |
| 内存泄漏 | 池大小上限 3，超出才 new |




五、启动速度
| 阶段 | 当前 | 方案 | 预期 |
| Application.onCreate | 串行加载所有字典 | 字典加载→协程并行 + 只加载索引（正文延迟读） | 冷启 ≤ 1.2s |
| 启动动画 | 2.8s 等待 | 动画期间预热 WebView 池 + 预先排版示例章节 | 2.8s → 书架瞬间出 |
| 字体加载 | 完整 Noto Serif SC 5MB | unicode-range 分片，首屏 2500 字 ≤ 200KB | 首屏渲染 < 400ms |




六、内存
| 组件 | 当前 | 方案 | 预期 |
| 四大词表 | 全量驻留 ~40MB | 紧凑二进制化 → 15MB | 省 25MB |
| WebView 池 | 每次 new，GC 不回收半死实例 | 单例池，用完回池 | 无泄漏 |
| 3D 沙盘 | 离开时丢给 GC | 离开时 dispose geometry/texture/material | 即时回收 |
| 阅读缓存 | 无上限 | 只保留前后各 3 章排版缓存，其余释放 | 峰值 ≤ 60MB |




七、iOS 独有
| 优化点 | 方案 |
| Metal 渲染 3D | WKWebView 默认用 Metal 后端，比 Android WebView 的 Skia 快 30% |
| 字典 | iOS 用 os_unfair_lock 替代 synchronized，并发读更快 |
| 排版 | Core Text + CTFramesetter 原生分页，不是 WebView 排版 |
