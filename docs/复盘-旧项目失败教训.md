# 复盘 · 旧项目「落文」(com.gain.luowen) 失败教训

> 结论先行：旧项目不是"功能想错了"，而是**技术选型错 + 工程纪律缺 + 摊子铺太大**，三者叠加，导致它永远只能停在"能打开、能看、但远不是成品"的原型态，最终被整体推倒重做（换成 legado 排版引擎 + Compose 原生自绘 + 东方美学）。以下教训逐条列，并对应新落文的做法。

## 一、失败教训（逐条）

1. **自造排版引擎是死路。**
   旧 `ReadEngine` 用 `TextView + StaticLayout` 拼分页：3000 字强制切章、1.2 万字防 OOM、无竖排、无真分页、无渲染管线。这是"假排版"，撑不住古籍阅读需要的竖排/复杂注疏/高级渲染。
   → **教训**：排版引擎是高门槛组件，自造必浅；正确做法是"借成熟引擎（legado 只保留排版层），只重写外面的壳"。

2. **传统 View 手工拼 UI 做不出高级感。**
   旧项目全是 `LinearLayout`/`TextView`/`ScrollView` 手堆，配色写死、无主题系统、无动画体系。绢帛、暖金、毛玻璃、spring、3D 地形这些要求，传统 View 手工根本做不出。
   → **教训**：要"高级感"必须 Compose 自绘 + 设计系统（12 色 token、冻结契约），不能拿 XML/View 硬凑。

3. **摊子铺太大、每块都浅。**
   书库 + 通读 + 知识层 + 笔记 + 检索 + 考点库，六块功能，每块只有十几到几十行浅实现，没有一块做到"成品级"。
   → **教训**：宁可一块做透，不铺六块浅层；划小范围、逐条验收，不攒批。

4. **数据资产是简本/小库，撑不起"字字有据"。**
   16 部古籍是简本 txt（无集注/故训传），字典 4.2M、典故库 5.1M 都是小库。所谓"字字有据"名不副实。
   → **教训**：数据质量决定功能上限；简本只配做占位，做真品必须上带注疏的全本（当前 legado assets 已用集注/补注/故训传）。

5. **没有工程纪律。**
   源码里无 test 目录、无 CI 配置、无版本规范、无验收机制，`versionCode=1` 从未前进。没有"写→验→push→编译→再验"的链，代码只会越堆越乱。
   → **教训**：没纪律的代码库最终只能推倒重来；纪律 = CI + 单测 + 铁律 + 独立验收 + 三布尔门禁。

6. **没有冻结的规格与契约，靠"感觉"反复改。**
   旧项目没有一份"冻结契约"定义排版接口、主题、命名、数据口径，改动随意，无法多人协作、无法稳定推进。
   → **教训**：必须冻结契约（VerticalLayoutEngine/hitTest/BubbleResolver/12 色 token 等），改动要有门禁、有回源锚点。

## 二、新落文对应的"反向做法"

| 旧项目踩的坑 | 新落文的做法 |
|---|---|
| 自造排版引擎 | 只保留 legado 排版层（page/provider、entities、api、vertical、text 一行不动） |
| 传统 View 手拼 UI | Compose 原生自绘 + 东方美学设计系统 |
| 六块浅铺 | 划小范围、逐条缺陷、独立验收、不攒批 |
| 简本/小库 | 集注/故训传/补注全本 + 名物库/人物库多源交叉 |
| 无测试/CI/验收 | GitHub Actions CI + 单测 + 独立验收代理 + 三布尔门禁 |
| 无冻结契约 | 冻结契约 + rule-gate 机械门禁 + 锚点回源 |

## 三、一句话总结

旧项目失败的本质是：**想用一个"临时原型"的架子，去扛一个"高级成品"的目标**——架子（自造排版 + 传统 View + 无纪律）撑不起目标（东方美学 + 古籍通读 + 字字有据）。所以新落文把"架子里唯一有价值的东西"（阅读+点字出义的**需求方向**）留下，把架子整个换掉（legado 排版引擎 + Compose + 铁律/CI/验收纪律）。
