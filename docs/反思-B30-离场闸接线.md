## 2. 踩的坑 / 教训

- 先被上一轮验收报告带偏：B30 上一轮已把闸类派生合并进基类、宿主也接了 `tryOpen`，初判「无事可做」。回扫现役代码才发现分叉残留在覆盖层组合判定（读负载槽）和弹窗可见判定（读局部镜像）两个接线层，闸类本身反而干净。教训：验收报告说 PASS 的是闸类判据，接线层口径要单独 sweep，不能凭上轮结论收工。
- 锚点卡文件名前缀与缺陷号反查规则：报告文件名带 B30，卡名若以 Q452 开头，R1 反查按前缀匹配不上会判红。最终用同内容 symlink 补 B30 前缀别名，真实卡片仍只有一份，没复制成双源。
- Compose 可见性改读闸 plain 字段后，重组触发不能丢：`exitingState` 写回仍是 `LaunchedEffect` 键与重组源，闸字段只承担取值。这一形态与 B29 控制器一致，改前先对照 `SheetExitController`，没把镜像删成无状态。

## 3. 我可能判断错的地方

- `ReaderSheetOverlay` 保留 `exitRequest ?: return` 作内容槽空值防御，不是组合判据；若将来出现「isComposed=true 但 retainedRequest=null」的路径，这个兜底会静默 return 掉子树，需要 CI 单测先兜住该不变量。
- 宿主双闸顺序（先 canOpen 后 tryOpen）是按 B21 状态层口径对齐；两道谓词在 OPEN/EXITING/REMOVED 三态合取结果与旧单道 tryOpen 等价，但若后续给 REMOVED 段加「冷却中不可开」语义，两道分工要重新划。
- 弹窗实例内 `isComposed / canOpen` 仍无生产消费点，只靠单测锁定；认为这是实例内无重开路径的合理边界，若验收方要求实例内也接 open 入口，需另单补。
