## 二、旧 discover 清单生成逻辑（改动前逐字全文）

位置：`.github/workflows/verify.yml` discover job 步骤 `Enumerate compiled test classes and split into 4 shards`（改动前 `:162-197`）。旧逻辑只看编译产物，不回查源码：

```yaml
      # 枚举编译产物中的顶层类，按排序后 round-robin 切成 4 份；
      # 并集必须 == 全量清单、两两不得重叠——这是"分片并集=全集"的第一道机制保证。
      - name: Enumerate compiled test classes and split into 4 shards
        run: |
          python3 - <<'PY'
          import glob, os, json, sys
          # 兼容 Kotlin/Java 两种编译产物根目录的实际落盘位置（变体名漂移时用通配兜底）
          roots = glob.glob('app/build/tmp/kotlin-classes/*UnitTest*') + \
                  glob.glob('app/build/intermediates/javac/*UnitTest*/classes')
          SKIP_BASE = {'R.class', 'BuildConfig.class', 'module-info.class'}
          classes = set()
          for root in roots:
              for path in glob.glob(os.path.join(root, '**', '*.class'), recursive=True):
                  rel = os.path.relpath(path, root)
                  base = os.path.basename(rel)
                  if '$' in base:
                      continue
                  if base in SKIP_BASE:
                      continue
                  classes.add(rel[:-6].replace(os.sep, '.'))
          if not classes:
              sys.exit('::error::未枚举到任何测试类（编译产物目录缺失？），拒绝生成空分片清单')
          cls = sorted(classes)
          shards = [sorted(cls[i::4]) for i in range(4)]
          union = set().union(*map(set, shards))
          if union != set(cls):
              sys.exit('::error::分片并集 != 全量测试类清单')
          for a in range(4):
              for b in range(a + 1, 4):
                  overlap = set(shards[a]) & set(shards[b])
                  if overlap:
                      sys.exit(f'::error::分片 {a+1} 与 {b+1} 存在重叠类: {sorted(overlap)[:5]}')
          for i, shard in enumerate(shards, start=1):
              with open(f'shard-{i}.txt', 'w') as f:
                  f.write('\n'.join(shard) + '\n')
          json.dump({'total': len(cls), 'classes': cls}, open('manifest.json', 'w'), ensure_ascii=False, indent=1)
          print(f'测试类总数={len(cls)}，分片大小={[len(s) for s in shards]}')
          PY
```

缺陷根因：`.class` 产物里既有可执行测试类，也有 `object` 引擎、`data class` 报告、`interface` 标记、文件 facade、辅助类；旧规则只排内部类（`$`）与 R/BuildConfig/module-info，其余原样进清单。

### 3.1 选型理由：新建独立脚本，而不是把过滤塞回 workflow heredoc

- 可回放：既有 artifact 清单能直接喂 `--from-lists` 复算本轮数字，不必等 CI 编译；heredoc 做不到离线回放。
- 可自测：过滤规则有 `--selftest` 双向夹具（真测试保留 / 伪条目剔除 / 孤儿判 missing-source），符合仓内 `data_scripts/` 门禁脚本惯例。
- 可维护：判定逻辑集中一处，后续新增测试基类或注解写法只改脚本；workflow 保持薄接线。
- 语义不变：编译产物枚举口径（roots 通配、内部类跳过、SKIP_BASE）原样搬进 `enumerate_build_classes()`，分片仍是排序后 round-robin，并集守恒 / 两两重叠断言保留在脚本内。

## 四、过滤规则（分片之前执行）

判定顺序即短路顺序，命中即落桶：

1. `missing-source`：FQCN 在 `app/src/test/java/` 下找不到对应 `.kt` / `.java` 源码（编译残留 / 改名未清产物）。
2. `non-class-decl`：声明是 `object` / `interface` / `data class` / `sealed` / `enum` / `abstract`，不是可被 JUnit 实例化执行的普通 `class`。
3. `no-test-annotation`：源码既无 `@Test`（含全限定 `@org.junit.Test`），也不继承 `TEST_BASE_SUPERCLASSES` 登记的已知测试基类。
4. `facade-no-test`：`*Kt` 文件 facade 对应源码里没有顶层 `@Test` 函数。
5. `category-tagged`：打了 `@Category(...)`，由 `rhino-eval-tests` / `slow-bench-tests` 独立 job 按 `includeCategories` 执行，不进四分片清单；但仍写入 `manifest.classes`，供 aggregate 跨 job 归属核对。

源码解析兜底：同名文件缺失时，在 FQCN 对应包目录内按声明名扫描（顶层 `data class` 与主声明共享同一文件的情形，如 `SearchBenchReport` 落在 `SearchBenchmark.kt`）。

## 六、反例推演：误杀路径与识别保护

### 6.1 `@Test` 写在 `companion object` 里

- 误杀后果：JUnit4 下 companion object 的静态测试方法仍会被执行；若过滤器按顶层 class 方法体扫描，会把这类用例整类剔除 → 用例静默消失、分片总条数下降、aggregate `total < BASELINE 3185` 断言失败，且 CI 不会在 discover 阶段报错（清单变少不红灯）。
- 本脚本识别方式：`TEST_ANNOT` 正则扫描**整份文件文本**，不解析 class 体边界；companion object 块内的 `@Test` 同样命中。内置夹具 `CompanionTest`（`companion object { @Test ... }`）验证保留。

### 6.2 注解写全限定名 `@org.junit.Test`

- 误杀后果：未 import 而内联全限定的测试方法不被短名 `@Test` 匹配 → 同上，静默掉用例、aggregate 总数掉档。
- 本脚本识别方式：正则 `@(?:org\.junit\.)?Test\b` 同时接受短名与全限定名；`\b` 排除 `@TestFactory` / `@TestParameterized` 等同前缀注解。内置夹具 `QualifiedTest`（`@org.junit.Test`）验证保留。
- 仓内现状扫描：无内联 `@org.junit.Test` 写法，全部经 `import org.junit.Test` + `@Test`；夹具覆盖该写法是防未来引入。

### 6.3 继承已知测试基类、自身文件无 `@Test`

- 误杀后果：基类提供 `@Test` 模板方法、子类只填数据时，子类文件自身无注解会被当 `no-test-annotation` 剔除。
- 本脚本识别方式：`TEST_BASE_SUPERCLASSES` 集合登记可执行测试基类；声明头冒号后超类型命中即保留。当前仓内无抽象测试基类（已穷举 `abstract class` / `: TestCase` / `: BaseTest` 零命中），集合留空；后续引入基类在此登记即可。

### 6.4 文件 facade 顶层 `@Test` 函数

- 误杀后果：Kotlin 顶层测试函数编译为 `*Kt` facade；若一律按 facade 剔除，顶层用例消失。
- 本脚本识别方式：facade 条目回找剥尾源文件，文件内含 `@Test` 即走 `facade-with-top-level-test` 保留通路；当前 4 个 bench facade 源文件均无 `@Test`，判 `facade-no-test` 剔除。

### 6.5 「只减伪条目」算术校验

- 正向：每条剔除条目都能回指到 4.1 的某条原因与具体源码行；27 条分类类全部含 `@Test`，归属独立 job 而非消失。
- 反向：5.3 节逐条复核新清单无源缺失 / 无分类残留 / 无无注解条目；过滤前后差值 46 = 19 剔除 + 27 分类，不存在第三条未解释的减量。

## 七、二三阶影响推演

- **aggregate 归属核对**：aggregate 步骤读 `manifest.json` 的 `classes` 字段，校验 XML 报告类 ⊆ 清单。新 manifest `classes` = 598 分片类 + 27 分类类；19 条伪条目永不产生 XML，缩出 manifest 不影响核对。新增 `shard_classes` / `category_classes` / `dropped` 字段为附加信息，旧字段 `total` / `classes` 语义保留。
- **`--tests` 模式数量**：每片 `--tests` 由 161 降到 150 / 150 / 149 / 149；Gradle 类路径扫描与模式匹配负担同步下降，分片按真实可执行类均分（旧清单含空扫条目，名义均分、实际负载不均）。
- **独立 job 不变**：rhino-eval-tests / slow-bench-tests 不带 `--tests`，靠 `includeCategories` 选取；分类类移出分片清单不改变其执行位置，互斥并集口径不变。
- **基线断言**：aggregate 硬断言 `total >= 3185` 针对 JUnit XML 用例条数，与清单类数无直接等式；被剔除的 19 条本就不产生用例 XML，27 条分类类仍在独立 job 出 XML，总条数不受影响。
- **未来新增顶层测试函数 / 测试基类**：脚本两条保留通路已留；若引入新的 JUnit 注解形态（如 JUnit5 `@org.junit.jupiter.api.Test`），需扩 `TEST_ANNOT` 与基类集合——当前仓内全量 JUnit4。
