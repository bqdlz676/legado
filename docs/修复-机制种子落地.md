## 三、两布尔口径

种子末段只认两个可机判的事实：HEAD 在哪（`git log --format='%h' -1`，`seed-check.sh:64`）、CI 是绿还是红（含单测全绿，`seed-check.sh:65-90`）。不报进度百分比、不报包（`docs/种子-机制种子.md:36`）。

百分比在长链路上必然失真：它把「写码 / 验收 / 提交 / push / CI / 出包」多段异构进度压成一个数，任何一段挂起都会让分子分母同时失真。历史教训：一条测试侧小错使 8 次 CI run 全 failure、出包步骤连续 skipped、一次都没走到出包（`docs/落文-进度续传快照.md:115`；`docs/复盘-返工根因.md:288` 标题「8 连红 + 11 条测试源集错成因链」、`:303`「一条测试侧小错的机会成本是 8 个 CI 周期 + 零出包」）；进度口径曾在约 55% 阶段出现 8 连红无包（口径记于 `docs/种子-机制种子.md:36`）。两布尔只承认「HEAD 哈希 + CI 绿红」，不给虚假完成感。

CI 状态取值 `green / red / running / none / unknown`（`seed-check.sh:80-88`）：`running` 是还没跑完，`none` 是同 sha 还没有 Verify run，二者都不是绿；`unknown` 是凭据缺 / 网络断 / API 错导致状态取不到。

## 四、退出码语义

- `SEED: READY` 只在 `fail=0 且 missing=0 且 unknown=0` 时出现（`seed-check.sh:100-101`），退出码 0；任一不为零，末行 `SEED: INCOMPLETE（fail=$FAIL missing=$MISS unknown=$UNKNOWN pass=$PASS）`，退出码 1（`seed-check.sh:104-106`）。
- `MISS`：`need` 行指向的文件不存在时显式记 `MISSING`，不算通过（`seed-check.sh:25-28`）；模块在岗与否一眼可见，不靠「命令没跑起来」隐式跳过。
- `unknown` 必须阻断：CI 状态取不到等于「构建可信不可确认」，不许让种子在两布尔 CI 腿空缺时报绿。

这条是 Q-286 修的。修之前：内嵌 python 任何异常都 `print('unknown')`，但旧终判只看 `FAIL` / `MISS`，`unknown` 不计入任何计数，种子能在 CI 状态不可知时仍报 `SEED: READY`，两布尔的 CI 腿是空的（`docs/修复-复核必改四条.md:78`）。修之后：`:11` 增 `UNKNOWN=0` 计数；`:94-95` 命中 `unknown` 即 `UNKNOWN=$((UNKNOWN+1))`；`:100` 终判三条件并列；`:104` INCOMPLETE 末行带 `unknown=$UNKNOWN` 与原因「CI 状态不可取，无法确认构建可信」（`docs/修复-复核必改四条.md:83-84`）。`unknown` 不并入 `FAIL`：它不是「门禁跑红」，而是「可信性无法确认」，单列便于末行区分原因，但终判与 `FAIL` / `MISS` 同等阻断（`seed-check.sh:12-14`）。

## 五、维护约定

- 新增门禁必须同时带 `--selftest` 才能进种子：无法自证的门禁等于不可信的门禁（`docs/种子-机制种子.md:84`；棘轮基线见 `data_scripts/selftest-baseline.json` 顶部 note「历史欠账棘轮：只许缩小，新增门禁必须自带 --selftest」）。
- 删除模块时必须同步删掉种子里对应的 `need` 行；否则 `MISSING` 会长期挂着，久而久之被当成噪声——这正是第一节要防的报警疲劳（`docs/种子-机制种子.md:85`）。
- 种子文件本身的改动也要走分桶提交，并在回执里写清「为什么加这一项、它替人挡掉了哪类错误」（`docs/种子-机制种子.md:86`）。
- 新增 `need` 行沿用 `need <名称> <文件> <命令...>` 形态：文件在才跑，不在记 `MISSING`（`seed-check.sh:25-28`），不许写成无条件 `step`。
