## 条款 2：防重时序走查 —— **有条件 PASS**（级别 B；窗口逐条列出）

### 守卫链（按执行顺序，提交内行号）

1. **VM 状态守卫**：`InkSearchViewModel.kt:123-124` 读 `_uiState.value`，`if (!state.canLoadMore) return`。
2. **`canLoadMore` 定义**：`SearchModels.kt:148-151` = `loadState is Content && hasMore && paging !is LoadingMore`。
3. **去抖守卫**：`InkSearchViewModel.kt:125-126` `SearchPagingPolicy.withinDebounce(lastLoadMoreAt, now, LOAD_MORE_DEBOUNCE_MS)`；策略实现 `SearchModels.kt:163-164`（`lastAt > 0 && now - lastAt < debounceMs`）；窗口常量 `SearchTokens.kt:119` `LOAD_MORE_DEBOUNCE_MS = 200L`。
4. **写时间戳 + 翻在途态**：`InkSearchViewModel.kt:127` `lastLoadMoreAt = now`；`:128` `dispatch(SearchIntent.LoadMoreStart)`。
5. **归约器二次闸门**：`SearchReducer.kt:170-175`，`if (!state.canLoadMore) return@reduce state`，不翻转状态。
6. **协程体内复核**：`InkSearchViewModel.kt:129-141`：模型空 / 关键词空 → `LoadMoreFailure`（`:132`）；离线 → `LoadMoreFailure(OFFLINE_MESSAGE)`（`:135-137`）；否则 `model.search(searchID, searchKey)`（`:140`）。
7. **底层第四道**：`SearchModel.kt:57-58` `synchronized(pageOwner) { if (searchId == mSearchId && pageOwner.isRunning()) return }`；同 id 非在途才 `searchPage++`（`SearchModel.kt:76-78`）。

### 同线程连发结论

主线程两次连续调用 `loadMore()`：第一次同步走完守卫、`dispatch` 同步更新状态为 `LoadingMore`；第二次读到 `paging = LoadingMore`，`canLoadMore=false` 被挡；即便状态读取存在交错，200ms 去抖窗口再挡一层。**同页在途重复请求在静态路径上被挡住**（级别 B：依赖 `dispatch` 同步落状态与主线程串行调用，未做并发压测）。

### 发现的时序窗口（逐条）

#### W1 跨词竞态（窄，级别 B）

- 位置：`InkSearchViewModel.kt:129-141` 的 IO 协程体只复核 `model / searchKey / 网络`，**未复核 `paging / hasMore / 当前命令序号`**。
- 推演：翻页协程体挂起期间，用户发起新检索，`runSearch`（`:166-189`）覆盖 `searchID / searchKey` 并清零 `lastLoadMoreAt`（`:176`）；旧翻页体随后用**新字段**再调一次 `model.search`。底层 `SearchModel.kt:58` 在 running 时拦截；若旧模型恰好已结束、新搜索也已完成，可能直接 `searchPage++` 多翻一页。
- 定性：非同页在途重复，属跨词串页风险；`SearchCommandGate`（`:311-335`）只罩 `runSearch`，未罩 `loadMore` 协程体。

#### W2 失败态滚动隐式重试（级别 B，设计上半明示）

- 位置：`SearchModels.kt:148-151` 的 `canLoadMore` 不排除 `LoadMoreError`（`:146` 注释明示"分页失败态允许重试，不在此拦阻"）；`InkSearchViewModel.kt:143-149` `retryLoadMore()` 虽有 `paging is LoadMoreError` 闸门，但滚动回调走的是 `loadMore()` 直连。
- 推演：翻页失败进 `LoadMoreError` 后，去抖 200ms 一过，滚动到底会经 `loadMore()` 自动再发一页，绕过脚注重试按钮的显式闸门。旧请求已终结，**不构成在途重复**；但与"重试只走脚注入口"的表述存在出入。

#### W3 多批次回调误路由 / 收口标记可能丢失（**本单最不确定一条**，级别 B，需 L2 / 运行时复核）

- 位置 A：`SearchReducer.kt:177-187` `LoadMoreAppend` 追加首批后即把 `paging` 置回 `Idle`（`hasMore=true` 时，`:185`）。
- 位置 B：`InkSearchViewModel.kt:207` 靠 `_uiState.value.paging is LoadingMore` 区分"翻页追加"与"首屏回填"；首批追加后 `paging` 已是 `Idle`。
- 位置 C：`SearchModel.kt:21` `onSearchSuccess(searchBooks)` 在 `onEach` 内**按书源批次多次回调**；`SearchModel.kt:27` `onSearchFinish` 在 `onCompletion` 末尾回调一次。
- 推演：单次翻页若有多书源批次，第二批 `onSearchSuccess` 到达时 `paging` 已非 `LoadingMore` → 走入 `InkSearchViewModel.kt:210-214` 的首屏 `ResultsReady` 分支（`resetPaging`，分页态被清）；随后 `onSearchFinish` 派发的 `LoadMoreFinish` 被 `SearchReducer.kt:201` 守卫拒收（`paging !is LoadingMore`），远端 `hasMore=false` 收口标记可能丢失，状态停在 `Idle / hasMore=true`，下一次滚动可能多发一页。
- 触发前提：单次翻页内存在多批次 `onSearchSuccess` 回调；单书源 / 单批次不复现。L1 静态无法确认生产书源数量与批次切分，**此条需 L2 或真机多书源场景复核**。

#### W4 归约拒收后去抖时间戳已占用（反向，级别 B）

- 位置：`InkSearchViewModel.kt:127` 先写 `lastLoadMoreAt`，`:128` 才 `dispatch`；若归约器 `SearchReducer.kt:173` 二次闸门拒收，时间戳已被占用，拒收后 200ms 内的合法触发也被去抖压住。
- 定性：方向是**漏触发**而非重复请求；影响面 200ms 窗口，级别低。
