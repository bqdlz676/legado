### 1.3 最高风险的 3 条

1. **旧阅读链 `ReadBookActivity` + `page/` View 层**：生产入口虽已切到 `InkReadActivity`（`BookInfoActivity.kt:1511`、`ContextExtensions.kt:74`、`FragmentExtensions.kt:102`），但 18 个 androidTest 仍直接 launch 它；朗读通知/媒体键/旧 intent extra 契约、`model/ReadBook` 与 `page/entities` 的共享态尚未切净。**误删 entities 会打断新分页引擎**（`vertical/LegadoChapterAdapter.kt:3` 仍 import `TextChapter`）。
2. **`help/JsExtensions` 及其子类 + proguard `* extends JsExtensions` keep**：书源/订阅源/登录 JS 规则的运行时桥，方法名由远端书源 JS 字符串调用，静态 grep 看不到调用方。删错 = 在线书源解析全灭，且 R8 关闭期不报错、运行期才 `TypeError/NoSuchMethod`。
3. **`help/http/ObsoleteUrlFactory`（名字误导，能力未失效）**：`App.kt:111` 全局 `URL.setURLStreamHandlerFactory` 桥，规则内 `HttpURLConnection` 经它走应用的 OkHttp（Cookie/SSL/代理/拦截器）。类名里的 "Obsolete" 指 JDK `setURLStreamHandlerFactory` 这个 API 老旧，**不是这个工厂已废弃**；误删会让 HttpURLConnection 直连，绕过 Cookie  Jar 与 SSL 兜底。

## ⑤ 专项三节

### 5.1 二阶三阶影响（铁律 59）

**现在不删的后果（二阶 → 三阶）：**

1. **编译时间**：旧栈 610 文件 / 11.9 万行全部参与 Kotlin 编译与全量 clean 构建；C4–C10 每拖一批，单包编译基线就多扛一份旧 AST。三阶：CI 队列变长、返工反馈周期拉长，铁律 46 的分层组装验收成本随文件数线性上升。
2. **误改风险（双栈同名概念）**：仓内已存在多组同名/近名双实现——`help/AllusionDict` ↔ `help/allusion/AllusionDict`、`help/PlaceDict/PlaceGeo` ↔ `help/place/*`、`page/InkView` ↔ `components/Ink*`、`ReadBookActivity` ↔ `InkReadActivity`。新人或子代理改错包的概率随双栈并存时间上升；历史上"修一处、崩三处"（crossing 245 条级联错）即同类根因。
3. **新人认知成本**：判断一个类属 A 还是 B，必须先读契约索引 + `ink/README.md` + `ReaderShellHost` 接口 + vertical 引擎 + bubble 链；`model/ReadBook` 2,292 行新旧职责混在一起，单文件无法自证。
4. **包体积与 CI 缓存**：`minifyEnabled false` + `shrinkResources false`（`c8ac66e`，release 同关），未引用类与 215 个 drawable、221 layout 全部进包；assets 116M 之外，代码侧死重持续叠加；CI 缓存随旧资源膨胀。
5. **规格漂移**：旧链残留的旧主题色/旧弹层会被新页面无意中复用（贴皮反复出现的根因），导致"东方美学"规格在边角页面回弹成 Material 观感。

**删错的后果（二阶 → 三阶）：**

1. **运行期 `ClassNotFound`/`NoSuchMethod`**：反射、JS 字符串、manifest 组件、Provider 路由四类静态盲区（§5.2）一旦删错，编译期不红，真机/远端书源调用时才崩。
2. **主题崩溃**：旧 Activity 删了但 manifest/主题引用残留，或新壳误用旧 `AppTheme` overlay，启动即 inflate 异常。
3. **旧用户偏好/备份丢失**：`ReadBookConfig`/`ThemeConfig` 字段与备份 JSON 咬合；删字段而备份读写未留兼容窗口，老用户恢复备份后配置静默归零。
4. **书源生态断裂**：JsExtensions 公共方法被远端书源 JS 调用，删方法 = 线上书源批量失效，且难定位是哪条规则触发。
5. **测试红连锁**：18 个 androidTest 钉住旧阅读链；旧类先删而测试未迁，CI 回归全红，遮蔽真实新功能缺陷。

### 5.2 反例与边界（铁律 61：假设删除判断是错的，逐条否证）

> 每条给出实际验证方式（本审计已执行的 grep / 读取点）；未覆盖的动态验证列入 §6。

1. **反射调用（`Class.forName` / `loadClass` / 字符串类名）**
   - 实测：`App.kt:202` `loadClass("com.google.android.gms.common.security.ProviderInstallerImpl")`（GMS 可选增强）；`FileDocExtensions.kt:66` `Class.forName("androidx.documentfile.provider.TreeDocumentFile")`；proguard `:118` keep 该类。未发现按字符串拼本仓 Activity/Dialog 类名 `forName` 的路径。
   - 否证结论：自有旧类不在反射白名单内；但 `LauncherIconHelp` 按 ComponentName 反射引用 `Launcher1-6`（`WelcomeActivity` 子类，见 `WelcomeActivity.kt` 尾部注释"类名不可改名"），**这 6 个别名类名是反射契约，删/改前必须核**。
   - 验证方式：`grep -rn "Class.forName\|loadClass\|ComponentName\|getDeclaredConstructor" app/src/main`；删类前再跑一遍。
2. **ProGuard/R8 keep 规则**
   - 实测：`proguard-rules.pro` 保留 `* extends JsExtensions`（:61）、`**.data.entities.**`（:63）、`HighlightStyle$**`（:65-66）、`CookieStore`/`CacheManager`/`StrResponse`（:83-86）、`ReturnData`（:146）、XPath `AxisSelector/NodeTest/Function`（:123-125）、GSY 播放器成员（:153-157）、appcompat `Toolbar/SubMenuBuilder/MenuBuilder`（:106-112）。
   - 否证结论：被 keep 的类即使代码引用为 0，也可能被序列化/反射/JS 框架实例化；删类前必须对照 keep 清单逐条确认。当前 `minifyEnabled false`（`app/build.gradle:127,137`），keep 不影响本次打包，但未来开启 R8 时这些引用会复活。
   - 验证方式：删类前核对 keep 行；实体类删除需同步评估 Gson/序列化字段。
3. **Manifest 组件 / alias / service / intent-filter**
   - 实测：manifest 注册 60+ Activity、13 service、2 provider、1 receiver；7 个 LAUNCHER 入口（`WelcomeActivity` + `Launcher1-6`）；`OnLineImportActivity` 挂 VIEW/SEND_MULTIPLE/PROCESS_TEXT；`ReaderProvider` exported；16 处 `exported="true"`（另见问题清单 M1）。
   - 否证结论：代码 grep 不到 launch 的 Activity，仍可能被外部 intent、通知 PendingIntent、桌面快捷方式拉起（`BookshelfManageActivity`/`RemoteBookActivity` 即此类待复核项）。删 Activity 必须同步删 manifest 条目与 intent-filter。
   - 验证方式：逐组件核对 manifest `<activity>/<service>/<provider>/<receiver>` 与 `android:name`、`<intent-filter>`、`android:targetPackage`；通知 `activityPendingIntent<X>` 清点。
4. **assets 内 JSON/JS 被动态加载**
   - 实测：`DefaultData.kt:52-171` 按名打开 10 个 `defaultData/*.json`；`js_source_template.js` 被 `assets/web` Vue 前端 fetch；`cronet.json` 启动读取；`char_dict.txt`/`person*.txt`/`place.txt`/`map/*` 等按名解析。
   - 否证结论：资产文件不被代码 import 语句引用，纯字符串路径；删资产前必须在解析器/前端里查名字符串。
   - 验证方式：`grep -rn "assets.open\|fetch(\|\.json\|\.txt\|\.bin" app/src/main` + `assets/web` 前端 bundle 内路径字符串。
5. **SharedPreferences 旧键被读取**
   - 实测：`PreferKey.kt` 297 个常量；具名 SP：`SourceConfig`、`JS_SOURCE_API_PREFS`、`permission_deny_count`、`ReplacePreviewConfig`、`ThemeStore`；读取统一走 `PreferencesExtensions` 带默认值。
   - 否证结论：删旧 dialog 不会清 SP 文件，老用户残留键不致崩溃；风险是"写入方已删、读取方仍在"导致偏好静默回默认，或反之读不到新键。删除配置字段时必须双向核对写入点与读取点。
   - 验证方式：按 `PreferKey` 常量名双向 grep `put*` / `getPref*`；具名 SP 逐个查。
6. **JS 规则内的字符串方法名/类名**（额外边界）
   - 实测：书源 mainJs 在远端/`defaultData/bookSources.json`，可调用 JsExtensions 公共方法；`web/vue` bundle 内 `openLegacyReview`/`runLegacyReview` 等接口名与 `api/controller` 路由字符串咬合。
   - 否证结论：静态 Kotlin grep 看不到 JS 侧调用；删桥方法/接口前要对照 JS 模板与路由表。
   - 验证方式：对照 `js_source_template.js`、`assets/defaultData/*.json`、`api/controller/*` 路由名。
7. **测试钉住旧类**（额外边界）
   - 实测：androidTest 64 文件中 18 个引用 `ReadBookActivity`/`ReadView`/`ContentTextView`；unit test 546 文件中若干以旧类路径做契约断言（如 `ImportSelectionCountResetTest`、`TocUpdateRequestsTest`）。
   - 否证结论：旧类删除会同时挂掉这些测试；须先迁移测试或随类删除，不能留红编译。
   - 验证方式：`git grep -l "<旧类名>" app/src/test app/src/androidTest`。

### 5.4 跨领域对照（铁律 60）

| 外域做法 | 机制 | 本项目对照 | 采纳 / 不采纳理由 |
|---|---|---|---|
| Android R8 shrinking + unused resource detection | 构建期自动剔除无引用类/资源，lint 报未使用声明 | 本项目 `c8ac66e` 主动关闭 minify/shrinkResources（7GB runner 上 R8 GC 抖动卡死），机器兜底缺失；本报告的"零引用"是人工 grep 近似 | **暂不依赖构建期剔除**：先人工静态清单 + 动态 intent 遍历；待 CI 资源允许再开 R8 做二轮收口 |
| 大型前端 monorepo dead-code 清理（ts-prune / knip / route-based codemod） | 依赖图分析找出无入边模块；按路由分批删，codemod 批量改 import；强类型编译期兜底 | 本项目旧页面仍可达（有入边），不是纯无入边死代码；Kotlin 编译期可挡断链，但反射/JS/manifest/asset 四个盲区编译器看不见 | **采纳"按路由（用户可感知页面）分批删"**：每批 = 一个 Compose 替换页 + 其旧壳/旧资源/旧测试，独立可回退、可验收；**不采纳"一次性全量删"**，理由见下 |

**为什么选"分批按用户可感知页面删"而不是一次性全量删：**

1. 旧栈不是死代码：11.9 万行旧 UI 中大部分仍被导航、通知、外部 intent 拉起，一次性删会拆断可达链路（§3 依赖图）。
2. 构建期兜底关闭：R8/资源压缩未开，删错不会在打包期暴露，只能靠编译 + 人工复核；分批把每次断链面压到一个页面域。
3. 四类静态盲区（反射/JS/manifest/asset）需要逐域核对，批量删无法逐条覆盖。
4. 备份 schema 与旧 SP 键需要兼容窗口：配置类字段不能随 UI 一刀切。
5. 与既有 C1–C10 派单节奏对齐（铁律 45/46）：一批一验收，旧实现保留到新页验收通过，回退成本最低。
