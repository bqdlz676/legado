## 一、背景与事实锚点

- 现象：CI 分片 job 反复「静默挂死」——Gradle 不产 JUnit XML、无逐用例进度，被超时取消。既往记录见 `docs/诊断-shard2挂死定位.md`（Verify `45801836915` shard 2/4，2714s 命中当时 `timeout-minutes: 45`，窗内无逐用例进度行、无 XML）。现行 `verify.yml` 的 `test-shard` job 已收窄到 `timeout-minutes: 15`。
- 挂死源随分片划分迁移：上轮挂死 shard 1 的类清单与本轮挂死 shard 2 的清单，161 条里重合 158 条——同一批类换片仍挂，说明 culprit 与分片归属（round-robin 落到哪一片）无关，按「哪片挂就查哪片日志归属」排嫌疑不可靠。
- 既有两件工具（先证不是重复造）：
  - `data_scripts/emit-shard-lists.py`：discover 阶段按磁盘源码净化清单（五桶判据）再 round-robin 切四片；解决的是「伪测试类混进 `--tests`」，不做挂死定位。
  - `data_scripts/find-hang-culprit.py`：从已落地 job 日志按 STARTED / 终态事件配对，点名「有 STARTED 无终态」的最后若干条用例。
- 既有工具的取证盲区：日志配对只能给出最后几条嫌疑，且必须等本轮熔断跑完拿到日志；一旦挂死发生在 job 启动阶段 / 测试类静态初始化期，一行 STARTED 都没有，取证器彻底瞎（落到 `NO_STARTED` 分支）。
- 本单所补：不依赖逐用例日志进度的第二条通路——把嫌疑类清单净化后折半成 a/b 两批，每批一个 8 分钟熔断的独立 job，哪批挂死就把嫌疑集折半，逐轮收敛到小集合再读 STARTED 日志。

## 二、脚本能力与用法

脚本：`data_scripts/bisect-suspects.py`。

入口：

- `--in <path>`：嫌疑类清单文件，默认 `/tmp/cl2/shard-2.txt`。
- `--in-classes a.b.C1,a.b.C2`：逗号分隔内联清单，与 `--in` 互斥。
- `--out-dir`：两批清单输出目录，默认 `/tmp/bisect`；产出 `suspect-a.txt` / `suspect-b.txt`（小集合模式只产 a）。
- `--emit-workflow <path>`：Actions 片段文件路径，默认 `docs/ci-bisect-片段.yml`；只写该文件，绝不改 `verify.yml`。
- `--selftest`：三组 /tmp 夹具自测，跑完自删。

净化口径（复用 `emit-shard-lists.py` 的 `classify()`，不在本脚本另造过滤器，避免两套判据漂移）：

- `keep`：普通 class 且源码含 `@Test`（短名与全限定 `@org.junit.Test` 均认）或继承已知测试基类 → 进二分批。
- `category-tagged`：打了 `@Category(...)`，由 `rhino-eval-tests` / `slow-bench-tests` 独立 job 执行，不进分片 job 也不进二分批——挂死发生在分片 job 内，独立 job 的类不是嫌疑；排除清单在 stdout 单列。
- `drop`：`missing-source`（无源残留）/ `non-class-decl`（object / interface / data / sealed / enum / abstract）/ `no-test-annotation` / `facade-no-test`，与 emit 脚本五桶一一对应。无源残留若带进二分批，`--tests` 匹配不到任何类，job 会假绿，二分结论被污染，必须先剔除。

二分规则：

- 净化保留集排序后，前半进 a（`ceil(n/2)`），后半进 b（`floor(n/2)`）；脚本内守恒断言：两批并集 == 净化全集、两两重叠为空，不满足即报错退出。
- 嫌疑集 < 4 条不再折半（见 §五-a）。

片段生成（`docs/ci-bisect-片段.yml`）：

- 触发器 `workflow_dispatch`；job `bisect`，`strategy.matrix.side: [a, b]`，`timeout-minutes: 8`；`fail-fast: false` 保证两批都跑完留证。
- 步骤：checkout → 预装 JDK 21（与 verify.yml 分片 job 同口径，零网络取 `JAVA_HOME_21_X64/ARM64`）→ 下载 `bisect-suspects` artifact → 按 `suspect-${{ matrix.side }}.txt` 拼 `--tests` 数组 → `./gradlew :app:testAppDebugUnitTest -PexcludeRhino -PexcludeSlowBench --no-daemon --build-cache --stacktrace "${ARGS[@]}"`，与现行分片 job 的 Gradle 口径一致。
- 批内空清单在步骤里显式 `::error::` 退出，拒绝空跑假绿。

## 三、收敛性论证（实算）

### 3.1 本轮嫌疑集实算（`/tmp/cl2/shard-2.txt`，161 条）

- 原始嫌疑 161；净化保留 149；分类打标排除 9；`non-class-decl` 剔除 3；`missing-source` 0；`no-test-annotation` 0；`facade-no-test` 0。
- 排除点名（12 条）：
  - category-tagged 9：`RhinoJsonInitializationTest`、`BubbleBenchmarkTest`、`AutoTaskCoreTest`、`CryptoJsCompatibilityTest`、`VerticalPageTurnBench`、`HalfSheetBenchTest`、`FontRegistryBenchTest`、`CrossingBenchTest`、`ReplayBenchTest`。
  - non-class-decl 3：`ComponentBenchmark`、`InkSlateBenchmark`、`SearchBenchReport`。
- 二分实落盘：`suspect-a.txt` 75 条，`suspect-b.txt` 74 条；并集 149 == 净化全集，重叠 0（集合口径复核通过）。

### 3.2 最坏轮次与总时长（实算，非估算）

单轮 a/b 两批并发各跑各的，单轮熔断 8 分钟；每轮只保留挂死那一批进入下一轮。

- 161 条原始嫌疑：`ceil(log2 161) = 8` 轮收敛到 1 个类；最坏路径规模阶梯 `161 → 81 → 41 → 21 → 11 → 6 → 3 → 2 → 1`；最坏总时长 `8 × 8 = 64` 分钟。
- 149 条净化后：`ceil(log2 149) = 8` 轮；阶梯 `149 → 75 → 38 → 19 → 10 → 5 → 3 → 2 → 1`；最坏总时长同样 64 分钟。
- 小集合规则叠加：规模降到 < 4 即停止折半、全量跑一轮读 STARTED 日志。161 条走 6 轮折半降到 3 条，再加 1 轮全量跑 = 7 轮内拿到小集合线索；149 条同口径 7 轮。

### 3.3 每轮判定口径

- 一批 8 分钟内无 XML / 无终态被取消 → culprit 在该批；下一轮以该批清单重跑本脚本。
- 两批都绿 → 本轮嫌疑集不含可复现 culprit：要么挂死与类无关（环境 / worker / 静态装配），要么是概率性挂死本轮未触发，转 §四 / §六 分支，不得把绿批直接当无罪定论。

## 四、两批都挂死的处置分支（二分失效）

**现象**：a、b 两批在同一轮都 8 分钟熔断挂死。

**含义**：折半法的基本假设被破坏——「挂死由集合内类触发，且触发条件随该类走，去掉该类的那一批应当变绿」。两批都挂只可能是：

1. 集合内不止一个 culprit（多类叠加 / 类间共享状态）；
2. 挂死与测试类无关：JVM / test worker 崩溃、机器资源、端口 / 临时文件占用、全局单例静态装配、环境差异；
3. 概率性挂死本轮两边都踩中时序（见 §六）。

**此时二分失效，禁止继续折半**：再折半只会反复得到「两批都挂」，空耗 8 分钟 × N 轮。必须换判定维度，三条通路按序尝试：

1. **串行化复跑**：`maxParallelForks=1` 单 worker 串行，排除并行交错 / 共享可变状态竞态；串行下若变绿，嫌疑收敛到「并发时序」而非某个类。
2. **按包前缀切**：不再按折半清单，改按测试包前缀（`ui.*` / `model.*` / `help.*` / `utils.*` …）切块，先定位到包，再在包内折半。
3. **绕开嫌疑包保 CI 绿**：临时用 `--tests` 排除当前嫌疑包，先让汇总断言与出包链转绿，再离线 / 独立 workflow 回头查该包；不得让整条验证车道被单个挂死包堵死。

## 五、边界处理

### a) 嫌疑集 < 4 条

不再二分：全部写进 `suspect-a.txt`，不产 `suspect-b.txt`（旧残留 b 文件会被脚本清掉，防上一轮清单串批）；stdout 提示「已收敛到小集合，读 STARTED 日志即可」；片段切 `bisect-small` 单 job 形态，单轮 8 分钟全量跑。

### b) 清单内有无源残留

先过 emit 净化逻辑再二分，口径与 discover 分片完全一致：找不到 `.kt` / `.java` 源码、facade 剥尾仍无源、同名声明在包目录扫描中也找不到，一律落 `missing-source` / `decl-not-found` 剔除。本轮 161 条实算无源残留 0 条；被剔的 3 条 `non-class-decl` 与 9 条 category 类在 stdout 按分因计数列出。

### c) 空清单必须报错退出

两种空集都拒绝出 job：输入文件 / 内联清单为空；净化后一条可执行类都没有（全部落桶）。退出码 1，不写清单文件、不写片段文件——空 `--tests` 清单会让 Gradle 跑空任务假绿，比红灯更危险。已用空文件夹具实测：报错后输出目录与片段路径均未创建。

## 六、反例推演：概率性挂死（最坏反效果）

**反例前提**：挂死是概率性的——同一个类有时挂、有时不挂，触发依赖时序 / 线程交错 / 资源竞争 / 外部环境。二分法在确定性挂死下收敛；在概率性挂死下会出最坏反效果：嫌疑折半到最后 1 个类，单独跑一次没挂，就得出「该类无罪」的错误结论，真正的 culprit 被放出嫌疑集。

**如何识别概率性挂死**：

- 同一嫌疑集（同一批清单）连跑两次，结果不一致——一次挂死、一次通过——记为 **flaky**，不记 `innocent`；单次绿跑不能脱罪。
- 批次归属不稳定：上一轮 a 批挂、下一轮同清单 b 批挂，或两批交替挂，也是 flaky 特征（确定性 culprit 应稳定落在含它的那一批）。
- 命中率口径：同一清单连跑 N 次，记录挂死次数 / N；命中率显著 > 0 即保留在嫌疑集，不按单次结果剔除。

**命中 flaky 后的处置**：

1. 静态特征逐类点名扫描（对照 `docs/诊断-shard2挂死定位.md` §一 特征清单，本单补充回溯 / 递归两类）：
   - 阻塞等待类：`Thread.sleep` / `SystemClock.sleep`、`CountDownLatch.await()` 无超时、`Future.get()` 无超时、`Object.wait`、阻塞队列 `.take()`、裸 `.join()`、`awaitTermination()` 无超时；
   - 协程 / 线程类：`runBlocking` 包外部回调、`GlobalScope` / 裸 `CoroutineScope` 起线程、`delay(` 无上限；
   - 计算爆炸类：正则灾难性回溯（嵌套量词如 `(a+)+`）、无限递归 / `while(true)` 无退出条件；
   - 外部资源类：`Socket` / `openConnection` / `HttpURLConnection` / `ServerSocket` / `URL(` 网络直连无超时、`ProcessBuilder` / `Runtime.exec`。
2. 对命中特征的类逐个在串行模式（`maxParallelForks=1`）下重复复跑取命中率；复跑样本量不足时不下结论。
3. 二阶影响：flaky 类在二分里批次归属漂移，§三 的「挂死批即 culprit 批」判定只对确定性挂死成立；flaky 场景回到命中率口径，不按单次批次定罪。
4. 三阶影响：8 分钟熔断是为取证速度设的，对需要特定时序才触发的慢挂可能过短；若两轮复跑均未复现，应拉长单轮时长或串行多轮复跑，而不是削减嫌疑类数量。

## 八、新发现问题

1. 挂死源在 shard 1 / shard 2 间迁移、两批清单 161 条重合 158 条：按分片日志归属排嫌疑不可靠，后续取证以二分清单折半为准，不按分片归属定罪 —— 已入队。
2. `app/build.gradle` 的 `testLogging` 仅开 `STARTED, FAILED`（Q-269 §六-1 已记），二分小集合轮次仍可能落在 `WARN_STARTED_ONLY` 口径，未闭环列表混入实际通过的用例；补 `PASSED, SKIPPED` events 属另一单，本单不碰 build.gradle —— 待裁。
3. 概率性挂死单次绿跑不能定罪也不能脱罪；本单已在脚本边界与 §六 给出「同集连跑两次不一致记 flaky、按命中率保留嫌疑」的判定规则 —— 已闭环。
4. 片段假设两批清单以 artifact `bisect-suspects` 上传；若贴进独立 workflow 运行，需先上传清单 artifact 或把清单提交到仓库固定路径 —— 待裁。
5. 两批都挂时二分假设被破坏，§四 已给出串行 / 包前缀 / 绕开嫌疑包三条换维度分支；若云端实跑命中「两批都挂」，需先在 `maxParallelForks=1` 串行下复跑一轮确认是否并发时序问题 —— 待裁。
