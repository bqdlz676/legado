## 二、方案：申领 / 交还判定收敛到唯一私有裁决入口

### 2.1 新方法 `syncShelfBridge()`

`app/src/main/java/io/legado/app/ui/main/bookshelf/InkShelfFragment.kt:274-281` 新增私有裁决方法：

```
private fun syncShelfBridge() {
    val visible = lifecycle.currentState.isAtLeast(Lifecycle.State.RESUMED) && !shelfHidden
    if (AppConfig.shelfParallaxEnabled && visible) {
        acquireShelfBridge()
    } else {
        releaseShelfBridge()
    }
}
```

判定口径只写这一处：申领仅当「偏好开启 && 生命周期至少 RESUMED && 未被藏槽」三者同时成立；其余一切路径——切后台、切 Tab、关开关、视图 / Fragment 销毁——一律交还。`visible` 局部变量只在本方法内出现一次，不再有第二份闸门。

## 三、销毁路径安全与重复 release 幂等推演

### 3.1 销毁路径不碰 requireContext / requireActivity

旧 `acquireShelfBridge()` 用 `requireActivity().windowManager.defaultDisplay.rotation` 与 `requireContext()`；这两个方法在 Fragment 解挂后会抛 `IllegalStateException`。新写法 `InkShelfFragment.kt:290-297`：

- `val ctx = context ?: return`（`InkShelfFragment.kt:291`）：Fragment 可空属性 `context` 取不到就放弃本轮申领，不抛异常。
- `val rotation = activity?.windowManager?.defaultDisplay?.rotation ?: 0`（`InkShelfFragment.kt:293`）：Activity 取不到时方向基准回落 `0`（即 `Surface.ROTATION_0`，与桥内 `displayRotation` 初值一致，`GyroBridge.kt:66`）。
- 兜底理由：申领只在裁决入口判 `visible=true` 时到达，而 `visible` 要求 RESUMED，此时 Fragment 必然 attached；可空取值是第二道防线，不是常态路径。拿不到 context 放弃本轮申领不等于永久失桥——回到可见路径会由 onResume / onHiddenChanged 再走裁决补申领，不静默降级。
- 摘牌路径 `releaseShelfBridge()`（`InkShelfFragment.kt:300`）只传身份串，方法签名不收 Context（`GyroBridge.kt:98` `fun release(host: String)`），onDestroyView / onDestroy 之后调用不触碰任何宿主资源。

### 3.2 重复 release 幂等：调用序列推演

桥侧持牌集合 `holders`（`GyroBridge.kt:53` `HashSet<String>()`）按宿主身份去重；`release(host)` 在 `synchronized(holders)` 内 `holders.remove(host)`，仅当移除成功且集合为空才 `teardown()`（`GyroBridge.kt:98-104`，短路判断在 `GyroBridge.kt:101`）。未上牌宿主 `remove` 返回 false，`empty=false`，不触发 teardown。记持牌集合为 H：

序列一 · 书架 onPause → onDestroy 连续两次交还（本单 N1 路径）：
1. 书架 onResume 申领，H={shelf}，监听存活。
2. onPause → `syncShelfBridge()` → `release("shelf")`，`remove` 成功，H=∅，`empty=true` → `teardown()` 注销清队。
3. onDestroyView → `syncShelfBridge()` → 第二次 `release("shelf")`，`shelf` 已不在 H，`remove` 返回 false，`empty=false`，**第二次不重复 teardown**。
4. onDestroy → 第三次 `release("shelf")`，同上幂等空操作。三次交还只摘自己的牌，不存在把集合清空后误拆他人牌的动作。

序列二 · 地图持牌中书架连续交还（交叉不误伤）：
1. 地图 onResume 申领，H={map}。
2. 书架 onPause → onDestroyView → onDestroy 三次 `release("shelf")`：`shelf` 本就不在 H，每次 `remove` 返回 false，H={map} 非空，**不 teardown**，地图监听与 FIFO 原样保留。
3. 地图后续 `pull()` 仍可取流；直到地图交还，H=∅ 才整体复位。

序列三 · 双持牌后书架先销毁：
1. H={shelf, map}，监听复用一路注册。
2. 书架 onPause / onDestroyView / onDestroy 连续交还，只移 `shelf`，H={map}，监听保留，地图姿态流不断。
3. 地图后续交还，H=∅ → teardown。顺序无关，不存在「B 在用被 A 拆」的交叉。

### 3.3 销毁路径裁决为何不会反向申领

onDestroyView 时 Fragment 生命周期状态已 ≤ STARTED，onDestroy 在 `super.onDestroy()` 之前状态为 CREATED；两处 `syncShelfBridge()` 读到的 `currentState` 都不满足 `isAtLeast(RESUMED)`，`visible=false`，必走交还分支。`shelfHidden` 即便残留旧值也不影响结论：RESUMED 这一半先判否。

## 六、自查反例 / 改坏推演

- 反例一：若把裁决写成两个方法（`shouldAcquire()` + 各生命周期仍自己拼 if）。判定口径还是散在多处，后续再加触发点仍会漏叠 RESUMED，N2 根因未除；现收敛为单一 `syncShelfBridge()`，申领 / 交还只在一处分叉。
- 反例二：若 onDestroyView / onDestroy 里仍调 `requireContext()` / `requireActivity()` 取方向。解挂后这两个方法抛 `IllegalStateException`，销毁路径直接崩；现申领路径用可空 `context` / `activity` 兜底，销毁路径只走不收 Context 的 release。
- 反例三：若销毁路径直接调桥的全局停桥口径。会把仍在用桥的地图 / 沙盘监听一并注销；现只 `release(HOST_SHELF)` 摘自己的牌，集合非空即保留共享监听（§3.2 序列二 / 三）。
- 反例四：若为补 N1 在 onDestroy 里再申领一次。销毁态生命周期非 RESUMED，申领既无意义又会在解挂后碰 Context；现销毁两处都走交还分支，裁决条件保证不会反向上牌。
- 反例五：若把 N2 修成「onHiddenChanged(false) 不看 RESUMED、只看偏好」。后台 show 回调仍会非前台抢传感器；现补叠 RESUMED 判断，与开关回调闸门同源同句。
- 反例六：若顺手放宽 Q441，hide 状态下也保留监听。切 Tab 后传感器 50Hz 事件持续投递，功耗要求被破坏；现 hidden=true 仍走交还，行为与 Q-441 / Q-447 验收口径一致。
- 反例七（二阶）：若 `acquireShelfBridge()` 拿不到 context 时静默上牌（传 null 或缓存旧 context）。桥内 `ensureStarted` 会用脏 context 取 SensorManager，状态不一致；现 `context ?: return` 放弃本轮，等回可见路径补申领，不造脏态。
- 反例八（三阶）：若裁决入口把 `shelfHidden` 漏判、只看 RESUMED。Fragment 在隐藏槽但生命周期处于 RESUMED（同屏 Tab 栈）时会白抢传感器；现闸门两半都在（`InkShelfFragment.kt:275`），与既有 D1 口径一致。
