## 6. 二阶 / 三阶影响与时序分析

### 6.1 注册时序：注册晚于首次查询会不会导致首屏空候选

- 注册发生点：
  - 路径 A（启动协程）：`App.kt:122` 在 `Application.onCreate` 内 `launch { runCatching { BubbleResolver.preload(appCtx) } }`，异步非阻塞；preload `:151` 重绑典故入口。
  - 路径 B（阅读壳同步预热）：`InkReadActivity.kt:159` `runCatching { BubbleResolver.preload(this) }`，在 `viewModel.initData(intent)`（`:161`）之前执行。
  - 路径 C（对象自注册）：`AllusionAnchorProvider.init` 仅在对象首次被触达时执行；生产路径首次触达即 preload `:151` 的显式调用。
- 首查早于重绑的窗口：若总线 `resolve` 在 preload 协程完成前被调用，`allusionProvider` 仍为 `null`，`:326` `?.invoke` 安全跳过 → 典故候选为空，不抛异常、不崩；重绑完成后的后续查询即带典故候选。该窗口与人物路 `personProvider` 完全同口径（人物亦靠 preload 重绑兜底），未引入新的时序风险。
- 气泡主链不受本注册时序影响：典故槽由 `WordProvider.matchAllusion` 直查 `AllusionDict`（`WordProvider.kt:30-37`），不经过总线 lambda；总线候选链服务同名 / 多义切换入口。当前 main 源码中 `ContextAnchor.resolve` 无生产直调点（仅测试与后续详情 / 关系屏预留），首屏气泡命中不依赖本次注册。
- 阅读壳入口：`InkReadActivity` 在数据初始化前同步 `runCatching` 预热，阅读场景下首点气泡前重绑已执行；`App.kt` 协程路径覆盖其余后台预热场景。

### 6.2 对消歧排序 / 默认命中的二阶影响

- 典故候选 `start/end = null`：在 `anchorComparator`（`ContextAnchor.kt:350-363`）时空档落入 `else -> 2` 桶（不占年精确 / 区间相交档）；`inAnchor`（`:346-347`）对 null 区间返回 false，锚定模式下不会成为默认命中；无锚点时 `defaultIdx = -1`（`:335`），全部 `isDefault=false`。即典故候选只进候选清单，不抢占人物 / 地名 / 纪年的默认命中位，与「典故在气泡槽位命中一次、总线仅提供同名多义候选」的定位一致。
- `tier=0`、`confidence=MEDIUM`：排序档位对齐 ERA 候选口径；MEDIUM `canDefault=true`，但因 null 区间在锚定闸下不进默认，不构成默认命中旁路。
- 去重键 `type.wire#id`（`:288`）：典故 id 为 `seed:…` 前缀，与 person / place / era 主键空间不撞。
