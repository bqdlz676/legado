## B33：`help/book/BookHelp.kt` books.json 清理行永久空操作

### 现象核实

1. 原位置：`BookHelp.kt` 的 `clearInvalidCache()` 末尾，原 `:199` 为 `FileUtils.delete("$filesDir/books.json")`，与上两行 `shareBookSource.json`、`shareRssSource.json` 的清理并列。
2. 空操作机理：`FileUtils.delete(path: String)`（`utils/FileUtils.kt:344-350`）在 `file.exists()` 为假时直接 `return false`，不抛异常。即目标文件不存在时该行只是一次无副作用的存在性检查。
3. 写入方核查：全仓 `books.json` 检索，生产代码（`app/src/main`、`modules`）零写入点、零读取点；唯一历史写入方是已被删除的旧导出器 `exportBookshelf`。
4. 历史依据：`git log -S "books.json" -- app/src/main` 命中 `95639ce`（清理B31:删孤儿类BookshelfViewModel，235→50行）；`git show 95639ce` 显示被删的 `exportBookshelf` 体内为 `val path = "${context.filesDir}/books.json"`，先 `FileUtils.delete(path)` 再 `createFileWithReplace(path)` 写出 name/author/intro 清单并分享。该提交之后仓内再无写出点。
5. 现存备份通道不是同一文件：`help/storage/Backup.kt:54` 的备份清单为 `bookshelf.json` / `bookGroup.json` / `bookMemo.json`，`:273` 写 `bookshelf.json`、`:285` 写 `bookGroup.json`，走完整 `Book` 实体备份/还原，与旧分享清单 `books.json` 两条通道不等价。
6. 注释核查：`clearInvalidCache()` 的 KDoc 仅为「清除已删除书的缓存 解压缓存」，该行附近 grep `旧` / `兼容` / `legacy` / `遗留` 零命中，不存在需要同步改写的「兼容旧版本遗留」注释。
7. 兄弟行仍有效：`shareBookSource.json` 有两个写入方（`ui/book/source/manage/SourceManageViewModel.kt:397`、`ui/book/manage/BookshelfManageViewModel.kt:114`），`shareRssSource.json` 有一个写入方（`ui/rss/source/manage/RssSourceViewModel.kt:95`），两行清理保留。

### 处置与理由（含否决方案）

1. 采纳路径①：删除该死分支。已删除 `FileUtils.delete("$filesDir/books.json")` 一行；`val filesDir = appCtx.filesDir` 仍被上两行使用，保留不动。
2. 否决路径②（修正条件让清理真实生效）：证据表明该文件已无任何写入方，不存在「本该清理却写坏了」的对象；为一个永远不会被创建的文件补条件、补断言属于制造新的无效代码，与清剿目标相悖。
3. 运行路径不依赖该行的调用链证据：`clearInvalidCache` 全仓仅两处调用——`App.kt:136`（启动清理过期数据）、`ui/main/MainActivity.kt:272`（Activity onDestroy 清理）。两条路径的职责是清缓存与过期数据，均不读取、不判断 `books.json` 是否存在，删除该行不改变任何可达行为。

### 二阶影响

1. 老用户磁盘残留：升级前旧版本可能在私有 `filesDir` 留下过 `books.json` 分享临时文件。删除本行后，该残留不再随缓存清理被自动摘除。判定不需要一次性 migration：当前代码对该文件零读取方；其内容仅为 name/author/intro 清单，不参与书架数据库、不参与备份还原；无任何代码分支按其存在与否判断行为；文件位于应用私有目录，对用户不可见，体积为单个 JSON。若后续产品要求统一清污，应在独立的一次性启动迁移中处理，不回补本行。
2. 对缓存清理主流程无影响：被删行处于 `withContext(IO)` 末尾的临时文件清理段，前后的书目录缓存、epub 缓存、`ArchiveUtils.TEMP_PATH` 清理逻辑未动；兄弟两条分享源 json 清理保留。
3. 三阶推演：未来若重新引入「向外分享书单」功能，应在新导出器落地时再决定其临时文件的清理归属，不应在本单回补旧文件名。

## B34：`ui/association/FileAssociationViewModel.kt` 联表导入 groupId 硬编码 0

### 现象核实

1. 原位置：`FileAssociationViewModel.importData()` 的 `"bookshelf"` 分支，原 `:162` 为 `importBookshelfJson(Uri.parse(source).readText(context), 0)`。
2. 分组语义：`importBookshelfJson(json, groupId)`（`ui/main/bookshelf/BookshelfViewModel.kt:20`）体内为 `if (groupId > 0) book.group = groupId`；`groupId = 0` 时不写分组位，`Book.group` 保持实体默认值 `0`（`data/entities/Book.kt:78`：`var group: Long = 0`）。书架分组是位掩码，`0` 即未分组（默认书架）。
3. 问题实质：裸字面量 `0` 无语义注释；导入成功后无任何去向提示，用户无法预期新书落入未分组，按分组整理的书架看起来像被「打散」。
4. 载荷不带分组：导入 JSON 仅解析 `name`、`author`（`BookshelfViewModel.kt:21-29`），清单本身不携带分组信息。
5. 调用方盘点：全仓 `importBookshelfJson` 仅 `FileAssociationViewModel.kt` 一个生产调用点，定义在 `BookshelfViewModel.kt:20`；`app/src/test`、`app/src/androidTest` 无其他调用点。

### 处置与理由（含否决方案）

1. 采纳路径②：显式「导入到默认（未分组）分组」并在 UI 上提示用户。
   - 把裸 `0` 提为具名常量 `private companion object { const val IMPORT_DEFAULT_GROUP_ID = 0L }`，注释写明：书架分组是位掩码，`0` 表示未分组（默认书架），`importBookshelfJson` 仅在 `groupId > 0` 时才写入分组位。
   - 调用点改为传 `IMPORT_DEFAULT_GROUP_ID`；`importBookshelfJson` 签名未改，无重载兼容壳。
   - 成功回调中仅对 `type == "bookshelf"` 分支调用 `context.toastOnUi(...)`，文案为「已导入到未分组书架，可在书架管理中移入分组」（默认英文：`Imported to the ungrouped shelf; move books into groups in bookshelf management.`）；`"backup"` 还原分支不弹此提示。
2. 否决路径①（沿用「当前可见分组」，由宿主传入当前 groupId），证据如下：
   - 入口上下文拿不到当前分组：`FileAssociationActivity` 是独立外部入口，manifest `:489-497` 注册 `ACTION_SEND` / `ACTION_SEND_MULTIPLE` / `ACTION_VIEW`；`OnLineImportActivity.kt:57-61` 跳转该 Activity 只带 `ACTION_VIEW` 与 data URI，未传任何 groupId extra。
   - 无持久化当前分组可借用：`AppConfig` 中与 group 相关的仅有 `importKeepGroup` / `importRememberGroup` / `importLastGroup` / `importLastGroupAdd`（书源分组按名称记忆）、`searchGroup`（搜索分组）与 `getBookSortByGroupId`（分组排序查询），不存在「书架当前可见分组 id」的持久化状态。
   - 书单 JSON 载荷不带分组（见核实第 4 条），无法从数据侧还原。
   - 强行实现①需要把 groupId 穿透 Intent → `ImportDataDialog` → ViewModel → `importBookshelfJson`，而外部入口没有合法取值可填；从偏好或记忆里猜一个分组属于隐式行为，用户不可预期，违背本单「不引入隐式行为 + 用户可预期」的判据。
3. 未采纳「导入时弹分组选择对话框」：该形态超出本单两条可选路径，且与现有书源导入的分组记忆机制不共用；记为后续产品单候选，不在本扩大改动面。

### 二阶影响

1. 分组统计：`group = 0` 的书不匹配 `bookGroups.groupId > 0` 的位掩码查询（`data/dao/BookGroupDao.kt:32`：`group & book_groups.groupId > 0`），与改动前行为一致；未分组 / 网络未分组视图照常收纳，既有分组统计与排序逻辑不破。
2. 重复书籍去重：`appDb.bookDao.has(name, author)` 跳过已在书架的书，该逻辑未动；导入失败仍按既有聚合异常抛出。
3. 提示时机：toast 在 `onSuccess` 内、`importedData.value = true` 之后触发；`ImportDataDialog` 观察 `importedData` 后关闭，toast 使用应用 context 发往主线程，对话框关闭后仍可见。`backup` 成功不触发该提示。
4. 语种覆盖：新字符串仅补默认英文（`values/strings.xml`）与简体中文（`values-zh/strings.xml`）；`values-es-rES`、`values-ja-rJP`、`values-pt-rBR`、`values-vi`、`values-zh-rHK`、`values-zh-rTW` 走 Android 资源回退到默认英文。仓内 `LocaleResourceConsistencyTest` 仅校验 `book_type` 数组，不做跨语种字符串键值对齐。
5. 三阶推演：若后续落地「导入前选分组」，应复用现有 `GroupSelectDialog` 回调链路（`ui/book/group/GroupSelectDialog.kt`），届时常量可替换为用户选定 id，本单的具名常量与 toast 提示不会成为兼容包袱。
