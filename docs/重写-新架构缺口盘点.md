### 5.1 Q-302 设置页 / Q-303 组件库 / Q-304 发现页 先后顺序

**结论：Q-303 组件库 → Q-302 设置页 → Q-304 发现页。**

- **Q-303（组件库六态）最先**。边界：`ui/components/` 除 inkslate 外的基础件（Button/Card/BottomSheet/Toast/EmptyState/Timeline/Sheet 容器）+ 七态补齐 + token 单源收口；不改既有签名（台账:305）。它是后两批的共同地基：设置页的设置行卡/分组容器/开关/Toast，发现页的战役横卡/典籍竖卡/专题条卡/马党卡，都必须从同一基座派生。
- **Q-302（设置页试点）次之**。边界：`ui/config/` 设置行三态 + 分组容器 + 真实 pref 接线；禁删旧页（台账:304）。它只消费组件库，不向发现页供组件；设置域不产生新基座件——但设置行卡本身是卡片族成员（切片-25:56），其实例须继承 B1 冻结的 `CardBase`，不在设置域私建行卡基座。
- **Q-304（发现页试点）最后**。边界：目标态路径 `ui/main/discover/`（台账:306，磁盘当前不存在，为 B6 落地后新建目录）；现存清点路径为 `ui/main/explore/`（双实现旧侧待验收后删）。三种卡片五态 + 真实数据源取证；禁碰旧壳。它同时依赖组件库基座与卡片族（CardBase），且真实数据源要等书架/名物库/纪年链路的口径稳定。

**排序理由**：组件库是横向共享层，设置页与发现页是纵向业务面；共享层不定型，业务面只能私有复制样式，后续基座升级要回炉改业务面。设置页比发现页简单——消费的是通用行卡/开关，不依赖卡片五态体系与外部数据取证，故排在发现页之前。

**反例（先做哪个会踩什么坑）**：

1. 先 Q-302 后 Q-303：设置行三态与分组容器在缺组件基类时各自实现；后补组件库时设置页要整体回炉改样式与状态映射，token 漂移风险高（仓内已有 `docs/修复-设计token漂移.md` 前科）。二阶影响：设置页私有组件会被发现页误抄，污染组件库收口。
2. 先 Q-304 后 Q-303：三种卡片五态无 CardBase 基座，12 类卡片复制阴影/圆角/骨架屏代码，直接违反切片-25:58 判据（CardBase 引用 ≥12）；数据源未取证先画 UI，空态/离线态无兜底方案。二阶影响：卡片私有实现焊死后，B1 基座收口时发现页是最大返工面。
3. Q-302 与 Q-304 并行：两者都向组件库提需求，组件签名未冻结会互相踩（同一设置行卡被两边改成不同形态）；按 D7 同文件串行原则，共享组件库文件域不允许两单并行。
